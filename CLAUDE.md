# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Seaquel is a database client built with Tauri 2 + SvelteKit 5 + TypeScript, with a Rust core. It supports PostgreSQL, MySQL/MariaDB, SQLite, MSSQL and DuckDB through the Rust engine crates in `crates/`. It ships as a desktop app, a self-hosted web app (`seaquel-server` behind a Node/SvelteKit server) and a browser demo.

SQLite and DuckDB connections are desktop-only. On web their "connection string" is a path on the server, so the web server refuses both (see `seaquel-server` below), and the web wizard doesn't offer them. The demo has DuckDB-WASM in the page and nothing else. SSH tunnels and shared projects (git) are desktop-only too.

## Development Commands

```bash
# Start development (frontend + Tauri)
npm run tauri dev

# Build production app
npm run tauri build

# Type checking
npm run check

# Type checking (watch mode)
npm run check:watch
```

Every script that runs Vite, svelte-check or vitest first runs `npm run wasm:build` (`scripts/build-wasm.mjs`), which builds `crates/seaquel-wasm` into `src/lib/wasm/pkg/` (gitignored). It needs the wasm32 target and wasm-bindgen-cli at the exact version in `Cargo.lock`:

`mise install` sets up Node, Rust and wasm-bindgen-cli from `mise.toml`, and `rust-toolchain.toml` adds the wasm32 target. Without mise:

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version "$(node scripts/build-wasm.mjs --bindgen-version)" --locked
```

When a dependency update bumps wasm-bindgen in `Cargo.lock`, update `"cargo:wasm-bindgen-cli"` in `mise.toml` to the same version.

- If that toolchain is missing the script fails, even when an older `pkg/` exists: a stale module would run old SQL checks, including the AI's read-only check. `SEAQUEL_WASM_PREBUILT=1` uses `pkg/` as it is without building (the Docker image does this); set it only when you know `pkg/` matches the crates.
- `dev` builds the module once at startup. After changing `crates/seaquel-sql` or `crates/seaquel-wasm`, rerun `npm run wasm:build`; Vite then reloads the new module.

On Linux (and in CI) `seaquel-secrets` links the system libdbus for the Secret Service, so install `libdbus-1-dev` and `pkg-config`.

The desktop app bundles the `seaquel-cli` binary as a Tauri sidecar (`bundle.externalBin`). `npm run cli:build` (`scripts/build-cli.mjs`) builds it and copies it to `src-tauri/binaries/seaquel-cli-<target-triple>` (gitignored); it takes `--release` and `--target`, honours `CARGO_TARGET_DIR`, and a host build without `--target` shares `target/debug` with the app. tauri-build refuses to build the app while that file is missing, so **`cargo check -p seaquel` needs it too**: run `npm run cli:build` once after cloning (`src-tauri/build.rs` stops with that hint; CI touches an empty placeholder). `npm run tauri` goes through `scripts/tauri.mjs`, which for `dev` builds the sidecar before Tauri starts (otherwise `tauri dev`'s ~180 s wait for Vite can run out on a cold build) and then sets `SEAQUEL_CLI_PREBUILT=1`, which makes `beforeDevCommand`/`beforeBuildCommand`'s `build-cli.mjs` only check that the file exists. `release.yml` builds it per target in its own step the same way.

The web app in development is `npm run dev:web:full`: `scripts/with-internal-secret.mjs` generates a `SEAQUEL_INTERNAL_SECRET` and runs `rust:dev` (the Rust service) and `dev:web` (Vite) under it. If you run `rust:dev` and `dev:web` separately, export the same `SEAQUEL_INTERNAL_SECRET` in both shells, or every licensing call is refused and the app shows the 503 page. In production `server.js` generates the secret itself.

## Architecture

### Frontend (src/)

- **SvelteKit 5** with static adapter (SSR disabled for Tauri)
- **Svelte 5 runes** (`$state`, `$derived`, `$props`) for reactivity
- **Tailwind CSS v4** for styling
- **bits-ui** for accessible UI components (shadcn-svelte pattern)

### Backend (Rust)

All database logic lives in Rust crates under `crates/`, shared by every interface. See `docs/plans/2026-09-24-rust-core-plugin-architecture-design.md` for where this is heading.

- `seaquel-core` — the only entry point interfaces use: engine registry, open connections, streaming and cancellation. `disconnect` cancels the connection's running streams, which end with a `CONNECTION_CLOSED` error event. `Core::open_workspace(WorkspaceSpec)` opens a `Workspace` (`workspace.rs`): one data dir's metadata `Storage` plus an optional `SecretStore`, behind Core's `storage`/`secrets` features. Core owns SSH tunnels (`ssh_open`/`ssh_close`; dropping Core closes them) and re-exports the other infrastructure crates, so interfaces never name them directly.
  - **Features.** The engines (`engine-postgres`, `engine-mysql`, `engine-sqlite`, `engine-mssql`, `engine-duckdb`, all default) plus `storage`, `secrets`, `ssh`, `git`, `license-desktop`, `license-server`, `workspace` (connecting, running and editing: `Workspace::connect`/`test`/`run`/`page` and the edits calls) and `ts` (the domain's TypeScript bindings, turned on by `seaquel-rpc/ts`), off by default. `src-tauri` enables `storage`, `secrets`, `ssh`, `git`, `license-desktop` and `workspace`; `seaquel-server` enables `storage`, `license-server` and the Postgres, MySQL and MSSQL engines (and `workspace` through `seaquel-rpc`); `seaquel-cli` and `seaquel-mcp` enable `storage`, `secrets`, `ssh` and `workspace`, and no `git` or `license-*` (the CLI checks no license). `browser` is the wasm32 build for phase 8 and enables nothing; combining it with an engine or infrastructure feature is a `compile_error!`.
  - **Re-exports**, since interfaces may not name these crates: `storage`, `secrets` (behind their features), `sql` (`seaquel-sql`, always) and `domain` (`seaquel-workspace`, always: it is pure, builds for wasm32, and its run types are on the `db` wire in every build; not named `workspace`, which is Core's own `Workspace` module). `RunLimits` and `EditLimits` are re-exported from it.
  - **`Workspace::connect(core, ConnectRequest)` and `Workspace::test`** (behind `workspace`; a saved target also needs `storage`, a tunnel `ssh`, a store `secrets`) connect a `ConnectTarget::Saved { id }` or `Form { form }` (`ConnectionForm`) through one builder, `seaquel_workspace::connections::plan`, pinned by `crates/seaquel-workspace/tests/fixtures/connect-config-v2`. `SuppliedSecrets` (redacted `Debug`) always win; a saved row reads the rest from the workspace's store under its save flags; a form reads nothing. `host_key` is `HostKeyPolicy::KnownOnly` (never writes known_hosts; `UNKNOWN_HOST_KEY` carries the fingerprint) or `Trust(fingerprint)` after the GUI's prompt; `restricted` sets `ConnectConfig::restricted` (DuckDB locked down; the MCP server). The tunnel belongs to the connection: `disconnect`, a failed connect, dropping Core or dropping the future closes it. A store read that fails gives `SECRET_UNREADABLE` (no store: `NO_SECRET_STORE`) before anything opens, and connect errors have every secret replaced by `<redacted>`. The GUIs (the `db` RPC group) and the MCP server all connect this way; nothing else builds a `ConnectConfig`.
  - **`ConnectPolicy`** has no default: a Core built without `CoreBuilder::connect_policy` answers `NOT_SUPPORTED` to every connect, test and `ssh_open`, whatever features Cargo unified. Desktop, CLI and tests use `Unrestricted`; the web server uses `Checked { check, allow_ssh: false }`, which refuses a target that needs a tunnel as soon as the row or form is read (before any secret read), then runs `check` (`web_config::check_connect_config`) on the finished config right before the driver opens it. The engine lookup comes first, so a refused engine is still `ENGINE_NOT_AVAILABLE`.
  - **`CoreBuilder::executor`** has no default either: Core takes its clock from the `Executor` (`monotonic()` for statement timings, `unix_time()` for history timestamps), and without one `db.run`/`db.page` answer `NOT_SUPPORTED`. `src-tauri`, `seaquel-server` and `seaquel-cli` pass `TokioExecutor`; tests build Core with both a policy and an executor.
  - **`Connection::sql_engine`** is the SQL rules a connection is scanned with, recorded at connect from the connection's database type, so a MariaDB connection (driver `mysql`) scans as MariaDB (`/*M! … */` is code). Runs and the read-only checks (`check_read_only`, `check_one_statement`) use it. `Core::connect` (engine tests) maps the driver id.
  - **Ownership.** Each `Workspace` has a random `WorkspaceId`. Connections it opens and streams it starts carry it, and its `query`, `query_stream`, `execute`, `transaction`, `engine` (a `ConnectionHandle` for the dialect and introspection calls; `seaquel_rpc::dispatch_on` runs an `EngineRequest` on it), `cancel` and `disconnect` refuse any other id with `CONNECTION_NOT_FOUND`, the same answer as an unknown id. Stream ids are scoped per workspace. `close_all(core)` cancels its streams and closes its connections and tunnels (web eviction); after it, a connect is `WORKSPACE_CLOSED`. `Workspace::events()` gives each subscriber a `WorkspaceEvent::ConnectionClosed` feed; today only `close_all` emits (`WORKSPACE_EVICTED`), and `CONNECTION_CLOSED`/`TUNNEL_CLOSED` are reserved, since Core doesn't notice a lost connection or tunnel. A workspace cancel for a stream id that isn't registered yet is remembered (256 per workspace, not for ids that already finished), so a cancel that overtakes its start still wins. Core's id-based methods (`Core::query`, `Core::disconnect`, …) reach any connection and stay for the engine tests; interfaces go through the workspace.
  - **`QueryOptions`** for `query_stream`: `read_only` (above), and, only with it, `max_rows` (return that many rows and mark the final `StreamBatch` `truncated` instead of failing with `RESULT_TOO_LARGE`), `max_bytes` (stop, `truncated`, once the kept rows' decoded cells reach it; one cell is never split) and `timeout` (enforced by the database, ending with `TIMEOUT`; a backstop for the caller dropping the stream, which stays the cancel). Any of the three without `read_only` ends the stream with `INVALID_OPTIONS`. Of the three, only `max_rows` crosses the Tauri and WebSocket transports (the in-app AI's `run_query` passes 1,000, `RUN_QUERY_MAX_ROWS`, and its tool result tells the model when rows were cut).
  - **`Workspace::run`/`page`** (`run.rs`; `db.run`/`db.page`, stream only) are the editor's runs on desktop and web. `seaquel_workspace::run::plan` (pure, no I/O, never panics) turns the text, the target (`all`, or `current` with a UTF-16 cursor converted by `seaquel_sql::offsets`, the same function the editor's wasm uses), the `{{param}}` values and the connection's `sql_engine` into statements, each with its SQL after substitution and its binds (`source`), query type and kind. Core runs them in order on one connection under the request's `streamId`, registered like a query stream, so `cancel`, an early cancel, `disconnect` and `close_all` reach a run the same way. Without an executor both answer `NOT_SUPPORTED`.
    - **Kinds.** A SELECT pages: `paginate(sql, pageSize + 1, offset)` through `query_stream`, reading one row past the page and then dropping the stream, so a cancel stops it on the server; `count_query` runs only when the page is full or comes back empty past the first page (a stale page number), and a failed or non-numeric count is estimated (`offset + pageSize + 1` for a full page, `offset` for an empty one) with `countEstimated`. It streams instead when the page size is 0 or it has its own LIMIT/OFFSET/FETCH/TOP. Insert, update and delete go through `execute`. Anything else (`other`) goes through `query`, unpaged, under its 100,000-row cap: with at least one column it shows its rows as one final batch (Decision 18: `WITH`, `SHOW`, `EXPLAIN`, `PRAGMA`, `VALUES`, DuckDB `FROM …`), with none it is a utility result the GUI hides. DuckDB answers `SET`, `CREATE`, `ATTACH`, … with a lone `Success` or `Count` column; unless the statement starts with a query word (`WITH`, `FROM`, `VALUES`, `TABLE`, `SELECT`, `SHOW`, `DESCRIBE`, `SUMMARIZE`, `EXPLAIN`, `CALL`, `PIVOT`, `UNPIVOT`; not `PRAGMA`), that counts as no columns, so `PRAGMA threads = 2` stays hidden. An empty result carries its column names on every engine.
    - **Events** (`RunEvent`, sent as `CoreEvent::Run`): per statement a `statementStart` (the typed SQL, its `source`, kind, page, and for a SELECT the source `table` and `columnRefs`), its `batch`es and a `statementDone` (`elapsedMs` from the executor, `totalRows`, `totalPages`, `countEstimated`, `rowsAffected`) or `statementError`; with `deferWrites` (pending changes on) every statement that isn't a SELECT comes back as `statementDeferred` and doesn't run; then one `done` (`statements`, `succeeded`, `history`) or `error`. A statement's failure doesn't stop the run; a cancel ends it and drops the statement in flight. Nothing to run is `done` with `statements: 0`. `db.page` re-pages one statement from the `source` the client sends back (Core keeps no run state) and refuses anything but one SELECT, but that isn't a write barrier: `SELECT … INTO`, writing functions and `FOR UPDATE` get through, as with `db.query`. A `{{name}}` with no value binds NULL, as the TS did.
    - **`CONFIRM_REQUIRED`.** A run holding a destructive statement (checked on the text before substitution, deferred statements included, before anything runs) ends with that `error` unless the request has `confirmed`; `destructive` lists the first 100 (`MAX_DESTRUCTIVE_LISTED`) and `destructiveTotal` counts them all. It guards against mistakes, not against an API caller: `db.execute` runs any SQL on the same connection.
    - **History.** Only `db.run` records, and only when the request has a `history` context (the saved connection's id, name and labels), the run wasn't cancelled, at least one statement ran and none failed. Core appends one row with `seaquel_storage::queries::query_history::append`, which also deletes the connection's non-favourite rows past the newest 500 (`HISTORY_KEEP`, `timestamp DESC, rowid DESC`), in one transaction; `done.history` is the row as stored. A failed append (a connection that isn't saved) is logged by code and doesn't fail the run.
    - **Limits.** `RunLimits` (`CoreBuilder::run_limits`, passed into `plan` in `PlanOptions` with the page cap) caps the text (and a page's SQL) and run all's statement count (`INVALID_ARGUMENT`), and the parameter values a run sends, by count and bytes (`INVALID_PARAMETERS`; `db.page` is exempt). Only the web sets it (`WEB_RUN_LIMITS`: 2 MiB, 10,000 statements, 1,000 values, 1 MiB of them); the desktop, CLI, MCP and the demo have none. On every interface but the demo's `TsQueryRunner`, filling in the values may add at most 32 MiB to a run (`check_substitution_budget` over `seaquel_sql::params::SizeBound`, `MAX_RUN_SUBSTITUTED_BYTES`, `INVALID_PARAMETERS`), since a value is copied (SQL Server, DuckDB) or bound (MySQL/MariaDB) once per use; only the growth counts, so a large dump with a few parameters runs. `plan` looks the values up once (`params::Values`, `substitute_with`) and `SizeBound` costs each used one once, so planning is linear in text plus values. `column_refs` returns `None` for a statement over 64 KiB (`MAX_COLUMN_REFS_BYTES`) without parsing it; the grid then isn't editable. A page size past `max_query_rows() - 1`, page 0 and an offset that overflows are `INVALID_ARGUMENT`. "Stream all" (page size 0) has no row cap of its own.
    - **Hand-typed transactions** aren't handled: on Postgres and MySQL/MariaDB each statement takes a pooled connection, so `BEGIN; UPDATE …; COMMIT;` may run on different connections (MySQL refuses `BEGIN` in the prepared protocol, 1295, and the UPDATE autocommits). SQL Server keeps one session.
  - **The edits service** (`edits.rs`; `db.planEdits`, `db.applyChanges` and `db.duckdbExtension`, unary, and `db.tablePage`, stream only) is every write the grid makes and the data tab's query, on desktop and web. Planning is `seaquel_workspace::edits` (pure, never panics).
    - **Intents.** The grid sends `Edit`s: `updateCell`, `setDefault`, `insertRow`, `deleteRow`, and `truncateTable`/`dropObject` from the sidebar; a table (`schema`, `table`), a key as `[column, value]` pairs picked out of the row by the GUI's routing, a column and a value in the cell wire format. The queue sends them back as `Change::Edit`, or `Change::Sql` for a statement the editor deferred or the table editor generated. Core builds each edit with the connection's `Dialect` builders at plan and again at apply time; no casts or default expressions cross the wire.
    - **Metadata, read per call.** For each table a call touches, Core calls `table_metadata` once (deduped within the call; no cache, so DDL run anywhere is seen at once). It gives the Postgres cast map (`cast_map`), SQLite's default expression for Set default (a column without one sets NULL) and the primary key. A table that isn't there or has no primary key, a key whose columns aren't exactly the primary key's (compared as a set; the WHERE keeps the key's order as sent) and an update, Set default or insert column the metadata doesn't list are `NOT_EDITABLE`, so views and keyless tables aren't editable from the grid. A failed metadata read fails the call with its code before anything runs.
    - **JSON columns** (Decision 19): in a column the metadata types `json`/`jsonb` (Postgres) or `JSON` (MySQL, MariaDB, SQLite's declared `JSON`, DuckDB), an `Array`, a number or a `Bool` binds as `Value::Json`; `Text` stays `Text`, because the grid sends typed JSON as a string, so a JSON string cell (`"abc"`) written back is sent as `abc`. MariaDB reports `JSON` as `longtext`; its `table_metadata` reports `json` when a column CHECK named after the column is exactly ``json_valid(`col`)`` (from `information_schema.CHECK_CONSTRAINTS`; a server without it keeps `longtext`).
    - **Applying** (`apply_changes`). One change is `single` (`execute`, keeping `lastInsertId`). Two or more that are all DML are `atomic`: one `Driver::transaction`, keyed edits with `expect_rows: {min: 1}`, and any failure rolls everything back. DML means an edit intent other than truncate and drop (a SQLite truncate is a `DELETE FROM` and counts), or a typed change whose `query_type` is insert, update or delete; `MERGE`, `WITH … UPDATE`, `CALL`, DDL and the rest aren't. Anything else is `inOrder`: `execute` one change at a time, stopping at the first failure. Each typed change must be one statement (split with the connection's `sql_engine`, else `INVALID_ARGUMENT`). Limits, metadata, keys, splitting and the destructive check all pass before the first statement runs; a refusal inside a batch is an `applied` outcome with `applied: 0` and `failed` naming the change, not an error. A keyed edit that matches no row is `NO_ROWS_AFFECTED` (a Postgres rule or SQLite INSTEAD OF trigger that reports 0 for a write it made is a known false positive). An unconfirmed batch holding a statement `destructive_reason` flags is `{outcome: "confirmRequired", destructive, destructiveTotal}`, as a run's `CONFIRM_REQUIRED` is (edits are checked as the SQL Core built; a keyed delete has a WHERE). `ddl: true` when a change that isn't DML ran. With a `history` context each applied change appends a row (its SQL as queued, rows affected, Core's time) through `query_history::append_many`, after the commit for an atomic batch; the outcome carries the rows. Immediate grid edits send no context and record nothing.
    - **Stopping.** The calls are unary. Dropping one drops the driver call, which rolls an atomic apply back; an in-order or single apply keeps what already ran, with no outcome and no history. Each workspace has a `closing` token that `close_all` cancels, and an apply races it, so an eviction mid-apply ends with `failed` `WORKSPACE_CLOSED` (atomic: rolled back unless the commit raced the close; in order: stopped at that change). On web Node aborts the call to Rust when the browser's socket closes (below).
    - **The data tab** (`table_page`): a stream registered like a run, so `cancel`, `disconnect` and `close_all` reach it. The GUI sends a typed `TableQuery` (the target, filters with a `FilterOp` from a closed enum serialised as the UI's text, `=` to `IS NOT NULL`, `AND`/`OR`, sort), a page and a page size (1 to `max_query_rows() - 1`). `seaquel_engine::select::build_table_select` (pure, like `crud.rs`) quotes the names and writes each filter as `CAST(col AS <text type>) <op> <placeholder>` with the engine's CRUD placeholders (`$1`, `?`, `@P1`); `IN`/`NOT IN` split the value on commas, trim each item and bind it (an empty list is refused); range operators compare text. On SQL Server it reads the column types on every page and casts `sql_variant`, `geography`, `geometry` and `hierarchyid` to `NVARCHAR(MAX)` (tiberius can't read them). It then runs as 5b's page kind: the count runs only for a full page or an empty page past the first, and a failed count is estimated.
    - **`duckdb_extension`** takes a typed `ExtensionAction` (`list`, `install`, `load`, `update`, `installCommunity`, `installAndLoad`), refuses a non-DuckDB connection and a name outside `^[A-Za-z0-9_]+$` (`INVALID_ARGUMENT`), and runs its statements one call each.
    - **`EditLimits`** (`CoreBuilder::edit_limits`, beside `run_limits`; none by default): only the web sets them (`WEB_EDIT_LIMITS`: 10,000 changes per apply or plan, at most 100 distinct tables per call since each is a metadata read (`max_tables`), 2 MiB of typed SQL, 16 MiB of values; per table page 100 filters and 100 sort columns, 1,000 `IN` items and 64 KiB per filter value). Past one, `INVALID_ARGUMENT` naming the limit, checked in one linear pass before anything is planned, read or run. A NUL in any schema, table, column, key, sort or filter name is refused on every interface. The desktop, CLI and MCP have no limits.
    - **Logs.** `Edit`, `Change`, `TableQuery` and the params types have hand-written `Debug` (table and column names, counts); the service logs activity names, ids, counts, modes and codes, never SQL, keys or values.
  - **`Core::explain_read_only(connection_id, sql, params, timeout)`** is the MCP server's EXPLAIN: the read-only token check, then exactly one statement (split on `;`; SQL Server counts statements from the ShowPlan XML), then `Driver::explain_read_only`. Refusals are `READ_ONLY`. The editor's `explain` is unchanged and isn't safe for model-written SQL: planning runs user code on Postgres and MariaDB, and SQLite and DuckDB run every statement.
  - **`ConnectionLimits`** (`CoreBuilder::connection_limits`; default none): `per_workspace` caps a workspace's open connections, counting connects and tests in flight under one lock, so concurrent calls can't pass it (`TOO_MANY_CONNECTIONS`, 429 on web, before anything is read or opened); `max_pool_size` reaches the engine as `OpenOptions` through `Engine::open_with` (Postgres and MySQL size their sqlx pool with it; SQL Server's read-only slots become `max_pool_size - 1`). Policy only, never on the wire. The web server's `WEB_CONNECTION_LIMITS` is 16 per user and pools of 6 (with 6 statements streaming on one connection, its next call, introspection included, waits for a pooled connection); desktop, CLI and MCP keep the engines' defaults.
  - **Features aren't a security boundary.** Cargo unifies features across a build, so `cargo test --workspace` compiles every engine and every infrastructure crate into `seaquel-server` too. Anything the web build must not do is refused in code as well: `with_plugins(|id| …)` registers only the engines it allows, and `dispatch_workspace` refuses SSH, git and license calls.
- `seaquel-engine` — the `Driver`/`Engine` plugin traits, the pure `Dialect` trait, and the generic DDL/CRUD builders (`ddl.rs`, `crud.rs`) that dialects parameterize. `Driver` has default `NOT_SUPPORTED` introspection methods (`list_schemas`, `schema_tables`, `table_metadata`, `statistics`, `explain`). One crate per engine: `seaquel-engine-{postgres,mysql,sqlite,mssql,duckdb}`. Read-only queries go through `query_read_only_with(sql, params, ReadOnlyOptions { max_rows, max_bytes, timeout })`, which returns a `CappedResult { columns, rows, truncated }`; `RowCap` (`fail`, `truncate`, `read_only(max_rows, max_bytes)`) decides per row whether to keep it, truncate or fail with `RESULT_TOO_LARGE`, and `max_rows` never goes past `max_query_rows()` (100,000, `SEAQUEL_MAX_QUERY_ROWS`). `explain_read_only` defaults to `NOT_SUPPORTED`, so an engine without it fails closed. `Driver::transaction` fails with `TransactionError { index, error }`: `index` is the failing statement's position when the database refused it, its parameters didn't bind or it fell short of `expect_rows` (`NO_ROWS_AFFECTED`), and `None` when connecting, BEGIN or COMMIT failed or a transaction opened by hand is already open (SQL Server and DuckDB refuse then, with code `TRANSACTION_OPEN` and the `TRANSACTION_ALREADY_OPEN` message; 409 on web. SQL Server reads `@@TRANCOUNT`; DuckDB compares two `txid_current()` calls, equal only inside a transaction, and a failed probe counts as open, since a nested BEGIN there would abort the user's transaction); `db.transaction`'s wire carries only `error`. An empty `query_stream` result still names its columns: the sqlx engines (Postgres, MySQL/MariaDB, SQLite) read column names from rows, so with no row they take them from the statement sqlx prepared (its statement cache, no extra round trip); SQL Server and DuckDB always sent them. `query` on an empty result still returns none. `transaction` returns each statement's rows affected. `select.rs` builds the data tab's SELECT (`build_table_select`, pure, parameterized by quote functions, placeholder and text type like `crud.rs`). `Dialect::paginate` puts `LIMIT`/`OFFSET` on a line of its own (Postgres, MySQL/MariaDB, SQLite, DuckDB; SQL Server already dropped trailing comments), so a query ending in a `--` comment pages; the demo's `duckdb.ts` still appends it on the same line. **Statement logging is off everywhere:** sqlx logs each statement at DEBUG, and each one slower than a second at WARN, with its whole SQL, so every sqlx pool and connection (engines, their cancel connections, `seaquel-storage`, `seaquel-license`) is built with `disable_statement_logging()` (`run_no_statement_logging` in the testkit checks an engine), and the server's `StderrLogger`, the desktop's `tauri-plugin-log` and the CLI's filter drop the `sqlx::query` target too. sqlparser logs literals at DEBUG, and Core parses runs natively, so the desktop and the CLI turn the `sqlparser` target off (the server passes dependencies only at WARN). **A stopped stream stops on the server:** `impl_sqlx_driver!`'s `stream_start` gives `query_stream` one connection and a `RunningStatement`; dropped unfinished (a cancel, a disconnect, eviction), Postgres sends `pg_cancel_backend` and MySQL/MariaDB `KILL QUERY` from a fresh connection (spawned, 5 s timeout) and closes the connection. It fires only while that session still runs a statement starting with `seaquel_engine::statement_prefix` (leading whitespace skipped; cut before the first `?` on MySQL, whose binlog expands parameters, and before any character above U+FFFF; under 8 characters it checks only that a statement runs). Behind PgBouncer in transaction mode, a statement with the same start from another client on that backend could be cancelled; with `track_activities = off` nothing is. The cancel paths log an error's kind and code, never its message. It costs one lookup round trip per stream. SQL Server stops when its session closes; DuckDB interrupts on drop; SQLite's plain stream isn't interrupted (local). A non-streamed `query`/`execute` still in flight at a disconnect isn't cancelled.
- `seaquel-types` — wire types, including the dialect types (`SchemaTable`, `ExplainResult`, `CreateTableDefinition`, …), `Value` and the metadata row types (`storage.rs`, the `Persisted*` types). `npm run types:gen` regenerates `src/lib/types/generated/` from `seaquel-types`, `seaquel-rpc`, `seaquel-sql`, `seaquel-wasm` and `seaquel-workspace` (the run and edit types); never edit those by hand.
- `seaquel-rpc` — `workspace.rs` holds the workspace RPC: `Request`/`Response` (`CoreRequest`/`CoreResponse` in TS) with the `storage`, `db`, `secret`, `ssh`, `git` and `license` groups, and `dispatch_workspace`. The `db` group (`db.rs`) runs on the workspace's own connections: `connect` and `test` (`{target: {type: "saved", id} | {type: "form", form}, secrets?, trustHostKey?, createIfMissing?}`), `disconnect`, `query`, `execute`, `transaction`, `engine` (an `EngineRequest`, the dialect and introspection calls, run by `dispatch_on` on a `ConnectionHandle`; since 5c it has no `paginate` or `build*` calls, which Core now does itself), `planEdits`, `applyChanges`, `duckdbExtension` and `cancel`. `connect`, `test`, `run`, `page` and the edit calls need the crate's `workspace` feature (on in `src-tauri` and `seaquel-server`; off in the wasm32 `browser` line, since Core's `browser` refuses `workspace`), and answer `NOT_SUPPORTED` without it. The streams, `queryStream`, `run`, `page` and `tablePage`, are served only by `dispatch_stream`, which yields `CoreEvent`s (`{type: "stream", streamId, event}` for a query stream, `{type: "run", streamId, event: RunEvent}` for a run, page or table page; `DbRequest::is_run_method` is the one list) and borrows the workspace for the stream's life; `dispatch_workspace` refuses them with `INVALID_ARGUMENT`. `RunParams`/`PageParams` `Debug` leave out the text, values and history context. `DbResponse` and `Response` are `Serialize` only. `workspace_events` turns the workspace's events into `CoreEvent::ConnectionClosed`. `ExecuteResult` and `StreamBatch` stay snake_case on the wire, as the TS reads them. Only the desktop serves the last four, each through its own function that needs no storage: `dispatch_secret` (the keychain), `dispatch_ssh` (Core's tunnels), `dispatch_git` and `dispatch_license` (the activation client). `dispatch_workspace` answers `NOT_SUPPORTED` for SSH, git and license whatever the features, so `/rpc` on web can never open a tunnel, touch a repo or call the license server. Every variant exists in every build, so the generated TS doesn't depend on features. Both levels are adjacently tagged (`{"method", "params"}`, responses `{"method", "result"}`), and `method` must come before `params`: stored JSON columns are `RawValue` and stay byte-identical, so parse bodies with `parse_request` from the raw bytes, never through a `serde_json::Value`. A method with no params leaves `params` out (`{}` is refused). Errors are `RpcError { code, message }`. It logs the method name only, never params.
- `seaquel-storage` — the metadata SQLite database: open, schema and one typed function per query (`queries/`); the only place SQL for it lives. `data_dir(identifier)` reads `SEAQUEL_DATA_DIR` (an empty value is ignored), else the platform data dir plus the Tauri identifier. The file is `<data_dir>/seaquel.db` on desktop and `DATA_DIR/users/<id>/meta.db` on web. `Storage::open` runs the frozen baseline (`schema.rs`, which upgrades every released file), then numbered expand-only SQL migrations (`migrations/`, rules in its README), then Rust data steps (`data_steps.rs`, recorded in `_seaquel_data_steps`). Schema changes are new migration files, never baseline edits. Query history is written only by `query_history::append` (the row plus the 500-row cap, favourites kept), `append_many` (Core's applies: many rows in one transaction, one prune; no RPC) and `set_favorite` (sets, never toggles), as `queryHistoryAppend`/`queryHistorySetFavorite`; `replace_all` stays only for its frozen repo fixture and has no RPC. A pending migration runs under a `BEGIN IMMEDIATE` lock held on the migrator's own connection (each migration is a savepoint inside it), so two pools or processes opening one file apply it once. `StorageOptions { read_only: true }` (for `seaquel-cli`) opens with `SQLITE_OPEN_READONLY`, never sets the journal mode or creates the file, and runs nothing: if the baseline (`schema::is_current`), a migration or a data step has work to do it fails with `STORAGE_NEEDS_UPGRADE`, a missing file with `STORAGE_NOT_FOUND`. Fixtures in `crates/seaquel-storage/tests/fixtures` (each release's schema, the repo cases) are frozen. Codes that block the app: `LEGACY_STORAGE` (only pre-2026.4.5 JSON files, no `seaquel.db`), `STORAGE_CORRUPT`, `NO_DATA_DIR`; anything else is `STORAGE_ERROR`.
- `seaquel-secrets` — `SecretStore` (`get`/`set`/`delete`), `KeychainStore` and `MemoryStore` for tests. `validate_key` allows only `db:<id>`, `ssh:<id>`, `ssh-key:<id>`, `ai-api-key:<id>` and `license-key`. The keychain service is `DESKTOP_SERVICE` (`app.seaquel.desktop`) in dev builds too, since changing it orphans saved passwords. Errors name the key, never the value. The web workspace has no store, so secret calls there are `NOT_SUPPORTED`.
- `seaquel-ssh` — SSH tunnels over russh 0.48: a local port forwarded through a bastion, password or key-file auth, and the host-key check against known_hosts. An unknown key fails with `UNKNOWN_HOST_KEY` and its `SHA256:…` fingerprint; the retry passes that fingerprint as `trustHostKey`, and only a key with exactly that fingerprint is recorded. `HOST_KEY_MISMATCH` is never accepted. A key of an algorithm known_hosts doesn't hold for the host counts as unknown, not a mismatch (russh compares only keys of the same algorithm). Closing a tunnel (or dropping it) aborts every forward and ends the SSH session. The error codes are the ones the TS host-key prompt matches on; keep them. Live tests need `SEAQUEL_TEST_SSH` (below).
- `seaquel-git` — shared projects' git over libgit2 (vendored): `Git`, with every call async over `spawn_blocking`. The home dir for default SSH keys is a field (`Git::from_env()` on desktop), so tests never read `~/.ssh`. The credential chain is agent, then the given key or the default keys, then user/password; it never hands out the same credential twice and gives up after 4, so a wrong password can't loop. A commit after a conflicted pull gets MERGE_HEAD as its second parent, and commit refuses while files are conflicted. A push the remote refuses fails with `PUSH_ERROR`; a non-fast-forward says `PUSH_REJECTED_NON_FAST_FORWARD`, which the TS matches exactly to mark the repo "behind".
- `seaquel-license` — two parts that share only the HTTP client (`http.rs`: rustls with the OS and webpki roots, built lazily so a broken OS certificate store can't panic at startup). `desktop` is the activation client (`DesktopClient`: activate, validate, deactivate); the 12-hour revalidation stays in `license.svelte.ts`. `server` is the web build's gate (`LicenseServer`): the install id, the control-plane client, the soft/hard TTL ladder (`SEAQUEL_LICENSE_SOFT_TTL`/`SEAQUEL_LICENSE_GRACE_TTL`, 24 h and 14 d), member licenses and air-gap bundles (Ed25519; canonical JSON byte-identical to what seaquel-app signs). It reads and writes the license tables in `auth.db` with sqlx, but Node keeps applying migrations 006–012 through `auth.ts`: until they have run, every call answers `NOT_READY` (503). The control-plane client adds the PEMs in `NODE_EXTRA_CA_CERTS` as roots and honours `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`. License keys never reach a log line, an error or `Debug`.
- `seaquel-sql` — pure SQL text work, no I/O: one hand scanner that follows each engine's quoting (`scan.rs`), with statement splitting, statement at cursor and the row-limit check on top; `statements.rs` (query type, the destructive-statement check, the source table for inline editing, `change_summary` for the pending-changes sheet's descriptions); `read_only.rs` (the AI's read-only check); `params.rs` (`{{param}}` substitution); `create_table.rs` (the table editor's SQL pane); and `ast/`, sqlparser-rs used only where an AST is needed (query builder and tutorial `ParsedQuery`, the Visual tab, column sources). It works in UTF-8 byte offsets. Parity fixtures in `crates/seaquel-sql/tests/fixtures` are frozen (see its README). Nothing in it may panic on user input: in the browser a panic is a trap.
- `seaquel-wasm` — wasm-bindgen glue over `seaquel-sql`, loaded by the Svelte app on desktop, web and the demo. Strings and JSON in and out, and every position that crosses is a UTF-16 offset (`utf16_to_byte` and friends live in `seaquel_sql::offsets`, re-exported by `offsets.rs`, so Core's `db.run` picks the same statement for a cursor as the editor). The root `src/routes/+layout.ts` awaits `initSeaquelWasm` before anything renders, so calls are synchronous. Linked with a 2 MB stack (`build.rs`).
- `seaquel-runtime` — `MaybeSend`, `BoxStream`, `Executor` (`spawn`, `sleep`, `unix_time`, `monotonic`; `TokioExecutor`, `WasmExecutor` over `performance.now()`), `#[seaquel_runtime::async_trait]`. Core crates must build for wasm32: no `tokio::spawn`, `Instant` or `SystemTime` (enforced by `crates/clippy.toml`).
- `seaquel-workspace` — the domain crate, reached as `seaquel_core::domain`; it may not name an engine crate. `edits`: the edit and data-tab wire types (`Edit`, `Change`, `ApplyOutcome`, `TableQuery`, …), `plan_edit`, `plan_sql`, `cast_map`, `classify`, `table_select` and `EditLimits` (above), pinned by the 180 recorded cases in `tests/fixtures/edits` (recorded from the pre-5c TS; `changes.json` lists the 89 that differ on purpose; replayed by `tests/edits_plan.rs`, `seaquel-core/tests/edits.rs` and, for the queue's side, `edit-service/fixtures-replay.svelte.test.ts`). `run`: the run's wire types (`RunParams`, `PageParams`, `RunEvent`, …, TypeScript behind `ts`), `plan`, `history_item` and `RunLimits`, pinned by the 95 recorded cases in `tests/fixtures/run` (recorded from the pre-5b TS runner; `changes.json` lists the 14 that differ on purpose, and the replay in `seaquel-core/tests/run.rs` fails on any other). `connections` (and `connection_string`): the one connection builder (`plan` → `Plan::tunnel` → `Plan::config`) that turns a saved row or a form plus secrets into a `ConnectConfig` and `TunnelConfig`, with phase 5a's quirk fixes (Decision 6). The 160 cases in `tests/fixtures/connect-config-v2` are the spec (README); the frozen v1 set in `tests/fixtures/connect-config`, recorded from the TS, is the diff report: a case differs from v1 exactly when its `changedBy` names a row. Change a v2 case only when the behaviour is meant to change, and say why in its README.
- `ConnectConfig` also has `tls_server_name` (MSSQL: the name the certificate is checked against while the socket goes to `host`, set through an SSH tunnel) and `duckdb_config` (DuckDB open options from `duckdb://path?key=value`; `restricted` wins over them).
- `seaquel-mcp` — the MCP server (rmcp 3.4.1), an interface library that only `seaquel-cli` may depend on (`INTERFACE_LIBS` in `check-crate-deps.mjs`). Eight tools, all read-only: `list_connections`, `list_schemas`, `list_tables`, `describe_table`, `run_query`, `explain_query`, `list_saved_queries`, `run_saved_query`. Errors are tool results with `isError: true` and `CODE: message`, never protocol errors. Its rules:
  - **stdout carries JSON-RPC only.** Nothing may print to it; logs go to stderr. It has its own line transport (`transport.rs`) so a line that isn't JSON gets `-32700` with `"id": null` instead of rmcp's silence.
  - **Only the connections named with `--connection`/`--project`** (id, else exact case-sensitive name) are exposed, resolved once at startup (`exposed.rs`); with neither, none. No tool takes a connection string, host, path or driver. A connection's AI schema and data sharing flags (after the global default in `app_state`'s `aiSettings`: schema on, data off) gate the tools, re-read on every call.
  - **No writes**, to databases or to Seaquel's own files: queries go through `query_stream` with `read_only`, EXPLAIN through `explain_read_only`, storage is opened read-only, and known_hosts is never written. A write opt-in is a follow-up with its own review.
  - **DuckDB opens restricted** (`ConnectRequest::restricted`). The workspace `duckdb` dependency links `json` statically so the JSON functions work there; `icu` can't be linked from crates.io, so time zones and TIMESTAMPTZ arithmetic fail on the MCP server (pinned in `seaquel-engine-duckdb/tests/restricted.rs`).
  - **Limits:** `max_rows` default 100, at most 1,000 (`tools/query.rs`); an 8 MB fetch budget (`MAX_FETCH_BYTES`, Core's `max_bytes`); a cell's text cut at 64 KB (`format::MAX_CELL_BYTES`, as a `{"truncated": true, "bytes", "text"}` object) and a result stopped before its JSON passes 4 MB (`MAX_RESULT_BYTES`); a 60 s timeout per call (`DEFAULT_CALL_TIMEOUT`, not counting a pending keychain prompt, `secret_wait.rs`). Past it the call's stream is dropped, which cancels it, and Core's `timeout` also stops the statement on the server (Postgres `pg_cancel_backend`, MySQL/MariaDB `KILL QUERY`, from a fresh connection).
  - Cells render like `$lib/values` `cellText` (`format.rs`): bigint and decimal as strings, bytes as `\x` hex, JSON through a `JSON.stringify` port; `null` stays `null`.
- `seaquel-cli` — the `seaquel-cli` binary (clap), with one subcommand, `mcp [--connection …] [--project …] [--log-level …]`. It opens `seaquel.db` read-only with `KeychainStore` (service `app.seaquel.desktop` in every build) and `~/.ssh/known_hosts`; the data dir is `data_dir("app.seaquel.desktop")`, `.dev` in a debug build, or `SEAQUEL_DATA_DIR`. `--version` prints the desktop app's version (`build.rs` reads `src-tauri/Cargo.toml`) and the terms line; it checks no license. The binary can't be named `seaquel`: the app owns that name on every platform. Debug builds only (`cfg!(debug_assertions)`) read the test hooks `SEAQUEL_CLI_TEST_SECRETS` (a JSON file loaded into a `MemoryStore`), `SEAQUEL_CLI_TEST_KNOWN_HOSTS` and `SEAQUEL_CLI_TEST_CALL_TIMEOUT_MS`; a release build ignores them. SIGTERM and SIGINT close connections and tunnels like stdin closing does. `tests/stdio.rs` runs the built binary and checks that stdout carries only JSON-RPC.
- Interfaces:
  - `src-tauri/` (desktop). Its commands are `core_call`; `cli_info` and `install_cli` (`cli_info.rs`, for the MCP settings panel); `core_stream` and `core_events` (below); and interface code (`copy_image_to_clipboard`, `open_path`, `get_data_dir`, `read_log_file`, `clear_log_file`, `get_username`, `install_update`, `check_for_update_command`, `read_dbeaver_config`, `read_tableplus_config`). There are no `db_*`, `git_*`, `ssh_*` or license commands: `core_call` serves storage, `db`, secrets, SSH, git and licensing. It takes the request as the raw bytes of a `Uint8Array` (`invoke("core_call", bytes)`); an object is refused. Storage opens lazily on the first storage call (`DesktopWorkspace`): `LEGACY_STORAGE`/`STORAGE_CORRUPT`/`NO_DATA_DIR` are kept and returned to every storage call, other failures retry on the next call, and secret, SSH, git and license calls work either way. `db` calls use one workspace for the whole run; if storage can't open for good, that's a stand-in workspace on an empty scratch storage, where form connects work and saved ones get the storage error.
    - **Streams and events.** `core_stream({request, channel})` takes a `db.queryStream`, `db.run`, `db.page` or `db.tablePage` request as JSON text (an invoke carrying a `Channel` can't have a raw body) and pushes `CoreEvent`s to the channel. It resolves with the number of events it sent, since the reply can overtake channel messages: the GUI waits for that many before it treats a stream with no `done`/`error` as cancelled. `core_events({channel})` is called once per page load; each webview label has its own sink and every sink gets every event. A second call from the same label (a reload) replaces its sink and cancels that webview's streams and runs (tracked by `DbRequest::stream_id`), and so does closing its window.
    - **The command line tool.** On macOS, and on Linux only when run as an AppImage (`cli_install::available`), the app menu has "Install Command Line Tool…" (`cli_install.rs`): macOS symlinks `/usr/local/bin/seaquel-cli` to `Contents/MacOS/seaquel-cli`, asking for admin rights through `osascript` only when needed and building that command from fixed paths only; the AppImage copies the sidecar into the data dir and links `~/.local/bin/seaquel-cli` to the copy. deb and rpm already install `/usr/bin/seaquel-cli`; Windows gets no item and no `PATH` change. Settings → MCP (`src/lib/components/settings/mcp/`, desktop only) shows the binary and whether it's on `PATH` (`cli_info`), the same install (`install_cli`), connection and project checkboxes, and the Claude Desktop JSON and `claude mcp add` line (`mcp-snippets.ts`, POSIX or PowerShell quoting, connections named by id).
  - `crates/seaquel-server/` (web; axum). `POST /rpc` takes the user from `X-Seaquel-User` and serves that user's workspace from an LRU (`workspaces.rs`, 1,024 open, `SEAQUEL_WORKSPACE_CAP` lowers it for tests; 2 `meta.db` connections each). Evicting a workspace runs its `close_all` in the background, so the user's database connections, streams and tunnels close and each of their `/rpc/stream` sockets gets `WORKSPACE_EVICTED`; an apply in flight stops too (its `failed` is `WORKSPACE_CLOSED`): an atomic one drops its transaction, which rolls it back unless its commit raced the close (the GUI marks the queue interrupted), and an in-order one stops at the statement in flight. Each user's calls in flight hold at most 40 MiB of bodies together (`MAX_IN_FLIGHT_BYTES_PER_USER`; a lone call and a body under 64 KiB, `SMALL_CALL_BYTES`, always run, the small one still counting), checked before parsing, and at most 4 of them are `db.applyChanges`, `db.planEdits` or `db.duckdbExtension` whatever their size (`MAX_EDIT_CALLS_PER_USER`, `routes/rpc.rs`); past either, 429 `TOO_MANY_REQUESTS`, which `errorText` shows as a sentence. The GUI's parallel startup loads are tiny next to the budget. It trusts that header, so **binding to loopback only is a security requirement** (`main.rs`): it refuses a non-loopback `BIND_ADDR` unless `SEAQUEL_ALLOW_NON_LOOPBACK=1`, which is never for deployments.
    - **`/rpc`** serves the `db` group; the HTTP status comes from the error code (`error::status_for`: `CONNECTION_NOT_FOUND` 404, refused engines and options and `NOT_EDITABLE` 400, `WORKSPACE_CLOSED`, `NO_ROWS_AFFECTED`, `CONFIRM_REQUIRED` and `TRANSACTION_OPEN` 409, `TOO_MANY_CONNECTIONS` and `TOO_MANY_REQUESTS` 429, `RESULT_TOO_LARGE` 413, `TLS_ERROR` 502, `TIMEOUT` 504). The body is always `RpcError`. A failure is logged as its `code`, `group` and `method` only.
    - **The log** (`startup.rs`): stderr, Seaquel's crates at INFO and dependencies at WARN, never `sqlx::query`, `sqlx::postgres::notice` or `tiberius::tds::stream::token` (`DROPPED_TARGETS`, submodules included: a `RAISE WARNING`'s text is the query's to choose, and tiberius logs every SQL Server error and `PRINT` with the server's text, which quotes values). The desktop and CLI log filters drop the same three and hold the rest of tiberius at WARN (its TLS warnings). sqlx's MySQL and SQLite drivers and duckdb-rs log no database text. `format_record` writes a record's key-values (`activity`, `code`, ids, counts, kinds; never SQL or values) after the message, logfmt style: control characters escaped everywhere, a value holding a space, `=`, `"`, `\` or a control character quoted, each value cut at 128 bytes (`MAX_LOG_VALUE_BYTES`) and the message at 1 KiB, since some ids come from the browser.
    - **`GET /rpc/stream`** (`routes/rpc_stream.rs`) is one WebSocket per browser page, multiplexing the user's query streams. Client frames are `{op: "start", streamId, request}` (`request` inline, parsed from its exact bytes, and it must be `db.queryStream`, `db.run`, `db.page` or `db.tablePage` with the same `streamId`) and `{op: "cancel", streamId}`; server frames are `CoreEvent`s. A `streamId` is at most 128 characters of `[A-Za-z0-9_.:-]` (`MAX_STREAM_ID_LEN`; the clients send UUIDs), since it reaches the log before Core's ownership check; another is `INVALID_ARGUMENT` and never echoed. A bad frame gets a stream `error` (`INVALID_ARGUMENT`, `TOO_MANY_STREAMS`; a `run` error when the request names `db.run`, `db.page` or `db.tablePage`), never a closed socket. Limits: 16 streams per socket (a run, page or table page is one), 8 sockets per user (a 9th closes with 1013 `TOO_MANY_SOCKETS`), 8 MiB frames (1009 past it), and a batch whose frame would pass 4 MiB is split by rows, a run's as a stream's (the first piece keeps `columns`, the last `is_final`/`truncated`). Closing the socket cancels its streams; a stream that ends with no `done`/`error` and wasn't cancelled by its own socket gets `error` `CANCELLED` (a `run` error for a run). Connection events come from a per-user hub (`Workspaces::listen`), so a socket also hears about workspaces opened after it.
    - **`/internal/license/*`** (`routes/internal_license.rs`) is licensing for Node's hooks and routes, through `src/lib/server/license-client.ts`. It refuses (403) a peer that isn't loopback and any request without the per-boot secret in `X-Seaquel-Internal`, compared in constant time. Loopback alone isn't enough, since a query running inside the process (DuckDB's httpfs, in a build that has it) also arrives from loopback. `server.js` generates `SEAQUEL_INTERNAL_SECRET` and hands it to both processes; Rust removes it from its own environment at startup. Neither `server.js` nor any SvelteKit route forwards `/internal/*`, so it also needs Node and Rust on one host: a non-loopback `SEAQUEL_RUST_URL` fails closed. When the license service can't be reached, Node answers 503 (`api-gate.ts`: `{code: "license_service_unavailable"}` on `/api/*`, an operator page otherwise); `/health` skips the gate.
    - **Engines.** `web_core()` builds Core with `with_plugins(|id| WEB_ENGINES.contains(&id))`, `WEB_ENGINES = ["postgres", "mysql", "mssql"]`, so SQLite and DuckDB fail with `ENGINE_NOT_AVAILABLE` (400) whatever Cargo compiled in (`tests/web_engines.rs`). `web_config.rs` refuses, on connect and test, connection options that name a file or socket on the server: Postgres and MySQL TLS certificate and key paths, `passfile`, MySQL `socket`, socket hosts and URLs without a host (`CONNECTION_OPTION_NOT_ALLOWED`, 400). So client certificates and socket connections are desktop-only.
    - **Environment.** `server.js` starts Rust with an allow-list (`shared/rust-env.js`: the variables the Rust crates read, the proxy and CA variables, `PATH`/`TZ`/`LANG` and temp dirs) and `HOME=/nonexistent`, because sqlx takes defaults from `PG*` variables and `~/.pgpass`. The binary also scrubs `PG*`/`MYSQL*` and sets that `HOME` itself at startup (`startup.rs`), which covers `npm run rust:dev`. A new env var the Rust service reads goes into the allow-list; its vitest scans the crates for them.
  - Node: `/api/rpc` requires a session, sets `X-Seaquel-User` from `locals.user.id` (dropping any the browser sent) and forwards the body bytes untouched. It aborts its call to Rust when the client's socket closes (`platform.req` under adapter-node, the `seaquel-client-request` Vite plugin's request in `dev:web`; `shared/client-request.js`), since SvelteKit's `request.signal` doesn't once the body has been read: an aborted apply rolls back (atomic) or stops at the statement in flight (in order).
  - **Body limits** (`shared/body-limit.js`, operator-facing): `/api/rpc` takes up to 20 MiB (`RPC_BODY_LIMIT`: `WEB_EDIT_LIMITS`' 16 MiB of values and 2 MiB of SQL, plus JSON), or the operator's higher `BODY_SIZE_LIMIT` up to 64 MiB (`rpcBodyLimit`), and answers a larger body 413 `INVALID_ARGUMENT` naming the limit. Node keeps every body it reads until Rust answers, so the route also holds each user's bodies in flight to 40 MiB (`RPC_USER_BUDGET`, `reserveRpcBody` in `$lib/server/body-limit.ts`; by `Content-Length` before reading, or counted as a chunked body arrives; a lone call and a body under 64 KiB always run, the small one still counting; released on every path; a slow sender holds its reservation until Node's request timeout) and answers 429 `TOO_MANY_REQUESTS` past it. Limits parse exactly as adapter-node's (`Number()` with a K/M/G suffix, so `1e6` works). Signup and the air-gap upload rethrow the hook's 413 `HttpError`. Every other route keeps `BODY_SIZE_LIMIT` (512K by default), as adapter-node documents it: `server.js` moves the operator's value to `SEAQUEL_BODY_SIZE_LIMIT` and sets adapter-node's to `Infinity` before loading its handler, and `handleBodyLimit` (first in `hooks.server.ts`) enforces both, refusing by `Content-Length` before anything is read and counting a body sent without one. Rust's own `/rpc` limit (64 MiB) is only the outer bound. Every state-changing `/api/*` call but `/api/auth/*` (Better Auth checks those) needs a trusted `Origin` (`handleOriginGate` in `hooks.server.ts`, rules in `src/lib/server/origin.ts`), or it gets 403 `ORIGIN_NOT_ALLOWED`: `SEAQUEL_TRUSTED_ORIGINS`, the origins of `BETTER_AUTH_URL` and `ORIGIN`, the install's own origin (an `Origin` naming the request's `Host`, only while neither `BETTER_AUTH_URL` nor `ORIGIN` is set and only for `localhost` or an IP-address `Host`, never a domain name, which DNS rebinding could supply; the stream proxy passes the upgrade's `Host` to `/api/account/stream-access` as `x-seaquel-upgrade-host`), and the localhost dev-server origins in dev builds only. There is no `/api/db`: the engine and option refusals are Rust's (`ConnectPolicy`). `/api/rpc/stream` is proxied by `shared/rpc-stream-proxy.js` on the HTTP server itself (`server.js`, or a Vite plugin in `dev:web`), since SvelteKit routes can't upgrade: it resolves the session through `/api/account/stream-access` (behind `handleApiGate`, with the browser's `Origin` and the upgrade's `Host`), opens Rust's fixed `/rpc/stream` URL with `X-Seaquel-User` and no browser header, and pipes frames unread (browser frames capped at 8 MiB). It applies backpressure both ways: when the side it writes to holds 16 MiB unsent (`PAUSE_BUFFERED_BYTES`) it pauses the other side and resumes once the writes flush, so a slow browser stalls Rust's sender and the query instead of Node's memory; more than 64 MiB arriving from a side after it was paused (`MAX_BUFFERED_BYTES`) closes both with 1013, while one wide row and the frames right behind it pass. Browser frames queued while the Rust socket opens are capped (64 frames, 64 MiB) and flushed through the same backpressure, and a Rust socket that doesn't open in 10 s (`RUST_CONNECT_TIMEOUT_MS`) closes the browser with 1013. It re-checks the session every 60 s: a 401/403 or another user closes with 1008 (the client stops and reports lost access), a failing or slow gate with 1013 (the client reconnects). Sockets close with 1000 after 12 h and reconnect. Rust's close code and reason reach the browser. `hooks.server.ts` caches each user's gate answer for 5 s.
- **The web tutorial runs DuckDB-WASM in the page**, never on the server: the web build serves its own copy of the bundles (`duckdb-local-bundles.ts`, about 75 MB of assets, so an air-gapped install has a tutorial), the demo loads them from jsDelivr, and desktop uses SQLite through Tauri. ### Dialects and engine calls

- **UI code never scans or parses SQL itself.** Splitting, statement at cursor, `{{param}}` handling, query type, the destructive and read-only checks, `CREATE TABLE` parsing and the AST helpers all come from `$lib/sql` (`src/lib/sql`), which calls `seaquel-wasm`. Pass the connection's engine; the checks follow its quoting. If the module traps, `callWasm` re-instantiates it and the per-keystroke functions return their "couldn't parse" value, so on the run path (anything that decides what SQL executes) use the `…OrThrow` variants, which fail instead of letting SQL run unchecked. On desktop and web the editor's runs are planned by Core (`db.run`, below); the wasm calls remain for the editor's own checks (its synchronous destructive prompt, Explain and Visualize at the cursor) and the demo's `TsQueryRunner`.
- **UI code never does dialect work itself.** Introspection, EXPLAIN, statistics and DDL generation go through `EngineClient` (`src/lib/engine`): `getEngineClient(connection, state)`. Pagination, counts, CRUD and the data tab's query are Core's (`db.run`/`db.page`, the edits service); `EngineClient` has no `paginate` or `build*` since 5c, and the demo's `TsQueryRunner` and `TsEditService` call the `duckdb.ts` adapter for them directly. Pass the app state so the client reads the live provider connection id on every call (it survives `reconnect()`). Don't cache clients across operations, and don't call `getAdapter(` outside `src/lib/engine/` and `src/lib/db/`.
- **Identifiers:** quote a name with `EngineClient.quoteIdent` and build a table name from a listed schema with `EngineClient.qualifiedTable` (DuckDB lists attached catalogs' schemas as `catalog.schema`, two names). Never hand-build `"${name}"`.
- **AI and dashboard SQL runs only through `executeReadOnly`** (`QueryCrud`, then `DatabaseProvider.selectReadOnly` and Core's `query_stream` with `QueryOptions::read_only`), and so do workflow query nodes. Core runs the token check (`seaquel_sql::read_only`) and then `Driver::query_read_only`, whose default is `NOT_SUPPORTED`. The client sets the `read_only` flag: it limits what the AI's SQL can do, and is no guard against the local user or an API caller. Per engine:
  - Postgres: `BEGIN READ ONLY` on a pooled connection, which is closed afterwards, not returned.
  - MySQL/MariaDB: `SET SESSION TRANSACTION READ ONLY`, then `START TRANSACTION READ ONLY`, on a pooled connection that is then closed.
  - SQLite: a private read-only connection with `PRAGMA query_only = ON`, an authorizer that refuses most PRAGMAs and `ATTACH` (`read_only::deny_settings`), and a gate that prepares the SQL with SQLite's parser and allows one statement for which `sqlite3_stmt_readonly` is true (`read_only::check`). `SqliteDriver` refuses SQL holding a NUL byte on every entry point: sqlx 0.8.6 loops forever on it.
  - DuckDB: a clone of the connection per call, `BEGIN TRANSACTION READ ONLY` and `SELECT * FROM query(?) LIMIT <cap + 1>` with the SQL bound. The token check also refuses DuckDB functions that act outside the query (`BLOCKED_FUNCTIONS_DUCKDB`: `enable_logging`, `checkpoint`, `query`, `mysql_execute`, …). For the in-app AI, files and URLs stay readable: its instance is the editor's, whose file functions need external access. Only the MCP server's own instances are restricted.
  - A lone `\r` ends a `--` comment in the scanner on SQL Server, Postgres and DuckDB, as those databases do. The read-only check (`read_only_error`) also reads every input a second time with a lone `\r` ending `--` and `#` comments, on every engine, and refuses if either reading does; so on MySQL, MariaDB and SQLite, code-looking text after a `\r` inside a comment is refused.
  - MSSQL has no read-only mode. Each call gets its own connection (`READ_ONLY_CONNECTIONS`, 4 at once; `READ_ONLY_TIMEOUT`, 60 s), never the held session. The SQL runs two transactions deep inside TRY/CATCH and is always rolled back; a query that ends the transaction comes back as `READ_ONLY`, but what it committed stays, and `NEXT VALUE FOR` advances. Only a read-only login closes that.
- `getEngineClient` returns `RustEngineClient` (`db.engine` through `CoreClient`) for Postgres, MySQL, MariaDB, SQLite, MSSQL and DuckDB on desktop (Postgres, MySQL, MariaDB and MSSQL on web), and `TsEngineClient` (the TypeScript `DatabaseAdapter` plus a provider) for the browser demo, which has no Rust core. `src/lib/db/duckdb.ts` is the only TypeScript adapter left, and it is demo-only (as are `alter-table.ts` and `crud-helpers.ts`; `index.ts` only re-exports the `SqlWithBindings` type from the latter); `getAdapter` throws for every other engine.
- **Every engine crate** has `dialect.rs` (the pure `Dialect`), `introspect.rs` (catalog SQL, parsers, EXPLAIN) and `decode.rs` (with `bind.rs` in all but DuckDB) for values. Postgres adds `numeric.rs`, the NUMERIC binary codec. `crates/seaquel-engine-mysql` serves MySQL and MariaDB: a `"mariadb"` connection connects with driver `"mysql"`.
- **SQLite:** cells decode by storage class (`typeof`), not declared type; BLOBs are bytes. SQLite has no `DEFAULT` in `UPDATE`, so Set to default writes the column's default expression, which Core reads from the table's metadata when it plans the edit (none: NULL). Edits SQLite can't make come back from `alterTable` as `-- …` note lines; the table editor shows them (`splitDdlScript` in `src/lib/utils/ddl-script.ts`).
- **MSSQL:** cells are native: decimal and money are `Decimal`, binary is `Bytes`, dates and times are SQL Server's own text (datetimeoffset as `2024-01-02 03:04:05.5 +01:00`). tiberius hands money over as an f64: it is exact only for |value| < 2^39 ≈ 5.5·10¹¹; above 2^53 units tiberius itself loses bits (up to ~1536 units near the ends of the range), and the maximum reads `922337203685477.5808`, which is out of range when bound back. A `Null` parameter is sent as the `NULL` literal (`inline_nulls`), since no declared type assigns to every column; so a column made only from it is int (`SELECT @P1 INTO`, `UNION`), `COALESCE`/`CASE`/`IIF` with only such NULLs fail (4127, 8133), and so does passing one as an `OUTPUT` argument (179). A `@Pn =` naming a parameter in an `EXEC` argument list is left alone. Query parameters (`{{name}}`) are inlined, strings as `N'…'`, so they work in `TOP`, `CREATE VIEW` and defaults. CRUD binds `@P1…`; EXPLAIN runs `SET SHOWPLAN_XML`/`STATISTICS XML` as separate batches and parses the ShowPlan XML with roxmltree; statistics are `NOT_SUPPORTED`.
- **DuckDB** uses the Rust crate on desktop (web has no DuckDB connections); the demo keeps `duckdb.ts`, whose behaviour shouldn't change. Attached catalogs are listed as `catalog.schema`, with a part holding `.` or `"` double-quoted (`"fx.we""ird".main`, or `"a.b"` for a default-catalog schema named `a.b`); `system` and `temp` are left out. Build `"schema"."table"` from a listed schema with `Dialect::quote_schema` in Rust (the CRUD/DDL builders' `_qs`/`_with` variants take it) and `EngineClient.qualifiedTable` in TypeScript, never by quoting the schema as one name. CRUD binds `?`. Edits DuckDB rejects (constraints in `ADD COLUMN`, column changes while the table keeps an index, dropping or retyping a PRIMARY KEY/UNIQUE column or a column before one) come back from `alterTable` as notes; the rules read `isUnique` and `inUniqueConstraint` (any UNIQUE constraint, composite too), which DuckDB's `table_metadata` reports on `SchemaColumn` and the table editor copies. `{{param}}` values are inlined (desktop, web and demo), skipping comments and quoted names.
- **The MSSQL driver runs on one connection**, except `query_read_only`, which opens its own per call (above). A call that doesn't finish (a UI cancel, a dropped request, `RESULT_TOO_LARGE`, a fatal error) closes it, and the next call reconnects. That loses `##global` temp tables, session context, app locks and any transaction opened by hand, which is silently rolled back. Code that changes session state (`SET SHOWPLAN_XML ON`, …) must wrap it in `Session::hold_state()`/`release_state()`; a failure before the matching OFF reconnects, with the same losses.
- **MSSQL statements run through `sp_executesql`**, with or without parameters, so a user's `SET` options and `#temp` tables end with the call and can't leak into introspection or grid edits. `USE` is the exception (it outlives an RPC call), so after a statement mentioning `USE` the driver switches back to the connection's database (`restore_database` in `driver.rs`). Only a parameterless statement that must start a batch (`CREATE VIEW`/`PROCEDURE`/`SCHEMA`, …; `must_start_batch`) and the driver's own BEGIN/COMMIT/ROLLBACK and EXPLAIN `SET … ON/OFF` go as plain batches. A plain EXPLAIN with parameters declares them without values, so its estimates are the generic ones.
- **MySQL/MariaDB TIMESTAMP values are shown as UTC wall-clock time**: sqlx sets the session `time_zone` to `'+00:00'`. Don't add a `timezone` to connection strings; in a zone with DST two instants print the same and a TIMESTAMP key would match the wrong row.
- The parity fixtures in `crates/seaquel-engine-*/tests/fixtures` were recorded from the TS adapters and are frozen; the recorder is gone (a reference copy is in `docs/plans/artifacts/`). Change a fixture only when the Rust behaviour is meant to change, and say why.

### Connections in the GUI

- **Every database call goes through `CoreClient`** (`src/lib/core`, `getCoreClient()`, picked per call): `call` for one `CoreRequest`, `stream` for a `db.queryStream` (`StreamEvent`s) or a `db.run`/`db.page` (`RunEvent`s) (an async iterator that always ends with exactly one `done` or `error`; aborting its signal or leaving the loop cancels it, ending with `CANCELLED`), and `events` for `connectionClosed`. `TauriCoreClient` uses `core_call`/`core_stream`/`core_events`; `HttpCoreClient` uses `/api/rpc` and one `/api/rpc/stream` socket per page, queueing past 16 streams, reconnecting with backoff (0.5 s doubling to 30 s) while something needs the socket, failing running streams with `WS_CLOSED` when it drops, `TOO_MANY_TABS` on 1013 `TOO_MANY_SOCKETS`, and `ACCESS_LOST` on 1008 (no reconnect until the next query). Run text and page SQL are sent through `wellFormed` (`toWellFormed`, with a fallback), since `serde_json` refuses a lone surrogate; U+FFFD is one UTF-16 unit too, so the cursor stays valid. `CoreProvider` is the one `DatabaseProvider` over it; the demo and the tutorial keep `DuckDBProvider`.
- **`ConnectionManager` sends targets, never configs.** `add`, `reconnect` and `test` send `{type: "form"}` with the form as typed (an empty SSL mode left out, so the engine's default applies; the wizard's "Default"); `autoReconnect` sends `{type: "saved"}` with only the secrets the client holds (web: the vault; desktop: a session password for a row that doesn't save one; Core reads the keychain). `withHostKeyPrompt` (`src/lib/core/host-key.ts`) wraps connect and test for the SSH trust prompt. A `connectionClosed` event marks the connection disconnected with a toast. The GUI never opens tunnels or edits connection strings to connect.
- **A connection string lives only while it's visible** (`src/lib/utils/connection-string-rules.ts`), because Core connects with the string and ignores the fields it encodes. The details step shows a non-empty string with a Clear button; editing host, port, database, user, SSL mode or a file path, or picking a type, clears it. A paste fills the fields and drops the string unless it holds something they can't (other query parameters, `+ssh`, not a URL). Rows from before phase 5a lose a string that equals what the old builder made of their fields, on load, and the cleaned row is saved once. Stored strings go through `stripConnectionStringSecrets` (URL, `+ssh` and query passwords, `Password`/`Pwd` pairs, credential-like DuckDB/SQLite options; anything it can't read is stored as `""`).

### Running queries in the GUI

- **The editor runs through a `QueryRunner`** (`src/lib/hooks/database/query-runner/`): `getQueryRunner` gives `CoreQueryRunner` (`db.run`/`db.page`) on desktop and web, and `TsQueryRunner` in the demo, the pre-5b TypeScript logic moved (wasm planning, `DuckDBProvider`, the `duckdb.ts` adapter's `paginateQuery`, history through sql.js) and emitting the same `RunEvent`s, until phase 8. `ts-runner-fixtures.test.ts` replays the 95 run fixtures through it. The TS runner has no substitution budget and no web limits.
- **`QueryExecutionManager`** (`query-execution.svelte.ts`) is a view model over run events. It decides nothing about what runs: no `$lib/sql` planning call outside `ts-runner.ts`, and no `provider.select`/`execute` on the Core path. One operation per tab: a new run cancels the tab's previous run (all of it, not only its stream), Stop and closing the tab cancel in Core, and a page request while a run is going is ignored. Events go to the tab they started on, looked up through the `$state` proxy each time (mutate results through `getProxiedResult`). A result keeps `pageSource` (the SQL after substitution and its binds) for `goToPage`/`setPageSize`, which send `db.page`; `statementSql` stays the typed text. `columnSourcesFromRefs`/`sourceTableFromRef` resolve Core's `table`/`columnRefs` against the schema cache. `statementDeferred` is queued as a `{type: "sql"}` change with its binds (`pendingChanges.addSql`).
- **Destructive statements.** The editor's own synchronous wasm check prompts first and sends `confirmed` after the user agrees. Any other caller (the file-drop run, the reruns after a grid row delete or Set default) gets Core's `CONFIRM_REQUIRED` as `pendingConfirm`, which the editor shows for the active tab ("…and N more" past 100); it is cleared when another tab becomes active or its tab goes, and Confirm refuses if the active connection changed. The reruns send no parameter values yet.
- **History is append-only in the GUI.** `QueryHistoryManager` is a cache: a Core run's `done.history` goes in with `insertRecorded` (trimmed by the same rule as the file) and triggers `licenseNudgeStore.recordQuery()`; an apply's rows come back in Core's outcome and go in with `insertRecorded` too (no nudge); only the demo's `TsQueryRunner` and `TsEditService` call `append`; the favourite toggle calls `setFavorite(id, value)`. Nothing replaces a connection's list, so a failed history load blocks nothing.

### Edits, pending changes and the data tab in the GUI

- **Edits go through an `EditService`** (`src/lib/hooks/database/edit-service/`, `plan`, `apply`, `tablePage`, `duckdbExtension`): `getEditService` gives `CoreEditService` (the edits service above) on desktop and web and `TsEditService` in the demo, the pre-5c TypeScript builders, apply loop and data tab query moved, over DuckDB-WASM, until phase 8. The demo's service applies DML-only batches in `BEGIN`/`COMMIT`, reads no metadata (so no key check), always counts a data tab page, and inlines filter values as escaped literals, since `DuckDBProvider.select` ignores binds. `QueryCrudManager`, `PendingChangesManager` and `DataTabManager` are view models over it; none builds, pages or classifies SQL. `$lib/sql`'s `changeSummary` feeds `describePendingChange`.
- **Edits go to the connection their data came from.** A `StatementResult` carries `connectionId` (the saved connection it ran on) and a data tab its own; edits, inserts, deletes, Set default, paging and the pending overlays use it, never the active connection, and look its Core id up after their last await, so a reconnect is followed and a disconnected or removed connection is refused. The sheet and header badge follow `state.pendingConnectionId` (the focused data tab's or result's connection, else the active one).
- **Queued or immediate** is the pending-changes setting (on by default). On, `db.planEdits` fills a queue entry's display fields and the entry keeps the `change` that apply sends back; a repeated edit of one cell replaces the queued one in data and query tabs alike, and a per-cell sequence drops a plan that lands after a later edit of that cell. Off, the edit is `db.applyChanges` with one change.
- **Apply** (`PendingChangesManager.apply`): a full success clears the queue; an atomic failure keeps it whole and marks the failed change; an in-order failure removes the applied prefix. An apply that ends without an answer (`NETWORK_ERROR`, `PROTOCOL_ERROR`, `UNKNOWN`, `CANCELLED`, `WS_CLOSED`, `HTTP_5xx`, or an atomic `WORKSPACE_CLOSED`) is `interrupted` whatever its mode, since an atomic batch may have committed before its reply was lost: the queue is kept and marked (`state.pendingChangesInterrupted`, the sheet's "may be partly applied" banner), and the schema and the connection's data tabs reload. The sheet's confirm dialog lists the destructive statements `$lib/sql` finds and sends `confirmed` only when it listed some, so Core's `confirmRequired` reopens it with Core's list. `NO_ROWS_AFFECTED` is shown with the change's table and key (`stale-edit.ts`, i18n), `TRANSACTION_OPEN` as `edit_transaction_open`. The sheet shows each change's SQL with its values beside it.
- The sidebar's DROP and TRUNCATE send `dropObject`/`truncateTable` intents with `confirmed` (their own dialogs asked); the table editor applies its generated statements as typed changes with `confirmed: true`.
- **The data tab** (`DataTabManager.refresh`) sends a `TableQuery` through `tablePage`; the filter bar's operators are the generated `FilterOp`. One operation per tab: a new refresh, closing the tab or a project switch aborts the previous one.
- **Workflow query nodes are read-only**: `executeReadOnly` on the node's saved connection, at most `WORKFLOW_MAX_ROWS` (10,000; a cut result says so on the node), one `AbortController` per node (re-running or deleting it cancels). A write is refused with `READ_ONLY`.
- **The DuckDB extensions tab** runs on its tab's connection through `db.duckdbExtension` on desktop, and through the demo provider's `executeRaw` in the demo.

### Cell values

Rows and parameters cross the wire in one format (`crates/seaquel-types/src/value.rs`, `src/lib/values.ts`). Values JavaScript holds exactly are plain JSON. Everything else is tagged as `{"$sq": kind, "v": …}` with kind `bigint`, `float` (NaN/±inf), `decimal`, `bytes` (base64) or `json`. The providers decode tags before any UI code sees a row and encode parameters with `encodeParam`, so the UI gets `bigint`, `Uint8Array` and `SqlDecimal` alongside plain values. Use the helpers in `$lib/values` (`cellKey` for comparing cells, `cellText`, `toNumber`, `jsonReplacer` for `JSON.stringify`, `toStorable` for persisted rows) instead of `String()`/`Number()`/bare `JSON.stringify` on cells.

The DuckDB driver reads Arrow chunks itself (`crates/seaquel-engine-duckdb/src/decode.rs`). Temporal types are Text in DuckDB's own format (TIMESTAMPTZ always in UTC, `2024-01-01 12:00:00+00`), STRUCT/MAP are `Json` with sorted keys, and the driver turns on `arrow_lossless_conversion` for its connection.

### Metadata storage

- **Read and write metadata only through `getStorage()`** (`$lib/storage`), which returns a `StorageClient`: `RustStorageClient` (`core_call` on desktop, `/api/rpc` on web) or, in the demo only, the sql.js repositories (`sqljs-client.ts`). UI code never sends SQL to the metadata database; a new query is a new `seaquel-storage` function and `StorageRequest` variant. `RustStorageClient` puts every write through one queue so writes land in the order issued (`PersistenceManager`'s debounced saves rely on it); reads skip it. Every method is classified in `STORAGE_METHOD_KIND`.
- **Never save a collection whose load failed** (`load-guard.ts`). A store that replaces a whole collection or record on save marks a failed load, and its saves refuse until a load succeeds: interactive saves throw `NotLoadedError` (show it with `errorToast`), background saves call `skipUnloadedSave` and return. `PersistenceManager` tracks this per key. New replace-all saves need the same guard. Query history needs none: it is only appended and flagged (`append`, `setFavorite`), never replaced.
- **The storage gate** (`storage-gate.svelte.ts`): `storageGate.check()` is the first storage call, awaited by `UseDatabase.initializeApp` and the `(app)` layout. `LEGACY_STORAGE`, `STORAGE_CORRUPT` and `NO_DATA_DIR` set `storageGate.blocked`, and `(app)/+layout.svelte` shows `storage-error-screen.svelte` instead of the app. Other errors are retried twice, then logged, and the app starts.

## Updating the Demo

The demo is a browser-based version using DuckDB WASM (instead of PostgreSQL) hosted at `seaquel.app/demo`.

From the website repo (`seaquel-app/main`), run:

```bash
npm run demo:update
```

This script removes old demo files, builds the demo with `BUILD_TARGET=demo`, and copies the output to `static/demo/`. Commit and deploy the website changes afterward.

The build runs `npm run wasm:build` in this repo, so the machine needs the wasm toolchain from "Development Commands" (Rust, the wasm32 target and the matching wasm-bindgen-cli). Without it the build fails; `SEAQUEL_WASM_PREBUILT=1` reuses an existing `src/lib/wasm/pkg/`, which may be out of date.

## Releasing a New Version

Version format: `YYYY.month.patch` (e.g., `2026.1.1`)

1. Update version in these files:
   - `src-tauri/Cargo.toml`
   - `src-tauri/tauri.conf.json`
   - `Cargo.lock` at the repo root (run `cargo check -p seaquel` after the `Cargo.toml` bump, which needs the sidecar from `npm run cli:build`, or edit the `seaquel` entry). `src-tauri` is a workspace member, so the root lockfile is the only one.
   - `package.json`
   - `package-lock.json`

2. Commit: `Bump version to X.Y.Z`

3. Create and push tag:

   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

4. GitHub Actions builds for macOS (Intel + ARM) and Linux (x86_64 + ARM64), signs binaries, and creates a draft release

5. Review and publish the draft release on GitHub
