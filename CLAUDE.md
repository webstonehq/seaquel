# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Seaquel is a database client built with Tauri 2 + SvelteKit 5 + TypeScript, with a Rust core. It supports PostgreSQL, MySQL/MariaDB, SQLite, MSSQL and DuckDB through the Rust engine crates in `crates/`. It ships as a desktop app, a self-hosted web app (`seaquel-server` behind a Node/SvelteKit server), a browser demo, and two terminal binaries: `seaquel-cli` (the MCP server) and `seaquel-tui` (a terminal client). No shipped binary but one links DuckDB: the desktop app and both terminal binaries run it in `seaquel-duckdb`, a helper process per DuckDB connection, downloaded once per version on first use into a folder they share (see `seaquel-duckdb` below). The demo runs DuckDB-WASM.

SQLite and DuckDB connections are desktop-only. On web their "connection string" is a path on the server, so the web server refuses both (see `seaquel-server` below), and the web wizard doesn't offer them. The demo has DuckDB-WASM in the page and nothing else, with Core compiled to wasm32 in the page beside it (see "The demo" below). SSH tunnels, shared projects (git) and the TablePlus and DBeaver imports are desktop-only too.

## Development Commands

```bash
# Start development (frontend + Tauri), as app.seaquel.desktop.dev
npm run tauri:dev

# Build production app
npm run tauri build

# Type checking
npm run check

# Type checking (watch mode)
npm run check:watch
```

Use `npm run tauri:dev`, not `npm run tauri dev`. The script passes `--config '{"identifier":"app.seaquel.desktop.dev"}'`, so the dev app keeps its data, its CLI and its DuckDB helper under `app.seaquel.desktop.dev`, where a debug `seaquel-cli` or `seaquel-tui` looks too. A plain `tauri dev` runs as the real `app.seaquel.desktop`: it reads and writes the installed app's `seaquel.db`, and its first DuckDB connect downloads the release helper of its version into the real `bin/duckdb/`. A debug app installs the `seaquel-duckdb` built beside it instead of downloading only when the identifier ends in `.dev` or `SEAQUEL_DATA_DIR` is set (`cli_download::may_use_debug_helper`).

The DuckDB helper's digest is built into release apps. `src-tauri/build.rs` reads `SEAQUEL_DUCKDB_HELPER_SIZE` (bytes, plain decimal, at most 64 MiB) and `SEAQUEL_DUCKDB_HELPER_SHA256` (64 hex digits, no `sha256:` prefix) through `src-tauri/src/helper_pin.rs`, which the app includes too, and compiles them in as one `SEAQUEL_DUCKDB_HELPER_PIN=<size>:<sha256>` read with `option_env!`; nothing reads them at run time. Neither set (every local build and test run) means no pin: the app asks GitHub's release API for the size and digest, as the terminal binaries do, and offers no "Install from a file…" and no prefetch. One without the other, or a value that doesn't parse, fails the build. `SEAQUEL_DUCKDB_HELPER_REQUIRE_PIN=1` (`release.yml` sets it on every app build) fails the build without both; unset, empty or `0` is off, anything else is an error.

Every script that runs Vite, svelte-check or vitest first runs `npm run wasm:build` (`scripts/build-wasm.mjs`), which builds `crates/seaquel-wasm` into `src/lib/wasm/pkg/` (gitignored). It needs the wasm32 target and wasm-bindgen-cli at the exact version in `Cargo.lock`:

`mise install` sets up Node, Rust and wasm-bindgen-cli from `mise.toml`, and `rust-toolchain.toml` adds the wasm32 target. Without mise:

```bash
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version "$(node scripts/build-wasm.mjs --bindgen-version)" --locked
```

When a dependency update bumps wasm-bindgen in `Cargo.lock`, update `"cargo:wasm-bindgen-cli"` in `mise.toml` to the same version.

- If that toolchain is missing the script fails, even when an older `pkg/` exists: a stale module would run old SQL checks, including the AI's read-only check. `SEAQUEL_WASM_PREBUILT=1` uses `pkg/` as it is without building (the Docker image does this); set it only when you know `pkg/` matches the crates.
- `dev` builds the module once at startup. After changing `crates/seaquel-sql` or `crates/seaquel-wasm`, rerun `npm run wasm:build`; Vite then reloads the new module.
- The demo's second module, `crates/seaquel-browser` (Core in the page), is built only where it's used: `predev:demo` and `prebuild:demo` run `npm run wasm:build:browser` (into `src/lib/wasm/browser-pkg/`), and `pretest`/`pretest:watch` run `wasm:build:browser-test` (the `test-hooks` variant vitest loads, into `browser-test-pkg/`). Desktop and web scripts never build it. Each module has its own stamp, and `SEAQUEL_WASM_PREBUILT=1` covers both.

On macOS, a wasm32 build or clippy of `seaquel-storage` or `seaquel-browser` (they compile SQLite's C through sqlite-wasm-rs) needs `CC_wasm32_unknown_unknown`/`AR_wasm32_unknown_unknown` pointing at an LLVM clang and llvm-ar, or Homebrew's llvm (`brew install llvm`) on its default path; Apple's clang has no wasm32 backend. So `npm test`, `dev:demo` and `build:demo` (and the website's `demo:update`) need `brew install llvm` once. `build-wasm.mjs --module browser` finds a clang itself (`CC_wasm32_unknown_unknown`, then Homebrew's llvm, then a `clang` on `PATH` whose `--print-targets` lists wasm32), prints the one it used and stops with the fix named when there is none; plain cargo doesn't look. CI sets `clang-18`/`llvm-ar-18`.

On Linux (and in CI) `seaquel-secrets` links the system libdbus for the Secret Service, so install `libdbus-1-dev` and `pkg-config`.

The terminal binaries, `seaquel-cli` and `seaquel-tui`, and the DuckDB helper, `seaquel-duckdb`, aren't in the app bundle (there is no `bundle.externalBin`). `release.yml` builds, signs and uploads each per target as a release asset (`seaquel-cli-<triple>`, `seaquel-tui-<triple>`, `.exe` on Windows, and `seaquel-duckdb-<triple>[.exe].gz`). Each `publish-tauri` matrix job builds the helper first, without `--gzip`, codesigns it on macOS with the hardened runtime and `src-tauri/macos/duckdb-helper.entitlements.plist` (its one entitlement, `disable-library-validation`, lets DuckDB load its extensions, which DuckDB signs; issue #114) or trusted-signs it on Windows, gzips it with `build-cli.mjs`'s `gzipFile`, so the `.gz` holds the signed file, pins the `.gz`'s size and SHA-256 into the app's build, and uploads only the `.gz` to the draft after the app (see "Releasing"). The app, the CLI and the TUI are signed with the hardened runtime and no entitlements: nothing they load needs one, and the entitlement would let any library load into them. The app downloads the helper on its first DuckDB connect (the dialog, below), and the version-matched `seaquel-cli` when the user asks (`cli_download.rs`, below); nothing installs `seaquel-tui` yet (the README gives a manual download), and the TUI and CLI fetch the helper themselves on first use. All three use one helper per version. `npm run cli:build` (`scripts/build-cli.mjs`) builds the CLI and copies it to `src-tauri/binaries/seaquel-cli-<target-triple>` (gitignored), `npm run tui:build` does the same for the TUI (`--bin seaquel-tui`) and `npm run duckdb-helper:build` for the helper (`--bin seaquel-duckdb`). The script takes `--release`, `--target`, `--bin seaquel-cli|seaquel-tui|seaquel-duckdb` and `--gzip` (also writes `<asset>.gz`), honours `CARGO_TARGET_DIR`, and a host build without `--target` shares `target/debug` with the app. `--release` builds with the root `Cargo.toml`'s `terminal-release` profile (fat LTO, one codegen unit, stripped; output in `target/[<triple>/]terminal-release/`); it keeps `panic = "unwind"`, which the TUI's panic hook and DuckDB's `catch_unwind` need. Without DuckDB (macOS arm64) the TUI is about 18.3 MB (8.6 MB gzipped) and the CLI 15.1 MB (7.2 MB), against 50 and 46 MB with it, and the helper is 34.7 MB (11.5 MB gzipped), downloaded once for all three. The app's release binary went from 101.9 MB (39.1 MB gzip -9) to 60.8 MB (27.0 MB) when DuckDB left it. Neither the app's build nor `cargo check -p seaquel` needs any of these files.

The web app in development is `npm run dev:web:full`: `scripts/with-internal-secret.mjs` generates a `SEAQUEL_INTERNAL_SECRET` and runs `rust:dev` (the Rust service) and `dev:web` (Vite) under it. If you run `rust:dev` and `dev:web` separately, export the same `SEAQUEL_INTERNAL_SECRET` in both shells, or every licensing call is refused and the app shows the 503 page. In production `server.js` generates the secret itself.

## Architecture

### Frontend (src/)

- **SvelteKit 5** with static adapter (SSR disabled for Tauri)
- **Svelte 5 runes** (`$state`, `$derived`, `$props`) for reactivity
- **Tailwind CSS v4** for styling
- **bits-ui** for accessible UI components (shadcn-svelte pattern)

### Backend (Rust)

All database logic lives in Rust crates under `crates/`, shared by every interface. See `docs/plans/2026-09-24-rust-core-plugin-architecture-design.md` for where this is heading.

- `seaquel-core` — the only entry point interfaces use: engine registry, open connections, streaming and cancellation. `disconnect` cancels the connection's running streams, which end with a `CONNECTION_CLOSED` error event. `Core::open_workspace(WorkspaceSpec)` opens a `Workspace` (`workspace.rs`): one data dir's metadata `Storage` plus an optional `SecretStore`, behind Core's `storage`/`secrets` features. Core owns SSH tunnels (`ssh_open`/`ssh_close`; dropping Core closes them) and re-exports the other infrastructure crates, so interfaces never name them directly. Since phase 5d it also writes the library (saved connections, projects, labels, saved queries, dashboards, workflows, AI chats), the settings and each window's view state, and announces every stored write (below). Since 5e it also projects shared projects into their git repos and reads other tools' connection files (`LocalFiles`, below). Since phase 6 it runs the AI assistant: the model calls, the tool loop, the tools and the chat writes (`ai`, below).
  - **Features.** The engines (`engine-postgres`, `engine-mysql`, `engine-sqlite`, `engine-mssql`, all default; DuckDB is `engine-duckdb-remote`, below) plus `storage`, `secrets`, `ssh`, `git`, `license-desktop`, `license-server`, `workspace` (connecting, running and editing: `Workspace::connect`/`test`/`run`/`page` and the edits calls), `imports` (TablePlus and DBeaver, with `plist` and `dirs`), `ai` (the assistant's turn and the tool registry, `seaquel_core::ai`; needs `workspace` and `storage`), `ai-native` (`seaquel-http`'s reqwest client and egress guard, as `ai::native`), `ai-system-proxy` (the OS proxy settings for that client) and `ts` (the domain's TypeScript bindings, turned on by `seaquel-rpc/ts`), off by default. `src-tauri` takes Core without its default features and enables the four engines, `storage`, `secrets`, `ssh`, `git`, `license-desktop`, `workspace`, `imports`, `ai-native`, `ai-system-proxy` and `duckdb-helper-install` (its own DuckDB and the CLI's); `seaquel-server` enables `storage`, `license-server`, `ai-native` and the Postgres, MySQL and MSSQL engines (and `workspace` through `seaquel-rpc`); `seaquel-terminal` takes Core without its default features and enables `engine-postgres`, `engine-mysql`, `engine-sqlite`, `engine-mssql`, `engine-duckdb-remote`, `storage`, `secrets`, `ssh` and `workspace` for both terminal binaries, and `duckdb-helper-install` through a feature of its own with that name, which both binaries turn on; `seaquel-cli` adds `imports` (and `ai` and `engine-duckdb-remote` through `seaquel-mcp`, for the registry and the helper's status, with no model client), `seaquel-tui` adds `ai-native`. Neither terminal binary has `git` or `license-*` (the CLI checks no license and calls no model; the TUI checks no license). There is no in-process DuckDB driver and no `engine-duckdb` feature (both deleted): `engine-duckdb-remote` is DuckDB through the helper (`seaquel-engine-duckdb/remote`, no `duckdb` crate), registered by `.duckdb_helper(…)`, never by `with_default_plugins()`, which registers the four engines; `duckdb-helper-install` is the helper's download (`engine-duckdb-remote` plus `seaquel-http`'s `release-asset`, so reqwest) and `duckdb-helper-testing` that plus `seaquel-http/testing` (below; `src-tauri` turns it on only as a dev-dependency, so its tests build in the release profile). `browser` is the wasm32 build for the demo (phase 8). It admits `storage`, `workspace` and `ai` (in-memory SQLite through `seaquel-storage`'s wasm32 executor; model calls through the page's fetch bridge); combining it with an engine feature (`engine-duckdb-remote` included: a child process), `secrets`, `ssh`, `git`, `license-*`, `imports` or `ai-native` is a `compile_error!`. `seaquel-browser` registers the DuckDB-WASM engine itself (`seaquel_engine_duckdb::browser_engine`, through `CoreBuilder::engine`).
  - **Re-exports**, since interfaces may not name these crates: `storage`, `secrets` (behind their features), `sql` (`seaquel-sql`, always) and `domain` (`seaquel-workspace`, always: it is pure, builds for wasm32, and its run types are on the `db` wire in every build; not named `workspace`, which is Core's own `Workspace` module). `RunLimits`, `EditLimits` and `LibraryLimits` are re-exported from it. Behind `ai`, Core's own `ai` module re-exports `seaquel-ai`'s `http`, `limits`, `prompt`, `sharing`, `sse`, `wire` and `tools`, so `seaquel-mcp` reaches the registry as `seaquel_core::ai::tools`.
  - **`Workspace::connect(core, ConnectRequest)` and `Workspace::test`** (behind `workspace`; a saved target also needs `storage`, a tunnel `ssh`, a store `secrets`) connect a `ConnectTarget::Saved { id }` or `Form { form }` (`ConnectionForm`) through one builder, `seaquel_workspace::connections::plan`, pinned by `crates/seaquel-workspace/tests/fixtures/connect-config-v2`. `SuppliedSecrets` (redacted `Debug`) always win; a saved row reads the rest from the workspace's store under its save flags; a form reads nothing. `host_key` is `HostKeyPolicy::KnownOnly` (never writes known_hosts; `UNKNOWN_HOST_KEY` carries the fingerprint) or `Trust(fingerprint)` after the GUI's prompt; `restricted` sets `ConnectConfig::restricted` (DuckDB locked down; the MCP server). The tunnel belongs to the connection: `disconnect`, a failed connect, dropping Core or dropping the future closes it. A store read that fails gives `SECRET_UNREADABLE` before anything opens, or `SECRET_STORE_UNAVAILABLE` when every failed read found no store to talk to at all (`SecretError::Unavailable`, below: no session bus or Secret Service, a macOS session with no GUI; phase 7a), with a neutral message so the TUI can ask for the password instead; a refusal among the reads keeps `SECRET_UNREADABLE`; on a workspace with no store (web) a saved row connects with only what was supplied, as a form does, so a trust-auth row with no stored password connects (`NO_SECRET_STORE` is 400 on web for any read that still answers it). Connect errors have every secret replaced by `<redacted>`. `ConnectRequest::with_saved_connection_id` (`db.connect`/`test`'s `savedConnectionId`) records which saved connection a form connect opened, which a turn checks (a saved target records its own id; one naming another is `INVALID_ARGUMENT`), and `with_origin` records the window that opened it (below). Opening is bounded by `CONNECT_TIMEOUT` (30 s each for the SSH open and the engine open, `CoreBuilder::connect_timeout` for tests), raced against the executor's `sleep`; past it, `TIMEOUT` (504 on web). The sqlx engines set their pools' `POOL_IDLE_TIMEOUT` (10 min) and `POOL_ACQUIRE_TIMEOUT` (30 s) explicitly (`seaquel-engine`; sqlx's defaults). The GUIs (the `db` RPC group), the TUI and the MCP server all connect this way; nothing else builds a `ConnectConfig`.
  - **`ConnectPolicy`** has no default: a Core built without `CoreBuilder::connect_policy` answers `NOT_SUPPORTED` to every connect, test and `ssh_open`, whatever features Cargo unified. Desktop, CLI and tests use `Unrestricted`; the web server uses `Checked { check, allow_ssh: false }`, which refuses a target that needs a tunnel as soon as the row or form is read (before any secret read), then runs `check` (`web_config::check_connect_config`) on the finished config right before the driver opens it. The engine lookup comes first, so a refused engine is still `ENGINE_NOT_AVAILABLE`.
  - **`CoreBuilder::executor`** has no default either: Core takes its clock from the `Executor` (`monotonic()` for statement timings, `unix_time()` for history timestamps), and without one `db.run`/`db.page` and every `ai` call answer `NOT_SUPPORTED` (a turn's timeouts and text coalescing run on it too). `src-tauri`, `seaquel-server` and `seaquel-cli` pass `TokioExecutor`, `seaquel-browser` `WasmExecutor`; tests build Core with both a policy and an executor. `Workspace::open` hands the executor to storage, whose write turn waits on its `sleep`.
  - **`Connection::sql_engine`** is the SQL rules a connection is scanned with, recorded at connect from the connection's database type, so a MariaDB connection (driver `mysql`) scans as MariaDB (`/*M! … */` is code). Runs and the read-only checks (`check_read_only`, `check_one_statement`) use it. `Core::connect` (engine tests) maps the driver id.
  - **Ownership.** Each `Workspace` has a random `WorkspaceId`. Connections it opens and streams it starts carry it, and its `query`, `query_stream`, `execute`, `transaction`, `engine` (a `ConnectionHandle` for the dialect and introspection calls; `seaquel_rpc::dispatch_on` runs an `EngineRequest` on it), `cancel` and `disconnect` refuse any other id with `CONNECTION_NOT_FOUND`, the same answer as an unknown id. Stream ids are scoped per workspace. `close_all(core)` cancels its streams and closes its connections and tunnels (web eviction); after it, a connect is `WORKSPACE_CLOSED`. **Windows own connections** (phase 6): each connection records the write origin of the call that opened it, with a Core-wide opening order; one opened with no origin (the CLI, MCP, engine tests) belongs to no window and nothing here touches it. Ownership is per Core, so it never reaches into another process: the TUI has a Core of its own, and its connects carry its origin (`tui-<8 hex>`), so a reconnect there replaces its own older connection as a window's does. A window's successful connect for a saved connection (a saved target, a form with `savedConnectionId`, or `db.bindSaved`) closes that window's connections for the same saved id that opened before it, cancelling their streams (`CONNECTION_CLOSED`) and announcing each as `CONNECTION_REPLACED`; never a newer one or another window's, and a failed connect closes nothing, except for an engine whose connection holds its file exclusively (`Engine::exclusive_file`: DuckDB with a file path, through its helper), where the older connections are closed right before the open, once the engine, the connect policy's check and `Engine::preflight` have passed, since they would block it, so a reconnect whose open itself fails there has closed them. A replaced, evicted or window-closed connection is taken out of Core and announced before its close is awaited, so a caller dropped mid-close has still announced it. Connections a connect will replace don't count against `per_workspace` (netted across connects in flight, each replaced connection discounted once). `close_owned_by(core, origin)` closes one window's connections (`WINDOW_CLOSED`); `alive(core, ids)` (`db.alive {connectionIds}`, at most 1,000) answers which of the ids this workspace still holds. `Workspace::events()` gives each subscriber the workspace's events: `WorkspaceEvent::ConnectionClosed` (`WORKSPACE_EVICTED` from `close_all`, `WINDOW_CLOSED`, `CONNECTION_REPLACED`, and `CONNECTION_CLOSED` for a connection lost unasked: Core watches each connection whose driver has `Driver::closed()` (the remote DuckDB driver; its helper died) on the executor (`lost.rs`), and when it fires takes the connection out (its streams cancelled, its tunnel closed) and announces it once with the driver's message, unless a disconnect, replace or `close_all` took it out first; other drivers don't notice a lost connection, and `TUNNEL_CLOSED` is reserved) and `StorageChanged` (below). Same-user origin spoofing (`X-Seaquel-Origin` is checked for shape only) can only replace or keep that user's own tabs' connections. A workspace cancel for a stream id that isn't registered yet is remembered (256 per workspace, not for ids that already finished), so a cancel that overtakes its start still wins. Core's id-based methods (`Core::query`, `Core::disconnect`, …) reach any connection and stay for the engine tests; interfaces go through the workspace.
  - **`QueryOptions`** for `query_stream`: `read_only` (above), and, only with it, `max_rows` (return that many rows and mark the final `StreamBatch` `truncated` instead of failing with `RESULT_TOO_LARGE`), `max_bytes` (stop, `truncated`, once the kept rows' decoded cells reach it; one cell is never split) and `timeout` (enforced by the database, ending with `TIMEOUT`; a backstop for the caller dropping the stream, which stays the cancel). Any of the three without `read_only` ends the stream with `INVALID_OPTIONS`. Of the three, only `max_rows` crosses the Tauri and WebSocket transports (dashboard widgets and workflow nodes); the assistant's and MCP's tools run in Core with all three (below).
  - **`Workspace::run`/`page`** (`run.rs`; `db.run`/`db.page`, stream only) are the editor's runs on desktop and web. `seaquel_workspace::run::plan` (pure, no I/O, never panics) turns the text, the target (`all`, or `current` with a UTF-16 cursor converted by `seaquel_sql::offsets`, the same function the editor's wasm uses), the `{{param}}` values and the connection's `sql_engine` into statements, each with its SQL after substitution and its binds (`source`), query type and kind. Core runs them in order on one connection under the request's `streamId`, registered like a query stream, so `cancel`, an early cancel, `disconnect` and `close_all` reach a run the same way. Without an executor both answer `NOT_SUPPORTED`.
    - **Kinds.** A SELECT pages: `paginate(sql, pageSize + 1, offset)` through `query_stream`, reading one row past the page and then dropping the stream, so a cancel stops it on the server; `count_query` runs only when the page is full or comes back empty past the first page (a stale page number), and a failed or non-numeric count is estimated (`offset + pageSize + 1` for a full page, `offset` for an empty one) with `countEstimated`, except a count that fails with `CONNECTION_CLOSED` or `CONNECTION_NOT_FOUND` (`connection_lost`; a DuckDB helper that died between the page and its count), which fails the statement (`statementError`), so the interface sees the connection is gone. It streams instead when the page size is 0 or it has its own LIMIT/OFFSET/FETCH/TOP. Insert, update and delete go through `execute`. Anything else (`other`) goes through `query`, unpaged, under its 100,000-row cap: with at least one column it shows its rows as one final batch (`WITH`, `SHOW`, `EXPLAIN`, `PRAGMA`, `VALUES`, DuckDB `FROM …`), with none it is a utility result the GUI hides. DuckDB answers `SET`, `CREATE`, `ATTACH`, … with a lone `Success` or `Count` column; unless the statement starts with a query word (`WITH`, `FROM`, `VALUES`, `TABLE`, `SELECT`, `SHOW`, `DESCRIBE`, `SUMMARIZE`, `EXPLAIN`, `CALL`, `PIVOT`, `UNPIVOT`; not `PRAGMA`), that counts as no columns, so `PRAGMA threads = 2` stays hidden. An empty result carries its column names on every engine.
    - **Events** (`RunEvent`, sent as `CoreEvent::Run`): per statement a `statementStart` (the typed SQL, its `source`, kind, page, and for a SELECT the source `table` and `columnRefs`), its `batch`es and a `statementDone` (`elapsedMs` from the executor, `totalRows`, `totalPages`, `countEstimated`, `rowsAffected`) or `statementError`; with `deferWrites` (pending changes on) every statement that isn't a SELECT comes back as `statementDeferred` and doesn't run; then one `done` (`statements`, `succeeded`, `history`) or `error`. A statement's failure doesn't stop the run; a cancel ends it and drops the statement in flight. Nothing to run is `done` with `statements: 0`. `db.page` re-pages one statement from the `source` the client sends back (Core keeps no run state) and refuses anything but one SELECT, but that isn't a write barrier: `SELECT … INTO`, writing functions and `FOR UPDATE` get through, as with `db.query`. A `{{name}}` with no value binds NULL, as the TS did.
    - **`CONFIRM_REQUIRED`.** A run holding a destructive statement (checked on the text before substitution, deferred statements included, before anything runs) ends with that `error` unless the request has `confirmed`; `destructive` lists the first 100 (`MAX_DESTRUCTIVE_LISTED`) and `destructiveTotal` counts them all. It guards against mistakes, not against an API caller: `db.execute` runs any SQL on the same connection.
    - **History.** Only `db.run` records, and only when the request has a `history` context (the saved connection's id, name and labels), the run wasn't cancelled, at least one statement ran and none failed. Core appends one row with `seaquel_storage::queries::query_history::append`, which also deletes the connection's non-favourite rows past the newest 500 (`HISTORY_KEEP`, `timestamp DESC, rowid DESC`), in one transaction; `done.history` is the row as stored. A failed append (a connection that isn't saved) is logged by code and doesn't fail the run.
    - **Limits.** `RunLimits` (`CoreBuilder::run_limits`, passed into `plan` in `PlanOptions` with the page cap) caps the text (and a page's SQL) and run all's statement count (`INVALID_ARGUMENT`), and the parameter values a run sends, by count and bytes (`INVALID_PARAMETERS`; `db.page` is exempt). Only the web sets it (`WEB_RUN_LIMITS`: 2 MiB, 10,000 statements, 1,000 values, 1 MiB of them); the desktop, the terminal binaries and the demo have none. On every interface, filling in the values may add at most 32 MiB to a run (`check_substitution_budget` over `seaquel_sql::params::SizeBound`, `MAX_RUN_SUBSTITUTED_BYTES`, `INVALID_PARAMETERS`), since a value is copied (SQL Server, DuckDB) or bound (MySQL/MariaDB) once per use; only the growth counts, so a large dump with a few parameters runs. `plan` looks the values up once (`params::Values`, `substitute_with`) and `SizeBound` costs each used one once, so planning is linear in text plus values. `column_refs` returns `None` for a statement over 64 KiB (`MAX_COLUMN_REFS_BYTES`) without parsing it; the grid then isn't editable. A page size past `max_query_rows() - 1`, page 0 and an offset that overflows are `INVALID_ARGUMENT`. "Stream all" (page size 0) has no row cap of its own.
    - **Hand-typed transactions** aren't handled: on Postgres and MySQL/MariaDB each statement takes a pooled connection, so `BEGIN; UPDATE …; COMMIT;` may run on different connections (MySQL refuses `BEGIN` in the prepared protocol, 1295, and the UPDATE autocommits). SQL Server keeps one session.
  - **The edits service** (`edits.rs`; `db.planEdits`, `db.applyChanges` and `db.duckdbExtension`, unary, and `db.tablePage`, stream only) is every write the grid makes and the data tab's query, on desktop and web. Planning is `seaquel_workspace::edits` (pure, never panics).
    - **Intents.** The grid sends `Edit`s: `updateCell`, `setDefault`, `insertRow`, `deleteRow`, and `truncateTable`/`dropObject` from the sidebar; a table (`schema`, `table`), a key as `[column, value]` pairs picked out of the row by the GUI's routing, a column and a value in the cell wire format. The queue sends them back as `Change::Edit`, or `Change::Sql` for a statement the editor deferred or the table editor generated. Core builds each edit with the connection's `Dialect` builders at plan and again at apply time; no casts or default expressions cross the wire.
    - **Metadata, read per call.** For each table a call touches, Core calls `table_metadata` once (deduped within the call; no cache, so DDL run anywhere is seen at once). It gives the Postgres cast map (`cast_map`), SQLite's default expression for Set default (a column without one sets NULL) and the primary key. A table that isn't there or has no primary key, a key whose columns aren't exactly the primary key's (compared as a set; the WHERE keeps the key's order as sent) and an update, Set default or insert column the metadata doesn't list are `NOT_EDITABLE`, so views and keyless tables aren't editable from the grid. A failed metadata read fails the call with its code before anything runs.
    - **JSON columns**: in a column the metadata types `json`/`jsonb` (Postgres) or `JSON` (MySQL, MariaDB, SQLite's declared `JSON`, DuckDB), an `Array`, a number or a `Bool` binds as `Value::Json`; `Text` stays `Text`, because the grid sends typed JSON as a string, so a JSON string cell (`"abc"`) written back is sent as `abc`. MariaDB reports `JSON` as `longtext`; its `table_metadata` reports `json` when a column CHECK named after the column is exactly ``json_valid(`col`)`` (from `information_schema.CHECK_CONSTRAINTS`; a server without it keeps `longtext`).
    - **Applying** (`apply_changes`). One change is `single` (`execute`, keeping `lastInsertId`). Two or more that are all DML are `atomic`: one `Driver::transaction`, keyed edits with `expect_rows: {min: 1}`, and any failure rolls everything back. DML means an edit intent other than truncate and drop (a SQLite truncate is a `DELETE FROM` and counts), or a typed change whose `query_type` is insert, update or delete; `MERGE`, `WITH … UPDATE`, `CALL`, DDL and the rest aren't. Anything else is `inOrder`: `execute` one change at a time, stopping at the first failure. Each typed change must be one statement (split with the connection's `sql_engine`, else `INVALID_ARGUMENT`). Limits, metadata, keys, splitting and the destructive check all pass before the first statement runs; a refusal inside a batch is an `applied` outcome with `applied: 0` and `failed` naming the change, not an error. A keyed edit that matches no row is `NO_ROWS_AFFECTED` (a Postgres rule or SQLite INSTEAD OF trigger that reports 0 for a write it made is a known false positive). An unconfirmed batch holding a statement `destructive_reason` flags is `{outcome: "confirmRequired", destructive, destructiveTotal}`, as a run's `CONFIRM_REQUIRED` is (edits are checked as the SQL Core built; a keyed delete has a WHERE). `ddl: true` when a change that isn't DML ran. With a `history` context each applied change appends a row (its SQL as queued, its bound values in `params`, rows affected, Core's time) through `query_history::append_many`, after the commit for an atomic batch; the outcome carries the rows. Immediate grid edits send no context and record nothing.
    - **Stopping.** The calls are unary. Dropping one drops the driver call, which rolls an atomic apply back; an in-order or single apply keeps what already ran, with no outcome and no history. Each workspace has a `closing` token that `close_all` cancels, and an apply races it, so an eviction mid-apply ends with `failed` `WORKSPACE_CLOSED` (atomic: rolled back unless the commit raced the close; in order: stopped at that change). On web Node aborts the call to Rust when the browser's socket closes (below).
    - **The data tab** (`table_page`): a stream registered like a run, so `cancel`, `disconnect` and `close_all` reach it. The GUI sends a typed `TableQuery` (the target, filters with a `FilterOp` from a closed enum serialised as the UI's text, `=` to `IS NOT NULL`, `AND`/`OR`, sort), a page and a page size (1 to `max_query_rows() - 1`). `seaquel_engine::select::build_table_select` (pure, like `crud.rs`) quotes the names and writes each filter as `CAST(col AS <text type>) <op> <placeholder>` with the engine's CRUD placeholders (`$1`, `?`, `@P1`); `IN`/`NOT IN` split the value on commas, trim each item and bind it (an empty list is refused); range operators compare text. On SQL Server it reads the column types on every page and casts `sql_variant`, `geography`, `geometry` and `hierarchyid` to `NVARCHAR(MAX)` (tiberius can't read them). It then runs as 5b's page kind: the count runs only for a full page or an empty page past the first, and a failed count is estimated, unless the connection is gone (above).
    - **`duckdb_extension`** takes a typed `ExtensionAction` (`list`, `install`, `load`, `update`, `installCommunity`, `installAndLoad`), refuses a non-DuckDB connection and a name outside `^[A-Za-z0-9_]+$` (`INVALID_ARGUMENT`), and runs its statements one call each.
    - **`EditLimits`** (`CoreBuilder::edit_limits`, beside `run_limits`; none by default): only the web sets them (`WEB_EDIT_LIMITS`: 10,000 changes per apply or plan, at most 100 distinct tables per call since each is a metadata read (`max_tables`), 2 MiB of typed SQL, 16 MiB of values; per table page 100 filters and 100 sort columns, 1,000 `IN` items and 64 KiB per filter value). Past one, `INVALID_ARGUMENT` naming the limit, checked in one linear pass before anything is planned, read or run. A NUL in any schema, table, column, key, sort or filter name is refused on every interface. The desktop and the terminal binaries have no limits.
    - **Logs.** `Edit`, `Change`, `TableQuery` and the params types have hand-written `Debug` (table and column names, counts); the service logs activity names, ids, counts, modes and codes, never SQL, keys or values.
  - **The library** (`library.rs`, behind `storage`; the `library` RPC group) is every write to saved connections, projects, custom labels, saved queries and their versions, on desktop and web, and since 5d-2 to dashboards, saved workflows, AI chats and a project's connection order (below). `seaquel_workspace::library` (pure, never panics) holds the drafts and patches, the checks, how a patch applies, the version prune and `LibraryLimits`; the 116 recorded cases in `tests/fixtures/library` pin it (`changes.json` lists the 49 intended differences from the pre-5d TypeScript).
    - **Core assigns ids and times.** Ids keep the old shapes (`conn-`, `project-`, `label-`, `saved-`, `ver-`, each plus a uuid); the default project (`default-seaquel`, made by `projectEnsureDefault`) and the demo's `demo-connection` are fixed. `Workspace::ensure_demo_connection` (`demo.rs`, behind `browser` and `storage`; the module's `ensureDemoConnection`) stores that row once, in `default-seaquel`, else the first project, else a default project it makes, through `connectionCreate`'s rules, and afterwards only sets `lastConnected`, so the visitor's labels, name and AI flags stay. Times come from the `Executor`. Checks run before anything is written: trimmed non-empty names and no NUL anywhere (`INVALID_ARGUMENT`); `type` one of the six engines, and on web one Core was built with (`ENGINE_NOT_AVAILABLE`); a whole port from 0 to 65535; label ids the predefined `local`, `staging`, `prod` or the project's own (`LABEL_NOT_FOUND`); parameters with a known type and unique names; a missing parent or row (`PROJECT_NOT_FOUND`, `CONNECTION_NOT_FOUND`, `SAVED_QUERY_NOT_FOUND`, `LABEL_NOT_FOUND`). A connection can't move to another project, and the last project can't be removed (`LAST_PROJECT`).
    - **Duplicate names** are `NAME_TAKEN`, with `takenBy` the id of the row that has the name (`RpcError.takenBy`; the GUI shows that row's name and never compares names itself). Connections clash within a project, saved queries within a project and folder (no folder and `""` are one), custom labels within a project, projects everywhere. Names compare by `name_key` (`seaquel_types::names`, re-exported by the library module): JavaScript's trim, NFC, full Unicode case folding, NFC again, so `Straße` equals `STRASSE`. Connections, projects and saved queries store it in a `name_key` column (below), so the check is an index lookup, and a row whose key is NULL is folded on the spot; labels live in the project's JSON and compare in memory. A rename to the row's own name in another case isn't a clash, and rows that already share a name can still be patched. **Changing `name_key` changes stored data**: a new version of the function (a Unicode update in `unicase` or `unicode-normalization` counts) needs a data step that recomputes the column. A draft with `renameIfTaken` (the imports) is stored under the first free name instead: the name, else `"<name> (2)"`, `"<name> (3)"`, ….
    - **Patches, not rows.** An update carries only what changes: a field left out is kept and `null` clears a clearable one (`Clearable<T>`, `ts(optional)`), applied to the row read inside the transaction, so two windows changing different fields both land. `labelIds` is one whole value (the last writer's list wins). `connected: true` sets `lastConnected`. Every write strips secrets from the connection string (`strip_connection_string_secrets`, a port of the TypeScript one).
    - **One `WriteTx` per call:** read, check, write and commit, then emit one event. On desktop the keychain is written first, outside any transaction, so a keychain prompt never holds the write lock: a failed create deletes the secrets it set, a failed update puts back the entries it changed, and after the commit the secrets whose save flag is now off are deleted (best effort). Setting a secret whose flag ends up off is `INVALID_ARGUMENT`. Web has no secret store: any `SecretChanges`, a delete included, is `NOT_SUPPORTED`, so the GUI never sends one there.
    - **Removal.** `connectionRemove` deletes the row (history, chats and labels cascade), then its keychain entries, or on web the vault's `user_credentials` rows for it, best effort and logged by code; it doesn't disconnect (the GUI does). `projectRemove` deletes the project's saved queries, dashboards and saved workflows by `project_id` (beta-era files have no foreign key there) and then the project, in one transaction, then its connections' secrets, and returns the removed connection ids. `labelRemove` refuses a predefined id and strips the label from every connection, in any project, in the same transaction.
    - **Versions are keyframes.** A `savedQueryUpdate` that changes the text appends the previous text whole, numbered `MAX(version) + 1` inside the transaction, then prunes to `query_version_limit` (0 keeps all), keeping back to the nearest keyframe, so Rust needs no diff code; it returns the row, the new version and the pruned ids. Unchanged text adds no version. Older diff versions stay readable. A patch of only `starred` leaves `updated_at`.
    - **`LibraryLimits`** (`CoreBuilder::library_limits`; none by default): only the web sets them (`WEB_LIBRARY_LIMITS`: 1 KiB per name, label name, folder and tag; 64 KiB per other field; 2 MiB of query text; 1,000 list items, which covers a connection's labels, parameters, tags and a project's custom labels; 10,000 connections, 1,000 projects and 50,000 saved queries per user; `max_version_bytes`, 16 MiB for one saved query's versions together). Past one, `INVALID_ARGUMENT` naming it, before anything is read. With `max_version_bytes` the prune also keeps only the newest versions that fit (always at least one), then back to a keyframe, so an old diff chain stays until about 8 new saves of a large query push it out. Library calls don't count toward the four-at-once edit cap.
    - **Logs.** Drafts, patches and `SecretChanges` have hand-written `Debug` (ids and which fields are present); the service logs activities, ids, counts and codes, never names, hosts, strings, query text or secrets.
  - **Dashboards, workflows and chats** (`state.rs`, 5d-2; the rules in `seaquel_workspace::state`, pinned with the settings and view state by the 112 cases in `tests/fixtures/state`, whose `changes.json` lists the intended differences from the pre-5d-2 TypeScript). Core makes `dashboard-`, `dver-`, `workflow-` and `theme-` ids plus a uuid, and plain uuids for chats and AI providers. Message ids are the GUI's (`^[A-Za-z0-9_-]{1,64}$`; one another chat owns is refused).
    - **Dashboards:** `dashboardCreate`, `dashboardUpdate` (a patch; widgets, viewport and date filter are whole values) and `dashboardRemove`. Names clash within a project (`NAME_TAKEN`, through `dashboards.name_key`). A draft with `renameIfTaken` takes the first free `"<name> (n)"` (the GUI's "New Dashboard" and the AI's create), and one with `shared: true` is stored shared in the same call and published to its linked project's repo. An update records a version of the previous state only when the patch says `captureVersion` (the GUI sets it on a rename, a widget added, changed or removed, a date filter and a restore, never on a move, resize, pan or zoom), numbered `MAX(version) + 1` inside the transaction, then prunes to `dashboard_version_limit` (0 keeps all); it answers the dashboard, the new version's metadata and the pruned ids. `starred` alone leaves `updated_at`. `dashboardVersionsList {projectId}` answers metadata only (`PersistedDashboardVersionMeta`: number, time, `widgetCount`, snapshot `bytes`) and `dashboardVersionGet {dashboardId, versionId}` one version with its snapshot (`DASHBOARD_VERSION_NOT_FOUND` for a version that dashboard doesn't have). Widgets are stored without run state and Core doesn't parse them.
    - **Workflows:** `workflowCreate`, `workflowUpdate`, `workflowRename` and `workflowRemove`. The stored JSON is today's `SavedWorkflow`, kept byte for byte except the top-level `id`, `projectId`, `createdAt` and `updatedAt`, which Core sets; `workflowRename` changes only `name` and `updatedAt`. `workflowsList {projectId}` answers metadata only (`PersistedWorkflowMeta`: name, times, `bytes`, read from `saved_canvases.meta`) and `workflowGet {workflowId}` the stored JSON; a body that doesn't decode is listed and fails when opened. **Chart nodes are stored without rows**, stripped in the GUI on `saveWorkflow` only (not on a rename): a chart node whose source node in the same workflow holds rows is saved with `rows: []` and filled from the source on load. A workflow saved before 5d-2 keeps its chart copies until its next `saveWorkflow`.
    - **Chats:** `chatCreate`, `chatUpdate` (`title`, `touched` for `updatedAt`), `chatRemove`, `chatMessagesPut` (upserts the listed messages and deletes none; a message without `parts` keeps the stored ones, as an older release's put does) and `chatMessagesRemove`. A turn's own rows are written by Core (`ai`, below), not with these calls. Messages read in `timestamp, rowid` order. `chatMessagesList` answers the messages, the chat's `storedBytes` and `full` (`chat_is_full`: the next message can't fit under `max_chat_bytes` or `max_messages_per_chat`; never on the desktop), so a full chat opens with sending off.
  - **Settings and window view state** (`state.rs`; the `settings` and `ui` RPC groups, 5d-2).
    - **Settings** are a closed set of app-state keys, each value checked by `settingSet` (`null` deletes the row): `editorKeybindingMode`, `pending_changes_enabled`, `skippedUpdateVersion`, `query_version_limit` and `dashboard_version_limit` (0 to 100,000; 0 keeps all), `license_nudge` (a JSON object, whole), `lastActiveProjectId` (read only; `windowActivate` writes it) and `connectionStringSecretsNotice` (only cleared). Any other key, Core's own keys and `activeRepoId` are `INVALID_ARGUMENT` naming the key. AI settings are targeted calls (`aiSettingsGet`/`Patch`, `aiProviderCreate`/`Update`/`Remove`) on the one `aiSettings` record, rewritten from the stored copy inside the transaction with unknown fields kept byte for byte, so the MCP server's reader doesn't change; the read does the old legacy cleanup and reads a malformed record as the defaults. **API keys:** on desktop `apiKey` (`Clearable`) rides the call, and Core writes `ai-api-key:<id>` before the record (taking it back if the write fails) and deletes it after a remove; on web `apiKey` is `NOT_SUPPORTED`, the vault keeps the key in the browser, and `aiProviderRemove` deletes the provider's `user_credentials` rows. `aiSettingsGet` reads no secret; `aiProviderHasKey {id}` (`Seqd<bool>`, a read) says whether one provider's keychain entry exists, so the settings form can show "key saved" without the key reaching the page (`NOT_SUPPORTED` with no store: web asks its vault, the demo its session keys; `AI_PROVIDER_NOT_FOUND` for an unknown id). Themes (`themesGet`, `themePreferencesSet`, `userThemeCreate`/`Update`/`Remove`; removing a theme in use resets that preference), onboarding (`onboardingPatch` merges top-level fields), tutorial progress and import state have their own calls.
    - **View state is per window** (`windowGet`, `windowActivate`, `windowStateLoad`, `windowStateSave`). A window's open tabs with their text, pane layout, active ids and active connection for one project are one JSON blob in `window_state` (`window_id`, `project_id`), stored byte for byte; its active project is in `windows`. The window id must equal the call's origin (else `INVALID_ARGUMENT`), so one tab can't write another's view. A window with no row for a project copies the most recently used window's row, else the legacy `project_state` and `tabs` rows, else nothing, and stores the copy as its own at once; `windowGet` answers the window's active project, else the most recently used window's, else `lastActiveProjectId`. "Most recently used" is the last write committed (`write_seq`, one past the highest, taken inside the write), not the clock. Every save also writes the legacy `project_state` and `tabs` rows (the mirror: a repeated tab id skipped, the stored connection order kept, `canvas` written as `workflow`), so an older release shows the latest window's tabs. **`rev`**: each save carries the page's counter (at most 2^53 − 1, `MAX_REV`), and one whose `rev` isn't above the stored one writes nothing, not even the mirror, and answers `{stale: true, rev}` with the stored `rev`. Each save prunes in bounded deletes: windows unused for 30 days, past `max_windows` (web 50, desktop 20) and past 20 states per project, never the saving window or, on desktop, `main`. The connection order stays shared per project (`projectSidebarGet`/`Set` in `library`).
    - **`StateLimits`** (`CoreBuilder::state_limits`; the desktop and the terminal binaries have only the window counts). `WEB_STATE_LIMITS`: 8 MiB per view state, 2 MiB per tab's text, 500 tabs; 16 MiB per workflow after chart copies are dropped (`max_workflow_bytes`), 1,000 workflows; 4 MiB per dashboard, 1,000 dashboards, 16 MiB of versions per dashboard; 1 MiB per message, 5,000 messages and 64 MiB of content per chat (`max_chat_bytes`), 10,000 chats; 256 KiB per setting value, AI settings record or user theme, 200 user themes, 50 AI providers. Past one, `INVALID_ARGUMENT` naming it; a view state, workflow or dashboard already past a limit stays saveable as long as it doesn't grow.
    - **Logs.** Every draft, patch and params type has a hand-written `Debug`; no tab text, widget JSON, message content, theme JSON, setting value or API key is logged.
  - **`LocalFiles`** (`CoreBuilder::local_files(LocalFiles::Allowed)`; no default, like `ConnectPolicy`) lets Core read and write the user's own files: git repos and other tools' config files. Without it every `shared` and `imports` call is `NOT_SUPPORTED` and no library call publishes, whatever features Cargo unified, and `dispatch_workspace` checks it again before either group. The desktop (`desktop_core`) and the CLI (`core_builder`) pass it with `ImportPaths::from_env()`; the web server doesn't.
  - **Shared projects** (`shared.rs`, behind `git` and `storage`; the `shared` RPC group; desktop only, phase 5e). A project linked to a git repo is projected into `<repo>/.seaquel/projects/<dir>/`: `project.yaml`, `connections/*.yaml` (templates, no credentials), `queries/**/*.sql` (YAML frontmatter, then the text) and `dashboards/**/*.json`; `labels.yaml` and a template's `labels` are read and not applied. `seaquel_workspace::shared` (pure, never panics) decides everything: the formats, file names, hashes, pairing and the sync and publish plans. `seaquel-git`'s `tree` does the file I/O, and Core orders the two. Pinned by `tests/fixtures/shared` (153 format cases and 52 projection cases with 225 steps, recorded from the pre-5e TypeScript; `changes.json` lists the intended differences), replayed by `seaquel-workspace/tests/shared_plan` and, over real repos, `seaquel-core/tests/shared`.
    - **Links are stored** (`0004`, `0005`): a project's directory in `projects.shared_dir`, so renaming the local project never moves it (`project.yaml`'s name follows); a saved query's or dashboard's file in `shared_path`; on all three kinds `shared_base` (the hash of the content both sides had at the last sync) and `shared_file_id` (the `id:` line or `"id"` key Core writes into each file and keeps across renames). A connection's template path stays in `shared_connection_id` (`<repoId>:<path>`, where older releases look), and `shared_origin` says whether the project shared it (`exported`) or a sync made it from a teammate's template (`imported`; a link with no origin counts as imported). NULL means the old rule: the slug of the name, no base. Core takes the repo from the row's project (`git_repo_path`), never from `activeRepoId`, and writes nothing for an unlinked project or a row that isn't shared.
    - **Sync** (`sync {projectId}`, `syncRepo {repoId}`). Each file pairs with at most one row: by file id, then stored path, then `name_key` (within the folder for queries), then slug path. Then the three-way rule, with the row's hash `R`, the file's `F` and the base `B`. Hashes are SHA-256 of the file Core would write (`write(parse(text))`), so formatting and line endings don't count, and a dashboard's viewport is left out (a pan or zoom alone neither writes nor changes anything). `R ≠ B, F = B` writes the file; `R = B, F ≠ B` updates the row (a query keeps its previous text as a version, a dashboard captures one); both changed, or no base and `R ≠ F`, the file wins and the row's previous content becomes a version, named in the notice. Templates sync host, port, database, SSL mode and SSH host and port; the user name, secrets, labels, AI settings and local-only flag never cross. A template changed on both sides wins, and the notice lists the values it replaced, never a user name or a secret; its `name:` renames the connection; a changed `type:` unlinks the connection, makes it local-only and imports the template as a new connection. A shared row whose file is gone is unshared and named (`removedInRepo`), unless it has a path and no base (its first write failed): then the sync writes it. A new file becomes a shared row under its exact name; a name another row holds skips it (`nameTaken`), and an update whose new name is taken applies the rest and keeps the row's name until the name is free. A teammate's rename and a local content change merge. A file that can't be read, doesn't parse, fails the library's checks (`invalid`) or is skipped by the bounds is never read as missing: nothing changes on either side, and its row stays out of pairing. A conflicted repo isn't synced (`conflicted: true`, nothing written). `SyncNotice` (`conflict`, `removedInRepo`, `nameTaken`, `unpaired`, `skipped`, `templateTypeChanged`) names a file once per session (`NoticeMemory`, per workspace), except that a project skipped whole (`skippedProjects`) is said on every sync. `syncRepo` goes on past a failing project (`failures`).
    - **Order.** Every call takes the repo lock first (`Core::repo_lock`: one async mutex per canonical repo path, `repo_path_key`), then the storage write lock, and never touches a file inside a `WriteTx`. A sync scans, plans outside the write lock, then writes the plan in a short `WriteTx` after checking a `PlanStamp` (every link column and every row the plan touches; a new row column must be added to it). A changed stamp plans again, and after two tries (`OPTIMISTIC_PLANS`) it plans inside the transaction. Then it writes the files, each on its own (a sync never deletes or renames one), and stores the links whose write succeeded. One event per kind and scope, the rows' right after their commit, with the caller's origin; none for a sync that changed nothing. A large project's sync holds the repo lock, so a publish to that repo waits for it.
    - **Publish from library calls**. `savedQueryCreate`/`Update`/`Remove`, `dashboardCreate`/`Update`/`Remove`, `connectionUpdate`/`Remove`, `projectUpdate` (a linked project's `project.yaml`) and the `shared`/`isLocalOnly` patches write the row's file after their commit: under the repo lock, read the row again, plan, write (a rename writes the new path, then deletes the old one unless it's the same ignoring case), store the base. The answer's `Seqd` carries `projection: {status: "written" | "deleted" | "failed", code?, message?}`. A failed write keeps the row and its path with no base, so the next sync writes it. Every write checks the file on disk against `expect_hash`: if a teammate changed it, nothing is written, the project syncs under the same lock and the answer is `FILE_CHANGED`. Unsharing or removing a shared row deletes its file first, keeping the bytes, and puts it back if the row write fails; a file that can't be deleted refuses the call with `FILE_ERROR` before the row changes. Only explicitly shared connections reach the repo: one with a link, made by the link dialog's ticks or the local-only switch. A connection with `is_local_only` 0 that was never shared (every row from before the local-only default) stays local.
    - **Link, unlink, import.** `linkProject {projectId, path, share}` registers the repo by path, picks the directory (one whose `project.yaml` names the project, else a free one), writes `project.yaml` if missing, shares the connections `share` ticks (clearing their local-only flag), stores `shared_dir` and syncs. A ticked connection first adopts a template under `connections/` that no connection claims (by its kept file id, else by `name_key` and type when exactly one matches), writing nothing; the template's base is taken only when its content equals the connection's, so a teammate's edit wins. A project linked elsewhere is `PROJECT_ALREADY_LINKED`; the same path again only shares and syncs. `unlinkProject {projectId, removeImported}` unlinks the project's linked connections and makes them local-only, with their secrets and their template's file id kept; the `imported` ones are removed with their secrets only when `removeImported`. It answers `removedConnectionIds`, `keptConnectionIds` and `repoRemoved`, and forgets the repo when no project uses it. `unlinkPreview` lists what that would remove, by the same rule (`unlink_class`). `scan {path}` reads a repo's projects for the import dialog (counts, templates, `linkedProjectIds`, `skippedDirs`), without the lock. `importProjects {path, dirs}` makes one project per directory (`renameIfTaken`) with `shared_dir` set, imports that directory's templates and syncs it; a directory that fails is undone whole, and one a project here already links fails with `PROJECT_ALREADY_LINKED` (`ImportedProjects {projectIds, failures}`).
    - **The repo list** (`reposList`, `repoRegister {path, name?, remoteUrl?}` by path, `repoUpdate {id, patch}` of `name`, `remoteUrl` and `branch`, `repoRemove {id}`, which is `REPO_IN_USE` while a project links to the repo) is the stored JSON rows, patched field by field with the rest kept byte for byte, so older releases read them. Paths compare in canonical form. `lastSyncAt` is Core's: a successful `git.pull` or `git.push` sets it, best effort. `activeRepoId` and `syncStatus` are never written.
    - **Files** (`seaquel-git::tree`). Everything stays under `<repo>/.seaquel/`. A path must be relative and `/`-separated, with no `..`, `.`, empty or hidden component, backslash, NUL or control character, Windows reserved name or trailing dot or space, and at most 1,024 bytes. No symlinks: every component is checked with `symlink_metadata` and files open with `O_NOFOLLOW | O_NONBLOCK`; a symlink is skipped on read and refused on write. `ScanBounds`: past 20,000 files (80,000 entries) or 256 MiB in a project directory nothing is read and the project is skipped whole; a file past 16 MiB is skipped alone. Only `.sql`, `.json`, `.yaml` and `.yml` are read, and a file that isn't UTF-8 is skipped and named. Writes go to a `.seaquel-tmp` file in the same directory and are renamed over the target, keeping the mode, and the folder is fsynced; a sync's scan removes temp files a crash left.
    - **Names and formats**. A new file's stem is the name in lower case after NFC, keeping letters, marks and digits of any script, other runs as `-`, `untitled` when empty, a Windows device name with `-file`, cut to 250 bytes; a stem taken in that directory (compared case-insensitively, after NFC) gets `-2`, `-3`. Existing files keep their paths; only renaming the row moves its file. Files are read with `\r\n` and a BOM and written with `\n`. A value that needs quotes and holds `"` or `\` but no `'` or newline is single-quoted; any other is double-quoted, with `\"`, `\n`, and `\\` only where Core's reader would misread it. **Quoting is per file:** a query or template carrying Core's `id:` line undoes those escapes; one without (2026.9.2's, or hand-written) reads double-quoted values literally, as 2026.9.2 does; `project.yaml` and `labels.yaml` always use the escape rule. A tag holding `,` is quoted in its inline list, and a description's newline is written `\n`. A value with both `'` and `"`, or `'` and `\`, and a tag with `,` don't survive a 2026.9.2 teammate's rewrite.
    - **Git under the lock.** `git.pull`, `push`, `commit` and `resolveConflict` run through `Workspace::shared_git_*`, or take the repo lock themselves when storage can't open, so a checkout never races a file write. The GUI calls `syncRepo` after a pull, a commit or a resolution.
    - **Logs** carry repo and project ids, kinds, counts and codes, never a path, a name, a host or a file's content; every params and plan type has a hand-written `Debug`. Codes: `REPO_NOT_FOUND`, `PROJECT_NOT_LINKED`, `PROJECT_ALREADY_LINKED`, `REPO_IN_USE`, `REPO_CONFLICTED`, `FILE_ERROR` (with a path relative to `.seaquel/`, in the message only) and `FILE_CHANGED`.
  - **Imports** (`imports.rs`, behind `imports`; the `imports` RPC group; desktop only, phase 5e). `candidates {source, projectId, path?}` reads TablePlus's `Connections.plist` (macOS only) or DBeaver's `workspace6/General/.dbeaver/data-sources.json` under `ImportPaths`' home, or the given file: at most 16 MiB (`MAX_IMPORT_FILE_BYTES`), on a blocking thread, and a plist past 64 levels or 2,000,000 events is unreadable before anything is built. Without `ImportPaths` the default locations are `found: false`, so tests never read the real home. It answers `{found: false}`, `{found: true, unreadable}` (Core's own message, never the I/O error's, which can name the path) or the candidates. `seaquel_workspace::imports` (pure) maps entries as the old TypeScript did, JavaScript's coercions included. Each candidate has a `key` (TablePlus: `id:<ID>`, or `pos:<n>` for an entry with no `ID` or a repeated one; DBeaver: the connection's key), `duplicateOf` (the project's connection with the same type, host, port, database and user) and a `problem` when it can't be imported (`noId`, `duplicateId`, `invalidPort`, `invalidSshPort`, `noName`); unsupported drivers are left out. `create {source, projectId, keys, path?}` reads the file again, refuses the whole call when a key's candidate has a problem, and imports the rest in one `WriteTx`: the duplicate check inside it (against the project and the call's earlier imports), `connectionCreate`'s rules with `renameIfTaken` and local-only, and the order append.   - **`StorageChanged`** (`changes.rs`): after every stored write commits, the workspace emits one `WorkspaceEvent::StorageChanged(StorageChange { kind, scope, ids, origin, seq })`, never a value. That covers library, settings, `ui`, `shared` and `imports` calls, a sync's row writes, the storage group's writes (`storage_change` in `seaquel-rpc`'s `workspace.rs` maps each write method, `ids` holding its key where it has one) and history appends from runs and applies. A refused or failed call emits nothing. Kinds: `connection`, `project`, `label`, `savedQuery` (its versions included), `history` and `storage`, and since 5d-2 `projectState` (scope the project, ids the window), `workflow`, `dashboard` (its versions included), `chat`, `chatMessages` (scope the chat), `setting` (ids the key), `aiSettings`, `theme`, `onboarding`, `tutorial` and `importState`, and since 5e `sharedRepo` (ids the repo: a repo list write, or files a sync or publish wrote, so each window refreshes that repo's status). `ids: None` means reload the kind in the scope; past 100 ids, an id over 1 KiB or 16 KiB of ids (`MAX_EVENT_IDS`, `MAX_EVENT_ID_BYTES`, `MAX_EVENT_IDS_BYTES`) the event says that instead, and a scope over 1 KiB widens it to `scope: None`. `origin` is the writer's window or tab (`WriteOrigin`: 1–64 of `[A-Za-z0-9_-]`, anything else dropped; `None` for Core's own writes; never logged, and its `Debug` hides it). **The change sequence** is `ChangeSeq { epoch, n }`, the epoch being the workspace's random id: a write takes its `n` while it holds the write lock, and the published `n` is the highest below which every taken number has completed, so a read that records it before its SELECTs sees every write up to it. Every write result and every `*List` result is a `Seqd { value, seq }`. The MCP server neither writes nor subscribes; the TUI writes with its origin and listens. **`external`** (phase 7a): a workspace opened `with_external_changes(interval)` polls `Storage::external_version` on the executor (native only; the desktop and the TUI at 1 s, web, the demo and the MCP server never) and emits one `StorageChanged { kind: External, scope: None, ids: None, origin: None }` per poll that saw another connection's commit, after taking and completing a sequence number (`record_storage_write`), since the GUI applies a refetched row only when its `seq.n` is higher. The first poll, right after the open's own work, is the baseline; a poll that finds the write turn taken (`None`) tries again next tick; failures are logged once per run of them, by code. The poll holds a `Weak<Workspace>` and ends with `close`/`close_all` or the last reference. `StoredKind::External` (`"external"`) is in `seaquel-workspace` and the generated TS; what the GUI does with it is under "Other windows' and tabs' changes" below. **A second process** (`WorkspaceSpec::second_process()`, the TUI) opens with `RequireCurrent` (applied at open, whatever `with_storage_options` set) and skips the open's maintenance writes: the string-secrets upgrade (whose keychain items the app's binary wouldn't own on macOS) and both refills. A row whose string still holds a pre-5a secret connects with it, as on the MCP server.
  - **The string-secrets upgrade** (`upgrade.rs`) runs once, when a writable workspace opens (a read-only or second-process one never runs it), because rows saved before phase 5a can hold a secret in `connection_string`. On desktop the password the driver reads moves to `db:<id>` and a TablePlus `+ssh` URL's SSH password to `ssh:<id>`, outside any transaction; an entry that's already there and different is kept, never overwritten. Then one `WriteTx` per row reads the string again (skipping a row another window saved meanwhile) and writes the stripped string and the save flags. A row that lost something it couldn't move (`unmovable`: a key=value password, DuckDB credentials, …, or a kept entry) is listed in the `app_state` key `connectionStringSecretsNotice`, which the GUI shows once and clears. On web every such row is stripped and listed. A failed keychain write leaves the row for the next open; `connectionStringSecretsUpgraded` is set once a pass leaves nothing to retry. Row updates run with `secure_delete`, and a pass that stripped anything then runs `VACUUM` (at most `MAX_VACUUM_ATTEMPTS`, 3, across opens) and `wal_checkpoint(TRUNCATE)`, each retried on the next open until it succeeds; both hold the write lock. On desktop this runs while the storage gate waits at startup, so any keychain prompt it causes shows then. Each row changed emits a `connection` event with no origin; on web nobody hears those, since the server subscribes after the open and every list is read after it. Nothing of a string or a secret is logged. After it, `refill_name_keys` fills `name_key` on rows an older release wrote (one `EXISTS` read when there are none).
  - **`Core::explain_read_only(connection_id, sql, params, timeout)`** is the MCP server's EXPLAIN: the read-only token check, then exactly one statement (split on `;`; SQL Server counts statements from the ShowPlan XML), then `Driver::explain_read_only`. Refusals are `READ_ONLY`. The editor's `explain` is unchanged and isn't safe for model-written SQL: planning runs user code on Postgres and MariaDB, and SQLite and DuckDB run every statement.
  - **The assistant** (`ai.rs`, `ai/{turn,tools,keys,chats,waiters}.rs`, behind `ai`; the `ai` RPC group; phase 6) runs on desktop, web and the demo. Nothing the assistant decides is decided in TypeScript: what the model is sent, which tools it may call, how a result is cut and what is stored. The rules (wire, registry, prompt, limits) are `seaquel-ai`'s, pinned by the 257 recorded cases in `crates/seaquel-ai/tests/fixtures/ts-baseline` (recorded from the pre-phase-6 TypeScript; `changes.json` lists every intended difference) and replayed by `seaquel-ai/tests/ts_baseline.rs`, `seaquel-core/tests/ai_replay.rs` and the page's `ai/page-replay.svelte.test.ts`.
    - **Policies with no default**, like `ConnectPolicy`: `CoreBuilder::ai_http` (an `HttpClient`: `ai::native::NativeHttp` natively, the page's fetch bridge in the demo) and `ai_egress` (`AiEgress::Off`, `Public` or `Any`). Without either, every `ai` call is `NOT_SUPPORTED`; `Off` is `AI_EGRESS_BLOCKED`. Desktop, the module and tests pass `Any`; the server reads `SEAQUEL_AI_EGRESS` (`public` when unset or empty, `any`, `off`; any other value stops it at startup without echoing it). `Public` (`seaquel-http`'s guard): `https:` only; the URL's host may not be an IP literal in a loopback, private, link-local, unique-local, CGNAT, multicast, unspecified, SIIT, Teredo/ORCHID or documentation range (IPv4-mapped included); the resolver drops such answers and fails when none are left; behind a proxy (`HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY`) the target is still resolved here first, a name whose answers are all local is refused, a name that doesn't resolve here goes to the proxy (the operator's proxy decides), the proxy's own host is trusted as configured and a target naming it is refused. No mode follows a redirect (a 3xx is `PROVIDER_ERROR`). Timeouts: 10 s to connect, 120 s with no byte (`IDLE_TIMEOUT`, the head included), 600 s per round or unary call (`ROUND_TIMEOUT`); past one, `TIMEOUT`.
    - **A turn** (`Workspace::ai_chat(core, ChatParams, origin)`, the stream `ai.chat {streamId, chatId, connectionId, userMessage {id, content}, assistantMessageId, approval: "ask" | "allowAll", clientTools, apiKey?, providerId?}`): the message ids are the page's. Checks, in order, each one `error` event with nothing stored and no request: policies, `WORKSPACE_CLOSED`, turns in flight (`max_turns_in_flight`, `TOO_MANY_REQUESTS`), `MESSAGE_TOO_LONG` (past `max_message_bytes`), the ids, one turn per chat (`TURN_IN_PROGRESS`), `CHAT_NOT_FOUND`, the chat's saved connection, `NO_PROVIDER` ("No AI provider is configured." / "The chat's AI provider no longer exists."), a supplied key's `providerId` (missing: `INVALID_ARGUMENT`; another provider: `AI_PROVIDER_CHANGED`), `AI_DISABLED` (`aiSettings.enabled` false), `http:` under `Public`, the key (`NO_API_KEY`; Anthropic only, an OpenAI-compatible provider may be keyless), `NO_MODEL`, `CHAT_FULL` (the chat can't take the message plus a reply), then the open connection (`CONNECTION_NOT_FOUND`) and `CONNECTION_MISMATCH` (its recorded saved id isn't the chat's). A turned-off assistant reads no key. Then Core stores the user's message, runs rounds and stores the reply.
    - **Events** (`AiEvent`, sent as `CoreEvent::Ai {streamId, event}`): `started {providerKind, model}`; `text {delta}`, coalesced to one per 50 ms or 4 KiB and flushed before any other event; `toolCall {callId, name, sql?}` and `toolDone {callId, ok, rows?, truncated?, code?}`; `approvalRequired {callId, sql}` and `clientTool {callId, name, input}`; then one `done {messages, seq, stop}` (`stop`: `end`, `maxTokens` or `tooLong`) or `error {code, message, messages?, seq?}`. Nothing follows a cancel.
    - **The tools** (`ai::tools::call(core, ws, &ToolContext, &Call)`, either profile). The assistant gets `run_query`, `explain_query`, `list_schemas`, `list_tables`, `describe_table`, `list_saved_queries` and `run_saved_query`, bound to the chat's connection (no `connection` argument; `run_query {sql, max_rows?}`), plus the five dashboard tools when the request says `clientTools`. Each answers what MCP's answers (same JSON, codes and messages) under a 256 KB budget where MCP has 4 MB: rows that fit, a plan cut at 256 KB, listings with a note naming what's left out. Queries go through `query_stream` with `read_only`, `max_rows` (100 by default, at most 1,000), 8 MiB `max_bytes` and a 60 s statement timeout; EXPLAIN through `explain_read_only`; no new SQL path. Sharing (`seaquel_ai::sharing`, MCP's rule, schema on and data off by default) is read at the turn's start and again before each call, so a call whose sharing went off gets `DATA_SHARING_OFF`/`SCHEMA_SHARING_OFF` before its arguments are parsed. Arguments are parsed strictly (unknown or ill-typed fields are an `INVALID_ARGUMENT` result with serde's path). Every call in a round runs, in order, and a refusal or failure goes back as an error result (`is_error` on Anthropic, an `Error: ` prefix on OpenAI-compatible). At most 20 tool calls per turn: the 21st ends it with `TOOL_LIMIT`.
    - **Approvals and client tools.** `run_query`, `explain_query` and `run_saved_query` wait for `ai.respond {streamId, callId, decision}` (`allow`, `deny`, `allowAll` for the rest of the turn), after sharing, arguments, `max_rows` and the read-only check pass (a saved query is checked after substitution), unless the turn started with `approval: "allowAll"`. A denial is `DENIED: User denied query execution`. A dashboard tool's widget query gets the read-only check, then the page answers `{result, isError}`; without schema sharing Core strips each widget's `query` from `get_dashboard`'s answer. `respond` for another workspace's turn, an unknown call or a finished turn is `NOT_FOUND` (404); a second answer is ignored; one of the wrong kind is `INVALID_ARGUMENT` and the turn keeps waiting. Waiting is bounded only by Stop.
    - **Keys.** Desktop: Core reads `ai-api-key:<providerId>` from the keychain itself; the `secret` group refuses `ai-api-key:*` (below), so no key reaches the page. Web and the demo: `apiKey` with its `providerId` rides each call as a `SuppliedSecret` (redacted `Debug`, never serialized back). A key never reaches a log, an event, a stored row or an error: a provider's message has every copy of the key replaced by `<redacted>` before its 1 KiB cut.
    - **What is stored**: two writes per turn, each with its `chatMessages` event (the caller's origin): the user's message before round 1, the reply at the end, on an error, or on Stop with what streamed; the reply's write also emits a `chat` event. Core's own refusals store nothing. A reply's `parts` (migration `0007`) is the ordered list `{round, type: "text", text}` / `{round, type: "tool", callId, name, input, ok, result, resultBytes?}`, each result cut at 16 KiB, stored only when a call got a result. A reply is cut at the lower of the chat's message limit and `AiLimits::max_reply_bytes` (1 MiB), ends `done {stop: "tooLong"}` and is stored ending with `REPLY_CUT_NOTE`; a reply refused for size with `parts` is written again without them. The error notice itself isn't stored, only what streamed.
    - **Prompt and history.** The system prompt names the engine, then the schema context when the connection shares its schema (built from `schema_tables` at the turn's start: schema-qualified table names only, no columns, since every engine's `schema_tables` returns none; cut at 128 KB of whole tables with a line pointing at `list_tables`/`describe_table`), then the tool guidance. History is read from storage, newest first, within 512 KiB, whole rounds only, with `parts` rendered back into tool calls and results; an empty stored reply is left out. `@mentions` are resolved by Core (at most 100 per message), and to the bare name without schema sharing.
    - **Stopping.** `Workspace::cancel(stream_id)` and `close_all` stop a turn: the provider's response, a query in flight and every waiter are dropped and the reply is stored with what streamed. **A transport stops a turn with `cancel` and keeps polling it to its end**; dropping the stream drops the reply's write. A turn's stream id is registered with no connection, so `disconnect` or a reconnect fails its next tool call (`CONNECTION_NOT_FOUND`, which the model sees) without ending it; `register_stream` refuses a key a turn holds, and a turn a taken key (`INVALID_ARGUMENT`).
    - **Unary calls.** `ai.generate {connectionId (saved), request, existingQuery, apiKey?, providerId?}` (the inline prompt) answers `{sql}`, the reply's first fenced block, through the same checks; a request holding `@` has its mentions resolved as a turn's when the connection shares its schema, else it goes as typed (for the TUI's Ask AI); `ai.models {providerId, apiKey?}` the model ids; `ai.test` `null` (any 2xx passes). `AiLimits` (`CoreBuilder::ai_limits`; `AiLimits::DEFAULT` has only the reply cap): the web's `WEB_AI_LIMITS` is 4 turns in flight per workspace and 1 MiB per message.
    - **Logs**: activity, ids, provider kind, model id, status, codes, round and tool-call counts, durations and token counts from `usage`; never a prompt, message, schema, SQL, tool input or result, provider message, URL path or key. `ChatParams`, `GenerateParams`, `SuppliedSecret`, `AiEvent` and `HttpRequest` have hand-written `Debug`. Tests never reach a provider: `seaquel-ai`'s `testing` feature has `MockProvider` and `LoopbackOnly`, which panics on any host but loopback, and the fake key `test-key-not-real`.
  - **`ConnectionLimits`** (`CoreBuilder::connection_limits`; default none): `per_workspace` caps a workspace's open connections, counting connects and tests in flight under one lock, so concurrent calls can't pass it (`TOO_MANY_CONNECTIONS`, 429 on web, before anything is read or opened); `max_pool_size` reaches the engine as `OpenOptions` through `Engine::open_with` (Postgres and MySQL size their sqlx pool with it; SQL Server's read-only slots become `max_pool_size - 1`). Policy only, never on the wire. The web server's `WEB_CONNECTION_LIMITS` is 16 per user and pools of 6 (with 6 statements streaming on one connection, its next call, introspection included, waits for a pooled connection); desktop, CLI and MCP keep the engines' defaults.
  - **Features aren't a security boundary.** Cargo unifies features across a build, so `cargo test --workspace` compiles every engine and every infrastructure crate into `seaquel-server` too. Anything the web build must not do is refused in code as well: `with_plugins(|id| …)` registers only the engines it allows, `dispatch_workspace` refuses SSH, git and license calls, and it refuses `shared` and `imports` on a Core without `LocalFiles`. Under `AiEgress::Public` the model client makes every proxy decision itself (`proxy_plan` and `ClientOptions::env_proxies_only` in `seaquel-http/src/client.rs`: the given proxy, else the environment's with `NO_PROXY`, else none) and turns reqwest's automatic proxies off, so `system-proxy` unified into a server build (the OS proxy, which the egress guard can't see) never takes effect. Under `Any` (desktop) reqwest's automatic proxies, the OS's included, stay.
  - **The DuckDB helper** (`duckdb_helper.rs`). `CoreBuilder::duckdb_helper(DuckdbHelper { dir, version })` (`DuckdbHelper` is `seaquel_engine_duckdb::HelperLocator`) registers the remote engine under `duckdb` and panics if `duckdb` is already registered (no compiled engine registers it since the native driver went; builders still start from `with_plugins(|id| id != "duckdb")`). `dir` is the install's `bin/duckdb` folder and the helper is `<dir>/<version>/seaquel-duckdb[.exe]` (`path()`, `file_name()`, and `check()`, the start's permission check with nothing spawned). `Core::duckdb_helper_status()` (no HTTP, no hashing) answers `Installed { path }`, `Unsafe` (the file is there but the check refuses it), `Outdated` (only another version's folder has one) or `Missing`. Behind `duckdb-helper-install`: `duckdb_helper_asset()` (name and compressed size, one metadata request), `duckdb_helper_install(&mut progress)` (`DuckdbHelperProgress { bytes, total }`, compressed bytes, about every 64 KiB) and `duckdb_helper_install_from_file(file, sha256: Option<&str>)`, each answering `DuckdbHelperInstalled { path, downloaded, pruned }`, and `NOT_SUPPORTED` without a locator or on a platform with no published triple. **The pin** (`CoreBuilder::duckdb_helper_pinned(size, sha256)`, the desktop's release builds; `DuckdbHelperPin`, `Core::duckdb_helper_pin()`; a size outside 1..=64 MiB or a digest that isn't 64 hex digits panics, since the build script refuses them first): `duckdb_helper_asset` answers from it with no request, the install builds the `Asset` from it and fetches only the download URL (never `api.github.com`, so no API rate limit), and `install_from_file(None)` checks against it, first refusing a file whose length isn't the pinned size or that doesn't start with gzip's magic with `WRONG_FILE` ("This isn't seaquel-duckdb-<triple>.gz from the v<version> release. Pick that file from the release page.", no path); a given hash wins over the pin, and `None` with no pin is `INVALID_ARGUMENT`. Under the pin an intact install is kept only when its `.installed` record names the pinned digest (or none). The pin governs what is downloaded or copied, not what runs: a helper a terminal binary installed from the release metadata is started like any other, after the start's check. A copied file goes through `open_regular` (`seaquel-http`), so a FIFO, device or folder is refused at once (`INVALID_ARGUMENT`, or `WRONG_FILE` under the pin). `CoreBuilder::duckdb_helper_slow_file_reads` (debug builds or `duckdb-helper-testing`, like `duckdb_helper_releases`) paces a copied file's reads for the CLI's SIGINT test. The install target is `<dir>/../..` (the `<identifier>` folder) with `bin`, `duckdb`, `<version>` below it, so the install and the check can't disagree, and Core runs `check()` after installing. One install at a time per Core. An install whose file matches its `.installed` record and passes the check fetches nothing (`downloaded: false`, offline too) after making the folders private again; a changed file or a missing record downloads again, so a broken file can't loop between `ENGINE_NOT_INSTALLED` and a no-op install. The hashing, the folder work and the `--from` copy run on tokio's blocking pool, and dropping a `--from` install sets its cancel flag (`CancelOnDrop`). Each successful install prunes version folders past the two newest (dot-separated numbers compared as numbers), ranking the running version among them and never removing it; other names and symlinks stay. `CoreBuilder::duckdb_helper_releases(DuckdbHelperReleases)` downloads from elsewhere and exists only in debug builds or with `duckdb-helper-testing` (Core's dev-dependency turns it on), so a release build fetches only from GitHub. Logs: `activity=duckdb.helper` `event=install|prune` with `downloaded`, `bytes`, `pruned` or a code, never a path, URL or message. A connect to DuckDB with no usable helper fails at once with `ENGINE_NOT_INSTALLED`, before anything spawns, so the 30 s `CONNECT_TIMEOUT` never covers a download: the interface downloads, then connects again. Core checks that in two steps, `prepare_connect` (the engine lookup, the connect policy's `check_config`, `Engine::preflight`, which for the remote DuckDB engine is the helper's start check) and `open_prepared`, so a refusal there closes nothing a reconnect would replace (the order under "Ownership").
- `seaquel-engine` — the `Driver`/`Engine` plugin traits, the pure `Dialect` trait, and the generic DDL/CRUD builders (`ddl.rs`, `crud.rs`) that dialects parameterize. `Driver` has default `NOT_SUPPORTED` introspection methods (`list_schemas`, `schema_tables`, `table_metadata`, `statistics`, `explain`), and `closed()` (default `None`): a future that yields `Some(error)` when the connection was lost unasked and `None` when it ended as asked, which Core watches (`lost.rs`). `Engine` has `preflight(config)` (default `Ok`; a refusal before anything opens) and `exclusive_file(config)` (default `false`; true when a connection holds its file so a second open of it can't succeed, the remote DuckDB engine with a file path), both used by `Workspace::connect` (Ownership, above). One crate per engine: `seaquel-engine-{postgres,mysql,sqlite,mssql,duckdb}`. Read-only queries go through `query_read_only_with(sql, params, ReadOnlyOptions { max_rows, max_bytes, timeout })`, which returns a `CappedResult { columns, rows, truncated }`; `RowCap` (`fail`, `truncate`, `read_only(max_rows, max_bytes)`) decides per row whether to keep it, truncate or fail with `RESULT_TOO_LARGE`, and `max_rows` never goes past `max_query_rows()` (100,000, `SEAQUEL_MAX_QUERY_ROWS`). `explain_read_only` defaults to `NOT_SUPPORTED`, so an engine without it fails closed. `Driver::transaction` fails with `TransactionError { index, error }`: `index` is the failing statement's position when the database refused it, its parameters didn't bind or it fell short of `expect_rows` (`NO_ROWS_AFFECTED`), and `None` when connecting, BEGIN or COMMIT failed or a transaction opened by hand is already open (SQL Server and DuckDB refuse then, with code `TRANSACTION_OPEN` and the `TRANSACTION_ALREADY_OPEN` message; 409 on web. SQL Server reads `@@TRANCOUNT`; DuckDB compares two `txid_current()` calls, equal only inside a transaction, and a failed probe counts as open, since a nested BEGIN there would abort the user's transaction); `db.transaction`'s wire carries only `error`. An empty `query_stream` result still names its columns: the sqlx engines (Postgres, MySQL/MariaDB, SQLite) read column names from rows, so with no row they take them from the statement sqlx prepared (its statement cache, no extra round trip); SQL Server and DuckDB always sent them. `query` on an empty result still returns none. `transaction` returns each statement's rows affected. `select.rs` builds the data tab's SELECT (`build_table_select`, pure, parameterized by quote functions, placeholder and text type like `crud.rs`). `Dialect::paginate` puts `LIMIT`/`OFFSET` on a line of its own (Postgres, MySQL/MariaDB, SQLite, DuckDB; SQL Server already dropped trailing comments), so a query ending in a `--` comment pages. **Statement logging is off everywhere:** sqlx logs each statement at DEBUG, and each one slower than a second at WARN, with its whole SQL, so every sqlx pool and connection (engines, their cancel connections, `seaquel-storage`, `seaquel-license`) is built with `disable_statement_logging()` (`run_no_statement_logging` in the testkit checks an engine), and the server's `StderrLogger`, the desktop's `tauri-plugin-log` and the terminal binaries' filter drop the `sqlx::query` target too. sqlparser logs literals at DEBUG, and Core parses runs natively, so the desktop and the terminal binaries turn the `sqlparser` target off (the server passes dependencies only at WARN). **A stopped stream stops on the server:** `impl_sqlx_driver!`'s `stream_start` gives `query_stream` one connection and a `RunningStatement`; dropped unfinished (a cancel, a disconnect, eviction), Postgres sends `pg_cancel_backend` and MySQL/MariaDB `KILL QUERY` from a fresh connection (spawned, 5 s timeout) and closes the connection. It fires only while that session still runs a statement starting with `seaquel_engine::statement_prefix` (leading whitespace skipped; cut before the first `?` on MySQL, whose binlog expands parameters, and before any character above U+FFFF; under 8 characters it checks only that a statement runs). Behind PgBouncer in transaction mode, a statement with the same start from another client on that backend could be cancelled; with `track_activities = off` nothing is. The cancel paths log an error's kind and code, never its message. It costs one lookup round trip per stream. SQL Server stops when its session closes; DuckDB interrupts on drop (the browser driver cancels its pending query, and the remote driver posts a `cancel` frame from `Drop`, ahead of any later call's request); SQLite's plain stream isn't interrupted (local). A non-streamed `query`/`execute` still in flight at a disconnect isn't cancelled. Postgres's `explain` is the exception (phase 7a): it runs on a connection of its own with the stream's cancel-on-drop (`stream_start`, the prefix check on the EXPLAIN text, disarmed when it returns), so dropping the call (Stop, the TUI's exit) sends `pg_cancel_backend` to an `EXPLAIN ANALYZE` still running; one more round trip per explain, the GUI's included.

Every variant exists in every build, so the generated TS doesn't depend on features. Both levels are adjacently tagged (`{"method", "params"}`, responses `{"method", "result"}`), and `method` must come before `params`: stored JSON columns are `RawValue` and stay byte-identical, so parse bodies with `parse_request` from the raw bytes, never through a `serde_json::Value`. - `seaquel-storage` — the metadata SQLite database: open, schema and one typed function per query (`queries/`); the only place SQL for it lives. `data_dir(identifier)` reads `SEAQUEL_DATA_DIR` (an empty value is ignored), else the platform data dir plus the Tauri identifier. `data_local_dir(identifier)` is the folder for files that belong to the machine, the CLI the app installs and the DuckDB helper (`dirs::data_local_dir()` plus the identifier: the data dir on macOS and Linux, under `%LOCALAPPDATA%` on Windows); `SEAQUEL_DATA_DIR` wins there too and is then that folder itself, so the terminal binaries, the app's install and the tests agree on one helper and never reach the real folder under test. The file is `<data_dir>/seaquel.db` on desktop and `DATA_DIR/users/<id>/meta.db` on web. `Storage::open` runs the frozen baseline (`schema.rs`, which upgrades every released file), then numbered expand-only SQL migrations (`migrations/`, rules in its README), then Rust data steps (`data_steps.rs`, recorded in `_seaquel_data_steps`). Schema changes are new migration files, never baseline edits. The first is `0001_name_keys.sql` (5d-1): nullable `name_key` columns on connections, projects and saved queries with their indexes, and triggers that set a row's key to NULL when an older release renames it without one. Storage writes the key with the name, the `backfill_name_keys` data step fills the rows already there, and `refill_name_keys` (on every writable open, after Core's secrets upgrade) fills any NULL an older release left. `0002_window_state.sql` (5d-2) adds `windows`, `window_state` and `dashboards.name_key` (its trigger and index as `0001`'s). `0003_window_order_and_list_meta.sql` adds `write_seq` to both window tables and the list metadata `saved_canvases.meta` and `dashboard_versions.widget_count`, so `workflowsList` and `dashboardVersionsList` read no bodies; a body that can't be read is marked (`'null'`, `-1`) so NULL only means "not filled yet", and `refill_list_meta` (right after `refill_name_keys`, on the same opens) fills the NULLs an older release's writes leave. `0004_shared_links.sql` (5e) adds the shared projection's link columns (`projects.shared_dir`; `shared_path`, `shared_base`, `shared_file_id` on saved queries and dashboards; `shared_base`, `shared_file_id` on connections) and `0005_shared_connection_origin.sql` `connections.shared_origin`; only `set_link`, `set_shared_dir` and `set_origin` write them, so no library write or older release's save moves a link, and NULL means "not known" (no data step). `0006_history_params.sql` adds `query_history.params`, the bound values of an applied change as a JSON array in the cell wire format (NULL for runs, for rows older releases wrote, and for an apply with no values). `0007_ai_message_parts.sql` (phase 6) adds `ai_messages.parts`, a reply's tool calls as a JSON list (NULL means none; an older release ignores it and shows the text, and its `chatMessagesPut` keeps the stored value through `COALESCE`); `append_turn_in` writes a turn's rows, and the chat budget (`CONTENT_BYTES`, `max_chat_bytes`, `storedBytes`) counts `parts` with the content. The data steps are the phase 3 password strip, `drop_legacy_built_connection_strings` (5d-1: drops a pre-5a string equal to what the old TypeScript builder made of the row's fields, which the GUI's load used to do), `backfill_name_keys` and `backfill_dashboard_name_keys` (5d-2). Each new migration or data step makes `seaquel-cli mcp` and `seaquel-tui` refuse the file (`STORAGE_NEEDS_UPGRADE`) until the app has opened it once. **Writes** go through `Storage::write`, which returns a `WriteTx` (`write.rs`): writers in one process queue on an async mutex that owns the storage's one **writer connection** (phase 7a; outside the pool, which gets `max_connections - 1`, at least 1; with `idle_timeout` set, as on web, a reaper closes it once it has gone unused that long), then begin with `BEGIN IMMEDIATE` on it; a writer still waiting after `WRITE_WAIT` (30 s) fails with `STORAGE_ERROR`, and read-only storage fails at once with `STORAGE_READ_ONLY`. Every write, `VACUUM` and checkpoint runs on that connection, and a `ROLLBACK` that fails closes it, so the next write opens a fresh one; `WriteTx` turns a `secure_delete` it set off again before handing the connection back. That includes the 25 single statements that used to go straight to the pool (`app_state::set`, `query_history::set_favorite`, `user_credentials`, `vault_state`, the license, `tutorial`, `import_state`, `themes::save_preferences`, the frozen-fixture saves), each now in its own `WriteTx`, so on read-only storage they fail with `STORAGE_READ_ONLY`. A write on any other connection would look external to the poll. `Storage::external_version()` (native) answers a counter over `PRAGMA data_version` on the writer connection, which only another connection's commit moves: it moves when the pragma differs from the last poll's, and once when the writer connection was replaced (two connections' values don't compare). It is `None` while a write holds the turn (`try_lock`); another connection's `wal_checkpoint(TRUNCATE)` also moves it once, with no commit; read-only storage polls on a connection of its own; `Storage::close` closes the writer after any write in flight. **Inside a write, read only through `&mut tx`**: a read through `&storage` takes a pool connection and doesn't see the transaction's writes (on wasm32, whose pool is the one connection, it waits for the transaction). The targeted functions (`connections`, `projects`, `project_labels`, `saved_queries`, `query_versions::append_keyframe`, and since 5d-2 `dashboards`, `dashboard_versions`, `saved_canvases`, `ai_chats`, `app_state`, `themes`, `windows`, `window_state`, `project_state::write_legacy_mirror`, and since 5e `shared_repos::{insert, update_json, delete}` and the link writes, …) take `&mut WriteTx`; the replace-all ones (`projects::save_all`, `saved_queries::save_all`, `project_state::save`, `ai_chats::replace_all_messages`, `themes::save_user_themes`, `shared_repos::save_all`, …) stay only for the frozen repo fixtures. `shared_repos::update_json` splices the named fields into the stored JSON and keeps every other byte. The `connection_overrides` table and its functions stay too, though nothing reads or writes overrides since they were retired in 5d-2. Query history is written only by `query_history::append` (the row plus the 500-row cap, favourites kept), `append_many` (Core's applies: many rows in one transaction, one prune; no RPC) and `set_favorite` (sets, never toggles), as `queryHistoryAppend`/`queryHistorySetFavorite`; `replace_all` stays only for its frozen repo fixture and has no RPC. A pending migration runs under a `BEGIN IMMEDIATE` lock held on the migrator's own connection (each migration is a savepoint inside it), so two pools or processes opening one file apply it once. While the baseline or a migration has work to do, the other opener retries the lock for up to 12 busy timeouts (`MIGRATION_WAIT_ATTEMPTS`, about a minute; `0003`'s fill takes about 3 s per GB of workflows and versions); with nothing pending it fails after one, so a lock another process holds doesn't stall startup. `StorageOptions { read_only: true }` (for `seaquel-cli`) opens with `SQLITE_OPEN_READONLY`, never sets the journal mode or creates the file, and runs nothing: if the baseline (`schema::is_current`), a migration or a data step has work to do it fails with `STORAGE_NEEDS_UPGRADE`, a missing file with `STORAGE_NOT_FOUND`. `schema: SchemaPolicy::RequireCurrent` (phase 7a, a second process such as the TUI; `WorkspaceSpec::second_process`) makes the same checks and refusals but opens writable: it never creates the file, leaves the journal mode as the app set it (WAL) and runs nothing; `max_bytes` applies. Fixtures in `crates/seaquel-storage/tests/fixtures` (each release's schema, the repo cases) are frozen. Codes that block the app: `LEGACY_STORAGE` (only pre-2026.4.5 JSON files, no `seaquel.db`), `STORAGE_CORRUPT`, `NO_DATA_DIR`; anything else is `STORAGE_ERROR`.

Natively `db/native.rs` re-exports sqlx under the names the queries use, so desktop and web storage is sqlx as before; nothing outside it names sqlx. On wasm32 `db/mem/` is the same API over `sqlite-wasm-rs`'s C API (`ffi.rs`, the crate's only `unsafe`, single-threaded SQLite), copying sqlx 0.8.6's binding, `rows_affected`, `fetch_optional` and type-compatibility rules and its error `Display` and codes, so `STORAGE_FULL`, the corrupt and busy checks read the same. The wrapper also compiles natively over `libsqlite3-sys` 0.30.1 for its tests. Its pool is one connection behind an async mutex (`lock.rs`: `futures::lock` on wasm32, tokio's natively), stricter than the native pools: a read through `&storage` while the same task holds a `WriteTx` waits, then fails after 30 s. `StorageOptions::in_memory(image)` (wasm32) deserializes an image (a desktop file's WAL header is rewritten first) or makes a new file, then runs the baseline, the migrations and the data steps as `Storage::open` does; `migrations.rs` (generated by `build.rs`) records them in `_sqlx_migrations` with sqlx's checksums (`migrations_match_sqlx` pins it), so a browser file opens natively with nothing pending (`tests/wasm_made.rs`, `tests/fixtures/wasm-made/`) and the other way round. `snapshot()` is `sqlite3_serialize`, refused while anyone holds the connection or a transaction is open; `commits()` counts commits through SQLite's commit hook and can run ahead of real changes (an empty `BEGIN IMMEDIATE … COMMIT` counts), never behind. The write turn races the executor's `sleep` (`Storage::with_executor`); a dropped `WriteTx` rolls back synchronously on wasm32. tokio, sqlx, `dirs` and `data_dir` are native only. The wasm tests run with `CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER=wasm-bindgen-test-runner cargo test --target wasm32-unknown-unknown -p seaquel-storage --all-targets` (and the clang above).
- `seaquel-secrets` — `SecretStore` (`get`/`set`/`delete`), `KeychainStore` and `MemoryStore` for tests. `validate_key` allows only `db:<id>`, `ssh:<id>`, `ssh-key:<id>`, `ai-api-key:<id>` and `license-key`. The keychain service is `DESKTOP_SERVICE` (`app.seaquel.desktop`) in dev builds too, since changing it orphans saved passwords. Errors name the key, never the value. `SecretError::Unavailable` (`unavailable()`; the wire code stays `SECRET_STORE_ERROR`, and Core turns it into `SECRET_STORE_UNAVAILABLE` on a connect) is a store that can't be reached at all, read from keyring's boxed platform error: no D-Bus session bus, no `org.freedesktop.secrets` provider or a lost bus on Linux, `errSecNotAvailable`, `errSecNoSuchKeychain` or `errSecInteractionNotAllowed` (no GUI session, as over SSH) on macOS; a locked keyring, a dismissed prompt and a denied dialog stay refusals. The D-Bus names come from dbus's and keyring's sources, not a run on a headless host. `SecretWait` (`secret_wait.rs`, moved from `seaquel-mcp` in phase 7a; `seaquel_core::secrets::SecretWait`) wraps a store and times its calls, with a 5-minute limit: `get`, `set` and `delete` each count (a save into an item the app created reads it first, so it can show the macOS dialog too), `pending()`/`pending_for` and `changed()` (a `watch` that flips on 0↔1) let the TUI show its keychain box, and the MCP server's call timeout pauses while one waits. - `seaquel-ssh` — SSH tunnels over russh 0.48: a local port forwarded through a bastion, password or key-file auth, and the host-key check against known_hosts. An unknown key fails with `UNKNOWN_HOST_KEY` and its `SHA256:…` fingerprint; the retry passes that fingerprint as `trustHostKey`, and only a key with exactly that fingerprint is recorded. `HOST_KEY_MISMATCH` is never accepted. A key of an algorithm known_hosts doesn't hold for the host counts as unknown, not a mismatch (russh compares only keys of the same algorithm). Closing a tunnel (or dropping it) aborts every forward and ends the SSH session. The error codes are the ones the TS host-key prompt matches on; keep them. Live tests need `SEAQUEL_TEST_SSH` (below).
- `seaquel-git` — shared projects' git over libgit2 (vendored): `Git`, with every call async over `spawn_blocking`. The home dir for default SSH keys is a field (`Git::from_env()` on desktop), so tests never read `~/.ssh`. The credential chain is agent, then the given key or the default keys, then user/password; it never hands out the same credential twice and gives up after 4, so a wrong password can't loop. A commit after a conflicted pull gets MERGE_HEAD as its second parent, and commit refuses while files are conflicted. A push the remote refuses fails with `PUSH_ERROR`; a non-fast-forward says `PUSH_REJECTED_NON_FAST_FORWARD`, which the TS matches exactly to mark the repo "behind". **A pull never overwrites local changes:** a fast-forward checks out with `CheckoutBuilder::safe()` before it moves the branch, and a merge that libgit2 refuses over local changes is refused too; both fail with `PULL_ERROR` "Commit or discard your changes to … first", naming at most ten paths as JSON strings (`PULL_REFUSED_LOCAL_CHANGES`; the GUI's `pull-error.ts` reads them). `resolve_conflict` and `resolve_conflict_deleted` (keep the side that deleted the file: the file goes and the deletion is staged) accept only a path the index holds as conflicted, relative, with no `..`, backslash, NUL or symlink on the way (`tree::check_resolvable`), and write through `tree`'s atomic no-follow write; anything else is `CONFLICT_ERROR`. `tree.rs` (5e) is the shared projection's file I/O: `scan`, `apply`, `restore`, `conflicted`, `project_dirs`/`project_dirs_listing`, under Core's file rules above. - `seaquel-license` — two parts that share only the HTTP client (`seaquel_http::client`'s `LazyClient`, below; its log lines keep `activity = "license.http"`). `desktop` is the activation client (`DesktopClient`: activate, validate, deactivate); the 12-hour revalidation stays in `license.svelte.ts`. `server` is the web build's gate (`LicenseServer`): the install id, the control-plane client, the soft/hard TTL ladder (`SEAQUEL_LICENSE_SOFT_TTL`/`SEAQUEL_LICENSE_GRACE_TTL`, 24 h and 14 d), member licenses and air-gap bundles (Ed25519; canonical JSON byte-identical to what seaquel-app signs). - `seaquel-http` — infra, native only (phase 6): `client.rs` (the HTTP client the license crate had: reqwest 0.12 with rustls, the OS and webpki roots built lazily with a fallback, so a broken OS certificate store can't panic at startup, extra roots from `NODE_EXTRA_CA_CERTS` through `load_extra_roots(path, activity)`, `HTTP(S)_PROXY`/`NO_PROXY`, and `proxy_plan`), `egress.rs` (`Egress::{Off, Public, Any}`, `Egress::parse`, the host check and the filtering resolver; `Refusal` surfaces as `AI_EGRESS_BLOCKED`) and `native.rs` (`NativeHttp`, `NativeHttpOptions`: `seaquel_ai::http::HttpClient` over reqwest, streaming bodies, the assistant's timeouts below, never a redirect). The `system-proxy` feature adds the OS proxy (the desktop, through Core's `ai-system-proxy`). Interfaces reach it only as `seaquel_core::ai::native` and through Core's DuckDB helper install. **`release_asset`** (feature `release-asset`: `flate2`, `sha2`, `tempfile`; only Core's `duckdb-helper-install` turns it on, so the web server doesn't link it) downloads and installs a gzipped release asset: `Fetcher::asset(version, name)` reads `v<version>`'s metadata from the `ReleaseSource` (`github()`; `new(api, download)` only in tests, debug builds and the `testing` feature) and takes the asset's size (at most 64 MiB) and `sha256:` digest; `Fetcher::install` makes the target's folders private, streams the body through a SHA-256 hasher and a gzip decoder into a 0600 `.seaquel-download-*.part` file in the version folder (at most 256 MiB unpacked, `ASSET_TOO_LARGE`), checks size, digest and the gzip trailer in that order, then `fchmod` 0700, `fsync`, rename, folder `fsync`, and writes the `<file>.installed` record the same way; `install_file`/`install_file_cancellable` take a file the user copied (`--from`) and its hash, gunzipping it if it starts with gzip's magic. Dropping the future deletes the `.part`; `.part` files older than 10 minutes (`STALE_PART_AGE`, a killed install's) are swept on the next install. **Folders** (`InstallTarget { root, folders, file_name }`): `root` is created 0700 if missing, must be this user's, and loses group and world write; each folder below is created 0700 or set to exactly 0700, must be this user's, and is opened `O_NOFOLLOW | O_DIRECTORY` and checked and `fchmod`ed through that handle top down, so a symlink anywhere from `root` down is `UNSAFE_FOLDER` with nothing written through it and another user's folder is refused, never tightened. On Windows (`seaquel_runtime::acl`, the same rule the start's check reads) a folder below `root` and the file get a protected DACL of the user and SYSTEM unless they already have exactly that (the file on its temporary name, before the rename); `root` keeps its DACL unless others may replace or rename in it, and is then repaired in place (every entry kept, the replacing rights taken out of others' allows, set protected); a link (a name-surrogate reparse point) or an owner other than the user, SYSTEM or Administrators is `UNSAFE_FOLDER`. An `UNSAFE_FOLDER` message says what to do: remove `bin/duckdb` in Seaquel's data folder and install again, or point `SEAQUEL_DATA_DIR` at a folder of your own. Folders an install made are removed again, deepest first while empty, when it fails, is refused or is dropped (`MadeFolders`); one that was there already, or holds anything, stays, and `root` is never removed. Under the pin (Core's `duckdb_helper_pinned`) `Fetcher::install` gets an `Asset` built from the pin and makes no metadata request, and a 404 from the download URL is `ASSET_NOT_FOUND` on either path (GitHub answers a missing release the same way there). `open_regular(path)` refuses anything but a regular file before opening it (`O_NONBLOCK` on Unix, checked again on the handle), so a FIFO can't block the blocking pool; `install_file_paced` is the copy with a pause per read, used only by the CLI's test hook. **Requests** carry only `User-Agent: Seaquel/<version>` and `Accept`; 15 s to connect, 60 s between reads, 60 s overall for the metadata (`METADATA_TIMEOUT`). Redirects are followed by hand, at most 5: every hop `https:` (plain `http:` to loopback only when the source itself is loopback, which also turns proxies off), and metadata hops only on the API's origin; else `REDIRECT_REFUSED` before connecting. - `seaquel-duckdb` — the DuckDB helper: `src/main.rs` and a `build.rs` that reads the app version from `src-tauri/Cargo.toml` (by `include!`ing `seaquel-terminal`'s parser, not depending on it). Every other route keeps `BODY_SIZE_LIMIT` (512K by default), as adapter-node documents it: `server.js` moves the operator's value to `SEAQUEL_BODY_SIZE_LIMIT` and sets adapter-node's to `Infinity` before loading its handler, and `handleBodyLimit` (first in `hooks.server.ts`) enforces both, refusing by `Content-Length` before anything is read and counting a body sent without one. Rust's own `/rpc` limit (64 MiB) is only the outer bound. Every state-changing `/api/*` call but `/api/auth/*` (Better Auth checks those) needs a trusted `Origin` (`handleOriginGate` in `hooks.server.ts`, rules in `src/lib/server/origin.ts`), or it gets 403 `ORIGIN_NOT_ALLOWED`: `SEAQUEL_TRUSTED_ORIGINS`, the origins of `BETTER_AUTH_URL` and `ORIGIN`, the install's own origin (an `Origin` naming the request's `Host`, only while neither `BETTER_AUTH_URL` nor `ORIGIN` is set and only for `localhost` or an IP-address `Host`, never a domain name, which DNS rebinding could supply; the stream proxy passes the upgrade's `Host` to `/api/account/stream-access` as `x-seaquel-upgrade-host`), and the localhost dev-server origins in dev builds only. There is no `/api/db`: the engine and option refusals are Rust's (`ConnectPolicy`). `/api/rpc/stream` is proxied by `shared/rpc-stream-proxy.js` on the HTTP server itself (`server.js`, or a Vite plugin in `dev:web`), since SvelteKit routes can't upgrade: it resolves the session through `/api/account/stream-access` (behind `handleApiGate`, with the browser's `Origin` and the upgrade's `Host`), opens Rust's fixed `/rpc/stream` URL with `X-Seaquel-User` and no browser header, and pipes frames unread (browser frames capped at 8 MiB). It applies backpressure both ways: when the side it writes to holds 16 MiB unsent (`PAUSE_BUFFERED_BYTES`) it pauses the other side and resumes once the writes flush, so a slow browser stalls Rust's sender and the query instead of Node's memory; more than 64 MiB arriving from a side after it was paused (`MAX_BUFFERED_BYTES`) closes both with 1013, while one wide row and the frames right behind it pass. Browser frames queued while the Rust socket opens are capped (64 frames, 64 MiB) and flushed through the same backpressure, and a Rust socket that doesn't open in 10 s (`RUST_CONNECT_TIMEOUT_MS`) closes the browser with 1013. It re-checks the session every 60 s: a 401/403 or another user closes with 1008 (the client stops and reports lost access), a failing or slow gate with 1013 (the client reconnects). Sockets close with 1000 after 12 h and reconnect. Rust's close code and reason reach the browser. `hooks.server.ts` caches each user's gate answer for 5 s.

### Dialects and engine calls

- **UI code never scans or parses SQL itself.** Splitting, statement at cursor, `{{param}}` handling, query type, the destructive and read-only checks, `CREATE TABLE` parsing and the AST helpers all come from `$lib/sql` (`src/lib/sql`), which calls `seaquel-wasm`. Pass the connection's engine; the checks follow its quoting. If the module traps, `callWasm` re-instantiates it and the per-keystroke functions return their "couldn't parse" value, so on the run path (anything that decides what SQL executes) use the `…OrThrow` variants, which fail instead of letting SQL run unchecked. The editor's runs are planned by Core (`db.run`, below) on every interface, the demo included; the wasm calls remain for the editor's own checks (its synchronous destructive prompt, Explain and Visualize at the cursor).
- **UI code never does dialect work itself.** Introspection, EXPLAIN, statistics and DDL generation go through `EngineClient` (`src/lib/engine`): `getEngineClient(connection, state)`. Pagination, counts, CRUD and the data tab's query are Core's (`db.run`/`db.page`, the edits service); `EngineClient` has no `paginate` or `build*` since 5c. Pass the app state so the client reads the live provider connection id on every call (it survives `reconnect()`). Don't cache clients across operations. There is no TypeScript dialect left: `src/lib/db/` (`getAdapter`, `duckdb.ts`, `alter-table.ts`, `crud-helpers.ts`) went in phase 8.
- **Identifiers:** quote a name with `EngineClient.quoteIdent` and build a table name from a listed schema with `EngineClient.qualifiedTable` (DuckDB lists attached catalogs' schemas as `catalog.schema`, two names). Never hand-build `"${name}"`.
- **Model-written SQL runs only read-only.** The assistant's and MCP's tools run in Core (`ai::tools::call`: `query_stream` with `read_only`, `max_rows`, 8 MiB and 60 s; `explain_read_only`). Dashboard widgets, the assistant's dashboard tools' widgets and workflow query nodes run in the page through `executeReadOnly` (`QueryCrud`, then `DatabaseProvider.selectReadOnly` and Core's `query_stream` with `QueryOptions::read_only`, `max_rows` only). The inline prompt only inserts what it generates (`ai.generate`); the user runs it. Core runs the token check (`seaquel_sql::read_only`) and then `Driver::query_read_only`, whose default is `NOT_SUPPORTED`. The `read_only` flag limits what model-written SQL can do, and is no guard against the local user or an API caller. Per engine:
  - Postgres: `BEGIN READ ONLY` on a pooled connection, which is closed afterwards, not returned.
  - MySQL/MariaDB: `SET SESSION TRANSACTION READ ONLY`, then `START TRANSACTION READ ONLY`, on a pooled connection that is then closed.
  - SQLite: a private read-only connection with `PRAGMA query_only = ON`, an authorizer that refuses most PRAGMAs and `ATTACH` (`read_only::deny_settings`), and a gate that prepares the SQL with SQLite's parser and allows one statement for which `sqlite3_stmt_readonly` is true (`read_only::check`). `SqliteDriver` refuses SQL holding a NUL byte on every entry point: sqlx 0.8.6 loops forever on it.
  - DuckDB: a clone of the connection per call, `BEGIN TRANSACTION READ ONLY` and `SELECT * FROM query(?) LIMIT <cap + 1>` with the SQL bound. The remote driver runs the same in the helper, each call on a clone of its own, at most 16 at once (the client queues the rest). The browser driver opens a fresh DuckDB-WASM connection per call and writes the SQL as a string literal (`query('…')`), then always sends `ROLLBACK` and closes it (cancel, `ROLLBACK` and close when the call is dropped). The token check also refuses DuckDB functions that act outside the query (`BLOCKED_FUNCTIONS_DUCKDB`: `enable_logging`, `checkpoint`, `query`, `mysql_execute`, …). For the in-app assistant, files and URLs stay readable: it runs on the editor's connection, whose file functions need external access. Only the MCP server's own instances are restricted.
  - A lone `\r` ends a `--` comment in the scanner on SQL Server, Postgres and DuckDB, as those databases do. The read-only check (`read_only_error`) also reads every input a second time with a lone `\r` ending `--` and `#` comments, on every engine, and refuses if either reading does; so on MySQL, MariaDB and SQLite, code-looking text after a `\r` inside a comment is refused.
  - MSSQL has no read-only mode. Each call gets its own connection (`READ_ONLY_CONNECTIONS`, 4 at once; `READ_ONLY_TIMEOUT`, 60 s), never the held session. The SQL runs two transactions deep inside TRY/CATCH and is always rolled back; a query that ends the transaction comes back as `READ_ONLY`, but what it committed stays, and `NEXT VALUE FOR` advances. Only a read-only login closes that.
- `getEngineClient` returns `RustEngineClient` (`db.engine` through `CoreClient`) for every engine: Postgres, MySQL, MariaDB, SQLite, MSSQL and DuckDB on desktop, Postgres, MySQL, MariaDB and MSSQL on web, and DuckDB in the demo (over the module).
- **Every engine crate** has `dialect.rs` (the pure `Dialect`), `introspect.rs` (catalog SQL, parsers, EXPLAIN) and `decode.rs` (with `bind.rs` in all but DuckDB) for values. Postgres adds `numeric.rs`, the NUMERIC binary codec. `crates/seaquel-engine-mysql` serves MySQL and MariaDB: a `"mariadb"` connection connects with driver `"mysql"`.
- **SQLite:** cells decode by storage class (`typeof`), not declared type; BLOBs are bytes. SQLite has no `DEFAULT` in `UPDATE`, so Set to default writes the column's default expression, which Core reads from the table's metadata when it plans the edit (none: NULL). Edits SQLite can't make come back from `alterTable` as `-- …` note lines; the table editor shows them (`splitDdlScript` in `src/lib/utils/ddl-script.ts`).
- **MSSQL:** cells are native: decimal and money are `Decimal`, binary is `Bytes`, dates and times are SQL Server's own text (datetimeoffset as `2024-01-02 03:04:05.5 +01:00`). tiberius hands money over as an f64: it is exact only for |value| < 2^39 ≈ 5.5·10¹¹; above 2^53 units tiberius itself loses bits (up to ~1536 units near the ends of the range), and the maximum reads `922337203685477.5808`, which is out of range when bound back. A `Null` parameter is sent as the `NULL` literal (`inline_nulls`), since no declared type assigns to every column; so a column made only from it is int (`SELECT @P1 INTO`, `UNION`), `COALESCE`/`CASE`/`IIF` with only such NULLs fail (4127, 8133), and so does passing one as an `OUTPUT` argument (179). A `@Pn =` naming a parameter in an `EXEC` argument list is left alone. Query parameters (`{{name}}`) are inlined, strings as `N'…'`, so they work in `TOP`, `CREATE VIEW` and defaults. CRUD binds `@P1…`; EXPLAIN runs `SET SHOWPLAN_XML`/`STATISTICS XML` as separate batches and parses the ShowPlan XML with roxmltree; statistics are `NOT_SUPPORTED`.
- **DuckDB** has two drivers in `seaquel-engine-duckdb` (web has no DuckDB connections), both with the id `duckdb`, sharing `dialect.rs`, `introspect.rs` (its `calls` serve both drivers' introspection through `query`) and `decode.rs`, which reads arrow-rs arrays (the same `arrow-array` 58.4 duckdb-rs re-exports), so nothing is forked. `cargo test -p seaquel-engine-duckdb` with the default features runs every suite through the helper with no DuckDB in the test binaries; `--features remote,helper` adds the helper's in-process `serve` and session tests, which compare against `src/test_reference.rs` (the frozen `cells.json` and literal results). `remote` (the default feature: `src/remote/`, tokio's `process`, `arrow-ipc`, `libc` on Unix, **no `duckdb` crate**) is every native interface's: a `Driver` over a `seaquel-duckdb` child process. `helper` (duckdb-rs, a DuckDB 1.5 build, tokio's clock; `helper.rs`, `session.rs`, `blocking.rs`, `kinds.rs`) is the loop that process runs. `browser` (wasm32: `src/browser/`, wasm-bindgen, `arrow-ipc`) is the demo's, over DuckDB-WASM 1.32 (DuckDB 1.4.3) through a bridge object the page passes in. The in-process native driver (`driver.rs`, `engine()`, the `native` feature, Core's `engine-duckdb`) was deleted. A build with none of `remote`, `helper` or `browser` doesn't compile, nor does `remote` on wasm32. `wire.rs` (the frames, under `remote` and `helper`) and `ipc.rs` (the Arrow IPC reader, `Columns` and `IpcStream`, under `browser`, `remote` or test) are shared. Core's `engine-duckdb-remote` is the client; `seaquel-duckdb` takes the crate with `default-features = false, features = ["helper"]`, `seaquel-browser` with `["browser"]`.
  - **The session.** `session.rs` is everything DuckDB does for a call (`open`/`open_sessions` with `duckdb_config`, `restricted` and `create_if_missing`, the binds, `prepare` with its cancelled check, `execute`, `transaction` with the `txid_current()` probe, the read-only and EXPLAIN scaffolding), generic over a `ChunkSink` (`columns`, `chunk(StructArray) -> Flow`, `finish`). The helper's sink writes Arrow IPC frames, with the column kinds `kinds::of` reads from DuckDB's logical types (its `catch_unwind` making an unknown type `Kind::Plain`). Chunks are read with `Statement::step()`, never duckdb-rs's Arrow iterator, which panics on an interrupt.
  - **Streaming execution** (the session's; the browser driver always streamed). `query_stream` starts DuckDB's streaming execution (`Execution::Streaming`, through `stream_arrow`, whose iterator is dropped unread), so its first batch comes after the first chunk instead of after the whole result, and a query can fail after batches have arrived. DuckDB runs ahead of its reader until `streaming_buffer_size` bytes (10^6 by default) are buffered, a session setting only (DuckDB refuses it as an open option, so a restricted instance can't change it). A stream dropped early keeps what DuckDB already did: an `INSERT … RETURNING` finishes before its first chunk, `nextval` advances for the rows produced. A stream that isn't read holds its connection's turn. `query`, the read-only path and EXPLAIN stay materialized.
  - **The protocol** (`wire.rs`, `PROTOCOL` 2): the helper's stdin and stdout, frames `[len u32 LE][kind u8][call u32 LE][payload]` with `len` at most 16 MiB (`MAX_FRAME`, checked from the header before allocating and before writing, on both sides; past it the process ends, `HELPER_PROTOCOL`). Control frames are JSON (`Request`/`Reply`, internally tagged, camelCase, `deny_unknown_fields`, hand-written `Debug`; a parse error names serde's category and position, never the text): `hello`, `open` (`OpenParams`: path, `create_if_missing`, `restricted`, `duckdb_config`; never a password or connection string), `query`, `stream`, `execute`, `transaction`, `readOnly`, `explainReadOnly`, `cancel`, `credit`, `close`, answered by `helloOk`, `opened`, `executed`, `committed`, `done` or `error` (`DbError`, plus `index` for a transaction). Rows are one `schema` frame, `[kinds_len u32][kinds JSON][IPC schema message]` (the column kinds from DuckDB's logical types, `kinds::of`, so lossy Arrow settings can't change the cells), then `batch` frames of IPC messages, each at most 8 MiB (`MAX_BATCH_FRAME`; a batch is sliced by rows, its new dictionaries first in a frame of their own; one row goes alone up to the frame cap, past it `RESULT_TOO_LARGE`). No end-of-stream marker: `done` ends the rows. Every call that returns rows has a credit window of 2 batch frames (`STREAM_CREDIT`, dictionary-only frames included), then one per `credit` frame, so a small answer waits behind at most two frames of another call. The client applies `RowCap` and the byte budget itself, on decoded rows.
  - **The remote driver** (`remote/`: `mod.rs`, `process.rs`, `conn.rs`, `driver.rs`, `closing.rs`). `remote_engine(HelperLocator)`; one helper per `Engine::open`. Before each start `process::check` looks at the file and every folder up to `<identifier>` (the parent of `bin`): no symlinks (`symlink_metadata`), and on Unix owned by `geteuid()` with no group or world write, the file also executable by its owner; on Windows each level's DACL and owner by `seaquel_runtime::acl`'s rule (above), so `%LOCALAPPDATA%`'s inherited entries pass and a folder given `Everyone:(M)` doesn't; else `ENGINE_NOT_INSTALLED` "…the DuckDB helper's folder has unsafe permissions" with nothing spawned, which Core's status reports as `Unsafe` and an install repairs. Folders above `<identifier>` aren't checked. The private version folder also guards the DLL search order on Windows. The child gets `CREATE_NO_WINDOW` on Windows, the cwd and the environment minus every `SEAQUEL_*_TEST_*` variable (and, started from an AppImage, minus the `LD_LIBRARY_PATH`/`LD_PRELOAD` entries under `$APPDIR`, `appimage_env`); on Unix spawns take a process-wide mutex (`SPAWN`), since macOS marks std's pipes close-on-exec only after creating them. Its stderr is drained and only counted. `hello { protocol, version }` must get `helloOk` with the same protocol and the client's app version within 5 s (a file this process hasn't started yet, by path, device, inode, size and mtime, gets one retry within 20 s, for macOS's slow first exec): another version, a refusal or EOF is `ENGINE_NOT_INSTALLED` ("DuckDB support for Seaquel 2026.x.y isn't installed: <reason>", no path; helper strings cut to 64 characters), a silent helper `ENGINE_UNAVAILABLE` (a download wouldn't help). Then `open`, under Core's connect timeout; a refused open returns the helper's own error (`FILE_NOT_FOUND`, `INVALID_CONNECTION`) and kills it. Calls start at id 2. Each call's slot is `Waiting`, `Discarding` (handle dropped, `cancel` posted) or `Answered`, and an id is reused only once its last frame is in and its handle gone. Requests, cancels from `Drop` and id allocation happen under one lock into the writer, so a cancel is on the wire before any later request; a request finding nothing queued is written by its caller at once (Unix; Windows writes pipes on the blocking pool, so always through the writer task). The reader never blocks on a call: a full per-call channel (`STREAM_CREDIT + 2`) means the helper overran its credit, a protocol break, as are a frame for no call or JSON that doesn't parse; a break kills the helper. Credit is granted one per batch frame as the driver takes it, only while the call's last frame hasn't arrived. A request whose JSON passes the frame is `INVALID_ARGUMENT` before anything is sent. **A helper that dies** fails every waiting and later call with `CONNECTION_CLOSED` ("The DuckDB helper stopped (signal 9). Reconnect to continue.", or "…broke the protocol…"). **Close**: `close` refuses new calls, posts `close` (calls in flight still get their last frame) and waits 2 s; a helper whose output ended (it took `close` and is checkpointing) is then detached (`HelperChild`, killed on drop by hand unless detached) and left to finish, one whose output is open is killed; dropping the driver kills. A detached helper is kept in `closing.rs` by its database's canonical path (none for `:memory:`), and an open of that path in this process waits for it to exit (polled every 20 ms, at most 25 s, under Core's 30 s connect timeout, then `CONNECTION_ERROR` "DuckDB is still saving this file. Try again in a few seconds."); across processes an open that meets DuckDB's lock conflict is retried every 250 ms for 10 s, then `CONNECTION_ERROR` "DuckDB is still closing this file in another Seaquel process. Try again in a few seconds.". **A file open twice in this process**: each live helper claims its file (`closing::claim`, keyed by `FileKey`: device and inode on Unix, so hard links match, else the canonical path, since std's Windows file index is unstable; a file the open created, after the open, with a WARN by code if that claim loses a race), and an open of a claimed file is refused at once with `CONNECTION_ERROR` "This DuckDB file is already open in another connection. Disconnect it first." (no path); the claim goes when the helper is gone (or handed to the closing list) or the driver is dropped, and from the start of its connection's `close` it is marked closing, so an open of that file waits for it (as for a detached helper, at most 25 s) instead of being refused. `Engine::preflight` (the install check) runs before Core closes anything a reconnect replaces. **Read-only calls** take one of 16 permits (`wire::MAX_READ_ONLY_CALLS`) before they are sent, held in the call's slot until its last frame arrives (a dropped call's included), so the helper's `TOO_MANY_REQUESTS` is only a backstop. **`Driver::closed()`** resolves with the calls' `CONNECTION_CLOSED` error when the helper ends without `close` (a signal, an exit of its own, a protocol break, the wedge) and with `None` after `close`, a detach or a dropped driver. `query` caps at `max_query_rows`; `query_stream` re-batches the helper's chunks into 5,000-row `StreamBatch`es; `execute` has no `last_insert_id`; `query_read_only_with` refuses binds and sends the cap's limit; `explain_read_only` counts statements first and parses with `parse_explain`. Logs: `activity=duckdb.helper` `event=spawn|ready|exit|crash|detach` with statuses, durations, byte counts and codes, never SQL, values, paths, payloads or the helper's stderr. `tests/HELPER.md` lists the helper's limits (a request or a row past the frame) and its failure modes.
  - **The browser driver:**
    - **The bridge** (`src/lib/core/browser/duckdb-bridge.ts`): `connect`, `runQuery`, `startPending`, `pollPending`, `fetchChunk`, `cancel`, `close`, bound as plain functions returning a promise, and each must post its request before it returns (the cancel and `ROLLBACK` a drop sends must reach the worker before the next call). It pings the worker with `getVersion()` once a request has waited 5 s; no answer in 10 s fails every waiting and later request with `DUCKDB_STOPPED` (undone if the ping answers late; never judged while a `runQuery` runs). A worker that answers `undefined` (terminated) is refused at once.
    - **Every statement is a pending query** with streaming on, decoded from Arrow IPC stream chunks in Rust (DuckDB-WASM sends no end marker; `IpcStream` copes), so every call can be cancelled and a drop cancels it. Calls on one connection take turns; a stream releases its turn before its final batch. Each Core connection is one DuckDB-WASM connection on the page's one database: the connect path and `duckdb_config` are ignored, and `restricted` is `NOT_SUPPORTED`.
    - **Binds are written as typed literals** (DuckDB-WASM sends prepared parameters as JSON and can't bind a `bigint`): `seaquel_sql::params::duckdb_bind_literal`, placed only in code as DuckDB's scanner reads it (`?`, `?N`, `$N`), each with a space on both sides. SQL holding a NUL is refused on every path, since DuckDB-WASM silently cuts the statement there.
    - **Differences from the frozen typed-cell expectations**, pinned by the live suite (`engine-duckdb-browser.test.ts`, every typed-cell case through the frozen `tests/fixtures/cells.json`): JSON reads as Text (also in lists and STRUCTs); BIT as Bytes; TIMETZ loses its offset; TIME_NS can't be exported; GEOMETRY doesn't exist without the spatial extension; a negative BIGNUM doesn't bind back; an ENUM column is shown only by a statement that is exactly one SELECT (re-run through `runQuery`, which can't be cancelled and runs the SELECT's side effects twice), and anything else returning one fails with `UNSUPPORTED_TYPE` asking for a cast to VARCHAR; a `DECIMAL(38, 0)` reads as an integer when it fits (1.4.3 sends HUGEINT as that type); `execute` reads `rows_affected` from a lone `Count` column, so a SELECT whose one column is named `Count` reports its value; a statement failing inside a transaction gets DuckDB-WASM's `Execute failed: ` prefix. `arrow_lossless_conversion` isn't set (it is global).
  - **Every driver:** attached catalogs are listed as `catalog.schema`, with a part holding `.` or `"` double-quoted (`"fx.we""ird".main`, or `"a.b"` for a default-catalog schema named `a.b`); `system` and `temp` are left out. Build `"schema"."table"` from a listed schema with `Dialect::quote_schema` in Rust (the CRUD/DDL builders' `_qs`/`_with` variants take it) and `EngineClient.qualifiedTable` in TypeScript, never by quoting the schema as one name. CRUD binds `?`. Edits DuckDB rejects (constraints in `ADD COLUMN`, column changes while the table keeps an index, dropping or retyping a PRIMARY KEY/UNIQUE column or a column before one) come back from `alterTable` as notes; the rules read `isUnique` and `inUniqueConstraint` (any UNIQUE constraint, composite too), which DuckDB's `table_metadata` reports on `SchemaColumn` and the table editor copies. `{{param}}` values are inlined (desktop, web and demo), skipping comments and quoted names.
- **The MSSQL driver runs on one connection**, except `query_read_only`, which opens its own per call (above). A call that doesn't finish (a UI cancel, a dropped request, `RESULT_TOO_LARGE`, a fatal error) closes it, and the next call reconnects. That loses `##global` temp tables, session context, app locks and any transaction opened by hand, which is silently rolled back. Code that changes session state (`SET SHOWPLAN_XML ON`, …) must wrap it in `Session::hold_state()`/`release_state()`; a failure before the matching OFF reconnects, with the same losses.
- **MSSQL statements run through `sp_executesql`**, with or without parameters, so a user's `SET` options and `#temp` tables end with the call and can't leak into introspection or grid edits. `USE` is the exception (it outlives an RPC call), so after a statement mentioning `USE` the driver switches back to the connection's database (`restore_database` in `driver.rs`). Only a parameterless statement that must start a batch (`CREATE VIEW`/`PROCEDURE`/`SCHEMA`, …; `must_start_batch`) and the driver's own BEGIN/COMMIT/ROLLBACK and EXPLAIN `SET … ON/OFF` go as plain batches. A plain EXPLAIN with parameters declares them without values, so its estimates are the generic ones.
- **MySQL/MariaDB TIMESTAMP values are shown as UTC wall-clock time**: sqlx sets the session `time_zone` to `'+00:00'`. Don't add a `timezone` to connection strings; in a zone with DST two instants print the same and a TIMESTAMP key would match the wrong row.
- The parity fixtures in `crates/seaquel-engine-*/tests/fixtures` were recorded from the TS adapters and are frozen; the recorder is gone (git history has it). Change a fixture only when the Rust behaviour is meant to change, and say why.

### Connections in the GUI

- **Every database call goes through `CoreClient`** (`src/lib/core`, `getCoreClient()`, picked per call): `call` for one `CoreRequest`, `stream` for a `db.queryStream` (`StreamEvent`s), a `db.run`/`db.page` (`RunEvent`s) or an `ai.chat` (`AiEvent`s; the `{type: "ai"}` frames, `isStreamFrame`, on all three transports) (an async iterator that always ends with exactly one `done` or `error`; aborting its signal or leaving the loop cancels it, ending with `CANCELLED`), and `events` for `connectionClosed` and `storageChanged`, with `onResubscribed` (each time the event channel starts: `initial` the first time, then after a web reconnect, an `EVENTS_LAGGED` close included, or a desktop re-registration; events sent meanwhile are lost, so a listener reloads what it shows) and `onEventsUnavailable` (`ACCESS_LOST`, `TOO_MANY_TABS`, `EVENTS_UNAVAILABLE`: updates stopped until the next `onResubscribed`). Register both before `events`. The page's write origin is `pageOrigin()` (`src/lib/core/origin.ts`), which is its window id (`src/lib/core/window-id.ts`): the webview label on desktop; on web `win-<uuid>`, kept in `sessionStorage` (`seaquel.windowId`) so a reload keeps it, and claimed on the `seaquel-window-ids` `BroadcastChannel` for 100 ms at load, so a duplicated tab (browsers copy `sessionStorage`) makes a new one; `demo` in the demo. `windowIdReady()` settles it before the first Core call (the storage gate, `httpCoreTransport` and the socket wait for it), and it is sent on every call as `X-Seaquel-Origin` and on the socket as `?origin=`. `TauriCoreClient` uses `core_call`/`core_stream`/`core_events`; the demo's `browserCoreClient` (`src/lib/core/browser/client.ts`) calls the module in the page (see "The demo" below); `HttpCoreClient` uses `/api/rpc` and one `/api/rpc/stream` socket per page, queueing past 16 streams, reconnecting with backoff (0.5 s doubling to 30 s) while something needs the socket, failing running streams with `WS_CLOSED` when it drops, `TOO_MANY_TABS` on 1013 `TOO_MANY_SOCKETS`, and `ACCESS_LOST` on 1008 (no reconnect until the next query). Every request goes through `wellFormedJson` (`encodeCoreRequest`, `$lib/core/well-formed.ts`: `toWellFormed`, with a fallback, on every string, keys included), on every transport, unary calls and the keepalive included, since `serde_json` refuses a lone surrogate; U+FFFD is one UTF-16 unit too, so the cursor stays valid. `CoreProvider` is the one `DatabaseProvider` over it, the demo's included; only the tutorial keeps `DuckDBProvider`.
- **`ConnectionManager` sends targets, never configs.** `add`, `reconnect` and `test` send `{type: "form"}` with the form as typed (an empty SSL mode left out, so the engine's default applies; the wizard's "Default"); `autoReconnect` sends `{type: "saved"}` with only the secrets the client holds (web: the vault; desktop: a session password for a row that doesn't save one; Core reads the keychain). `withHostKeyPrompt` (`src/lib/core/host-key.ts`) wraps connect and test for the SSH trust prompt. A `connectionClosed` event marks the connection disconnected with a toast, except the quiet codes and `CORE_RESTARTED` (only the demo's trap recovery sends it), which `handleConnectionClosed` reconnects at once in the background, showing an error only if that fails (see "Connections lost and reconnected"). The GUI never opens tunnels or edits connection strings to connect.
- **A connection string lives only while it's visible** (`src/lib/utils/connection-string-rules.ts`), because Core connects with the string and ignores the fields it encodes. The details step shows a non-empty string with a Clear button; editing host, port, database, user, SSL mode or a file path, or picking a type, clears it. A paste fills the fields and drops the string unless it holds something they can't (other query parameters, `+ssh`, not a URL). Rows from before phase 5a lose a string that equals what the old builder made of their fields in the `drop_legacy_built_connection_strings` data step, not on load. Core strips every stored string on every write (`strip_connection_string_secrets`: URL, `+ssh` and query passwords, `Password`/`Pwd` pairs, credential-like DuckDB/SQLite options; anything it can't read is stored as `""`); the TypeScript `stripConnectionStringSecrets` it was ported from has had no caller outside its test since the demo's `TsLibrary` went in phase 8.

### Running queries in the GUI

- **The editor runs through a `QueryRunner`** (`src/lib/hooks/database/query-runner/`): `getQueryRunner` gives `CoreQueryRunner` (`db.run`/`db.page`) on every interface, the demo included.

The reruns send no parameter values yet.

A row with `params` (an applied grid edit) shows its values under the SQL, and opening it queues it again as a `{type: "sql", sql, params}` pending change (origin `history`) on the row's connection, focusing that connection's queue and opening the sheet, whatever the pending-changes setting; a row without them opens in an editor tab. Nothing replaces a connection's list, so a failed history load blocks nothing.

### Edits, pending changes and the data tab in the GUI

- **Edits go through an `EditService`** (`src/lib/hooks/database/edit-service/`, `plan`, `apply`, `tablePage`, `duckdbExtension`): `getEditService` gives `CoreEditService` (the edits service above) on every interface, the demo included. `QueryCrudManager`, `PendingChangesManager` and `DataTabManager` are view models over it; none builds, pages or classifies SQL. `$lib/sql`'s `changeSummary` feeds `describePendingChange`.
- **Edits go to the connection their data came from.** A `StatementResult` carries `connectionId` (the saved connection it ran on) and a data tab its own; edits, inserts, deletes, Set default, paging and the pending overlays use it, never the active connection, and look its Core id up after their last await, so a reconnect is followed and a disconnected or removed connection is refused. The sheet and header badge follow `state.pendingConnectionId` (the focused data tab's or result's connection, else the active one).
- **Queued or immediate** is the pending-changes setting (on by default). On, `db.planEdits` fills a queue entry's display fields and the entry keeps the `change` that apply sends back; a repeated edit of one cell replaces the queued one in data and query tabs alike, and a per-cell sequence drops a plan that lands after a later edit of that cell. Off, the edit is `db.applyChanges` with one change.
- **Apply** (`PendingChangesManager.apply`): a full success clears the queue; an atomic failure keeps it whole and marks the failed change; an in-order failure removes the applied prefix. An apply that ends without an answer (`NETWORK_ERROR`, `PROTOCOL_ERROR`, `UNKNOWN`, `CANCELLED`, `WS_CLOSED`, `CONNECTION_CLOSED`, `HTTP_5xx`, or an atomic `WORKSPACE_CLOSED`) is `interrupted` whatever its mode, since an atomic batch may have committed before its reply was lost; so is an outcome whose `failed` change carries `CONNECTION_CLOSED` (an engine out of process lost mid-apply), in any mode, after dropping what Core says ran: the queue is kept and marked (`state.pendingChangesInterrupted`, the sheet's "may be partly applied" banner), and the schema and the connection's data tabs reload. The sheet's confirm dialog lists the destructive statements `$lib/sql` finds and sends `confirmed` only when it listed some, so Core's `confirmRequired` reopens it with Core's list. `NO_ROWS_AFFECTED` is shown with the change's table and key (`stale-edit.ts`, i18n), `TRANSACTION_OPEN` as `edit_transaction_open`. The sheet shows each change's SQL with its values beside it.
- The sidebar's DROP and TRUNCATE send `dropObject`/`truncateTable` intents with `confirmed` (their own dialogs asked); the table editor applies its generated statements as typed changes with `confirmed: true`.
- **The data tab** (`DataTabManager.refresh`) sends a `TableQuery` through `tablePage`; the filter bar's operators are the generated `FilterOp`. One operation per tab: a new refresh, closing the tab or a project switch aborts the previous one.
- **Workflow query nodes are read-only**: `executeReadOnly` on the node's saved connection, at most `WORKFLOW_MAX_ROWS` (10,000; a cut result says so on the node), one `AbortController` per node (re-running or deleting it cancels). A write is refused with `READ_ONLY`.
- **The DuckDB extensions tab** runs on its tab's connection through `db.duckdbExtension`, on desktop and in the demo.

### The library in the GUI

- **Library writes go through a `LibraryService`** (`src/lib/hooks/database/library/`, `getLibrary()`): `CoreLibrary` (the `library` group) on every interface, the demo included, sharing `RustStorageClient`'s write queue so writes land in the order issued. `ConnectionManager`, `LabelManager`, `ProjectManager`, `SavedQueryManager` and `DashboardManager` call it at once, with no debounce. They build no ids, times, versions or prune plans and never compare names; an edit sends a patch of the fields that changed. `add` connects and loads the schema first and then calls `connectionCreate`, since the row's id is Core's; a failed create disconnects and leaves nothing. On web the vault is unlocked before `connectionCreate` (a cancelled unlock saves nothing) and the ciphertext written after it answers; if that write fails (a toast says so), the row keeps `savePassword` with nothing behind it and the next connect asks for the password. Refusals are worded by `library/messages.ts`; `NAME_TAKEN` names the row `takenBy` points at.
- **Other windows' and tabs' changes** (`ChangeFeed`, `LibrarySync`). The feed subscribes once per page, before the first `*List` call. It skips events carrying `pageOrigin()` (the write's answer already updated the page), groups the rest per kind and scope for 100 ms, and `LibrarySync` refetches what each group names and hands it to the manager that shows it. `RowSeqs` keeps the `seq` last applied per row (and per project's version list): a value is applied only when its `n` is higher, a deleted row leaves a tombstone, and a refetch of a row with this page's write in flight waits for that write's answer. A `projectState` event would apply only when it names this window without carrying its origin, which Core's origin check makes impossible, so other windows' view state never reloads here. A new epoch, and every `onResubscribed`, reload every list and setting (one during the first load reloads once after it). So does an `external` event (another process, such as the TUI, wrote the file; phase 7a): any number within 100 ms make one `{reason: "external"}` reload, which no kind subscriber sees and a new epoch or `stop` drops. It reads the repo list without any `git status` (`refreshRepos(ids, {status: false})`), and the managers keep the object a row already shows when it reads back unchanged (`keepSame(current, fromWire(row, current))`, `library/same-data.ts`: a deep comparison where `Date`s compare by time and a key holding `undefined` counts as absent), so a reload a second after every TUI query doesn't re-render the lists. `onEventsUnavailable` shows the header's "Not receiving updates" badge until the channel is back. The demo runs the same feed, but each tab has its own Core, so another tab's writes never arrive (the last tab to write wins).

Kinds without a live view (a project that isn't active, history that isn't shown) are read when next shown.

- **The secrets notice** (`stores/connection-secrets-notice.svelte.ts`, `components/connection-secrets-notice.svelte`): after the connections load, the page reads `connectionStringSecretsNotice`, names those connections once and clears the key when it's dismissed.

- **Settings, view state, dashboards, workflows and chats** (5d-2). `getSettings()` gives a `SettingsService` (`CoreSettings` over the `settings` group), `getUi()` a `UiService` (`CoreUi`; the demo's window is `demo`), and the dashboard, workflow and chat calls are on `LibraryService`, the demo included. ### Connections lost and reconnected

- **`connectionClosed`** marks the connection disconnected with a toast, except `WINDOW_CLOSED` and `CONNECTION_REPLACED` (`QUIET_CLOSE_CODES`: disconnected, no toast) and `CORE_RESTARTED` (reconnected at once).
- **A DuckDB helper that dies** (a DuckDB abort, an OOM kill, `kill -9`) reaches the page as `connectionClosed` with `CONNECTION_CLOSED` and the helper's message (Core's `lost.rs`): the connection shows disconnected with `connection_closed_lost`, and clicking it reconnects through `autoReconnect`, which starts a new helper. Nothing reconnects it on its own, since the query that killed the helper may kill the next one.
- **Core lost a connection the page shows.** On every event-channel restart that isn't the first, `ConnectionManager.checkAlive` asks `db.alive` about the Core ids the page shows (nothing when it shows none). `getCoreClient()` wraps every client in `watchClient` (`$lib/core/connection-watch.ts`): a `db` or `ai` call or stream that fails with `CONNECTION_NOT_FOUND` reports its connection id to `onConnectionNotFound` (`disconnect` and `alive` aren't reported); the failed call isn't retried. Either way `handleConnectionLost` reconnects the connection once, quietly (`reconnectQuietly`), with `connection_closed_lost` as a toast only if that fails; on desktop a DuckDB connection is only marked disconnected with that toast and never reconnected quietly (above). Whichever of the event and the not-found arrives first marks it, so there is one toast.
- **Quiet reconnects** (`CORE_RESTARTED`, `db.alive`, `CONNECTION_NOT_FOUND`) run in the background: `markDisconnected(…, {background: true})` only clears the Core id, the active connection never moves, no tab opens, schema tabs stay unless the reconnect fails, and a Disconnect meanwhile (`userDisconnected`) closes the late connection without a toast. `autoReconnect` and `reconnect` are single-flight per connection id. `reconnect` sends `savedConnectionId`, `autoReconnect` a saved target, and `add` binds its form connection with `db.bindSaved` right after `connectionCreate`.
- **Web vault reads before a reconnect.** `heldSecrets` reads strictly (`getDbPasswordStrict`): a stored password the vault can't decrypt (`VaultEntryUnreadableError`), a failed read or a cancelled unlock means no dial and `autoReconnect` answers false; a vault with no password for the row (trust auth) still connects.

### Cell values

Rows and parameters cross the wire in one format (`crates/seaquel-types/src/value.rs`, `src/lib/values.ts`). Values JavaScript holds exactly are plain JSON. Everything else is tagged as `{"$sq": kind, "v": …}` with kind `bigint`, `float` (NaN/±inf), `decimal`, `bytes` (base64) or `json`. The providers decode tags before any UI code sees a row and encode parameters with `encodeParam`, so the UI gets `bigint`, `Uint8Array` and `SqlDecimal` alongside plain values. Use the helpers in `$lib/values` (`cellKey` for comparing cells, `cellText`, `toNumber`, `jsonReplacer` for `JSON.stringify`, `toStorable` for persisted rows) instead of `String()`/`Number()`/bare `JSON.stringify` on cells.

The workspace builds `serde_json` with `float_roundtrip`, so a double read from the wire has the bits it was written with (`floats_cross_the_wire_bit_for_bit` in `seaquel-types`); without it FLOAT's maximum came back one ULP high and no longer matched its own row. `src-tauri` takes `serde_json` from the workspace too.

The DuckDB drivers read Arrow themselves (`crates/seaquel-engine-duckdb/src/decode.rs`): the remote one from the helper's Arrow IPC frames with the column kinds the helper sends beside them (`kinds::of`, from DuckDB's logical types), the browser one from DuckDB-WASM's Arrow IPC bytes. Temporal types are Text in DuckDB's own format (TIMESTAMPTZ always in UTC, `2024-01-01 12:00:00+00`) and STRUCT/MAP are `Json` with sorted keys. The helper turns on `arrow_lossless_conversion` for its connections; the browser driver can't, and its differences are listed under DuckDB above.

### Metadata storage

- **Read and write metadata only through `getStorage()`** (`$lib/storage`), or `getLibrary()` for the library (above), which returns a `StorageClient`: `RustStorageClient` (`core_call` on desktop, `/api/rpc` on web, the module in the page in the demo, set by `useBrowserCore` through `setBrowserCoreTransport`). Settings go through `getSettings()` and view state through `getUi()` (above). UI code never sends SQL to the metadata database; a new query is a new `seaquel-storage` function and `StorageRequest` variant (or a `library`, `settings`, `ui`, `shared` or `imports` method). `RustStorageClient` puts every write, those groups' included, through one queue so writes land in the order issued; reads skip it, but `windowStateLoad` counts as a write, since a first load copies a row. Every method is classified in `STORAGE_METHOD_KIND`, `SETTINGS_METHOD_KIND`, `UI_METHOD_KIND`, `SHARED_METHOD_KIND` or `IMPORTS_METHOD_KIND`, and Rust's `storage_change` names the event kind of each storage-group write. The storage group now holds only query history, the license, the web vault's state and its credentials (13 methods); the shared repos moved to the `shared` group in 5e.
- **Never save a collection whose load failed** (`load-guard.ts`). A store that replaces a whole collection or record on save marks a failed load, and its saves refuse until a load succeeds: interactive saves throw `NotLoadedError` (show it with `errorToast`), background saves call `skipUnloadedSave` and return. The guards left are the view state (`windowState:<projectId>`, in `WindowStateManager`) and the license. New replace-all saves need the same guard. Query history, the library and the settings need none: history is only appended and flagged (`append`, `setFavorite`), and the rest is written row by row or field by field through Core.
- **The storage gate** (`storage-gate.svelte.ts`): `storageGate.check()` is the first storage call (`settingGet("lastActiveProjectId")`, once the window id has settled), awaited by `UseDatabase.initializeApp` and the `(app)` layout. `LEGACY_STORAGE`, `STORAGE_CORRUPT` and `NO_DATA_DIR` set `storageGate.blocked`, and `(app)/+layout.svelte` shows `storage-error-screen.svelte` instead of the app. Other errors are retried twice, then logged, and the app starts.

## The demo

The demo (`npm run dev:demo`, `npm run build:demo` into `build-demo/`, hosted at `seaquel.app/demo`) is a static build with no backend. Since phase 8 Seaquel Core runs in the page: the `seaquel-browser` module plans and runs queries, applies edits and stores the library, settings, history and view state, as on desktop and web, against DuckDB-WASM, with its metadata file in memory and a snapshot of it in IndexedDB. Every engine and domain fix reaches the demo in the same build; the TypeScript twins (`TsLibrary`, `TsState`, `TsSettings`, `TsUi`, `TsQueryRunner`, `TsEditService`, `TsEngineClient`, `duckdb.ts`, the sql.js storage) are gone, and so is `sql.js`.

- **Which build is the demo.** `isDemo()` is the build constant (`VITE_BUILD_TARGET === "demo"`, or `VITE_IS_DEMO`), not a fallthrough. `isSupportedBuild()` is the desktop app, the web build or the demo build; anything else (`npm run dev` opened in a plain browser) gets the unsupported-build page from the root layout (`unsupported-build.svelte`, which says to run `npm run dev:demo`), and nothing below it mounts: no Core, editor module or storage. Every demo-only import sits behind `import.meta.env.VITE_BUILD_TARGET === "demo"`, which Rollup folds, so `build` and `build-web` contain no `seaquel_browser` file or reference; check the three outputs after touching the demo's start.
- **The start.** `src/routes/+layout.ts` awaits `openDemoCore()` (`$lib/demo/core.ts`) beside the editor module, before anything renders; a failure shows the root's load-error page with the code (`CORE_FAILED`). It starts the demo's DuckDB-WASM (`pageDuckDb`) at the same time without waiting for it: the bridge's `connect` waits (`lazyDuckDb`), and a DuckDB that can't start fails that connect with the reason. Then `startDemo` (`$lib/demo/init.ts`, from `(app)/+layout.svelte`): `whenReady`, `ensureDemoConnection`, `db.connect` with the saved `demo-connection`, the sample SQL (`sample-data.ts`) through `db.execute` one statement at a time, `ConnectionManager.addDemoConnection(stored, coreId)` (no query tab when the project already has one), and `createDemoDashboard`, which creates the sample dashboard only when the project has none of that name (trimmed, lowercased) and otherwise only reruns its widgets. DuckDB is in memory, so the sample tables are seeded again on every load and grid edits to them don't survive a reload; the metadata does.
- **`openBrowserCore`** (`src/lib/core/browser/index.ts`), in order: removes `localStorage["seaquel_db"]` and every `seaquel_db.*` key unread, on every start (the old sql.js file; a stale cached older build can write it again); opens the snapshot store (IndexedDB `seaquel-demo`/`files`/`meta.db`, read within 3 s, `LOAD_TIMEOUT_MS`); opens the module on the snapshot, or on a new file; replays the view-state journal; listens for `pagehide`, `visibilitychange` and traps. `useBrowserCore` makes the opened Core the page's `CoreClient` (`browserCoreClient`) and `RustStorageClient`'s transport. Notices (`STORAGE_UNAVAILABLE`: IndexedDB can't be used or the snapshot can't be read, so Core runs in memory and never writes over that snapshot; `STORAGE_CORRUPT`: the snapshot didn't open, or made Core trap, and was moved to `meta.db.unreadable`, keeping only the newest) are shown once as warning toasts. When `localStorage`/`sessionStorage` throw on access (storage blocked), `app.html` gives the page an in-memory `Storage` first, so the page loads and shows `STORAGE_UNAVAILABLE`.
- **The transport** (`transport.ts`, `BrowserCore`): calls and streams run under a trap guard. Events, stream items and a stream's end reach TypeScript through one mailbox in a later microtask, in order, so nothing calls into the module from inside a callback it is running. A stream ends with exactly one `done` or `error`; aborting it sends `db.cancel`, which cancels the pending query in DuckDB. `onResubscribed` fires `initial` at open; `onEventsUnavailable` never fires.
- **The snapshot.** After each call or stream that moved the commit counter, one macrotask later, the transport takes `snapshot()` and stores it; one save is in flight at a time, a busy snapshot is retried when the next call ends, and the newest wins. `pagehide` and `visibilitychange` to hidden save at once (`flushNow`). Two tabs each load the file when they open and the last to write wins. A private window keeps nothing after it closes. WebKit may drop an IndexedDB write still running when the page unloads, so a write made just before closing the tab (a saved query, a dashboard edit) can be lost there.
- **The view-state journal** (`$lib/storage/view-state-journal.ts`). Chromium runs no task between `beforeunload` and `pagehide`, so a view-state save queued at unload never committed before the snapshot. At `pagehide` the demo writes the active project's pending `ui.windowStateSave` request synchronously to `localStorage["seaquel.demo.pendingViewState"]` (at most 60 KiB, like a keepalive body; `RustStorageClient.saveWindowStateKeepalive` in a demo build), and `openBrowserCore` replays it through Core right after the next open, before the page loads its view state, then forgets it; Core keeps it only if its `rev` is newer. It is the only `localStorage` key the demo writes.
- **A trap is survivable.** The module is `panic = "abort"`. The transport restarts on the panic hook's `onTrap`, on a non-string throw from an export, and on a `RuntimeError` in the window's `error`/`unhandledrejection` events that `__seaquel_isCurrentTrap` says is the live instance's. A restart fails every call in flight with `CORE_RESTARTED`, waits up to 3 s (`SAVE_WAIT_MS`) for saves in flight, closes the dead instance's DuckDB connections, re-instantiates and reopens on the newest stored snapshot, then sends `connectionClosed` (`CORE_RESTARTED`) for each connection and `onResubscribed({initial: false})`; `ConnectionManager` reconnects at once. DuckDB's data survives (it lives in its worker); what's lost is the failed call and anything committed after the last stored snapshot. A trapped open goes the same way. More than 3 restarts in 60 s (`MAX_RESTARTS`, `RESTART_WINDOW_MS`) is fatal: every call fails with `CORE_FAILED` until a reload.
- **Product choices** (`features/index.ts`): no new or edited connections, connection type selector, SSH, MSSQL, file export, updater or shared projects.
- **The assistant** runs on the module's Core like everywhere else, with the visitor's own key for the session. The settings form creates the provider in Core without a key and keeps the key in `sessionKeys()` (page memory only: never storage, the snapshot, IndexedDB, a URL or a log; forgotten on reload or close, and when the provider is removed or the key cleared); `CoreAi` sends it with each call. Model calls go through the page's fetch bridge (`src/lib/core/browser/fetch-bridge.ts`, `makeFetchBridge`), passed as `open`'s fourth argument on the first open and on every restart: `credentials: "omit"`, `referrerPolicy: "no-referrer"`, `cache: "no-store"`, `redirect: "error"`, fixed error text; `abortAll()` runs on a trap restart, so a dead instance's request doesn't keep going. Core adds Anthropic's direct-access header from the page. An OpenAI-compatible server must allow the demo's origin (CORS); the form says so, and says the key goes in the key field, never the URL (which is saved). `session-keys.ts` and the store's demo branches test `import.meta.env.VITE_BUILD_TARGET === "demo"` itself, so `build` and `build-web` don't carry them. A reload mid-turn loses the reply (Core lives in the page); the user's message stays. The tutorial has no assistant. Core runs with no `RunLimits`, `EditLimits`, `LibraryLimits` or `StateLimits`, as on desktop. The "Demo" badge and `demo-connection`'s locked actions are the other `isDemo()` branches.
- **Tests** load the test module from its bytes and DuckDB-WASM's Node build (`src/lib/core/browser/testing/node.ts`; `testing/meta.ts`'s `openModuleCore` for the replays). A test module older than the sources it's built from fails the suite; rerun `npm run wasm:build:browser-test` (or `npm test`, whose `pretest` does). A `RuntimeError` is swallowed only while a test has set `globalThis.__seaquelExpectedTraps`.

### Updating the demo

From the website repo (`seaquel-app/main`), run:

```bash
npm run demo:update
```

It removes `packages/marketing/static/demo`, runs `npm run build:demo` in this repo and copies `build-demo` there as `static/demo`. Commit and deploy the website changes afterward.

## Releasing a New Version

Version format: `YYYY.month.patch` (e.g., `2026.1.1`)

1. Update version in these files:
   - `src-tauri/Cargo.toml`
   - `src-tauri/tauri.conf.json`
   - `Cargo.lock` at the repo root (run `cargo check -p seaquel` after the `Cargo.toml` bump, or edit the `seaquel` entry). `src-tauri` is a workspace member, so the root lockfile is the only one.
   - `package.json`
   - `package-lock.json`

2. Commit: `Bump version to X.Y.Z`

3. Create and push tag:

   ```bash
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

4. GitHub Actions builds macOS (Intel and ARM), Linux (x86_64 and ARM64) and Windows (x86_64 and ARM64), each on a runner of its own architecture. Each `publish-tauri` job, in order: builds and signs `seaquel-duckdb`, notarizes it on macOS, gzips it, pins it ("Pin the DuckDB helper for the app's build": `scripts/release-pin.mjs export` writes the `.gz`'s size and SHA-256 to `$GITHUB_ENV` and a record, `duckdb-pin-<triple>.json`), builds and signs the CLI and TUI and on macOS notarizes them, builds the app with `tauri-action` under `SEAQUEL_DUCKDB_HELPER_REQUIRE_PIN=1` (so an unpinned app fails its build), checks that the binary carries the pin ("Check the app carries the pin", `release-pin.mjs verify-app`, also the copy inside the macOS bundle), and uploads that target's helper `.gz` to the draft ("Upload the DuckDB helper to the draft", `actions/github-script` with `scripts/upload-helper-asset.mjs`, which re-hashes it against the record; no `gh` in the matrix jobs). On macOS the three `codesign` calls use `--options runtime --timestamp`, and `scripts/notarize-macos.sh` (zip, `xcrun notarytool submit --wait`, fail unless `Accepted`, print `notarytool log` otherwise; the `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` secrets tauri-action notarizes the app with) notarizes the helper before its gzip and pin and the CLI and TUI together before their upload, so a copy downloaded in a browser passes Gatekeeper. They are notarized, not stapled (a bare Mach-O can't be): Gatekeeper fetches the ticket online. Notarizing doesn't change a file's bytes. `tauri-action` creates the draft as a **pre-release** titled "NOT CHECKED: Release <tag>". `publish-cli` adds `seaquel-cli-*` and `seaquel-tui-*`. Every app and terminal binary downloads its helper from the release named `v<its version>`, so a release missing a target's `.gz` leaves DuckDB unusable there; the app's first DuckDB connect fails with `ASSET_NOT_FOUND`.

5. **`check-release`** (`needs` every other job, `if: always()`; `scripts/check-release.mjs`) fails unless every job before it succeeded and, for each of the six targets, there is a pin record, the app is pinned, the draft has its helper with the record's size and SHA-256 and its CLI and TUI, and `latest.json` has the tag's version, every target and only assets that are in the draft with a signature. On a pass it renames the draft "Release <tag>"; on a failure "NOT READY (check-release failed): Release <tag>". Only a draft or pre-release is renamed, and a release that isn't a pre-release fails it, so a re-run after promotion fails and leaves the title alone. A re-run of a failed matrix job rebuilds its helper (a new digest), its app with the new pin and replaces the uploaded `.gz`; then re-run `check-release`.

6. **Publish only a draft titled "Release <tag>"** with `check-release` green. The website's update check (`seaquel.app/updates/check/…`, in `seaquel-app`) offers the newest published release that isn't a pre-release, cached for an hour, and checks nothing else, so promotion is the step that reaches users. First publish it as it is, a public pre-release the update check skips, and run the owner's release checks: the jobs' logs, the digests by hand against each job's "Pin" line, `latest.json`, `codesign -d --entitlements -` showing none on the app, CLI and TUI and `disable-library-validation` on the gunzipped helper, notarization (the app's, and `spctl --assess --type execute -vv` printing "source=Notarized Developer ID" on quarantined browser downloads of the CLI, TUI and gunzipped helper), then installing it over the previous release on macOS, Windows and Linux. Then untick "pre-release" and tick "latest".

7. CI's required checks in branch protection are named "DuckDB through the helper (macos-latest)", "DuckDB through the helper (windows-latest)" and "Desktop app (tests, clippy)" (formerly "DuckDB on both drivers (…)" and "Desktop app compiles"); a rule still naming the old ones leaves PRs waiting on checks that never report.
