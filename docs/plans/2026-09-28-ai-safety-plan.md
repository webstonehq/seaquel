# AI Safety Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (or superpowers:executing-plans) to implement this plan task-by-task.

**Goal:** Close the two high-priority AI Follow-ups from phase 2b before phase 3. First, every query the AI runs (the `run_query` tool and dashboard widgets) runs in a mode the database itself enforces, on top of fix 14's token check. Second, each AI tool call is checked against, and runs on, the connection its chat belongs to, and refuses cleanly when that connection is gone or disconnected.

**Architecture:** A new `Driver::query_read_only` in `seaquel-engine`, implemented by each engine with its own mechanism (below). Core exposes it as a `read_only` option on `query_stream`, so an AI query gets the stream registry for free: cancel by query id, `CONNECTION_CLOSED` on disconnect, and the Tauri channel and WebSocket transports that already exist. Core also runs fix 14's `read_only_error` in that mode, so the CLI and MCP server get the same gate later. The TS side gets `DatabaseProvider.selectReadOnly`, and `QueryCrud.executeReadOnly(connectionId, sql, signal)` is the only way AI and dashboard SQL reaches a database.

**Tech Stack:** Rust (sqlx 0.8.6, libsqlite3-sys 0.30.1, duckdb-rs 1.10505 = DuckDB 1.5.5, tiberius 0.12.3), TypeScript/Svelte 5, vitest, the e2e Docker databases. The demo runs DuckDB-WASM 1.32.0 (DuckDB 1.4.3).

**Inputs:** the phase 2b plan's first two Follow-ups, fix 14's stance ("gates statements, not a sandbox") and its execution notes, including the dashboard-widget gate added in the Tasks 9/10 review; the design doc's "Phase 2b cost" recommendation (4–8 h for the first item, under an hour for the second, review fixes at 40%); phase 2's ground rules for live engine tests. The per-engine decisions below come from live probes against the Docker servers, DuckDB 1.5.5 through duckdb-rs, DuckDB 1.4.4 through `@duckdb/node-api`, and DuckDB-WASM's Node build.

## Open questions

Each has a recommendation. The plan is written as if the recommendation is taken; if it isn't, only the named task changes.

**Answered (2026-09-28):** the user took all three recommendations: every dashboard widget runs read-only; the SQLite gate uses SQLite's own parser through a pinned `libsqlite3-sys` with a small unsafe FFI; SQL Server and DuckDB connections show a one-line hint under "Allow all queries", plus a release note.

1. **Should every dashboard widget run read-only, or only the ones the AI wrote?** Widgets have no connection of their own: `executeWidget` runs on whichever connection is active, on first render, on "refresh all" and on auto-refresh, with no human in the loop. Shared dashboards come from a git repo, so a teammate's widget query runs on your connection when you open the dashboard. Tracking which widgets the AI wrote would need a new persisted field, and a user can paste AI SQL into a widget by hand anyway. **Recommendation: every widget run goes through `executeReadOnly`.** A widget that writes fails with a clear error, and so does one that is a DuckDB `PIVOT` statement or more than one statement. If you'd rather keep user widgets read-write, Task 7 adds an `origin: "ai"` field to `DashboardWidget` and only those go read-only.
2. **SQLite: a direct `libsqlite3-sys` dependency and about 40 lines of `unsafe` in the engine crate?** The SQLite gate needs SQLite's own parser to count statements and `sqlite3_stmt_readonly` to catch `VACUUM INTO` (Decision 1). sqlx doesn't expose either, but it hands out the raw handle (`lock_handle().as_raw_handle()`). The alternative is to count statements with `seaquel_sql::scan::split_statements` and block `VACUUM` by token, which puts the gate back on our scanner, the thing phase 2b's reviews bypassed four times. **Recommendation: take the dependency**, pinned to the version sqlx-sqlite locks (`=0.30.1`; it `links = "sqlite3"`, so there can only be one), with the unsafe code in one small module and its own tests.
3. **An in-app hint for the gaps?** The approval card has an "Allow all queries this session" checkbox. **Recommendation: yes, one line under it on SQL Server and DuckDB connections** ("SQL Server has no read-only mode; use a read-only login" / "DuckDB queries can read files and URLs"), one new `messages/en.json` key per engine. The fuller note goes in the release notes (Task 8).

### 2. Where it lives

- **`Driver::query_read_only(&self, sql, params) -> Result<QueryResult, DbError>`**, default `NOT_SUPPORTED`, so an engine that doesn't implement it fails closed. Non-streaming: the AI formats five rows and a widget needs its whole result for the chart, so nothing reads the rows incrementally. It keeps `query()`'s row cap (`max_query_rows()`, 100,000 by default, `RESULT_TOO_LARGE` past it), as the AI's `db_query` path has today.
- **`Core::query_stream(query_id, connection_id, sql, params, QueryOptions { read_only })`.** In read-only mode Core first runs `seaquel_sql::read_only::read_only_error(&sql, engine)`, where the engine comes from the connection's engine id (`mysql` also serves MariaDB; `read_only_error` reads both the same way and refuses any `/*M!` up front). A refusal is `DbError::read_only(READ_ONLY_MESSAGE)`, the exact text the TS shows. Then it drives the driver's future as a one-item stream under the same `take_until(token.cancelled())`, so `cancel_stream`, `disconnect` (`CONNECTION_CLOSED`) and a dropped channel or socket all drop the future. One `Batch`, then `Done`. `seaquel-core` gains a dependency on `seaquel-sql`; Core may depend on anything.
- **Transports.** Tauri's `db_query_stream` gets `read_only: Option<bool>`; the web WebSocket's first frame gets `"read_only": true` (`#[serde(default)]` in `StreamRequest`). `server.js` re-serializes the parsed frame after rewriting `connection_id`, so the field passes through with no change there. Frontend and Rust ship together on both targets (one bundle, one Docker image), so there's no version skew to handle.
- **Not an `EngineRequest`.** An `EngineCall` has no query id, so it can't be cancelled, and it would need its own disconnect handling. `query_stream` already has both.
- **TS.** `DatabaseProvider.selectReadOnly(connectionId, sql, signal?)` returns row objects (deduped column names, as `select` does) and rejects with the stream's error. `QueryCrud.executeReadOnly(connectionId, sql, signal?)` looks the connection up by id, refuses if it's gone or disconnected, runs `readOnlyError(sql, connection.type)` against that same object, then calls the provider. `getAdapter` and `EngineClient` aren't involved: running a query is provider work, as `select` is.

### 3. Cancellation

AI queries can't be cancelled today. `runAndFormat` calls `provider.select`, a single `db_query` invoke with no signal: Stop ends the tool loop, and the query runs on. The read-only path takes the AI's `AbortSignal` down to `db_cancel_stream` (desktop) or a closed WebSocket (web). What that stops depends on the engine, as for the editor's streams: DuckDB is interrupted; SQL Server closes the connection and the server aborts; Postgres and MySQL drop the connection, and the server may keep running the statement until it next writes to the socket (sqlx has no cancel request; Follow-ups).

Stop during an approval also leaves a promise hanging today: `cancelAIStream` clears `pendingApproval` but never calls `deny`, so `handleToolCall` awaits forever. The approval promise resolves with "Query cancelled" when the signal aborts (Task 7).

### 4. Connection state

The read-only path never returns a connection it changed to anyone else. Postgres and MySQL take one from the pool and close it; SQLite opens its own and closes it; DuckDB clones a fresh connection for every call and drops it afterwards, so what a query does to its session ends with the call (on a shared clone, `enable_profiling()` inside a SELECT outlived the rollback); state global to the database, such as `enable_logging()`, is left to Core's token check (Decision 1). DuckDB's read-only session also doesn't follow the user's: `SET search_path`, `USE`, `SET TimeZone`, temp tables and temp macros and `SET VARIABLE` from the editor don't apply to AI queries or widgets (global settings, persistent macros and attached databases do); SQL Server opens a connection of its own for every call and drops it afterwards (as built, Task 5; the plan's held session under `hold_state` would have kept session context, app locks and global cursors), so the user's held session, its `##temp` tables and a transaction opened by hand on it are never touched. `PRAGMA query_only` is only ever set on the SQLite path's own connection. MySQL's `time_zone = '+00:00'` comes with the pooled connection (checked: a read-only connection reported `+00:00`), so TIMESTAMP values print as they do in the editor.

### 5. Error reporting

Drivers map their engine's read-only refusal to code `READ_ONLY` and keep the database's message: Postgres SQLSTATE 25006, MySQL/MariaDB 1792, SQLite code 8 and the gate's own refusals ("one statement at a time", "writes to the database"), DuckDB "Expected a single SELECT statement" and "transaction is launched in read-only mode", SQL Server's escape ("The query ended the read-only transaction; what it changed after that was committed"). The AI tool returns it to the model as today, `Query error: <message>`; a widget shows it as its error.

### 6. "Allow all queries"

Read from the code: `aiAllowAllQueries` only skips the per-query approval in `handleToolCall`. `readOnlyError` runs before the branch, so the token check applies either way, and the read-only path will too. The dashboard tools never ask for approval, with or without it. It is reset when the active connection changes (`onActiveConnectionChanged`), and it's read once, when the message is sent: ticking the checkbox during a message takes effect from the next message. None of that changes.

### 7. Binding tool calls to a connection

- **A chat already belongs to a connection** (`AIChat.connectionId`, the active connection when the chat was made). `_dispatchToAI` resolves the chat's connection and passes `connection: { id, type, name }` and a `runQuery(sql, signal)` bound to that id, replacing `databaseType` and `executeQuery` in `SendAIMessageParams`. The system prompt and the token check use `connection.type`.
- **The tool call runs on that id**, whatever is active by then, through `executeReadOnly`, which looks it up again (it survives `reconnect()`, which replaces the object) and refuses with "The connection "X" was removed" or "… is disconnected; reconnect it and try again" (widgets show the same message). The check runs again against the looked-up connection, so a connection whose type was edited can't be checked under the old one.
- **Approval.** The card already shows the captured connection name. Approving after switching connections runs on the chat's connection, not the active one; today it runs on the active one.
- **Dashboard tools.** A widget has no connection; it renders against the active one. `add_widget` and `update_widget` refuse when the chat's connection isn't the active one ("The active connection is Y; switch back to X to change this dashboard"), so a query checked for one engine is never stored for another. The widget's first run and every later run go through `executeReadOnly` on the connection that runs it, which checks it against that connection (open question 1).

### 8. Estimates

The design doc budgeted 4–8 h for the first item and under an hour for the second. The probes found more than that budget assumed: MySQL needs a session setting, not a transaction; SQLite needs its own parser through FFI; DuckDB needs the `query()` wrapper and its own connection; SQL Server needs escape detection; cancellation doesn't exist on the AI path yet; and widgets have to move too. The task rows add up to ~7.5–11 h, plus review fixes at 40% (the design doc's rate for code that decides what SQL runs): **~10.5–15.5 h**. Phase 2b's first passes ran at about half their estimate; if that holds, expect ~7–10 h logged. The binding alone is still about an hour.

## User-facing note

For the release notes and the website's AI page, and shortened for the in-app hint (open question 3). Updated in Task 8 to match what was built:

> **AI queries run read-only.** Seaquel checks every query the AI runs, then runs it in a read-only mode the database enforces: a read-only transaction on PostgreSQL, a read-only session and transaction on MySQL and MariaDB, a separate read-only connection on SQLite that runs a single statement and can't change settings, and a single read-only SELECT on DuckDB. Dashboard widgets run the same way. Two gaps remain:
>
> - **SQL Server has no read-only mode.** Seaquel runs each AI query on its own connection, in a transaction it always rolls back. A single `COMMIT` or `ROLLBACK` in the query no longer gets out of it. A query that commits more than once can still change data: Seaquel reports it as an error, but the change stays. Taking a value from a sequence also sticks. For full protection, connect with a login that can only read.
> - **DuckDB can read files and URLs.** A query such as `read_csv('https://…')` can send data to a web server, and a query that needs an extension can make DuckDB download it. There's no way to switch either off for a single query. Seaquel does refuse the DuckDB functions that act outside the query, such as `enable_logging`, `checkpoint` and `mysql_execute`.
>
> On any database, a login that can only read is the strongest guard: it also stops file writes (`SELECT … INTO OUTFILE` on MySQL) and server settings that a read-only transaction allows.

**Review:**

- `hold_state` is set before the user's request, so every failure path, and a drop at any await, leaves the connection dirty and closed.
- A server that rolled back by itself (`XACT_ABORT ON` and an error) isn't reported as an escape: the user's request failed with its own error, not 266, and nothing was committed.

**As built (replaces steps 1–4).** The steps above ran on the held session. They changed because a probe found that `SET CONTEXT_INFO`, `sp_set_session_context`, a session app lock and a `GLOBAL` cursor all survive both ROLLBACK and the end of `sp_executesql`. Closing the held session after every call would have dropped the user's `##temp` tables, session context and app locks on every widget refresh, so each call now runs on a connection of its own:

- **Its own connection.** `query_read_only` opens a new tiberius client from the stored `ConnectConfig`, with the same connect timeouts and `SET NOCOUNT OFF`, and always drops it afterwards. The user's held session is never touched. A transaction opened by hand on it is left alone and no longer refused. The AI query doesn't see the user's uncommitted changes, and under READ COMMITTED it waits on rows that transaction has locked, for up to the 10 s lock timeout (error 1222). At most 4 read-only calls run at once (`READ_ONLY_CONNECTIONS`, a semaphore); the rest wait for a slot. The whole call, waiting included, is cancelled after 60 s (`TIMEOUT`), which frees its slot and drops its client. Dropping the future drops the client, and the server aborts and rolls back. A drop mid-call is logged at debug, not as a warning.
- **Begin batch.** `SET XACT_ABORT OFF; SET LOCK_TIMEOUT 10000; SET IMPLICIT_TRANSACTIONS ON; BEGIN TRANSACTION; IF @@TRANCOUNT < 2 BEGIN TRANSACTION; CREATE TABLE #seaquel_read_only …; SELECT CURRENT_TRANSACTION_ID(), @@TRANCOUNT`. The transaction is two deep, so one COMMIT only unnests it. With implicit transactions on, a write after the query ended the transaction opens a new one, which is rolled back. The `#temp` marker is gone once the transaction was rolled back; only the deadlock rule below reads it. `XACT_ABORT OFF` is the default, whatever the server's user options say. Needs SQL Server 2016+ (`CURRENT_TRANSACTION_ID`).
- **The query.** `BEGIN TRY EXEC sp_executesql @sql, @decl, @P1 = @P1, … END TRY BEGIN CATCH … END CATCH`, itself one `sp_executesql` RPC (`Keep::First`). The user's SQL (after `inline_nulls`) is a parameter of the inner call, never spliced into the wrapper, and the bound parameters are forwarded under the types tiberius declares for them (`bind::declared_type`). The CATCH decides what an error means:
  - The same transaction still open (`CURRENT_TRANSACTION_ID()` against the id the begin batch read): the query's own error, re-raised with `THROW;`, so its number and message stay. That covers the batch-aborting errors that doom the transaction (245 conversions and `UNION` mismatches, 241 dates, 9400 XML, 13609 JSON: XACT_STATE -1, trancount 2) and `SET XACT_ABORT ON` in the query, which only dooms it inside TRY.
  - A deadlock victim (1205) with the marker gone: re-raised as well, since the server rolled back.
  - Anything else (another transaction, or none): the query ended the transaction and then failed. `THROW 59173` with `Error <n>: <message>`, which the driver returns as the `READ_ONLY` escape with that error.
  - (Review: option (a) reported every error after an ended transaction as an escape, which turned the AI's most common mistakes into escapes, because those errors roll the transaction back even with `XACT_ABORT OFF`. This is option (b), checked live.)
  - Past the row cap the rest of the response is read and dropped, so the end batch still runs and an escape followed by `RESULT_TOO_LARGE` is still reported.
- **End batch.** `SELECT @@TRANCOUNT, CURRENT_TRANSACTION_ID(); IF @@TRANCOUNT > 0 ROLLBACK`. The server raises no 266 while implicit transactions are on, so detection compares the transaction id and depth:
  - The CATCH's escape signal: `READ_ONLY` escape with the query's error.
  - Same id, different depth (or a 266): `READ_ONLY`, "tried to commit, roll back or open a transaction … nothing was committed".
  - Any other server error: the query's own, as the CATCH decided. A doomed transaction is rolled back when the request ends, so the end state doesn't decide here.
  - Same id and depth: the query's result, or `RESULT_TOO_LARGE`.
  - Ended (another transaction id, or depth 0) after rows: `READ_ONLY` escape. After `RESULT_TOO_LARGE`: the escape with that error.
- **Results.** `COMMIT; DELETE`, `ROLLBACK; INSERT`, `COMMIT; COMMIT; DELETE` and a procedure that commits once now leave no trace. `DELETE …; COMMIT; COMMIT` and a procedure that commits until `@@TRANCOUNT` is 0 still commit, and are reported as escapes. `ROLLBACK; SET IMPLICIT_TRANSACTIONS OFF; DELETE …; <error>` and `DELETE …; COMMIT; COMMIT; DROP TABLE #seaquel_read_only; <error>` commit and are reported as escapes. Ordinary failing queries (`CONVERT(INT, 'x')`, `UNION` mismatches, bad dates, XML and JSON, syntax errors, unknown tables, `SET XACT_ABORT ON; …; SELECT 1/0`) come back as `QUERY_ERROR` with their own error. `NEXT VALUE FOR` advances the sequence. `known_gaps_behave_as_documented` asserts every one of these.
- **Further known gaps (review).**
  - Not blocked by fix 14: an existing UDF that calls an extended stored procedure runs it; locking hints (`WITH (TABLOCKX)`, `UPDLOCK`, `HOLDLOCK`) block other sessions for as long as the query runs, a DoS bounded by the 60 s call timeout; `NOLOCK`/`READ UNCOMMITTED` reads see uncommitted data (acceptable: it's a read).
  - Blocked by fix 14, but not stopped by the driver if called directly: `DBCC FREEPROCCACHE` and `DBCC DROPCLEANBUFFERS`, `CHECKPOINT` and `UPDATE STATISTICS` (not undone by the rollback), `RECEIVE` that disables a queue through poison-message handling, `EXEC … AT` a linked server when the call isn't promoted to a distributed transaction.
  - One login per call: a big dashboard on Azure SQL may hit login throttling. The cap of 4 connections at once limits it.
  - An escape followed by a query slow enough to reach the 60 s call timeout commits and returns `TIMEOUT`, undetected: the call is dropped before the end batch. Fix 14 blocks the COMMIT it needs.
  - An escape followed by a column tiberius can't decode (`SELECT CAST(1 AS SQL_VARIANT)`) commits and returns `UNSUPPORTED_TYPE`, unreported: the panic leaves the response unread, so no end batch runs. Needs no special privilege. Fix 14 blocks the COMMIT or ROLLBACK it needs.
  - An escape followed by a fatal error (`RAISERROR('x', 20, 1) WITH LOG`, sysadmin only) commits and returns `QUERY_ERROR`, unreported: the server closes the connection. Fix 14 blocks the COMMIT or ROLLBACK it needs.
  - Past the row cap, draining a huge result keeps one client and one core busy until the 60 s timeout.

**Checkpoint.**

## Execution notes (2026-09-28)

The plan was executed task by task, Tasks 2–7 in parallel after Task 1, with a review after each and a round or two of review fixes on Tasks 2–5. Where the result departs from the text above, the repo is authoritative; the Decisions table and Task 5 were updated as built during the reviews. Per-task times and surprises are in `2026-09-28-ai-safety-effort.md`. The measured cost is in the design doc ("AI safety cost").

**What went differently from the plan**

- **MySQL/MariaDB needs both a session setting and a read-only transaction** (Task 2). The session setting alone let a `CALL` write: a procedure that runs `SET SESSION transaction_read_only = 0` before its INSERT wrote on both servers, because a procedure runs each statement as its own. `START TRANSACTION READ ONLY` on top stops it. The review changed `SET SESSION transaction_read_only = 1` to `SET SESSION TRANSACTION READ ONLY`, which MariaDB 10.x and MySQL before 5.7.20 accept too.
- **Postgres rolls back only after a successful query** (Task 2 review). After an error or the row cap, `ROLLBACK` first read the rest of the result (4.6 s against 0.17 s on 20M rows); closing the connection aborts the transaction instead. sqlx's error text carries no SQLSTATE, so a small `Executor` wrapper notes 25006 for `fetch_capped`.
- **SQLite got an authorizer and a NUL refusal** (Task 3 and its review). `sqlite3_stmt_readonly` is true for process-wide PRAGMAs, and `PRAGMA hard_heap_limit` crashed the process, so the read-only connection denies every PRAGMA but a short allowlist, and `ATTACH`/`DETACH`. FTS5 prepares `data_version` and FTS3/4 `page_size` internally, so both are on the list; without them every FTS5 table was unreadable. A NUL byte in SQL text makes sqlx 0.8.6 loop forever, on every path, not just this one, so `SqliteDriver` wraps the macro's driver and refuses it on every entry point. A progress handler interrupts a dropped query, which otherwise kept running and holding its locks.
- **DuckDB clones a connection per call and blocks 18 functions** (Task 4 reviews). One shared clone let `enable_profiling()` outlive the rollback and rewrite its file after every later call. `enable_logging()` is global to the database, and the attached-database scanners (`mysql_execute`, `postgres_execute`, …) run their SQL outside DuckDB's read-only transaction, so Core's token check refuses those on DuckDB (`BLOCKED_FUNCTIONS_DUCKDB`), found by sweeping `duckdb_functions()` with every autoloadable extension loaded (1,389 names). `query(?)` got a `LIMIT` one past the row cap. `arrow_lossless_conversion` is global, so the clones decode as the main connection does.
- **SQL Server runs AI queries on connections of their own** (Task 5, replacing its steps 1–4; see "As built" there). `SET CONTEXT_INFO`, session context, app locks and global cursors survive both ROLLBACK and `sp_executesql`, so the held session couldn't be reused. The transaction is two deep with implicit transactions on, so a single `COMMIT` or `ROLLBACK` no longer escapes, and SQL Server never raises 266 in that mode, so escapes are detected from the transaction id and depth. The first review added `XACT_ABORT OFF`, a 10 s lock timeout, a 60 s call timeout and draining past the row cap; the second replaced "any error after the transaction ended is an escape" with the TRY/CATCH rule, since conversion and date errors roll the transaction back by themselves. Needs SQL Server 2016+.
- **`server.js` did need a change** (Task 6). It flushed a buffered first frame to Rust after the browser had gone. The WebSocket handler also only noticed a closed socket on its next send, and a read-only query sends nothing until it's done, so a web Stop never reached it; it now `select!`s on the socket.
- **The demo can't interrupt a read-only query** (Task 6). DuckDB-WASM 1.32 runs a prepared statement to completion in its worker, and `cancelSent` only interrupts `conn.send`. Stop rejects at once and the query finishes in the background (Follow-ups).
- **Two more widget paths** (Task 7). The widget editor's preview and the version diff view also ran widget SQL through `executeRaw`; both now go through `DashboardManager.runWidgetQuery`.
- **DuckDB names repeated columns `a`, `a_1`** through `query()`, where the editor's path gives `a`, `a_2`. A widget saved before this phase whose chart names `a_2` needs editing (release notes).

**Decisions made during execution**

- A transaction opened by hand on SQL Server is left alone and no longer refuses AI queries; they don't see its uncommitted changes and wait up to 10 s on its locks.
- DuckDB's read-only session doesn't follow the user's (`SET search_path`, `USE`, temp objects, `SET VARIABLE`). Accepted: a fresh connection is what contains `enable_profiling()`.
- `checkpoint()` is blocked on DuckDB even though it changes no data, since it writes the file from a read-only call.
- MotherDuck's `md_*` and DuckLake's maintenance functions weren't probed (they need that catalog attached); left open for the owner (Follow-ups).

**Final review.** The review of the whole phase came back ready, with six minor items, all handled in Task 8: the `Driver::query_read_only` doc comment and Decisions 1 and 4 still described SQL Server's held session (fixed), CLAUDE.md's "one connection" rule for MSSQL needed the read-only exception (added), SQL Server logged the model's own errors as `error!` (now `debug!`, with `warn!` for a detected escape and `error!` for timeouts and connection failures), and two new Follow-ups: the demo's missing row cap and "Allow all" carrying over to another connection.

**Status (Task 8):** done. CLAUDE.md, the user-facing note, the release notes below, the design doc's "AI safety cost" and the effort log's totals are written. The full check list result is in the Task 8 report. The manual checks above are not run yet.

**Release notes**

- **AI queries run read-only.** The user-facing note above, in full.
- **AI queries can be stopped.** Stop now cancels a running AI query, not just the reply. DuckDB and SQL Server stop at once; on PostgreSQL and MySQL the connection is dropped and the server may finish the statement; in the demo the query finishes in the background.
- **Approving after switching connections** runs the query on the chat's connection, not the active one. If that connection was removed or disconnected, the AI is told so and nothing runs.
- **Dashboard widgets run read-only**, on every refresh, in the editor's preview and in the version diff. A widget whose query writes, runs more than one statement, or doesn't start with `SELECT` or `WITH` (a DuckDB `PIVOT`, `FROM t` or `SUMMARIZE`) now shows an error. On DuckDB, a repeated column name now comes back as `a_1` instead of `a_2`; a chart that names `a_2` needs editing.

- **Shared dashboards from git still run on open.** Their widgets now run read-only, but nobody approves them first, and on DuckDB a widget can still reach the network (`read_csv('https://…')`).
- **SQL Server:** AI queries and widgets run on a connection of their own, so they no longer touch the editor's session or a transaction opened there. They need SQL Server 2016 or later.
- **SQLite:** SQL containing a NUL byte is refused with an error. It used to hang the connection it ran on, and a few such queries hung the database until Seaquel restarted.

## Follow-ups (not in this phase)

- **A separate login for AI queries.** Per connection, optional credentials used only by the read-only path. The only full fix on SQL Server, and it closes the file-write and `SET GLOBAL` gaps on the others.
- **DuckDB egress.** For file databases, the AI path could open its own DuckDB instance with `enable_external_access = false`. A second instance on the same file opened in-process with `@duckdb/node-api`, but consistency with the writer wasn't checked, and it would also stop views over CSV or Parquet files from working for the AI.
- **DuckDB extension autoinstall.** A plain SELECT autoinstalls known extensions it needs (icu for a time zone, avro, iceberg, sqlite_scanner and others), a download and a write into the extension directory. One option: build duckdb-rs with the static `json`, `parquet` and `icu` features and set `autoinstall_known_extensions = false`, which the editor would then also lose for the rest. The user's call.
- **MotherDuck `md_*` and DuckLake maintenance functions (open, the owner's call).** The `duckdb_functions()` sweep listed them, but they need a MotherDuck or DuckLake catalog attached, so what they do from a read-only call wasn't probed. Either block `md_` and the DuckLake maintenance names on DuckDB without probing (the check already blocks by prefix, `BLOCKED_FUNCTION_PREFIXES`; the cost is refusing the ones that only read), or probe them with a MotherDuck account and a DuckLake catalog first and block only what writes or reaches outside the query.
- **Fetch only a sample for the AI.** `run_query` shows the model five rows but fetches up to 100,000, and fails past that. A row limit in `QueryOptions` would let the driver stop early.
- **Server-side cancel on Postgres and MySQL.** sqlx doesn't send a cancel request, so a dropped query can keep running until it next writes to the socket.
- **Report the NUL-byte hang to sqlx upstream.** In sqlx-sqlite 0.8.6 SQL text with a NUL byte makes `VirtualStatement` loop forever on SQLite's zero-length tail, pinning a worker thread and its pooled connection (a pool's worth hung the database for good). The SQLite driver now refuses `\0` on every entry point (Task 3 review); the fix belongs in sqlx.
- **Confirm before the first run of a dashboard loaded from git.** Its widgets run read-only, but they run on open without anyone approving them; on DuckDB that includes network egress.
- **Widgets that store their connection.** Today a widget renders against whatever is active; storing a connection id would make a dashboard mean the same thing after a switch.
- **A cancel that arrives before its stream (desktop).** `db_cancel_stream` can reach Core before `db_query_stream` has registered the stream; the cancel is then ignored and the query runs to completion. Older than this phase, and harmless for read-only queries.
- **Interrupt the demo's read-only query.** DuckDB-WASM runs a prepared statement to completion in its worker, so Stop rejects at once but the query finishes in the background. Reading `send()` results in chunks, which `cancelSent` can interrupt, is one way to stop it.
- **A row cap in the demo.** `selectReadOnlyOn` (`duckdb-provider.ts`) runs `SELECT * FROM query(?)` with no `LIMIT`, where native DuckDB stops at `max_query_rows()` and returns `RESULT_TOO_LARGE`. The demo's data is small, but `range(1e9)` would materialize in the browser. `LIMIT 100001` and the same error would match native.
- **"Allow all" can carry over to another connection.** Ticking it on an approval card sets a session-wide flag that is only reset when the active connection changes. If the card's chat isn't on the active connection, the flag still applies to every chat, the active connection's included, until the active connection changes; the user ticked it for another one. Unlikely (approving from a chat on another connection), but the flag should belong to the chat's connection.
- **Mark tool errors as errors.** Refusals reach the model as plain tool text (`Query error: …`); Anthropic's `is_error` and the OpenAI equivalent would say so explicitly.
