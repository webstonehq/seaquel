**Goal:** the desktop app stops linking DuckDB. Every native interface (desktop, TUI, CLI/MCP) then reaches DuckDB the same way: the remote driver and a `seaquel-duckdb` helper process, version-matched and downloaded once into the folder the terminal binaries already use. The first DuckDB connect in the GUI asks, downloads about 11.5 MB with progress, and connects. The installer and every update get about 11 MB smaller. A DuckDB crash no longer takes the app down. The demo keeps its browser driver over DuckDB-WASM, and web keeps refusing DuckDB.

**Architecture:**
- **`desktop_core`** registers DuckDB the way `seaquel-terminal` does: `with_plugins(|id| id != "duckdb").duckdb_helper(DuckdbHelper { dir: <data_local_dir>/<identifier>/bin/duckdb, version })`. `src-tauri`'s Core dependency drops its default features and names four engines, so `libduckdb-sys` leaves the app's tree. CI checks that, as it does for the terminal binaries.
- **One Core installs for everything.** The app's main Core has the locator, so the GUI's dialog, "Install Command Line Tool…" and the MCP settings panel all use it. `cli_download.rs`'s second Core goes.
- **Install from the GUI** goes through desktop-only Tauri commands beside `cli_info`/`install_cli` (Q5): status and size, an install with progress over a `Channel`, a cancel, and an install from a file the user picked.
- **The dialog** is one global component, opened by a `withDuckdbHelper` wrapper around `ConnectionManager.connectCore` and `test`, the same shape as `withHostKeyPrompt`. The pending connect waits on the dialog and is sent again unchanged after the install (Q4). Decision 10 of the helper plan holds: the download happens between two connects, never inside `CONNECT_TIMEOUT`.
- **The digest is built into the app** (Q1): the release job already builds and gzips the helper before `tauri-action` builds the app, on the same runner. It passes the `.gz`'s SHA-256 and size into the app's build, so the app downloads straight from the release's download URL and checks against a value inside its own signed binary. No GitHub API call, no API rate limit, and the offline file picker needs no hash typed in.
- **GUI fixes the move needs** (Decisions 5–8): read-only calls past the helper's 16 wait instead of failing (dashboards run every widget at once); a second open of a file this process already has open is refused at once in plain words; Core sends the reserved `ConnectionClosed { code: CONNECTION_CLOSED }` when a helper dies, which the GUI already handles; a webview reload closes that webview's connections.
- **The native driver goes in this plan** (Q7 A). The native `Engine`, its `Driver` and its `Value` sinks are deleted, with Core's `engine-duckdb` feature. The engine crate keeps only what the helper runs (the session code, the interrupt guard and the column kinds) under `helper`, and the client under `remote` (Decision 18). Every DuckDB suite runs through the helper on macOS, Windows and Linux (Q8). There is no fallback build; "Risks" says what covers that.

**Tech stack:** Rust (`src-tauri`, `seaquel-core`, `seaquel-engine-duckdb`, `seaquel-http`), TypeScript/Svelte 5 (`ConnectionManager`, a store and a dialog, `$lib/api/tauri.ts`), paraglide messages in six locales, GitHub Actions (`ci.yml`, `release.yml`). No new crates.

## What the code shows

### Where the app gets DuckDB today

1. **`src-tauri` takes Core's default features** (`src-tauri/Cargo.toml:33`), and `engine-duckdb`, the native driver, is one of them (`crates/seaquel-core/Cargo.toml:8`, `:14`). `desktop_core` registers every compiled engine with `with_default_plugins()` (`src-tauri/src/lib.rs:64-82`, the call at `:69`), which is `with_plugins(|_| true)` over `compiled_engines()` (`crates/seaquel-core/src/lib.rs:727-761`, DuckDB at `:758-759`). It is built before Tauri's `setup` runs, in `.manage(desktop_core(…))` (`lib.rs:978`), so it doesn't know the app's identifier yet.
2. **The app already links the remote client and the download.** Since the helper plan's Task 8, `src-tauri` turns on `duckdb-helper-install` (`Cargo.toml:33`, comment `:28-32`), which brings `engine-duckdb-remote`, `seaquel-http`'s `release_asset`, arrow-ipc and reqwest. Moving the app adds no dependency; it only removes `libduckdb-sys`.
3. **Nothing else in `src-tauri` names DuckDB** except the CLI's helper install (`cli_download.rs:236-345`, `cli_install.rs:410-420`, `cli_info.rs:30-75`, `:154`) and the drag-and-drop extension list (`lib.rs:1022`, `"duckdb"` among the extensions the page's file drop handles).
4. **`cli_download.rs` builds a second Core** for the CLI's helper: `helper_core` is `with_plugins(|_| false).duckdb_helper(…)` (`cli_download.rs:250-264`), used by `duckdb_helper_status` (`:267-270`) and `install_duckdb_helper`, which runs on a current-thread runtime of its own (`:309-323`). The folder is `seaquel_core::storage::data_local_dir(identifier)` + `bin/duckdb` (`:242-246`), so it already follows `SEAQUEL_DATA_DIR`. The comment at `:12-14` says the second Core exists because the main one registers native `duckdb`. Once the main Core has the locator, the second Core has no reason to exist, and one Core means one install lock (`duckdb_helper_installing`, `crates/seaquel-core/src/lib.rs:366-367`) for the dialog, the CLI flow and the settings panel.
5. **Identifiers.** The app's data dir and the CLI's helper folder use `app.config().identifier` (`lib.rs:1081-1084`, `cli_info.rs:154`): `app.seaquel.desktop` from `tauri.conf.json:5`, and `app.seaquel.desktop.dev` only under `npm run tauri:dev`, which passes `--config '{"identifier":"app.seaquel.desktop.dev"}'` (`package.json:46`). The terminal binaries use `.dev` in every debug build (`crates/seaquel-terminal/src/core.rs:10-14`). So a plain `npm run tauri dev` puts the app on the real `app.seaquel.desktop` folders while debug terminal binaries look under `.dev`. Today `cli_download::debug_helper` (`:275-281`) then installs a 113 MB debug helper into the user's real `bin/duckdb/<version>/`, where a released TUI of the same version would run it. The same rule will apply to the GUI's install unless it changes (Decision 3).

### What the measurements say about size

6. **The installed 2026.9.2 app binary** (`/Applications/Seaquel.app/Contents/MacOS/seaquel`, arm64, CI's release profile, not stripped) is 83,361,696 bytes, 29,520,921 bytes gzip -9. Of its 47.0 MB `__text`, 26.6 MB are functions in DuckDB's C++ namespaces (summed from `nm -n -m` address gaps). The helper, which is DuckDB plus about 1 MB of Rust, is 34,691,328 bytes stripped and 11,503,115 gzip (helper plan, Checkpoint H-2). Taking DuckDB out of the TUI took 33.9 MB raw and 11.1 MB gzip off it (50.12 → 16.21 MB, helper plan S8).
7. **Estimate for the app:** about 50 MB raw and 18.5 MB gzip (−33 MB, −11 MB), with nothing added, since the remote client is already in (item 2). Every updater artifact (`.app.tar.gz`, AppImage, NSIS and MSI) and every installer (DMG, deb, rpm) carries the binary compressed, so each shrinks by about 11 MB. Task 1 measures it. Separately, the binary keeps its symbols (19.9 MB of `__LINKEDIT`); stripping is a follow-up, not this plan.
8. **Build time:** `release.yml` compiles DuckDB twice per target today, once for the app (`tauri-action`, `:201-226`) and once for the helper (`:170-172`). After the move only the helper compiles it. CI's `desktop` job (`ci.yml:428-444`, `cargo check -p seaquel`) also runs `libduckdb-sys`'s build script today, so it gets much faster.

### Every GUI path that touches a DuckDB connection

9. **Connects all go through `ConnectionManager.connectCore`** (`src/lib/hooks/database/connection-manager.svelte.ts:465-475`), which wraps `provider.connect` in `withHostKeyPrompt` (`src/lib/core/host-key.ts:34-48`): `add` (`:600`) from the wizard and the file drop; `reconnect`/`connectExisting` (`:800-940`, `connectExisting` at `:847`) from the connection tab; `autoReconnect` (`:1191-1230`) from the sidebar (`components/sidebar/manage/connections.svelte:78-101`), the connection selector, the command palette, the empty-state cards and the getting-started tab, each of which opens the connection's tab when it answers `false`; and the quiet background reconnects (`reconnectQuietly`, `:553-565`). `test` (`:1031-1040`) is the only connect that doesn't go through `connectCore`. Nothing connects at startup.
10. **The file drop is a DuckDB path for people who never chose DuckDB.** Dropping a CSV, Parquet, JSON or Excel file onto the window creates or reconnects an in-memory "Quick Query (DuckDB)" connection and runs `read_csv(…)` on it (`src/lib/services/file-drop.svelte.ts:42-77`, `:79-100`); dropping a `.duckdb` file adds a connection to it (`:101-118`). So the dialog can appear right after a drag and drop.
11. **The wizard** picks a file with the Tauri dialog (`components/connection-wizard/wizard-step-details.svelte:99-121`) or `:memory:` (`:124-130`); the path goes to Core as typed. The connection tab offers "create" on `FILE_NOT_FOUND` for SQLite only (`components/connection-tab-view.svelte:228-232`). The helper answers `FILE_NOT_FOUND` as natively (helper plan, Task 3 notes), after the install check, so a missing helper and a missing file are asked in that order.
12. **Everything after the connect is Core's** and runs unchanged on the remote driver: the editor's runs and pages (`db.run`/`db.page`), the data tab (`db.tablePage`), edits (`db.planEdits`/`applyChanges`), introspection (`db.engine`, through `introspect::calls` over `query`), the extensions tab (`db.duckdbExtension`, `components/extensions-duckdb-tab.svelte`), the assistant's tools (`query_stream` read-only, `explain_read_only`), and dashboards and workflow nodes (`executeReadOnly`, `query_stream` with `read_only`). Every DuckDB suite already runs against the remote driver (helper plan, Task 5), so what changes is limited to the differences and failure modes below.
13. **Extensions** install into `~/.duckdb/extensions/v1.5.x/<platform>` from inside DuckDB. The app's native DuckDB and the helper are the same duckdb-rs build (1.10505, DuckDB 1.5), so extensions a user installed in the app stay installed. The helper loads them only because its signature carries `disable-library-validation` (helper plan, Task 8 review C1).

### What changes on the remote driver, for the GUI

14. **The 16 MB frame** (`REMOTE.md`, "Differences"): a single statement whose SQL and values pass 16 MiB is `INVALID_ARGUMENT`, and a single row past 16 MiB is `RESULT_TOO_LARGE`. Core splits a script into statements, so only one huge statement (a pasted `INSERT … VALUES` dump) or one huge cell hits it. The GUI shows both as `CODE: message` (`errorText`, `src/lib/hooks/database/error-text.ts:23-30`). Kept (Decision 9).
15. **Read-only calls are capped at 16 per helper** (`MAX_READ_ONLY_CALLS`, `crates/seaquel-engine-duckdb/src/helper.rs:97`; past it `TOO_MANY_REQUESTS`). Natively there is no cap. The GUI runs every widget of a dashboard at once (`executeAllWidgets`, `src/lib/hooks/database/dashboard-manager.svelte.ts:398-404`), so a DuckDB dashboard with more than 16 widgets would show errors on some of them after the move. Decision 5 fixes it in the client.
16. **Two connections to one file.** In one process DuckDB lets a second instance open a file the first holds: with `@duckdb/node-api` 1.4.4 (the seeder's), the second `DuckDBInstance.create(file)` in the same process opened and wrote (`…/scratchpad/desk-duck/twice.mjs`). The native driver opens a fresh instance per connection too, so the app lets two connections open one file today, which risks the file. With the helper, each connection is a process, DuckDB's file lock applies, and the second open is retried for 10 s (`closing::LOCK_RETRY`, `remote/closing.rs:31`), then refused with "DuckDB is still closing this file in another Seaquel process" (`closing.rs:99`). In the GUI that happens on:
    - **Test** on the connection tab of a DuckDB connection that is connected: 10 s, then that message, which is wrong.
    - **Two saved connections to one file**, or a dropped `.duckdb` file that is already connected.
    - **A webview reload (Cmd+R) followed by a reconnect.** The reloaded page holds no Core ids. Core still holds the old connection, and the desktop never closes a webview's connections (`forget_webview` and `set_event_sink`, `lib.rs:284-305`, only cancel streams). Core closes the older connection for the same saved id only after the new connect succeeds (CLAUDE.md, "Windows own connections"), so the new helper meets the old one's lock and fails after 10 s.

    Decisions 6 and 8 cover these.
17. **A helper that dies** (a DuckDB abort, an OOM kill) fails every later call with `CONNECTION_CLOSED` ("The DuckDB helper stopped (signal 9). Reconnect to continue."). Core doesn't notice: `ConnectionClosed` with `CONNECTION_CLOSED` is reserved and never sent (`crates/seaquel-core/src/workspace.rs:197-200`). So the GUI keeps showing the connection as connected, every call fails with that text, and `watchClient` doesn't help, since it reports only `CONNECTION_NOT_FOUND` (`src/lib/core/connection-watch.ts:59-81`). The GUI already knows what to do with the event: `handleConnectionClosed` marks the connection disconnected and toasts `connection_closed_lost` (`connection-manager.svelte.ts:258-268`, `:573-590`). An apply cut off by it is already "interrupted" (`pending-changes.svelte.ts:108-126`, `:417`; helper plan probe fix F1). Q6.
18. **`ENGINE_NOT_INSTALLED`, `ENGINE_UNAVAILABLE` and `ENGINE_NOT_AVAILABLE` have no GUI handling.** No TS file names them outside one replay test, so today they would reach the user as `CODE: message` toasts.
19. **The rest of `REMOTE.md`:** `close` waits up to 60 s for the checkpoint in the helper and the client lets a closing helper go after 2 s; a reconnect to a file this process's helper is still closing waits up to 65 s (`closing::DETACHED_WAIT`, `closing.rs:28`), cut by the 30 s connect timeout. The connection tab's Save & reconnect disconnects first (`connectExisting`, `:847-865`), so it lands in that wait, which normally lasts milliseconds.

### Lifecycle in a long-running app

20. **Quitting doesn't drop Core.** The app ends with `.run(tauri::generate_context!())` (`lib.rs:1093`) and no run-event callback. Tauri's runtime runs tao's event loop, whose `run` ends in `process::exit` on macOS, Linux and Windows (`tao-0.35.3/src/platform_impl/macos/event_loop.rs:196-203`, `linux/event_loop.rs:998`, `windows/event_loop.rs:230`; `tauri-runtime-wry-2.11.4/src/lib.rs:3238-3242`). Managed state is never dropped, so no `HelperChild` is killed (its drop kills unless detached; helper plan probe fix F3). The process's pipe ends close at exit, every helper reads EOF, cancels its calls, waits up to 60 s for DuckDB's close checkpoint, and exits 0. So quitting never kills a helper mid-checkpoint today; it does leave helpers running after the app for up to 60 s, re-parented to `launchd`/`init`. Natively the app's DuckDB is never closed at exit, so the next open replays the WAL. The helper is an improvement there. The updater's restart takes the same path.
21. **Windows and webviews.** Only the main webview connects; the theme editor and log viewer make no `db` calls. `close_owned_by` is never called on desktop (item 16).
22. **Reaping.** The remote driver waits on its child (`watch_exit`), and a detached child is kept in the closing registry and `try_wait`ed, or handed to tokio after 65 s (`closing.rs`). tokio reaps orphaned children on SIGCHLD through its signal driver, which needs the runtime the open ran on to be built with `enable_all`. Tauri's async runtime is. No zombie should outlive a minute; the probe checks after a day-long session with many connects (Task 10).

### Release

23. **The order today.** Each matrix job of `publish-tauri` builds the CLI, the TUI and the helper, uploads them as workflow artifacts, then runs `tauri-action`, which uploads the app's assets and `latest.json` straight into the draft release (`release.yml:201-226`). `publish-cli` (`needs: publish-tauri`, `:228-255`) uploads the helpers' `.gz` afterwards. The matrix is `fail-fast: false` (`:13`), so if one target fails, `publish-cli` never runs, and the draft holds apps for five targets and no helper for any.
24. **The updater** asks `seaquel.app/updates/check/{target}/{arch}/{version}` (`tauri.conf.json:54-59`, the endpoint at `:56-58`). The website (`seaquel-app`, `packages/marketing/src/routes/updates/check/[target]/[arch]/[current_version]/+server.ts`) offers the latest release that is neither a draft nor a pre-release, by its `latest.json`, cached for an hour, and checks nothing else. Publishing a draft that lacks the helpers would update every app to a version whose first DuckDB connect fails with `ASSET_NOT_FOUND`.
25. **Versions** come from `src-tauri/Cargo.toml` for the app (`cli_download::VERSION`, `CARGO_PKG_VERSION`, `cli_download.rs:31-33`) and for the helper (`crates/seaquel-duckdb/build.rs`). The Windows job rewrites only `tauri.conf.json`'s version for MSI (`release.yml:99-110`), so both stay `2026.x.y` there.
26. **The metadata request.** Core's install asks `api.github.com/repos/webstonehq/seaquel/releases/tags/v<version>` for the size and digest (helper plan, Decision 10), twice per dialog install (helper plan, F5). Unauthenticated, GitHub allows 60 API requests an hour per IP address. For a TUI user that never mattered. For an office of desktop users behind one NAT, updating on the same morning, it can.

### CI today

27. **`src-tauri` is never tested or linted in CI.** The workspace lines exclude it (`ci.yml:58`, `:66`), and the `desktop` job only runs `cargo check -p seaquel` (`:444`). Its 56 lib tests, `cli_download`'s among them, run only locally. After the move the app's Core and the install commands are the GUI's whole DuckDB path, so this plan adds `cargo test -p seaquel` to the `desktop` job (Task 9).
28. **DuckDB coverage:** the native suites run in `rust` (Linux) and in `duckdb-drivers` on macOS and Windows (`ci.yml:375-426`); the same suites on the remote driver run in `rust`'s second invocation (`:75-85`) and in `duckdb-drivers`; the seeded live cases run only in `engines` (`:353-360`) and `duckdb-drivers`.

### The macOS signature

29. **The app's entitlements file** holds one entitlement, `com.apple.security.cs.disable-library-validation` (`src-tauri/macos/entitlements.plist`), there so the app's in-process DuckDB can load extensions signed by DuckDB's team (issue #114). The CLI, the TUI and the helper are signed with the same file (`release.yml:118-121`, `:143-146`, `:174-176`). After the move, only the helper loads DuckDB's extensions. The entitlement lets any library signed by anyone load into the process, so keeping it on the app, the CLI and the TUI is attack surface with no use (Q12).

### Licensing and the rest

30. **Nothing treats DuckDB specially on desktop beyond the above.** `seaquel-license` and the license stores don't name it. `features/index.ts:31-35`, `:77` turns DuckDB off on web only. The assistant's approval card has a DuckDB hint (`components/ai-assistant.svelte:428-429`), which stays true.

## Spikes (planned, Task 0)

Four short checks whose answers change a decision. Each takes minutes; they run before Task 1.

- **S1. duckdb-rs opening a file twice in one process.** The node-api result (item 16) is 1.4.4 through C++; check the native driver (1.5) and the remote driver side by side: two `Engine::open`s of one file, a write on each. Expected: native opens both, remote waits 10 s then refuses. Decision 6 assumes this.
- **S2. macOS privacy prompts (TCC) for a child process.** Open a DuckDB file under `~/Documents` from the helper started by a signed app, in a user account whose TCC grants are reset. Expected: the prompt names Seaquel (the responsible process is the app) and access works once granted. If it names `seaquel-duckdb`, or fails silently, the dialog's copy and the manual checks need a line about it.
- **S3. The AppImage's environment.** Start the AppImage on Linux and print the environment a child inherits (`LD_LIBRARY_PATH`, `LD_PRELOAD`, `APPDIR`, GTK/GIO variables). If `LD_LIBRARY_PATH` points into the AppImage's mount, the helper (which links the system `libstdc++`) may load the AppImage's copy. Expected: nothing harmful; if not, the remote driver drops variables that point into `$APPDIR` when spawning (Task 2, +0.3 h).
- **S4. An app that exits with `process::exit`** while its helper holds a 1 GB WAL: the helper must exit 0 within 60 s with the WAL checkpointed. Run with a small Rust program on the remote driver, not the app. Confirms item 20 and becomes Task 2's test.

## Answered questions (2026-10-04)

Each keeps the options that were weighed, so later changes start from them. The owner answered Q2, Q3, Q7 (and with it Q8) and Q9; the coordinator took the recommendation for Q1, Q4–Q6 and Q10–Q13 with the owner's go-ahead.

### Q1. Where the app gets the helper's size and digest

- **A: GitHub's release API, as the TUI and CLI do.** Nothing new. Each install makes one or two unauthenticated API requests, which GitHub limits to 60 an hour per IP (item 26), and offices behind one address will hit it after an update. An offline install needs the user to paste the SHA-256 from the release page. 0 h.
- **B: built into the app at release time.** The matrix job already builds and gzips the helper before `tauri-action` (`release.yml:170-199`, then `:201`). It computes the `.gz`'s SHA-256 and size and passes them to the app's build as `SEAQUEL_DUCKDB_HELPER_SHA256` and `_SIZE` (read with `option_env!`). Core gets `CoreBuilder::duckdb_helper_pinned(name, size, sha256)`; `release_asset::Fetcher::install` already takes an `Asset` (helper plan, Task 4), so the install skips `asset()` and fetches only `github.com/…/releases/download/v<version>/<name>`, which isn't the API. The dialog knows the size offline, a tampered release asset is refused (the digest comes from the app's own signed binary: the helper plan's Q7 B, for the app, without a key to manage), and the offline file picker needs nothing typed. Debug builds and builds without the variables fall back to A. +0.8–1.2 h.
- **C: from seaquel.app**, an endpoint next to the update check, cached. Avoids the rate limit but adds a dependency on the website for every first DuckDB connect, and the digest is only as good as the website. +1 h here plus the website's work.

**Recommended: B.** It removes the one network dependency that grows with the user base, makes the offline path usable, and costs about an hour. The terminal binaries can take the same values later (they are built in the same job; a follow-up).

**Answer (coordinator, owner's go-ahead): B.** Decision 4.

### Q2. Offline and air-gapped desktops

- **A: "Install from a file…" in the dialog.** When the download fails with `NETWORK_ERROR` (or always, as a secondary button), a file picker takes a copied `seaquel-duckdb-<triple>[.exe].gz`, and Core's `duckdb_helper_install_from_file` checks it against the pinned digest (Q1 B), or against a SHA-256 the user pastes (Q1 A). +0.3 h (the picker and a field) on top of the dialog.
- **B: A, plus a mirror for managed fleets.** `SEAQUEL_DUCKDB_HELPER_URL`, an `https:` base that replaces `github.com/…/releases/download`, honoured in release builds only when the digest is pinned (Q1 B), so a mirror can't serve a different file. +0.3 h. (The app's OS proxy settings are already used: `ai-system-proxy` unifies `seaquel-http/system-proxy` into the app, which the download's client honours.)
- **C: a machine-wide location** (`/Library/Application Support/Seaquel/duckdb/<version>/`, `%ProgramData%`, `/usr/lib/seaquel`), read-only for users and installed by an admin or MDM, looked up before the per-user folder. New trust rules (root-owned, not user-owned) for the start's check. +1.5 h.
- **D: an "offline" installer that carries the helper** (Q6 B of the helper plan, as a second bundle per platform). Doubles the release matrix's bundles. +2–3 h.

**Recommended: A and B now**; C and D as follow-ups if an enterprise asks. The CLI's `seaquel-cli duckdb install --from` keeps working for scripts.

**Answer (owner): A only.** "Install from a file…" in the dialog, checked against the built-in hash (Q1 B), so nothing is typed. No `SEAQUEL_DUCKDB_HELPER_URL` mirror: it moves to the Follow-ups with C and D. Decisions 4 and 10.

### Q3. Prefetch for existing DuckDB users

Everyone with DuckDB connections who updates will meet the dialog on their next DuckDB connect, and again after every later update, since each version needs its own helper.
- **A: no prefetch.** The dialog asks each time. 0 h.

## Decisions (2026-10-04)

Settled with the answers above. Numbered from 1.

### Scope

#### 1. Scope

- In: the app's Core on the remote engine and `src-tauri` without `libduckdb-sys`; one install path through the main Core; the pinned digest (Q1 B); the install commands (Q5 A); the dialog, its wrapper and the offline file install (Q2 A, Q4 A); prefetch (Q3 B); the GUI fixes of Decisions 5–8; deleting the native driver and Core's `engine-duckdb`, with the features re-scoped (Q7 A, Decision 18); the suites through the helper everywhere (Q8, Decisions 19–20); the Windows ACL check on install and every start (Q9 A); the release order and check (Q11 B); split entitlements (Q12 B); CI for the app and the dependency check; a probe; docs.
- Not in: a mirror variable (Q2 B), a machine-wide or bundled helper (Q2 C, D); an emergency build on the native driver (there is none, "Risks"); the website's release check (Q11 C); pinned digests for the terminal binaries; the TUI switching to Core's `ConnectionClosed` event; stripping the app binary.

### The app's Core

#### 2. Registration

`desktop_core` takes the identifier and builds `seaquel_core::with_plugins(|id| id != "duckdb")…duckdb_helper(DuckdbHelper { dir: duckdb_helper_dir(identifier), version: VERSION })`. `run()` makes the context first (`let context = tauri::generate_context!()`) and reads `context.config().identifier` before `.manage(desktop_core(…))`. With no data-local dir, DuckDB isn't registered and a WARN says so; a DuckDB connect then answers `ENGINE_NOT_AVAILABLE`, which the GUI words (Decision 10). `src-tauri`'s Core dependency takes `default-features = false` with `engine-postgres`, `engine-mysql`, `engine-sqlite`, `engine-mssql` and its current features. There is no `native-duckdb` feature: Core no longer has a native DuckDB engine to offer (Decision 18).

#### 3. One Core installs

`cli_download.rs`'s `helper_core` goes. `install_duckdb_helper`, `duckdb_helper_status` and `cli_info` take the app's `Core` (`app.state::<Core>()`), and the install runs on Tauri's runtime instead of a current-thread one of its own. The CLI flow, the dialog and the prefetch share Core's install lock. **Debug builds** install a `seaquel-duckdb` built beside the app (`debug_helper`) only when the identifier ends in `.dev` or `SEAQUEL_DATA_DIR` is set (the TUI hook's M1 rule); otherwise they download the release of their version like a release build, so a plain `npm run tauri dev` never writes a debug helper into the user's real folder. CLAUDE.md says to use `npm run tauri:dev`.

#### 4. The pinned asset (Q1 B)

`release.yml` builds the helper first in each matrix job (before the CLI and TUI, which don't need it), gzips the signed file, and exports `SEAQUEL_DUCKDB_HELPER_SHA256` and `SEAQUEL_DUCKDB_HELPER_SIZE` to `$GITHUB_ENV` for `tauri-action`. `src-tauri/build.rs` re-runs when they change (`cargo:rerun-if-env-changed`). With both set, `desktop_core` calls `CoreBuilder::duckdb_helper_pinned(size, sha256)`; the asset name stays Core's (`seaquel-duckdb-<triple>[.exe].gz`). Core then:
- answers `duckdb_helper_asset` from the pin, with no request;
- installs with `Fetcher::install` from the download URL alone;
- checks `duckdb_helper_install_from_file` against the pin when the caller passes no hash (the dialog's "Install from a file…" never passes one).
Without the pin (debug builds, local `tauri build`) everything is as today. A pinned size or digest that doesn't parse is a build failure, not a runtime fallback; so is no pin when `SEAQUEL_DUCKDB_HELPER_REQUIRE_PIN=1`, which `release.yml` sets (Task 9).
**Limit (Task 3 review):** the pin governs what the app downloads or takes from a file, not what it runs. A pinned app may run a helper that a terminal binary (or an older unpinned run) installed from the release metadata: an install under the pin replaces an intact one only when its record names another asset digest, and when the status is already `Installed` nothing calls install at all. The start's check (version handshake, ownership, permissions) still applies to it.

### Fixes the GUI needs

#### 5. Read-only calls wait for a slot

The remote client holds a semaphore of `MAX_READ_ONLY_CALLS` (16) permits per driver; `query_read_only_with` and `explain_read_only` take a permit before sending and release it when the call's last frame arrives (or the call is dropped and its `cancel` posted). The helper's cap stays as a backstop. A dashboard with 40 DuckDB widgets then runs 16 at a time, as a native thread pool would queue them. No GUI change.

#### 6. A file open twice in this process (Q13 A)

The remote engine records each live helper's canonical database path (none for `:memory:`; a file the open created gets its key after the open, as the closing registry does) and refuses a second open of it at once: `CONNECTION_ERROR`, "This DuckDB file is already open in another connection. Disconnect it first." A path still closing keeps the existing wait. `ConnectionManager.test` for a DuckDB form whose path equals a connected DuckDB connection's path answers success without calling Core. The cross-process message ("…still closing this file in another Seaquel process…") stays for other processes.

#### 7. A helper that dies (Q6 A)

`Driver::closed()` (default `None`); the remote driver's resolves when `watch_exit` sees the helper end without `close` or a drop. Core spawns a watcher per connection that has one, and on firing removes the connection and emits `WorkspaceEvent::ConnectionClosed { code: CONNECTION_CLOSED, message }` with the driver's message. The workspace docs (`workspace.rs:197-200`) and CLAUDE.md lose "reserved" for this code. The GUI's `handleConnectionClosed` already marks the connection disconnected and toasts `connection_closed_lost`. Clicking the connection reconnects it through `autoReconnect`, which starts a new helper. No automatic reconnect: the query that killed the helper may do it again.

#### 8. A reload closes the webview's connections

When `set_event_sink` replaces an existing sink for a label (a reload, `lib.rs:284-294`) and when a webview is destroyed (`forget_webview`, `:296-305`), the app calls `Workspace::close_owned_by(core, label)` after cancelling the label's streams. The reloaded page holds no Core ids (connections start disconnected on load), so nothing it shows breaks, and a reconnect finds the file free (or closing, and waits). Every engine benefits: the old page's connections leaked until quit.

#### 9. The 16 MB limits stay

A statement over 16 MiB or a row over 16 MiB stays refused (`tests/HELPER.md`'s "Limits", Decision 19). The release notes say so for the app. `MAX_FRAME` is a constant and the protocol is version-locked, so raising it later is cheap if users hit it.

#### 10. The dialog (Q4 A)

### Platforms and release

#### 13. Windows (Q9 A)

The ACL rule of Q9 A in `release_asset` (set on install) and `remote::process::check` (read on start), with `windows-sys`. Its tests are `cfg(windows)` and run in `duckdb-drivers`' Windows leg.

**Amended after Task 7's review (coordinator, 2026-10-04):**
- **The app's folder (`<identifier>`) has a narrower rule**, mirroring Unix's "no group or world write" there. Only what replaces or renames `bin` or the folder itself counts: `FILE_DELETE_CHILD`, `DELETE`, `WRITE_DAC`, `WRITE_OWNER` and `GENERIC_ALL` (`acl::rights::REPLACE`). Others may add files and folders.
  - **`DELETE` stays in the set.** With it, anyone who can add folders to the parent can rename the app's folder away and put their own in its place. `Authenticated Users` can add folders on `C:\`, for example. So an inherited `Authenticated Users:(M)` is refused until the repair.
  - **The root's repair keeps its DACL.** It keeps every entry, Administrators included, takes the replacing rights out of others' allows, and sets the result protected. It never replaces the whole DACL.
- **SYSTEM is accepted as an owner**, beside the user and Administrators.
- **Only name-surrogate reparse points (symlinks, junctions) are links.** WOF compression, dedup and cloud placeholders pass.
- **A refusal says what to do:** remove `bin/duckdb` and install again, or point `SEAQUEL_DATA_DIR` at a folder of your own. This holds in Core's message, the GUI's hint, the TUI, the CLI and the app's CLI-install dialog.

#### 14. macOS signing (Q12 B)

Two entitlements files: the app, the CLI and the TUI get none (`tauri.conf.json`'s `bundle.macOS.entitlements` removed, and the CLI's and TUI's `codesign` without `--entitlements`); the helper keeps `disable-library-validation` in `src-tauri/macos/duckdb-helper.entitlements.plist`.

#### 15. Release order (Q11 B)

Each matrix job uploads its helper `.gz` to the draft right after `tauri-action`; `publish-cli` uploads the CLI and TUI as before. A `check-release` job (`needs: [publish-tauri, publish-cli]`, `if: always()`) fails unless every target with an app bundle has its helper. CLAUDE.md's "Releasing" says to publish only when it is green, and that the website's update check offers the newest published release at once (cached an hour).

#### 16. Quit (Q10 A)

No exit hook. A test pins that a client process that ends with `process::exit` leaves its helper to checkpoint and exit 0, and the probe checks it with the real app.

#### 17. Logs

The commands log `activity=duckdb.helper` with `event=offer|install|cancel|prefetch`, `downloaded`, `pruned`, codes and byte counts, as Core does. Never a path, a URL, a connection name or a file the user picked. The dialog's store logs codes only through the page's logger.

### The native driver goes (Q7 A, Q8)

### Added in Task 2's review

#### 21. A window's reconnect to a file one connection holds (review I1 b, coordinator)

A window that connects the same saved connection again (a reload's reconnect) normally keeps its older connection until the new one has opened, so a failed reconnect closes nothing (phase 6 probe F4). For an engine whose connection holds its file exclusively, the older connection blocks the new one (Decision 6's registry, and DuckDB's own lock), so `Workspace::connect` closes the window's older connections for that saved id **right before the open**: after everything that can refuse the connect without opening anything has passed (the engine lookup, the connect policy's check and `Engine::preflight`, which for the remote DuckDB engine is the helper's install check, so `ENGINE_NOT_INSTALLED` keeps the old connection). It announces them `CONNECTION_REPLACED` as before, each taken out of Core and announced before its close is awaited (so a reconnect dropped mid-close has still announced it), and waits for their close (and for their helper, through the closing claim of review I1 a, at most 25 s, then "DuckDB is still saving this file"). For that engine only, a reconnect whose open itself fails has then closed the old connection, which would have blocked it anyway. The engine says so through `Engine::exclusive_file(config)` (default `false`; the remote DuckDB engine answers `true` for a file path, not `:memory:`); every other engine keeps the replace after the open. In Core this is `prepare_connect` (lookup, policy, preflight) and `open_prepared`, with the close between them. Also from that review: an open that meets a connection whose `close` has begun waits for its helper (bounded by `DETACHED_WAIT`) instead of being refused (I1 a), and claims are keyed by device and inode on Unix (M1).

### Risks: no fallback build

With the native driver deleted (Q7 A) there is no build of the app that runs DuckDB without the helper. If the helper path fails for a group of users after a release (a Windows antivirus that blocks the spawn, a macOS policy that blocks an unbundled executable, an AppImage environment that breaks the helper, a corporate network that blocks GitHub's download host), DuckDB connections fail for them until a fix release; every other engine keeps working. The updater can't roll a user back. What covers it:
- **Before the release:** every DuckDB suite through the helper on macOS, Windows and Linux in CI (Decision 20); the app's own tests in CI with a real helper; the probe (Task 10) runs the app's Core end to end on macOS and Linux, the spawn under a sandbox that denies the network, an AppImage's environment (S3), the TCC prompt (S2), and 500 connect cycles.

Manual checks 25, 27 and 28 are these (numbered as consolidated in Task 11).
- **After it:** a user stuck without a download has the dialog's "Install from a file…" (a helper copied from another machine); a user whose machine refuses the helper outright has the previous app version from the releases page, which still has native DuckDB. The release notes say both.
- **Fix-forward:** a fix release is the remedy. `check-release` (Decision 15) keeps a half-built release from being published.

**P1 (Minor): a helper file that lost its execute bit can't be repaired from the app.**
- Evidence: `chmod 0600` on the installed `seaquel-duckdb`. Status stays `Installed`, and the connect gives `ENGINE_NOT_INSTALLED` "…the DuckDB helper didn't start (PermissionDenied)". The install answers `downloaded: false` and leaves the file 0600, so the next connect fails the same way.
- In the GUI this is the dialog's "installed but can't be used" with no way out: no second download is offered, and nothing says to remove the folder. A restore from a backup, a copy tool that drops modes, or a sync of the data dir can cause it.
- Cause: the start's check accepts any file mode without group or world write (`crates/seaquel-engine-duckdb/src/remote/process.rs:158`, `meta.mode() & 0o022 == 0`). The install's intact shortcut (`crates/seaquel-core/src/duckdb_helper.rs:367-378`) only compares the hash and runs that check.
- Fix: in the Unix check, also require owner execute on the file (`mode & 0o100 != 0`, the file only), worded like the other permission refusals. Status is then `Unsafe`, the dialog offers the repair, and the shortcut fails, so the install downloads (or copies) over it. Alternatively, `prepare_target` could also `fchmod` the file 0700.
- Test: a 0600 helper is `Unsafe`, and an install makes it connect.

## Release notes

**A smaller app, and DuckDB in a process of its own**

- **Seaquel is about 11 MB smaller to download**, for the installer and for every update. DuckDB is no longer built into the app.
- **DuckDB support is a separate download of about 11.5 MB, once per version.** The first time you connect to a DuckDB database, or drop a CSV, Parquet, JSON or Excel file on the window, Seaquel tells you the size and asks. It shows the progress, then connects. If you already have DuckDB connections, Seaquel fetches it in the background shortly after it starts, so most of you won't be asked at all, now or after later updates.
- **Without internet access,** download `seaquel-duckdb-<your platform>.gz` for this version from the releases page on another machine, copy it over, and choose "Install from a file…" in the dialog. Seaquel checks both the download and a file you pick against a checksum built into the app, and refuses anything else.
- **One copy for everything.** `seaquel-cli` and `seaquel-tui` of the same version use the same DuckDB support, so it's only downloaded once.
- **Fixed: lost writes with two connections to one DuckDB file.** Until now, two connections could open the same file at once, and a write that Seaquel reported as saved could silently disappear when both closed. Opening a file that another connection already has open now says so, and asks you to disconnect the other one first.
- **A DuckDB crash no longer takes Seaquel down.** Each DuckDB connection runs in its own process. If it stops, the connection shows as lost and you reconnect with a click; your other connections and tabs aren't affected.

**Changes you might notice**

- A dashboard with many DuckDB widgets loads them 16 at a time.
- A single statement larger than 16 MB, or a single row larger than 16 MB, is refused on a DuckDB connection.
- After you quit, a `seaquel-duckdb` process can stay for a few seconds while DuckDB finishes writing the file.
- **macOS:** Seaquel, `seaquel-cli` and `seaquel-tui` are now signed without the "disable library validation" entitlement, so macOS refuses to load code into them that Apple or we haven't signed. Only the DuckDB helper keeps it, because DuckDB's own extensions need it.
- **macOS:** `seaquel-cli`, `seaquel-tui` and the DuckDB helper are now notarized, so a copy you download from the releases page in a browser runs without `xattr -d com.apple.quarantine` (on first run macOS checks the notarization online).
- **Windows:** the folder that holds DuckDB support is now private to you (you and SYSTEM only), and Seaquel won't start a helper from a folder others can change. If yours was loosened, the dialog offers to repair it.

**Known issues**

- If Seaquel couldn't fetch DuckDB support in the background (offline, or a proxy in the way), the first DuckDB connection after an update needs the download.
- On macOS, opening a DuckDB file in Documents, Desktop or Downloads may ask for access the first time. (Keep this line only if manual check 19 shows the prompt naming the helper or asking again.)
- If DuckDB support can't be downloaded or started on your machine, every other database keeps working. Version 2026.9.2 on the [releases page](https://github.com/webstonehq/seaquel/releases) still has DuckDB built in: install it over this one to get DuckDB back, and choose Skip when Seaquel offers this version again. Please tell us what happened in an issue.
