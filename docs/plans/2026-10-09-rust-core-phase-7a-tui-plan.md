**Goal:** `seaquel-tui`, a lazygit-style terminal client over Core in a binary of its own, as the owner's design shows it: numbered panels (Connection, Tables, Saved/History, Pending Changes), a main view with tabs, a command log, a context keybinding bar and `?` help. Browse a table and stage edits; review them as a diff and commit them in one transaction; write and run SQL with completion and an EXPLAIN ANALYZE tree; ask the assistant for SQL. Everything it decides comes from Core; the TUI only presents.

**After this phase, a second process writes `seaquel.db` beside the running app, and each hears the other.** Core polls `PRAGMA data_version` on the connection it writes with, so a change made by any other connection, in any process, becomes one `StorageChanged` event, and the desktop app reloads what the TUI saved.

**Phase 7b** (CLI commands: `conn list|test|add|import`, `query`, `schema`, `saved`, `export`, `ask`) is not in this plan. It inherits what this phase forces: writable storage for a second process, the polling, the moved `SecretWait`, `seaquel-terminal`, and the rules for passwords, keychain writes and host keys, which 7b's commands reuse in line mode.

**Architecture:**
- **`seaquel-tui`** (new interface crate with its own `seaquel-tui` binary and release asset, Q1): ratatui 0.30 over crossterm 0.29, `ratatui-textarea` for the editor's buffer (Q7). A pure model (`state/`: panels, tabs, the grid, the pending queue, the editor's modes, dialogs) updated by messages, a renderer (`view/`) that only reads it, and a runtime (`runtime/`) that owns the terminal, the event loop and the Core calls.
- **`seaquel-terminal`** (new interface library, `INTERFACE_LIBS`): what both terminal binaries share, moved out of `seaquel-cli`: the app identifier and data dir, the Core builder, the debug-only test hooks, the log filter, and the version and terms line (`build.rs` reading `src-tauri/Cargo.toml`). `seaquel-cli` and `seaquel-tui` both depend on it (Decision 22).
- **Distribution:** `scripts/build-cli.mjs` takes `--bin seaquel-cli|seaquel-tui`; `release.yml` builds, signs and uploads `seaquel-tui-<triple>` beside `seaquel-cli-<triple>` (Decision 21). How the app offers it is Q13.
- **`seaquel-storage`:** a writable open that does no schema work (`SchemaPolicy::RequireCurrent`, Q2), a dedicated writer connection, and `Storage::external_version()` (`PRAGMA data_version` on it).
- **`seaquel-core`:** `WorkspaceSpec::with_external_changes(interval)`: a poll task on the executor that emits `StorageChanged { kind: External }` after taking a change-sequence number (Decision 6). The desktop app and the TUI turn it on; web and the demo don't.
- **`seaquel-secrets`:** `SecretWait` moves here from `seaquel-mcp`, gains `pending()`, and counts writes and deletes as well as reads, so the TUI can say it's waiting for a keychain dialog whether it reads or saves a password (Q5).
- **TypeScript:** `ChangeFeed` treats `external` as "reload every list", as it treats a resubscribe. Nothing else in the GUI changes.

**Tech stack:** Rust (`seaquel-tui`, `seaquel-terminal`, `seaquel-cli`, `seaquel-core`, `seaquel-storage`, `seaquel-secrets`, `seaquel-mcp`, `seaquel-workspace`), ratatui 0.30.2, crossterm 0.29, ratatui-textarea 0.9.2 (all MIT), tokio, ratatui's `TestBackend` for render tests; a few lines of TypeScript (`change-feed.ts`) and the regenerated `StoredKind`.

## What the code shows

### The CLI today

1. **`seaquel-cli` is a clap binary with one subcommand, `mcp`** (`crates/seaquel-cli/src/lib.rs:41-58`, `subcommand_required = true`, `arg_required_else_help = true`). `mcp.rs` builds Core like the app (every engine, `ConnectPolicy::Unrestricted`, `TokioExecutor`, `LocalFiles::Allowed`, import paths; `mcp.rs:177-188`), opens `seaquel.db` read-only (`:206-210`) with `KeychainStore` wrapped in `SecretWait` (`:204`, `:211`), and checks SSH host keys against `~/.ssh/known_hosts`, never writing it.
2. **Its Core features** are `storage`, `secrets`, `ssh`, `workspace`, `imports` (`Cargo.toml:16`), plus `ai` through `seaquel-mcp` (`crates/seaquel-mcp/Cargo.toml:11`). No `ai-native` (so no HTTP client: `cargo tree -p seaquel-cli -i reqwest` finds nothing), no `git`, no `license-*`. Core's `Cargo.toml` comment says seaquel-cli enables `ai-native`; it doesn't.
3. **Logs go to stderr** through `tracing-subscriber` (`mcp.rs:139-150`), with `log_filter` dropping `sqlx::query`, `sqlx::postgres::notice`, tiberius's token stream and `sqlparser` at every level (`:117-137`). rmcp isn't held at WARN (phase 6's follow-up).
4. **Test hooks, debug builds only:** `SEAQUEL_CLI_TEST_SECRETS` (a JSON file loaded into a `MemoryStore`), `SEAQUEL_CLI_TEST_KNOWN_HOSTS`, `SEAQUEL_CLI_TEST_CALL_TIMEOUT_MS` (`mcp.rs:50-52`, `:153-160`).
5. **The CLI is no longer a sidecar.** It's a per-target release asset (`release.yml:112-134`), downloaded and checked by size and SHA-256 when the user installs it from Settings (`src-tauri/src/cli_download.rs`), into `<data_local_dir>/<identifier>/bin/` (`:33-40`), with `cli_install.rs` linking it onto `PATH`. `ci.yml:285-290` still makes a placeholder sidecar for `cargo check -p seaquel`, which `tauri.conf.json` no longer needs (it has no `externalBin`). The design doc's "same sidecar binary" now means "the same downloaded `seaquel-cli`".

### Core has nearly everything the screens need

6. **Library and settings reads:** `list_connections`, `list_projects`, `list_saved_queries(core, project_id)`, `list_query_versions`, `get_setting`, `get_ai_settings` (`library.rs:371-1083`, `state.rs:1039-1103`). History is read through storage: `seaquel_core::storage::query_history::load_by_connection` (`crates/seaquel-storage/src/queries/query_history.rs:39`).
7. **Connecting:** `Workspace::connect`/`test` with `ConnectRequest::saved(id)`, `.with_secrets(SuppliedSecrets)`, `.with_host_key(HostKeyPolicy::Trust(fp))` (`workspace.rs:747-907`). An unknown SSH host is `UNKNOWN_HOST_KEY` with the `SHA256:…` fingerprint; the retry with `Trust(fp)` writes known_hosts for exactly that key. A store read that fails is `SECRET_UNREADABLE`.
8. **Introspection** through `Workspace::engine(core, id)` → `ConnectionHandle`: `list_schemas`, `schema_tables` (tables, views and materialized views with columns, indexes and an approximate `row_count`; `crates/seaquel-types/src/dialect.rs:119-135`), `table_metadata`, `statistics`, `explain(sql, params, analyze)`, `column_types`, `create_table`, `alter_table`. `ExplainPlanNode` carries `actual_total_time`, `actual_rows`, `actual_loops`, conditions and children (`dialect.rs:146-214`), enough for a self-time tree. **Missing:** functions, enums and sequences (the design's Functions and Enums tabs), CHECK constraints (the Constraints tab gets keys and uniques from `SchemaColumn`), the server version (panel 1's "pg 16.2"), and real DDL for an existing table (the GUI's table editor builds `CreateTableDefinition` from metadata; `create_table` on that is an approximation).
9. **Runs:** `Workspace::run`/`page` (`run.rs:100`, `:264`) stream `RunEvent`s: `statementStart` (typed SQL, `source`, kind, page, `table`, `columnRefs`), `batch`, `statementDone` (`elapsedMs`, totals, `rowsAffected`), `statementError`, `statementDeferred`, then one `done` (with `history` when a `HistoryContext` was sent) or `error` (`CONFIRM_REQUIRED` with `destructive`). Cancel is `Workspace::cancel(core, stream_id)`.
10. **Edits:** `plan_edits` → `PlannedChange { sql, params, query_type, dml, summary }`; `apply_changes` → `ApplyOutcome` (`applied` with mode `single`/`atomic`/`inOrder`, `failed`, history rows; or `confirmRequired`); `table_page` streams a typed `TableQuery` (filters, sort) as page events (`edits.rs:236-679`). Two or more DML changes apply in one transaction, which is the design's "commit runs them in one transaction".
11. **AI:** `ai_generate` (the inline prompt: SQL only, the first fenced block, no tools), `ai_chat`/`ai_respond` (a full turn with tools and approvals), `ai_models`, `ai_test` (`ai.rs:578-680`). Sharing is `seaquel_core::ai::sharing(row, global)`. All need `ai_http` and `ai_egress` on the builder, which only `ai-native` provides natively.
12. **Events:** `Workspace::events()` yields `ConnectionClosed` and `StorageChanged(StorageChange { kind, scope, ids, origin, seq })`, in-process only (`workspace.rs:171-183`, `changes.rs:73`).

### Two processes on one file

13. **Already safe for two writers:** WAL and `busy_timeout = 5000` on every connection (`open.rs:213-218`); writers queue on an in-process mutex, then `BEGIN IMMEDIATE` (`write.rs:12-31`); a writer waits at most `WRITE_WAIT` (30 s); a pending migration runs under `BEGIN IMMEDIATE` on the migrator's own connection and is re-checked under it, with retries (`open.rs:438-479`).
14. **Writes take any pool connection.** `Storage::write` acquires from the pool after the write mutex (`write.rs:190-197`), so the connection a write uses changes from call to call. That matters for `data_version` (S4).
15. **No cross-process notification.** Nothing polls `PRAGMA data_version`; `StorageChanged` is emitted only by the process that wrote. A query saved in the TUI wouldn't reach a running app until something else made it reload.
16. **A writable open does work a second process shouldn't.** `Core::open_workspace` runs `upgrade_string_secrets` (moves secrets from pre-5a connection strings into the keychain, then `VACUUM`), `refill_name_keys` and `refill_list_meta` on every writable open (`lib.rs:864-891`). The secrets upgrade from `seaquel-cli` would create keychain items owned by the CLI's binary, which the app would then have to ask the user about on macOS (item 18).
17. **View state is shaped for the GUI.** `window_state` rows are opaque per window, but a window with no row copies the most recently used window's row, and every save also writes the legacy `project_state`/`tabs` mirror, which Core builds by reading the GUI's tab shape (`state.rs:1940-2075`). A TUI blob stored there would be copied into the next new GUI window and mirrored as GUI tabs. The window id must equal the call's origin (`check_window`).

### Keychain, SSH and the terminal

18. **macOS keychain:** keyring 3.6 uses the legacy file keychain, where each item trusts only the app that created it, so the CLI's first read of each item shows the OS's "Allow / Always Allow / Deny" dialog, outside the terminal (design doc, "As built in phase 4"). `SecretWait` (`crates/seaquel-mcp/src/secret_wait.rs`, 158 lines) times pending reads with a 5-minute limit; it lives in `seaquel-mcp`, which the TUI shouldn't depend on for it.
19. **The CLI never wrote known_hosts.** The GUI's trust prompt (`ssh-host-key-dialog.svelte`, `withHostKeyPrompt`) retries with the fingerprint; Core does the write.
20. **The production label** is the predefined label id `prod` (`src/lib/types/project.ts:36`). Nothing in the GUI asks for more than a confirm on a prod connection; "type prod to confirm" is new.

### What the design asks for that nothing has yet

21. **An index hint** (1b: "Seq Scan reads 312k rows to match 31.9k invoices", `i stage index`): no engine, Core or GUI code suggests indexes.
22. **Git status on saved queries** (1a/1b: `⎇ main ↑1`, `M`/`A`): Core's git is behind the `git` feature (libgit2, vendored with OpenSSL), which the CLI doesn't have.
23. **A Chart tab** (1b): the GUI's charts are Svelte components; nothing to reuse in a terminal.
24. **Ctrl+Enter to run** (1b): most terminals send the same byte for Ctrl+Enter and Enter. crossterm reports Ctrl+Enter only where the kitty keyboard protocol is on (kitty, WezTerm, Ghostty, foot, recent Alacritty, iTerm2 with CSI u reporting). Terminal.app and tmux by default send `\r` for both. (By reading; the probe checks each terminal.)

**S3. Testing.** `TestBackend`'s buffer turns into plain text lines (`buffer[(x, y)].symbol()`), which compare well as checked-in snapshot files. The spike's split is the one to keep: `update(&mut Model, Msg) -> Vec<Effect>` is pure; `view(&Model, &mut Frame)` only reads; the runtime turns `Effect`s into Core calls and feeds their results back as `Msg`s. So most tests are `update` tests with no terminal and no Core, render tests are a model fixture drawn at 148×42 and 80×24, and a few integration tests drive scripted keys through the real loop with a real Core on SQLite in a temp dir. No snapshot crate is in `Cargo.lock`; a 60-line helper (`UPDATE_SNAPSHOTS=1` rewrites, otherwise compare and print a diff) is enough.

**S4. `PRAGMA data_version` across processes.** sqlx 0.8.6 on a WAL file, a "writer" connection polled in process A, a child process B committing 20 times, 137 ms apart:
- A's own five writes on the writer connection: `data_version` 2 → 2 (unchanged). A write on **another connection in the same process**: 2 → 3 (changed). A read on another connection: unchanged. A's own `wal_checkpoint(TRUNCATE)`: unchanged. B's `wal_checkpoint(TRUNCATE)` after its commits added no extra change.
- One poll costs **13.3 µs** (10,000 polls).
- Latency from B's commit to A seeing it: 50 ms polling, p50 30 ms, max 61 ms (20 of 20 seen); 250 ms polling, p50 125 ms, max 237 ms (12 detections, commits between polls coalesce); 1 s polling, p50 583 ms, max 861 ms. A's own writes interleaved with the polls never showed up as changes.
- **So "external" is exact only when every write of the process goes through the polled connection.** Today's pool hands writes to any connection (item 14), and a write on a sibling connection looks external. Hence the dedicated writer connection (Decision 5). Polling lives in two layers: storage owns the connection and the pragma (`external_version()`), Core owns the timer and the event, since it owns the executor and the change sequence.

**S5. The editor and `$EDITOR`.**
- **`ratatui-textarea` 0.9.2** (MIT; the ratatui organisation's maintained successor of `tui-textarea` 0.7.0): multi-line buffer, undo/redo, selection, search, line numbers, `screen_cursor()` to place a completion popup. It has no per-token styling, and vim modes exist only as an example (a few hundred lines). +0.57 MB with ratatui (S1).
- **edtui** 0.11.7 (MIT): vim modes built in, syntect highlighting; +1.1 MB over ratatui. syntect's SQL grammar doesn't follow each engine's quoting the way `seaquel-sql`'s scanner does, so `$$…$$`, `[names]` and backticks highlight wrong, and its default features pull `arboard` (X11/Wayland clipboard on Linux).
- **Hand-written** over `seaquel_core::sql`'s scanner: highlighting that matches what Core splits and runs, at the cost of writing the buffer, undo and wide-character handling ourselves (~1,000 lines).
- **`$EDITOR`:** `ratatui::restore()`, `sh -c '$EDITOR "$1"'` on a temp file, `ratatui::init()` again: 8.7 ms round trip with a script as the editor, which saw cooked mode (`icanon`), and its edit came back. **`Terminal::clear()` after the re-init sent a cursor-position query (`ESC[6n`)** and failed after 2 s under `script`, where nothing answers it; redraw without `clear()` (a fresh `Terminal` already repaints everything). `ratatui::init()`'s panic hook put the terminal back in cooked mode after a panic.

## Answered questions (2026-10-09)

The owner answered Q1–Q12 on 2026-10-09. Each keeps the options that were weighed, so later changes start from them. Q1's answer was none of the three options as written; it is recorded as given. Q13 was raised by Q1's answer and answered the same day.

### Q1. Where the TUI lives, and how it starts

- **A:** a new interface library `seaquel-tui` (classified in `INTERFACES` and `INTERFACE_LIBS`), run as `seaquel-cli tui`, and also as bare `seaquel-cli` when stdin and stdout are both terminals; anything else keeps printing help, so scripts and MCP hosts see no change. Cost: in the plan; a CI clippy line and the crate rules.
- **B:** A without the bare launch: only `seaquel-cli tui`. Saves nothing measurable; one more word to type.
- **C:** a module inside `seaquel-cli`. One crate less, but ratatui and the TUI's tests join the CLI's, and 7b's commands land in the same crate. No time saved.

**Recommended: A.** lazygit starts bare; the TTY check keeps every non-interactive use as it is.

**Answer (owner): a separate binary** (given as "C, a separate binary"; the plan's C was a module inside `seaquel-cli`, so this is a fourth option). `seaquel-tui` is its own binary with its own release asset, not a subcommand: started as `seaquel-tui`, with `seaquel-cli` unchanged. Decisions 2, 21 and 22; Q13.

### Q2. Writable storage and migrations

The TUI writes history, staged edits' history rows and saved queries, so it can't open read-only like the MCP server.
- **A:** open writable but **do no schema work**: if the baseline, a migration or a data step has anything to do, refuse with `STORAGE_NEEDS_UPGRADE` ("Open the Seaquel app once…"), as the MCP server does; skip the secrets upgrade and the two refills (Decision 3). Cost: one `StorageOptions` field and its tests (~0.3 h).
- **B:** migrate like the app. Works, since migrations are expand-only and serialised across processes, but the TUI would then run `upgrade_string_secrets`, creating keychain items the app's binary doesn't own (item 16), and a TUI newer than the app would migrate files under it.
- **C:** B, minus the secrets upgrade.

**Recommended: A.** The CLI is downloaded by the app, version-matched, so the app has always opened the file first; the rule users already know from MCP stays one rule.

**Answer (owner): A.** Decision 3. (With Q13 A the TUI is downloaded by hand and may be newer than the app; the refusal then says which version of the app to open.)

### Q3. What the other process hears

- **A:** one `StorageChanged { kind: "external", scope: None, ids: None }` per poll that saw a change, after Core takes a sequence number for it (Decision 6). The app's `ChangeFeed` reloads every list and setting, as on a resubscribe; the TUI reloads what it shows. Cost: in the plan (~0.3 h of Task 1 for the GUI side).
- **B:** a change journal: migration `0008` adds `_seaquel_changes(seq, kind, scope, ids)`, every write appends its row in its own transaction, and the poller reads the rows past its last one, so the other process gets exact kinds and ids. +2–3 h (every write site), and one more "open the app once" for MCP users. Older releases don't append, so the poller still needs A's fallback.
- **C:** A, with the app's reload throttled to once per 2 s while external events keep coming.

**Recommended: A**, with the probe measuring a reload on a large library while the TUI runs a query a second (each run appends history). Move to C if that reload is visible; B only if both are too coarse.

**Answer (owner): A.** Decision 6.

### Q4. The TUI's view state

Item 17: a TUI blob in `window_state` would be copied into new GUI windows and mirrored as GUI tabs.
- **A:** its own file, `<data_dir>/tui/state.json` (last project and connection per project, open query tabs with their text, panel tabs, the theme), written atomically 500 ms after a change and at exit. No storage writes, no migration. Each TUI process overwrites it on exit (last one wins).
- **B:** `window_state` with an interface column: migration `0008` adds `interface` (NULL is the GUI), copies stay within an interface, the mirror is skipped for anything but the GUI; the TUI's window id is `tui-<uuid>`. +1.5–2 h, and the design doc's Decision 8 as written ("the TUI gets its own key").
- **C:** nothing persisted: it starts on the last connection used (from history) with empty tabs.

**Recommended: A** for 7a, with B as a follow-up if the owner wants the TUI's tabs to follow the data dir between machines (they don't today: `seaquel.db` is per machine too).

### Scope and placement

#### 1. Scope (Q9, Q10)

- In: the `seaquel-tui` binary with the four screens, minus Q9's deferred items; `seaquel-terminal`; its build, signing and release asset; writable storage for a second process; `data_version` polling in the app and the TUI; `SecretWait` moved; host-key trust; password prompts with "Save password" (Q5 B); the TUI's log file; Ask AI (Q10 A).
- Not in: Q9's deferred items (the Chart tab, Functions and Enums, git status, the index hint, the server version, the narrow layout); the app downloading or installing the TUI (Q13 A); phase 7b's commands; creating or editing connections from the TUI (7b's `conn add` and a TUI form after it); MCP write tools; the MCP server re-reading its connections on an external change (the poll makes it possible; behaviour change for 7b); the server's graceful shutdown (phase 6 follow-up, unrelated).

#### 2. Crates (Q1)

- `crates/seaquel-tui/`, a bin crate with a library half for its tests: `main.rs` (parse, `seaquel_tui::run(args)`), `lib.rs` (`run(TuiArgs) -> ExitCode`, clap's `TuiArgs`), `state/` (the model: `app.rs`, `panels.rs`, `grid.rs`, `pending.rs`, `editor.rs`, `explain.rs`, `dialogs.rs`, `keymap.rs`, `log.rs`), `view/` (one module per panel and dialog, `theme.rs`, `layout.rs`), `runtime/` (`terminal.rs`, `event_loop.rs`, `effects.rs`, `core.rs`, `logging.rs`, `state_file.rs`), `testing/` (snapshot helper, model fixtures, scripted keys).
- Dependencies: `seaquel-terminal`, `seaquel-core` (features `storage`, `secrets`, `ssh`, `workspace`, `ai-native`; no `imports`, `git` or `license-*`), `seaquel-runtime`, `seaquel-types`, ratatui, crossterm (`event-stream`), ratatui-textarea, clap, tokio, `log`, `tracing-subscriber` (the file writer). No `seaquel-rpc` (introspection goes through `ConnectionHandle` directly) and no `seaquel-mcp`.
- `check-crate-deps.mjs`: `seaquel-tui` in `INTERFACES` only (nothing depends on it); `seaquel-terminal` in `INTERFACES` and `INTERFACE_LIBS`, beside `seaquel-mcp`. The script's own test gains both. `ci.yml`, "Interfaces build on their own features": `cargo clippy -p seaquel-tui -- -D warnings` and `cargo clippy -p seaquel-terminal -- -D warnings`, so a feature only `seaquel-cli` turns on can't hide a missing one (5e's follow-up about CI building the CLI on its own).
- The command line: `seaquel-tui [--project …] [--connection …] [--theme dark|light] [--no-mouse] [--page-size N] [--log-level …]`. `--version` prints the app's version and the terms line, `--help` ends with the terms line, as the CLI's do (Decision 22). `seaquel-cli` doesn't change.

#### 3. Writable storage for a second process (Q2)

- `StorageOptions.schema: SchemaPolicy::{Upgrade, RequireCurrent}` (default `Upgrade`, today's behaviour). `RequireCurrent` opens writable and runs `schema::is_current`, the migration check and the data-step check as the read-only open does; anything pending is `STORAGE_NEEDS_UPGRADE`, a missing file `STORAGE_NOT_FOUND`, and nothing is created or changed. Journal mode is left alone (the app set WAL).
- `WorkspaceSpec::second_process()` sets it and tells `open_workspace` to skip `upgrade_string_secrets`, `refill_name_keys` and `refill_list_meta`: a second process does no maintenance writes. A row whose string still holds a pre-5a secret connects with it, as the MCP server does today.
- The TUI uses the CLI's data dir rule, from `seaquel-terminal`: `data_dir("app.seaquel.desktop")`, `.dev` in a debug build, or `SEAQUEL_DATA_DIR`.
- Since the TUI may be downloaded by hand (Q13 A) and be newer than the app, its `STORAGE_NEEDS_UPGRADE` message names its own version: "This file needs Seaquel <version> or later. Open the app once…".

#### 4. What the TUI writes

- Through Core calls only, each with the TUI's origin (`tui-<8 hex>`, random per process; Core's `WriteOrigin` rules): run history (`db.run` with a `HistoryContext`), applied changes' history rows, `savedQueryCreate`/`Update` (Ctrl+S), and a password the user chose to save: `connectionUpdate` with the save flag and `SecretChanges` (Decision 23). Nothing else in 7a: no other connection fields, no project, label, dashboard or setting writes, and no view state in `seaquel.db` (Q4 A).
- **Shared projects:** the TUI has no `git` feature, so a saved query edited in the TUI isn't published to its file; a `connectionUpdate` that only sets a save flag changes nothing a template carries. Its row keeps its old `shared_base`, so the app's next sync sees "row changed, file not" and writes the file (5e's three-way rule). The TUI says "will be written to the repo by the app's next sync" on save in a linked project.

#### 5. One writer connection per storage

- Native `Storage` keeps one dedicated writer connection behind the existing write mutex, outside the pool; `Storage::write` uses it instead of `pool.acquire()`. The pool's size drops by one (`max_connections` counts the writer), so the web's two per user become one reader and one writer, as today's peak use already is.
- A writer connection left in an unknown state (the failed-`ROLLBACK` path that today calls `close_on_drop`) is replaced on the next write.
- `Storage::external_version() -> Result<Option<i64>>`: `PRAGMA data_version` on the writer connection, taken with `try_lock` on the write mutex (`None` while a write holds it; the next tick tries again). Migrations, data steps and the open's own work happen before the first call, which records the baseline.
- wasm32 storage is unchanged (one connection already; no polling).

#### 6. External changes become events (Q3)

- `WorkspaceSpec::with_external_changes(Duration)`; off by default. The desktop app and the TUI pass 1 s (S4: p50 ~0.6 s, max ~0.9 s; 13 µs per poll); web and the demo don't.
- The task (on the workspace's executor, ended by `close`/`close_all`) compares `external_version()` with the last value. On a change it **takes a change-sequence number and completes it** (`take_seq`), then emits `StorageChanged { kind: External, scope: None, ids: None, origin: None, seq }`. Taking a number matters: the GUI applies a refetched row only when its `seq.n` is higher than the one it holds (`RowSeqs`), and an external write doesn't move this process's sequence on its own, so without it the reload's answers would carry the same `n` and be dropped.
- `StoredKind::External` (`"external"`), in `seaquel-workspace` and the generated TS. `ChangeFeed` maps it to `emitReload({reason: "external"})`; `ReloadReason` gains it; the handlers already reload every list and setting. The 100 ms grouping applies.
- A read-only workspace (the MCP server) may poll too, on any of its connections, since it never writes; the MCP server doesn't turn it on in 7a (Decision 1).

#### 7. `SecretWait` moves to `seaquel-secrets`

- Unchanged behaviour for reads, plus `pending() -> bool` and `changed()` (a `tokio::sync::watch` receiver) so the TUI redraws when a call starts or ends. `set` and `delete` are now counted too (today only `get` is, `secret_wait.rs:120-131`): a TUI save into an item the app created reads it first and can show the macOS dialog (Q5). For the MCP server this only ever extends a timeout, and it never writes. `seaquel-mcp` re-exports it from `seaquel_core::secrets`; its tests move with it.

#### 11. Browse

- **The grid** reads a page through `table_page` (100 rows, the GUI's page size): `g`/`G` first and last row of the page, `n`/`p` next and previous page (`total_pages` from `statementDone`, "≈" when `countEstimated`), `hjkl` move the cell cursor, columns scroll horizontally when they don't fit, the footer shows `column · type` and, for a staged cell, `old → new`.
- **`/` filters the loaded page** as the prototype does (rows whose cells contain the text; "no rows match the filter · esc to clear"). A server-side filter (`TableQuery` filters with the generated `FilterOp`s) is `F`: a one-line form, column, operator, value. Sort is `s` on a column (ascending, descending, off).
- **`e`/Enter edits a cell** in place; typing `NULL` sets NULL (the prototype's rule; `\NULL` for the text "NULL"); the value goes in as typed text, the cell wire format's `Text`, and Core casts it per the metadata, as the GUI's edits do. A primary-key column says "id is the primary key" in the log and doesn't edit (prototype), a keyless table or a view says Core's `NOT_EDITABLE` message.
- **`d`** stages or unstages a row delete; **`a`** stages an insert (a blank row at the top, each cell editable, `Esc` drops it while empty); **`D`** on a cell stages Set default.

#### 12. Pending Changes and commit

- **The queue is the TUI's** (`state/pending.rs`), a port of the GUI's documented rules, not its code: a repeated edit of one cell replaces the staged one; an edit back to the loaded value unstages it; each entry keeps its `Change` (`Change::Edit` with the table, key, column and value), the row as loaded (for the diff) and its `PlannedChange` once planned. A plan that arrives after a later edit of the same cell is dropped (a per-cell counter).
- `space` unstages, `u` undoes the last staging action (edit, delete, unstage, insert), `e` re-edits the value, `D` discards all (asks).
- **`c` opens the commit dialog**: the counts per kind and table, Core's destructive list when the batch has deletes, and on a `prod` connection "type prod to confirm" (Q11). `p` shows the full SQL. Enter calls `apply_changes` with `confirmed: true` only when the dialog listed destructive statements; a `confirmRequired` answer reopens it with Core's list. With a `HistoryContext`, so the applied changes join History.
- **Outcomes**, as the GUI's: full success clears the queue and refreshes the affected pages; an atomic failure keeps everything and marks the failed entry with its message (`NO_ROWS_AFFECTED` names its table and key); an in-order failure drops the applied prefix. There is no "interrupted" state: Core is in-process, so an apply always answers unless the process dies.
- The log shows `BEGIN;`, each statement with its time, and `COMMIT; n statements` for an atomic apply (Core reports the mode and per-change results), or the in-order steps.

#### 13. The command log

- Shows what Core reports: each run statement's typed SQL with its time (`statementStart`/`statementDone`), each data-tab page query (`table_page`'s `statementStart`), staged and unstaged changes (`staged`/`unstaged`/`undo` tags, as the prototype), applies, errors, connects and disconnects. Introspection appears as a named line (`schema tables · 23 ms`), not its catalog SQL, which Core doesn't expose; the count query isn't shown.
- Kept in memory (last 500 lines), never written to a file or the log. `L` opens it full screen with search.
- A Core trace hook that reports every statement a driver sends (catalog SQL, counts, `BEGIN`/`COMMIT`) is a follow-up.

- **Completion** (Tab or Ctrl+Space, and after `.` automatically): table names, then `alias.` columns, from the cached `schema_tables`; keywords from a short fixed list. The popup lists name and type (`issued_at date`), as 1b shows. Which alias maps to which table comes from `seaquel_core::sql::ast` column refs where it parses, else from a scan of `FROM`/`JOIN` words; the popup is advice, never SQL that runs.
- **Run** (Ctrl+R; Q8): `db.run` with the whole text, or the statement at the cursor with Alt+R, or `R` in Normal mode (terminals send Ctrl+Shift+R as Ctrl+R) (`RunTarget::Current` with the UTF-16 cursor, converted with `seaquel_core::sql::offsets`). `{{param}}`s open a form first (`seaquel_core::sql::params` finds them). The editor's own destructive check (`seaquel_core::sql`) asks first, as the GUI's does, and sends `confirmed`; Core's `CONFIRM_REQUIRED` reopens the dialog with Core's list. Ctrl+C cancels a running statement from anywhere in the tab, and Esc does when the focus is on the results (in the editor Esc means Normal mode). One run per tab; a new run cancels the tab's previous one.
- **Results:** the last SELECT's grid, paged with `db.page`; the Results tab title says `statement 2 of 3` when a run had several, `[`/`]` switch. **Messages:** every statement's outcome. A cell opens full size with Enter (wrapped, JSON pretty-printed).
- **Explain** (Ctrl+X; Alt+X or `:analyze` for ANALYZE): the plan as a tree with rows, self ms and share of total, computed from `actual_total_time × actual_loops` minus the children's; `ANALYZE ✓ · 412.3 ms` from `execution_time`. ANALYZE runs the statement, so for anything but a plain SELECT (`seaquel_core::sql` query type) it asks first, naming the kind.
- **`$EDITOR`** (Ctrl+O): the tab's text goes to a temp file under the data dir (mode 0600), the terminal is restored, `$VISUAL`, else `$EDITOR`, else `vi` runs, the text comes back. Never `Terminal::clear()` after (S5).
- History rows open in a new tab; nothing re-runs by itself.

#### 15. Rows in memory

- A page is at most 100 rows by default (`--page-size`, at most Core's cap). "Stream all" (Ctrl+R with a count prefix, or `:all`) keeps at most 100,000 rows in the model and says when it stopped; the stream is cancelled at the cap (S2: 400k rows stayed in memory without one).
- Cells render like `$lib/values`' `cellText` (bigint and decimal as text, bytes as `\x` hex, JSON compact), cut at the column width with `…`; wide characters are measured with `unicode-width`.

### Prompts, logs and the terminal

#### 16. Keychain, passwords and host keys (Q5, Q6)

- **Waiting for the keychain:** while `SecretWait::pending()` is true, a centred box: "Waiting for macOS to allow access to the keychain. Choose Always Allow in the dialog, which may be behind this window." Esc gives up (the connect fails with `SECRET_UNREADABLE`, worded). The 5-minute limit stays.
- **Passwords:** connecting a saved row whose `savePassword` is off asks first (masked input, a "Save password" checkbox, Esc cancels); a connect that fails on authentication offers to retry with a typed password. The password is used for this connect as `SuppliedSecrets`; it's saved only after the connect succeeds and only when ticked (Decision 23). Unsaved ones last the session; never logged, never in `Debug`, dropped on disconnect.
- **SSH:** the same for an SSH password or key passphrase the row doesn't save, with the same checkbox (`saveSshPassword`, `saveSshKeyPassphrase`). `UNKNOWN_HOST_KEY` opens the trust dialog (host, port, fingerprint, "Trust and connect" / "Cancel"); Trust retries with `HostKeyPolicy::Trust(fp)`.
- **Test hooks** (debug builds only, as the MCP server's), read through `seaquel-terminal` with the TUI's prefix: `SEAQUEL_TUI_TEST_SECRETS` (a JSON file loaded into a `MemoryStore`, which also takes the TUI's writes), `SEAQUEL_TUI_TEST_KNOWN_HOSTS`, `SEAQUEL_TUI_TEST_ORIGIN` (fixes the write origin for snapshot tests) and `SEAQUEL_TUI_TEST_PANIC`. A release build ignores them. The CLI keeps its `SEAQUEL_CLI_TEST_*` names.

#### 17. Logs

- Never to stdout or stderr while the screen is up. A file, `<data_dir>/logs/tui.log`, at `--log-level` (default `warn`), rotated at 5 MB, two kept, created 0600.
- The filter is the MCP server's `log_filter`, moved to `seaquel-terminal` with its tests, plus `rmcp` held at WARN (phase 6's follow-up closes here; the TUI doesn't link rmcp, the CLI does) and `ratatui`/`crossterm` at WARN. Both binaries use the one function.
- Same rules as every interface: no SQL, values, secrets, names, hosts or paths in a log line; the TUI's own lines carry activity names, ids, counts, codes and durations. The command log (Decision 13) is screen-only.
- A startup failure (storage refused, no data dir) is printed to stderr after the terminal is restored, with the exit code non-zero.

#### 18. The terminal's lifecycle

- `ratatui::init()` (raw mode, alternate screen, its panic hook) plus mouse capture (Q8) and, where supported, the kitty keyboard flags; `restore()` undoes all of them in reverse on every exit path.
- **Panics:** the hook restores the terminal first, then the default hook prints. A panic in a spawned task (a Core call) is caught by the runtime (`JoinError::is_panic`), which restores, prints "seaquel-tui crashed; the log is at …" and exits non-zero.
- **Signals:** SIGTERM and SIGHUP (a closed terminal or SSH session) restore, close the workspace (`close_all`: streams, connections, tunnels) and exit. Ctrl+C and Ctrl+Z arrive as keys in raw mode: Ctrl+C cancels a running statement, else asks to quit; Ctrl+Z restores, raises SIGTSTP, and redraws on SIGCONT (Unix only).
- Windows: Ctrl+C as a key; console close ends the process (crossterm restores on drop where it can).

#### 19. Colour (Q12)

- `view/theme.rs` holds the design's palette as roles (focus, muted, cursor, modified, deleted, added, header, name, warning), not colours, so the light theme and `NO_COLOR` are other tables. Truecolor when `COLORTERM` says so; else the nearest of the 256-colour cube; `NO_COLOR` set to anything non-empty means no colour at all (bold, dim, reverse and underline carry focus, selection and change markers, and `~`/`-`/`+` markers are always shown as characters, so nothing depends on colour alone).

### Ask AI (Q10)

#### 20. The popup

- Opens over the query tab (Ctrl+K or `:ask`; Ctrl+A is tmux's prefix for many users). Title: `Ask AI`, then the sharing line from Core's rule for the tab's connection (`schema shared · data not shared · read-only`); "read-only" always, since only reads may run from it.
- The prompt is one line that grows; `@` opens completion of tables (schema-qualified), saved queries and dashboards; Enter sends `ai_generate { connectionId (saved), request, existingQuery }`. While waiting: a spinner and Esc to cancel (the future is dropped, which closes the request, phase 6 S1).
- The answer: `✓ generated in 1.8s · <model>` and the SQL, highlighted. Enter inserts at the cursor (replacing the selection); Tab refines; Ctrl+R per Q10; Ctrl+S saves as a new saved query.
- Errors are Core's codes worded in the popup (`NO_PROVIDER`, `NO_API_KEY`, `NO_MODEL`, `AI_DISABLED`, `PROVIDER_ERROR` with the provider's message cut at 1 KiB, `RATE_LIMITED`, `TIMEOUT`). The API key is read by Core from the keychain (a keychain wait shows Decision 16's box).
- The TUI's Core has `ai-native` with `AiEgress::Any`, as the desktop's (`src-tauri/src/lib.rs:60-71`); `seaquel-terminal`'s builder takes the HTTP client as an option, so the CLI's Core stays without one.

### Distribution and shared code (Q1, Q5)

#### 21. Building and shipping `seaquel-tui`

- **Build script:** `scripts/build-cli.mjs` is generalised with `--bin seaquel-cli|seaquel-tui` (default `seaquel-cli`, so `npm run cli:build`, `scripts/tauri.mjs` and the release step keep working); it copies to `src-tauri/binaries/<bin>-<triple>[.exe]` as today. `npm run tui:build` runs it with `--bin seaquel-tui`. The script's `--release`, `--target` and `CARGO_TARGET_DIR` handling don't change. One script, not a sibling: the two would differ in one constant.
- **`release.yml`**, per matrix target, after "Build seaquel-cli": "Build seaquel-tui", "Sign macOS TUI" (`codesign` with the same identity, hardened runtime and entitlements as the CLI), "Sign Windows TUI" (`trusted-signing-cli`), and an `upload-artifact` named `seaquel-tui-<triple>`. `publish-cli` downloads `seaquel-cli-*` and `seaquel-tui-*` and uploads both to the release. About 3–6 minutes more per job on a warm cache (most crates are shared with the CLI's build). The first tagged draft release is the test: `codesign -dv --verbose=4` and `signtool verify /pa` on the assets.
- **Version:** `seaquel-terminal`'s `build.rs` reads the app's version from `src-tauri/Cargo.toml` (the CLI's `build.rs`, moved) and exports `VERSION`, `VERSION_TEXT` and `TERMS_LINE`; both binaries use them for `--version` and `--help`. The release checklist in CLAUDE.md doesn't change (no new version field).
- **Size:** about 68 MB raw, 56 MB stripped, 23 MB gzip -9 on macOS arm64 (S1's last row); `seaquel-cli` is unchanged. (Superseded: both ship from the `terminal-release` profile since 2026-10-03; see "Binary size" under Task 9's notes.)
- **The app (Q13 A):** nothing in `src-tauri` changes; the docs give the manual install (Task 9).

#### 22. Code the two binaries share: `seaquel-terminal`

- A small interface library rather than duplication: the shared parts are policy (which Core features and builder options a terminal binary gets, which logs never pass), and two copies kept in step by a test would still drift where the test doesn't look.
- It holds: `APP_IDENTIFIER` and `data_dir()`; `core_builder(BuilderOptions)` (every engine, `ConnectPolicy::Unrestricted`, `TokioExecutor`, plus `local_files`/import paths and an optional AI HTTP client as options); `TestHooks::from_env(prefix)` (secrets file → `MemoryStore`, known_hosts, call timeout, origin, panic; all `None` in a release build); `log_filter(level)` with its tests; `shutdown_signal()`; and the version constants (Decision 21).
- Its Core features are the union both binaries need through it (`storage`, `secrets`, `ssh`, `workspace`); `imports` and `ai-native` stay on each binary's own `seaquel-core` dependency, so neither binary links the other's extras. CI's per-crate clippy lines check each on its own features.
- `seaquel-cli` keeps its behaviour and its tests unchanged (`tests/stdio.rs`, `tests/cli.rs`, the `mcp.rs` unit tests that move are re-pointed, not rewritten).
- Crate rules: `seaquel-terminal` is an interface in `INTERFACE_LIBS`; it may use Core, the runtime and the types, nothing else of ours.

#### 23. Saving a password from the TUI (Q5)

- Only after a successful connect with the typed secret, and only when the checkbox is ticked: `connectionUpdate { id, patch: { savePassword: true }, secrets: SecretChanges { db: Set(pw) } }` (or the SSH flag and `ssh`), with the TUI's origin. Core writes the keychain before the row, outside the transaction, and puts back what it changed if the row write fails; the TUI never calls a `SecretStore`.
- While Core writes, `SecretWait` may be pending (an existing item the app created: macOS asks before the TUI may read and update it), so Decision 16's box shows.
- After a new item is saved on macOS, the TUI says once: "Saved. The Seaquel app will ask once to read this password; choose Always Allow." It can't tell a new item from an existing one, so it says it whenever the row had no saved password before.
- A failure (`SECRET_UNREADABLE`, a keychain error, a denied dialog) leaves the connection connected with the session password and says the password wasn't saved.
- The TUI doesn't offer to forget a saved password in 7a; the app does that.

#### 24. The inline prompt resolves `@mentions` (Task 7 review I1)

- `ai.generate` resolves the request's `@mentions` as a chat turn does: tables (from the schema context), the connection's project's saved queries and dashboards, as a "Referenced context" section after the request. With schema sharing off nothing is read for them and the request goes as typed, byte for byte. Before 7a only turns resolved them, so the TUI's `@` would have sent plain text.
- The GUI's inline prompt gets it too (it sends what's typed; no completion there). Recorded in phase 6's Decision 18 and as rule (10) of `changes.json`'s `*` entry; the recorded `generate.json` cases hold no `@` and stay unchanged. Pinned by `seaquel-core/tests/ai_turn.rs` `generate_resolves_mentions_as_a_turn_does` (schema on, off, and no mention).

#### 25. Ask AI's Ctrl+R gate (Task 7 review I2)

- Ctrl+R's gate is Core's read-only **token check** (`seaquel_core::sql::read_only`, with the connection's engine) on the one statement the answer must be, plus the TUI's own conditions (connected to the popup's connection, the cursor not inside a statement of the user's, the statement reading back as the answer). The run itself is an **ordinary editor run** (`db.run` with `RunTarget::Current`), not a read-only transaction: what the token check misses runs with the connection's rights. That is Q10 A as answered (insert, and run only what the check passes, as phase 6's Q9 option B put it). A `db.run` read-only flag is a Follow-up.

## Ground rules

From phase 6, unchanged:
- **No git writes, by anyone executing this plan.** Not `git add`, `commit`, `checkout`, `restore`, `rm`, `reset`, `stash`, `switch`, `merge`, `rebase` or `push`, and no worktrees. Read-only `status`, `diff`, `log` and `show` are fine. Phase 6 had two incidents where a cleanup command discarded work; if a file needs undoing, edit it back by hand.
- **No subagents spawned by implementers.** The coordinator dispatches tasks; an implementer does its task itself.
- Conventions: `errorToast` for the GUI's one change (none expected), never edit `src/lib/components/ui/*`, oxfmt.
- The Core crate rules (`npm run crates:check`; `seaquel-tui` classified).
- Parallel tasks own their files and make small, re-read edits to shared ones (`Cargo.toml`, `check-crate-deps.mjs`, `ci.yml`, CLAUDE.md).
- **Tests never touch the real keychain, data dir, `~/.ssh` or home.** Every TUI test sets `SEAQUEL_DATA_DIR` to a temp dir and uses the debug-only test hooks; a test that builds a `KeychainStore` fails review.
- **No secrets, names, hosts, strings, SQL or values in `Debug`, errors, logs or events.** The TUI's model types that hold a password, a cell or SQL text get hand-written `Debug`.
- The full check list, with npm and cargo through `mise exec --`; one shared `CARGO_TARGET_DIR` for the phase (`…/scratchpad/p7a/target`).
- **Never call a real model provider or use a real API key** (Task 7 uses `seaquel-ai`'s `MockProvider` and `LoopbackOnly`).
- TDD: each task's tests are written first and seen failing (a stub with `todo!()` counts).
- Effort log: `docs/plans/2026-10-09-phase-7a-effort.md`.

Added for 7a:
- **i18n:** the TUI is English only, its strings in one module (`state/text.rs`), so a later translation has one place to look. No new GUI message keys unless Q11 C.
- **The terminal is always restored.** Every code path that can end the process (return, `?`, panic, signal, Ctrl+Z) is listed in `runtime/terminal.rs`'s docs and has a test or a probe item.
- **The TUI decides no SQL.** It builds no SQL text except what the user typed: no quoting, no `LIMIT`, no `EXPLAIN` prefix, no `CREATE INDEX`. Core builds pages, edits, filters and plans (CLAUDE.md's "UI code never does dialect work itself").

### Constraints the executors must obey

- `update` is pure: no Core, no I/O, no clock (time comes in `Msg::Tick(Instant)`), so every key path is testable without a terminal.
- `view` only reads the model.
- One run, one table page and one apply per tab at a time; a new one cancels the old (stream id per operation, as the GUI).
- No write to `seaquel.db` except through Core calls with the TUI's origin.
- Polling is native only, off unless the spec turns it on, and never runs during the open.

### Things a task could quietly skip

Reviews check each by name:
- a write path in storage that still takes a pool connection (the writer connection rule broken; a sibling write would look external);
- the external event emitted without taking a sequence number (the GUI drops the refetch);
- the poll task outliving `close`/`close_all`, or running on web;
- `RequireCurrent` creating the file, changing the journal mode or running a refill;
- the terminal left raw after a panic in a spawned task, SIGHUP, or `$EDITOR` failing to start;
- `Terminal::clear()` after a resume;
- a password or cell value in a `Debug` derive, the log file or a panic message;
- the key bar or help written by hand instead of from the keymap table;
- a staged edit applied without `confirmed` when the dialog listed destructive statements, or `confirmed` sent when it didn't;
- a plan landing after a later edit of the same cell overwriting it;
- the command log written to disk;
- (Ask AI) Ctrl+R running model SQL that the read-only check refused, or running more than the inserted statement;
- a password saved before the connect succeeded, saved when the box wasn't ticked, or written to the store by the TUI instead of through `connectionUpdate`;
- `SecretWait` still counting reads only (a save's keychain dialog then shows no box);
- `seaquel-tui` picking up `imports`, `git` or rmcp through `seaquel-terminal`, or `seaquel-cli` picking up `ai-native` through it;
- a `release.yml` step that builds or signs `seaquel-tui` for some targets but not all, or an upload pattern that misses it;
- the test hooks read in a release build.

### Notes from Task 1 (as built)

- **Storage.** `SchemaPolicy::{Upgrade, RequireCurrent}` on `StorageOptions.schema`. `RequireCurrent` shares the read-only open's path (`open_checked`): `preflight` without creating, the `immutable` first check, then a writable pool with `create_if_missing(false)` and no journal mode, and the authoritative check on one of its connections. `max_bytes` applies to it too.
- **The writer connection** lives inside the write mutex (`write.rs`'s `Writer`, `Arc<Mutex<Writer>>` instead of `Mutex<()>`). `WriteTx` takes the connection out of the slot and puts it back on commit or a successful rollback. A failed `ROLLBACK` (explicit or in `Drop`'s task) closes it, and the next write opens a fresh one. Without a runtime in `Drop`, the connection is forgotten and the slot left empty. The pool gets `max_connections - 1` (at least 1) when writable; a read-only pool keeps them all.
- **With `idle_timeout` (the web), the writer connection closes once it has gone unused that long** (review fix 1: first built as a close after every write, about 2.8 ms a write once the reader had idle-closed, since SQLite checkpoints and deletes the WAL on the last close; a kept writer costs about 0.03 ms). `put_back` records the last use and starts one reaper task per idle period (`Handle::try_current().spawn`, holding a `Weak` of the write mutex); the reaper closes the connection once it's been unused for `idle_timeout`, waits again while writes keep it in use, and ends when the storage or the connection is gone. The web's `user_storage_options` names `SchemaPolicy::Upgrade`.
- **Every write is on the writer.** The 25 single-statement writes that went straight to `st.pool()` (`app_state::set`, `query_history::set_favorite`, `user_credentials`, `vault_state`, `license` through `save_singleton_json`, `tutorial`, `import_state`, `themes::save_preferences`, the frozen-fixture removes and saves) now each run in their own `WriteTx`. `VACUUM` and `wal_checkpoint` run on the writer too. The only `pool().acquire()`/`begin` left in `src/` are reads, the open's own schema work (before the `Storage` exists) and wasm32's one-connection pool. Side effect: on read-only storage those calls now fail with `STORAGE_READ_ONLY` instead of SQLite's read-only error.
- **`Storage::external_version()`** (native) answers a counter, not the raw `data_version`. The counter moves when `data_version` on the writer connection differs from the last poll's, and once when a polled connection was replaced (the values of two connections can't be compared). It returns `None` while the write turn is held (`try_lock`). Read-only storage polls on a connection of its own. `Storage::close` closes the writer connection after any write in flight, and nothing reopens it afterwards (`PoolClosed`).

The key is the primary key's columns **in the metadata's order** with their values as loaded (`browse::row_key`); a keyless table or a view sends an empty key and Core's `NOT_EDITABLE` message is what the log says (`read-only` tag). Staging waits for nothing: each staging is an `Effect::PlanEdit` (`plan_edits` with one edit) and Core's answer either logs Core's SQL (`staged`, with its placeholders) or, refused, takes the staging back.
- **The queue** (`state/pending.rs`). A refused plan restores the entry as the step that staged it found it (or removes it) and drops that undo step. `u` restores the queue before the last staging action (snapshots, at most 1,000) and plans again any restored entry still `Planning` (its earlier answer may have been dropped as stale). `Model::staged` is `queue.counts()` after every change; panel 2 marks a table `+1 ~1 -1` before its count.

- **F1, Important: `alias.` completion lists no columns, and panel 2's preview says "0 columns".**
  - Evidence: `SELECT * FROM users u WHERE u.` opens no popup, and neither does Ctrl+Space; `FROM us` + Tab does. An unopened table's preview reads `0 columns`. Every engine's `schema_tables` returns `columns: vec![]` (phase 6's F3: `seaquel-engine-postgres/src/introspect.rs:168` and the other five), and the TUI's completion and preview read only that list (`crates/seaquel-tui/src/runtime/core.rs:220-231`, `state/completion.rs:133-155`).   - Fix: when an `alias.` resolves to a table without columns, ask Core's `table_metadata` for it (`Effect::LoadColumns`), cache the columns on the model's `TableItem`, and reopen the popup when they arrive. Do the same for the preview. Or read every table's columns in one catalog query per connect, which fits phase 6's schema-cache follow-up. Pin it with a live test of `alias.` against SQLite.
- **F2, Important: Esc followed quickly by a key loses both keys.**
  - Evidence: crossterm reads `ESC x` arriving in one read as Alt+x, which the editor ignores. With tmux's default `escape-time` (500 ms in tmux 3.3a, the version in Debian 12 and Ubuntu 22.04/24.04), tmux itself turns Esc then `:` within 500 ms into `ESC :` (attached-client test: lost at 0, 50 and 200 ms, works at 600 ms; with `escape-time 10` it works from 50 ms). For an editor with vim's modes this happens all the time (Esc `:w`, Esc `dd`). Over SSH the bytes can merge too.
  - Fix: where the Insert-mode editor, the `:` line or the Ask prompt gets an Alt+char that its keymap doesn't bind, handle it as Esc followed by that char (what vim does in a terminal). The keys involved are in `state/app.rs`'s key dispatch, before `query::typing` (`state/query.rs:804`). Esc then `r` or `x` in one read stays Alt+R/Alt+X, which run or explain the statement, the same as `R` would after Esc. Task 9's docs should recommend `set -sg escape-time 10` for tmux.
- **F3, Important: the mouse only focuses.**
  - Evidence: Q8 A promised clicking a row to select it, scrolling, and a help line about Shift-drag. `on_mouse` (`crates/seaquel-tui/src/state/app.rs:1273`) acts only on a left button press and only focuses the box under it. Because mouse capture is on, the terminal's own wheel scrolling doesn't happen either, so the wheel does nothing anywhere. A click on a tab title does nothing.
  - Fix: hit-test list rows and grid cells (`layout::areas` plus each list's scroll offset) to set the selection; map `ScrollUp`/`ScrollDown` to `k`/`j` in the box under the pointer (and to the editor's and the cell view's scroll); map tab titles to `[`/`]`. - **F4, Important: on Linux with no Secret Service (a headless host over SSH), a row with a saved password can't connect at all.**
  - Evidence: Linux release, no D-Bus session, `--connection pg`.   - Fix: on `SECRET_UNREADABLE` or a store error, offer "Enter the password" (the `ProblemRetry` path, `state/connect.rs:667-690` and `state/dialogs.rs:126`), using the typed secret for the session as `SuppliedSecrets`, with Save password off and disabled while the store can't be written. - **F5, Minor: closing the terminal window aborts the TUI.**
  - Evidence: when the pty's master end is closed (idle or while streaming), the TUI ends with SIGABRT (exit −6) within 0.2 s. Cause: ratatui's `Terminal` drop and the TUI's own exit lines (`src/lib.rs:150-163`) and panic hook (`runtime/terminal.rs:217`) use `eprintln!`, which panics when the write fails; the hook's own `eprintln!` then aborts. ### Binary size (owner decision, 2026-10-03)

A size study after Task 9 measured five ways to build the terminal binaries (MB, macOS arm64; gzip -9 of the stripped binary):

| Variant | TUI raw | TUI gzip | CLI raw | CLI gzip |
|---|---|---|---|---|
| A (old release) | 70.26 | 21.28 | 63.13 | 18.73 |
| B (new) | 50.12 | 18.89 | 46.17 | 17.15 |
| B2 (B with `opt-level = "s"`) | 37.17 | 13.89 | 34.34 | 12.58 |
| D (no DuckDB + B) | 16.21 | 7.76 | 12.25 | 6.02 |
| E (no DuckDB + B2) | 11.62 | 5.75 | 8.76 | 4.44 |

The owner chose **B**: DuckDB stays in both binaries, and `build-cli.mjs --release` builds them with a `terminal-release` profile in the root `Cargo.toml` (`inherits = "release"`, `lto = "fat"`, `codegen-units = 1`, `strip = true`), so the output is `target/[<triple>/]terminal-release/`. It keeps `panic = "unwind"`: the TUI's panic hook restores the terminal, and the engines' `catch_unwind` (DuckDB's blocking pool and decoder) turns an engine panic into an error. `release.yml` needed no change (it calls the script and signs and uploads from `src-tauri/binaries/`). B has no measurable runtime cost (startup about 180 ms, key latency about 7 ms, query speed unchanged) and adds about 60 s per clean build. Debug builds are unchanged.

## Release notes

For the release that ships phase 7a. Earlier notes still apply as written.

**New: Seaquel in the terminal**

- **`seaquel-tui`** is a terminal client for your saved connections, laid out like lazygit: the connection, its tables and views, your saved queries and history, and the changes you've staged, each in a numbered panel, with the table or the query editor beside them. Browse a table, edit cells, stage inserts and deletes, review them as a diff and commit them in one transaction. Write SQL with completion, run it, page through results, read an `EXPLAIN ANALYZE` tree, and ask the AI assistant for a query. Press `?` for the keys.
- **Download it from the release.** It's a separate file per platform (`seaquel-tui-aarch64-apple-darwin`, `seaquel-tui-x86_64-unknown-linux-gnu`, `seaquel-tui-x86_64-pc-windows-msvc.exe`, …); the app doesn't install it yet. The README's "Terminal UI" section has the `curl` command. The binaries are signed but not notarized: a file downloaded with a browser on macOS needs `xattr -d com.apple.quarantine` before it starts.
- **It uses the app's data.** Saved connections, passwords, SSH settings, saved queries and history are the app's, and it runs beside the app. It never upgrades the app's data file: if the file needs an update, it stops and names the app version to open. Open the app once after updating either.
- **Passwords.** On macOS the first read of each saved password shows a dialog asking whether `seaquel-tui` may use it; choose Always Allow. You can type a password the app doesn't save and tick "Save password": the app then asks once, the first time it reads that password. On a machine with no keyring to reach (a Linux server over SSH), the TUI asks for the password each session and can't save it.
- **What it keeps.** Open query tabs, unsaved SQL included, are kept between runs in `tui/state.json` in the app's data folder, readable only by you (a tab over 1 MB isn't kept). Its log, `logs/tui.log`, holds no SQL, values, passwords or connection names.

**The app**

- **The app picks up what the TUI saves.** A query saved, a history row or a password saved in the TUI shows in the app within about a second, without reloading. Any other program writing the app's data file has the same effect.
- **The inline AI prompt (⌘K) now understands `@mentions`.** `@table`, `@saved query` and `@dashboard` in the request send that object to the model as context (a table by name and kind, without its columns; a saved query with its SQL; a dashboard with its widgets), as the assistant's chat already did, when the connection shares its schema with AI. With schema sharing off, the request goes as typed.
- **PostgreSQL: an abandoned `EXPLAIN ANALYZE` stops on the server.** Before, an Explain whose caller went away (the TUI quitting while it ran) kept running on the server until it finished; now dropping it cancels the statement. Each Explain uses a connection of its own for this, in the app too.

**The command line tool**

- **`seaquel-cli mcp --log-level debug` no longer writes each tool call's SQL to stderr** (last release's known issue): the MCP library's own debug line is held back. SSH's debug lines, which named the bastion and its host keys, are held back too, here and in the app's log.
- A saved password that can't be read because there's no keyring at all (no Secret Service in an SSH session on Linux) is now reported as `SECRET_STORE_UNAVAILABLE`, apart from a denied or failed read (`SECRET_UNREADABLE`).
- No change to the app's data file in this release, so `seaquel-cli mcp` keeps working without opening the app first.

Known issues:

- The app doesn't download or install `seaquel-tui`, and the binaries aren't notarized (see above).
- Windows builds are made and signed but untested.
- In tmux with its default `escape-time`, Esc followed quickly by `r` or `x` runs or explains the statement. Add `set -sg escape-time 10` to `~/.tmux.conf`.
- On macOS, Option+R and Option+X type characters unless the terminal sends Option as Meta. The keys the bar shows (Ctrl+R, Ctrl+E, Ctrl+X) don't need it.
- Ask AI's Ctrl+R runs the answer only if the read-only check passes, but that check reads the SQL text: the statement then runs with the connection's own rights, not in a read-only transaction.
- Not in the TUI yet: charts, functions and enums, git status for shared queries, index hints, a layout narrower than 80 columns, creating or editing connections, and forgetting a saved password (use the app). The DDL tab is rebuilt from the table's metadata, so it's approximate, and Constraints shows no CHECK constraints.
- A saved query edited in the TUI in a shared project reaches its git repo on the app's next sync.
- When the TUI writes, the app reloads every list, not only what changed.
