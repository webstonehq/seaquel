# seaquel-server (web)

Moved from the root `CLAUDE.md`, which has the overview and the crate map. "Above" and "below" may point at sections that now live in another `CLAUDE.md`. The Node side (`/api/rpc`, body limits, the stream proxy) is in `src/lib/server/CLAUDE.md`.

- `crates/seaquel-server/` (web; axum). `POST /rpc` takes the user from `X-Seaquel-User` and serves that user's workspace from an LRU (`workspaces.rs`, 1,024 open, `SEAQUEL_WORKSPACE_CAP` lowers it for tests; 2 `meta.db` connections each). Evicting a workspace runs its `close_all` in the background, so the user's database connections, streams and tunnels close and each of their `/rpc/stream` sockets gets `WORKSPACE_EVICTED`; an apply in flight stops too (its `failed` is `WORKSPACE_CLOSED`): an atomic one drops its transaction, which rolls it back unless its commit raced the close (the GUI marks the queue interrupted), and an in-order one stops at the statement in flight. Each user's calls in flight hold at most 40 MiB of bodies together (`MAX_IN_FLIGHT_BYTES_PER_USER`; a lone call and a body under 64 KiB, `SMALL_CALL_BYTES`, always run, the small one still counting), checked before parsing, and at most 4 of them are `db.applyChanges`, `db.planEdits`, `db.duckdbExtension`, `ai.generate`, `ai.models` or `ai.test` whatever their size (`MAX_EDIT_CALLS_PER_USER`, `is_slow_call` in `routes/rpc.rs`; a model call can hold its request for 10 minutes; `ai.respond` doesn't count, and turns are under `WEB_AI_LIMITS`); past either, 429 `TOO_MANY_REQUESTS`, which `errorText` shows as a sentence. The GUI's parallel startup loads are tiny next to the budget. It trusts that header, so **binding to loopback only is a security requirement** (`main.rs`): it refuses a non-loopback `BIND_ADDR` unless `SEAQUEL_ALLOW_NON_LOOPBACK=1`, which is never for deployments.
  - **`/rpc`** serves the `storage`, `library`, `settings`, `ui`, `db` and `ai` (but `chat`) groups; `shared` and `imports` answer `NOT_SUPPORTED` (501), since `web_core()` has no `LocalFiles`, and a web library write never publishes (`tests/rpc_shared.rs`, with both compiled in). It reads the write origin from `X-Seaquel-Origin` and checks it again (a bad one is dropped, not refused). The HTTP status comes from the error code (`error::status_for`: `CONNECTION_NOT_FOUND`, `PROJECT_NOT_FOUND`, `SAVED_QUERY_NOT_FOUND`, `LABEL_NOT_FOUND`, `DASHBOARD_NOT_FOUND`, `DASHBOARD_VERSION_NOT_FOUND`, `WORKFLOW_NOT_FOUND`, `CHAT_NOT_FOUND`, `THEME_NOT_FOUND`, `AI_PROVIDER_NOT_FOUND` and `NOT_FOUND` (`ai.respond`) 404, refused engines and options, `NOT_EDITABLE`, `NO_SECRET_STORE`, `NO_PROVIDER`, `NO_MODEL`, `NO_API_KEY`, `AI_DISABLED`, `CONNECTION_MISMATCH` and `TOOL_LIMIT` 400, `WORKSPACE_CLOSED`, `NO_ROWS_AFFECTED`, `CONFIRM_REQUIRED`, `TRANSACTION_OPEN`, `NAME_TAKEN`, `LAST_PROJECT`, `STORAGE_READ_ONLY`, `CHAT_FULL`, `TURN_IN_PROGRESS` and `AI_PROVIDER_CHANGED` 409, `TOO_MANY_CONNECTIONS`, `TOO_MANY_REQUESTS` and `RATE_LIMITED` 429, `RESULT_TOO_LARGE` and `MESSAGE_TOO_LONG` 413, `TLS_ERROR` and `PROVIDER_ERROR` 502, `AI_EGRESS_BLOCKED` 503, `TIMEOUT` 504, `STORAGE_FULL` 507). The body is always `RpcError`. A failure is logged as its `code`, `group` and `method` only.
  - **The log** (`startup.rs`): stderr, Seaquel's crates at INFO and dependencies at WARN, never `sqlx::query`, `sqlx::postgres::notice` or `tiberius::tds::stream::token` (`DROPPED_TARGETS`, submodules included: a `RAISE WARNING`'s text is the query's to choose, and tiberius logs every SQL Server error and `PRINT` with the server's text, which quotes values). The desktop's and the terminal binaries' log filters drop the same three and hold the rest of tiberius at WARN (its TLS warnings), and `russh`/`russh_keys` too (their DEBUG lines name the SSH bastion and its host keys; phase 7a). sqlx's MySQL and SQLite drivers and duckdb-rs log no database text. `format_record` writes a record's key-values (`activity`, `code`, ids, counts, kinds; never SQL or values) after the message, logfmt style: control characters escaped everywhere, a value holding a space, `=`, `"`, `\` or a control character quoted, each value cut at 128 bytes (`MAX_LOG_VALUE_BYTES`) and the message at 1 KiB, since some ids come from the browser.
  - **`GET /rpc/stream`** (`routes/rpc_stream.rs`) is one WebSocket per browser page, multiplexing the user's query streams. Client frames are `{op: "start", streamId, request}` (`request` inline, parsed from its exact bytes, and it must be `db.queryStream`, `db.run`, `db.page`, `db.tablePage` or `ai.chat` with the same `streamId`) and `{op: "cancel", streamId}`; server frames are `CoreEvent`s. A `streamId` is at most 128 characters of `[A-Za-z0-9_.:-]` (`MAX_STREAM_ID_LEN`; the clients send UUIDs), since it reaches the log before Core's ownership check; another is `INVALID_ARGUMENT` and never echoed. A bad frame gets a stream `error` (`INVALID_ARGUMENT`, `TOO_MANY_STREAMS`; a `run` error when the request names `db.run`, `db.page` or `db.tablePage`, an `ai` error for `ai.chat`, by `StreamKind` even when the frame doesn't parse), never a closed socket. Limits: 16 streams per socket (a run, page, table page or turn is one), 8 sockets per user (a 9th closes with 1013 `TOO_MANY_SOCKETS`), 8 MiB frames (1009 past it), and a batch whose frame would pass 4 MiB is split by rows, a run's as a stream's (the first piece keeps `columns`, the last `is_final`/`truncated`). Closing the socket (or losing it, or `EVENTS_LAGGED`) cancels its streams through Core and aborts their tasks, except a turn's, which runs on until it has stored its reply (aborted only after `TURN_STOP_WAIT`); a `respond` for it is then `NOT_FOUND`. A stream that ends with no `done`/`error` and wasn't cancelled by its own socket gets `error` `CANCELLED` (a `run` or `ai` error for those). **Closed windows' connections**: each socket with an origin holds its window (`Workspaces::hold_window`); when a window's last socket closes and none of that window's returns within `WINDOW_GRACE` (10 minutes; `with_window_grace` for tests), `close_owned_by` closes its connections in the user's open workspace (never opening one), and the user's other sockets get `connectionClosed` `WINDOW_CLOSED`. A reload comes back within the grace and its reconnects replace the old connections. A socket without an origin keeps nothing. Workspace events (`connectionClosed`, `storageChanged`) come from a per-user hub (`Workspaces::listen`), so a socket also hears about workspaces opened after it. The browser can't set headers on a WebSocket, so the page's origin comes as `/api/rpc/stream?origin=…`, which Node checks and turns into `X-Seaquel-Origin`; it can show up in a reverse proxy's access log, which is acceptable (the tab's window id, random, kept across that tab's reloads, naming no user and useless outside that user's session). Each socket's event queue is bounded at 1,024 events and 8 MiB (`LISTENER_EVENT_BOUND`, `LISTENER_EVENT_BYTE_BOUND`); a socket that falls behind either is closed with 1013 `EVENTS_LAGGED`, and the client reconnects and reloads. The loop takes an event only when the outbox has room, so a `cancel` is still read while events back up; refusals of client frames waiting for that room are capped at 64 (`MAX_PENDING_REFUSALS`), past which the socket closes with 1008 `TOO_MANY_PENDING`.
  - **`/internal/license/*`** (`routes/internal_license.rs`) is licensing for Node's hooks and routes, through `src/lib/server/license-client.ts`. It refuses (403) a peer that isn't loopback and any request without the per-boot secret in `X-Seaquel-Internal`, compared in constant time. Loopback alone isn't enough, since a query running inside the process (DuckDB's httpfs, in a build that has it) also arrives from loopback. `server.js` generates `SEAQUEL_INTERNAL_SECRET` and hands it to both processes; Rust removes it from its own environment at startup. Neither `server.js` nor any SvelteKit route forwards `/internal/*`, so it also needs Node and Rust on one host: a non-loopback `SEAQUEL_RUST_URL` fails closed. When the license service can't be reached, Node answers 503 (`api-gate.ts`: `{code: "license_service_unavailable"}` on `/api/*`, an operator page otherwise); `/health` skips the gate.
  - **Engines.** `web_core()` builds Core with `with_plugins(|id| WEB_ENGINES.contains(&id))`, `WEB_ENGINES = ["postgres", "mysql", "mssql"]`, so SQLite and DuckDB fail with `ENGINE_NOT_AVAILABLE` (400) whatever Cargo compiled in (`tests/web_engines.rs`). `web_config.rs` refuses, on connect and test, connection options that name a file or socket on the server: Postgres and MySQL TLS certificate and key paths, `passfile`, MySQL `socket`, socket hosts and URLs without a host (`CONNECTION_OPTION_NOT_ALLOWED`, 400). So client certificates and socket connections are desktop-only.
  - **One reader per user.** Since phase 7a a user's two storage connections are one reader and the writer, so the user's reads queue on that one pooled reader: a large chat or workflow read holds up their other reads (writes don't wait for it).
  - **Per-user size cap.** Each user's `meta.db` opens with `PRAGMA max_page_count` from `SEAQUEL_USER_DB_MAX_BYTES` (bytes; 2 GiB by default, clamped to 64 MiB–1 TiB; `StorageOptions::max_bytes`, `user_storage_options`). A write past it fails with `STORAGE_FULL` (507) and stores nothing; a file already past a lowered cap stays readable. It is a backstop behind the per-call limits (`WEB_LIBRARY_LIMITS`, `WEB_STATE_LIMITS`), not a quota the GUI shows. The desktop has no cap. `WriteTx` sends `BEGIN`/`COMMIT`/`ROLLBACK` itself, because SQLite rolls a transaction back on `SQLITE_FULL` and sqlx's `Transaction` would leave the pooled connection unusable after the failed `ROLLBACK`.
  - **Environment.** `server.js` starts Rust with an allow-list (`shared/rust-env.js`: the variables the Rust crates read, the proxy and CA variables, `PATH`/`TZ`/`LANG` and temp dirs) and `HOME=/nonexistent`, because sqlx takes defaults from `PG*` variables and `~/.pgpass`. The binary also scrubs `PG*`/`MYSQL*` and sets that `HOME` itself at startup (`startup.rs`), which covers `npm run rust:dev`. A new env var the Rust service reads goes into the allow-list; its vitest scans the crates for them (`seaquel-http` included). **Model calls** (phase 6): `web_core_from_env()` builds Core with `NativeHttp` under `SEAQUEL_AI_EGRESS` (README's configuration table, `deploy/docker/.env.example`), trusting `NODE_EXTRA_CA_CERTS`, and `WEB_AI_LIMITS`. The page decrypts the provider's key from the vault and sends it with each `ai.chat`, `generate`, `models` and `test`; the server holds it in memory for that call only, as it does database passwords. An OpenAI-compatible server on the user's own machine isn't reachable from web; one next to the server is, under `any`.
