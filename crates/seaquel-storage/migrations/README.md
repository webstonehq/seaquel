# seaquel-storage migrations

Numbered schema and data migrations for the metadata database, run by `sqlx::migrate!` every time `Storage::open` opens a file, right after the baseline (`src/schema.rs`) and before the data steps (below).

- **The baseline is frozen.** It brings every file any release ever wrote up to the schema of 2026.9.x. Every schema change after that is a new file here, never another step in `schema.rs`.
- **Names:** `NNNN_description.sql`, numbered from `0001` with no gaps. sqlx reads the number before the first `_` as the version and runs files in version order.
- **Never edit a migration that has shipped.** sqlx stores each file's checksum in `_sqlx_migrations` and refuses to open a file whose recorded checksum doesn't match. Fix a mistake with a new migration.
- **Each file runs in its own transaction,** a savepoint inside the migration lock's `BEGIN IMMEDIATE` (below). It is recorded as applied only if it succeeds, and a failure also rolls back the files this open applied before it. sqlx 0.8's SQLite migrator ignores `-- no-transaction`, and a file can't leave the lock's transaction anyway, so don't write one that needs to run outside a transaction (`PRAGMA foreign_keys = OFF` for a table rebuild, `VACUUM`).
- **A file must work on every database the baseline can produce**, including files that started on `v2026.4.5-beta.1`: there, `saved_queries.project_id` and `dashboards.project_id` are nullable, last in column order and have no foreign key (see `tests/fixtures/README.md`). Name columns explicitly; never rely on column order.
- **Migrations are expand-only.** Going back to an older release has to keep working: releases 2026.4.5 through 2026.9.x already open files a newer build changed, and the migrator ignores applied versions it doesn't know (`set_ignore_missing(true)`). So a migration may add tables, columns, indexes and rows, and must not:
  - drop or rename a table, column or index;
  - add a `NOT NULL` column without a default;
  - change what an existing column means or how its values are encoded.
- **A breaking change needs an explicit gate.** If a change can't be expand-only, it also writes a new `schema_version` value, and the release that ships it teaches `Storage::open` to refuse a file whose highest version is above what it knows, with its own error code, before touching it. Builds older than that gate can't refuse, which is why the rule above comes first.
- **Opens are serialised around the migrator** (phase 4). sqlx's own migrate lock is a no-op on SQLite, so `Storage::open` (`migrate` in `src/open.rs`) does it: it reads `_sqlx_migrations` without a lock, and only when something is pending (or the table is missing, or a record is dirty or has another checksum) takes `BEGIN IMMEDIATE` and runs the migrator on that connection, which reads what's applied again under the lock. A second pool or process opening the file at that moment waits for the lock and then finds nothing left to do, so both opens succeed and each migration runs once. This covers the web server's second pool on a user's file while an evicted one is still finishing a request (`crates/seaquel-server/src/workspaces.rs`), and the app next to another process. While the baseline or a migration has work to do, a busy `BEGIN IMMEDIATE` is retried up to 12 busy timeouts of 5 s (`MIGRATION_WAIT_ATTEMPTS`, since 5d-2's `0003`); an open with nothing pending waits one busy timeout and then fails with `STORAGE_ERROR`, so a lock another process holds doesn't stall startup. Keep migrations short anyway: a waiting opener past about a minute still fails. Data steps take the same kind of lock, each in its own transaction. `tests/open.rs` races two pools on a test-only migration (`tests/test_migrations/`).
- **Read-only opens run none of this.** `StorageOptions { read_only: true }` (the CLI) refuses a file the baseline, a migration or a data step would change, with `STORAGE_NEEDS_UPGRADE`, and never writes it. So a new migration or data step makes the CLI refuse files until the app has opened them once; the bundled CLI and the app ship together, so in practice the app already has. A data step that keeps failing is the exception: the app logs the failure and starts anyway, so the CLI keeps refusing the file after the app has opened it. That refusal (`StorageError::DataStepPending`, still `STORAGE_NEEDS_UPGRADE`) says the app couldn't finish a data cleanup and points to the app's log, so a step must not fail on data a user can't fix.
- **The browser runs them too** (phase 8). On wasm32 there is no sqlx: `build.rs` embeds these files as a list, and `src/open_mem.rs` applies them the way sqlx's SQLite migrator does (the same `_sqlx_migrations` table, version, description and SHA-384 checksum, each file in a savepoint under one `BEGIN IMMEDIATE`). `src/migrations.rs` checks natively that the list matches `sqlx::migrate!`. After adding a migration or a data step, regenerate `tests/fixtures/wasm-made/meta.db` (see `tests/fixtures/README.md`); until then `tests/wasm_made.rs` checks only what the fixture recorded and says so.
- **Tests:** `tests/baseline.rs` opens every frozen release schema. Add a case for a migration that moves data. The frozen schema fixtures stop at the baseline, so the tests compare a file `Storage::open` made with the fixture plus every file here (`load_migrated` and `migrated_shape` in `tests/common/mod.rs`). The test-only migrators in `tests/test_migrations*` number their files from `9001` so they never clash with these.

## Migrations

- **`0001_name_keys.sql`** (phase 5d-1 probe fix). Adds a nullable `name_key` column to `connections`, `projects` and `saved_queries`, an index for Core's duplicate-name check on each (`(project_id, name_key)`, `(name_key)`, `(project_id, COALESCE(folder, ''), name_key)`), and a trigger per table that sets `name_key` to NULL when `name` changes and `name_key` doesn't. The key is `seaquel_types::names::name_key(name)`: storage writes it with every name it stores (`connections::insert`/`update`, …, in a second statement so the trigger can't leave a case-only rename NULL), and the `backfill_name_keys` data step fills the rows that were there before. NULL always means "not known": the lookups (`connections::with_name_key`, …) also read the rows with a NULL key and compare their names in Rust. Older releases keep working: they write rows without a key (NULL), and when they rename a row the trigger drops its key, so no key is ever stale.
- **`0002_window_state.sql`** (phase 5d-2, Decisions 21 and 22 of the 5d plan). Adds `windows` (one row per desktop window or web browser tab: `window_id`, `active_project_id` without a foreign key, `updated_at`) and `window_state` (one window's view of one project as a JSON blob, with `rev`, the page's save counter, keyed `(window_id, project_id)` and cascading from both `windows` and `projects`), with the indexes the prunes and the "most recent window" read first used (`idx_windows_updated`, `idx_window_state_project(project_id, updated_at DESC)`; `0003` moved "most recent" to `write_seq`). Also `idx_saved_canvases_project`, since saved workflows are now listed and removed per project, `idx_ai_messages_chat_time(chat_id, timestamp)`, so a chat's messages are read in order without a sort, and `dashboards.name_key` with its index `(project_id, name_key)` and a `dashboards_name_key_stale` trigger, exactly as `0001` does for the other three tables (filled by `backfill_dashboard_name_keys`). Older releases never read the new tables; they keep reading `project_state` and `tabs`, which every view-state save still writes as a mirror (`project_state::write_legacy_mirror`). Like `0001`, it makes `seaquel-cli mcp` refuse a file until the app has opened it once.
- **`0003_window_order_and_list_meta.sql`** (phase 5d-2 Task 7 probe fixes). Adds `write_seq INTEGER NOT NULL DEFAULT 0` to `windows` and `window_state`, with `idx_windows_write_seq` and `idx_window_state_project_seq(project_id, write_seq)`: every window write stores one past the table's highest (for `window_state`, the project's), so "most recent" is the last write committed even for writes in one millisecond, where the rowid tie-breaks disagreed and an upsert kept its rowid. The rows already there are numbered in the order the old queries read them. Also `saved_canvases.meta` (a workflow's `{name, createdAt, updatedAt}` as JSON, written with its data, cleared by the `saved_canvases_meta_stale` trigger when `data` changes without it) and `dashboard_versions.widget_count`, both filled here for the rows already there, so `workflowsList` and `dashboardVersionsList` answer without reading any body; a NULL (a row an older release wrote) is computed from that row's body when it's listed. Older releases write whole `saved_canvases` rows without `meta` and versions without a count, which is exactly that NULL. A body that can't be read is marked (`meta` `'null'`, `widget_count` `-1`) rather than left NULL, so NULL only ever means "not filled yet", and partial indexes (`idx_saved_canvases_meta_pending`, `idx_dashboard_versions_count_pending`, `WHERE … IS NULL`) let every writable open check for such rows with two index lookups and fill them (`refill_list_meta`, run after `refill_name_keys` by Core and by a capped web open; not a recorded data step), since an older release's replace-all save of a project's workflows writes rows without `meta` again. Like `0001` and `0002`, it makes `seaquel-cli mcp` refuse a file until the app has opened it once.

  **Its fill runs inside the migrator's `BEGIN IMMEDIATE`**, parsing every stored workflow and version once: about 3 s per GB of them, so about 6.5 s on a web user's file at the 2 GiB cap, longer than the 5 s busy timeout another opener of the file waits. That is acceptable: on desktop it runs while the storage gate waits at startup, before any other call; on web only the race between an evicted workspace's pool and a fresh one on the first open after the upgrade can see it. And that opener no longer fails: when the baseline or a migration has work to do, `Storage::open` retries `BEGIN IMMEDIATE` on `SQLITE_BUSY` up to 12 busy timeouts (about a minute, `MIGRATION_WAIT_ATTEMPTS` in `src/open.rs`) before it gives up with `STORAGE_ERROR`. An up-to-date file (every other open) still waits one busy timeout, so a lock another process holds doesn't stall startup.

- **`0004_shared_links.sql`** (phase 5e Task 3, Decision 33 of the 5e plan). Adds nullable link columns: `projects.shared_dir` (the project's directory under `.seaquel/projects/` in its repo, so a rename of the local project never moves it), `saved_queries` and `dashboards` `shared_path` (the repo-relative path of the row's file), `shared_base` (the hash of the content both sides had at the last sync) and `shared_file_id` (the `id` Core writes into the file), and `connections.shared_base`/`shared_file_id` (a template's path stays in `shared_connection_id`, `<repoId>:<path>`, where older releases match it), with `idx_saved_queries_shared_path` and `idx_dashboards_shared_path` on `(project_id, shared_path)`. NULL means "not known" (the slug rule, no base); there is no data step, since the first sync fills them from what it pairs. Only the `set_link`/`set_shared_dir` functions write them; `insert`, `update` and the frozen replace-all saves leave them alone, and the `Persisted*` reads carry `sharedPath`. Older releases keep working: they never read the columns, and their saves (whole-row inserts and `ON CONFLICT DO UPDATE` upserts naming their own columns) leave a link as it was, so an older release's edit reaches Core as a row change against an unchanged base. Unlinking a project (Q31) clears a kept connection's `shared_connection_id`, base and origin but keeps its `shared_file_id`, so linking again adopts that connection's template instead of writing a second one (5e probe fix 1). Like `0001`–`0003`, it makes `seaquel-cli mcp` refuse a file until the app has opened it once.
- **`0005_shared_connection_origin.sql`** (phase 5e Task 7 review, Q31 of the 5e plan). Adds a nullable `connections.shared_origin`: `exported` for a linked connection the project shared (ticked at link time, or shared later with the local-only switch), `imported` for one a sync made from a teammate's template. Unlinking a project keeps the `exported` ones and asks before removing the others. NULL means "not known": no link, or a link an older release stored, and every such link came from importing a template, so Core treats it as imported. Only Core writes it (`connections::set_origin`; `set_link` clears it with the link and keeps it while the link stays); `insert`, `update` and the frozen saves leave it alone, and the reads carry it as `sharedOrigin`. It is a new file and not an edit of `0004`, which hadn't shipped in a release but had been applied by dev builds since Task 3: sqlx would refuse those files over the changed checksum (`MigrationState::Mismatch`). Dev databases from phase 5e Tasks 3–6 (at `0004`, no `0005`) get the column on their next writable open, NULL on the links those builds stored, the exported ones included: until such a connection is shared again, an unlink counts it as imported and asks before removing it (`tests/shared.rs`, `a_dev_file_at_0004_is_refused_read_only_and_upgraded_by_a_writable_open`). Like `0001`–`0004`, it makes `seaquel-cli mcp` refuse a file until the app has opened it once.
- **`0006_history_params.sql`** (cleanup pass B). Adds a nullable `query_history.params`: the JSON array of values an applied change was bound with, in the cell wire format (`seaquel_types::Value`), next to the row's `query`, which stays the SQL Core ran with its `$n`/`?`/`@Pn` placeholders. NULL means no values: a run (recorded with its `{{param}}`s), a change without binds, a row written before `0006` or by an older release. Only `query_history::append`, `append_many` (Core's applies) and the frozen `replace_all` write it, as NULL for `None` or an empty list; `load_by_connection` reads it back as `params`, and reads a value that isn't such an array as `None` instead of failing the list. Older releases keep working: their loads read columns by name, and their appends name their own columns, so their rows get NULL. No data step. Like `0001`–`0005`, it makes `seaquel-cli mcp` refuse a file until the app has opened it once.

## Data steps

A data step is a one-off rewrite of stored rows done in Rust. `Storage::open` runs the pending ones right after the numbered migrations (`src/data_steps.rs`), each in its own `BEGIN IMMEDIATE` transaction, and records each by name in `_seaquel_data_steps(name TEXT PRIMARY KEY, applied_at TEXT)`, so each runs once per file. The step creates that table the first time it runs; the baseline doesn't, and schema comparisons skip it, as they skip `_sqlx_migrations`. A file that has had every step only gets a read at open.

**Which one to write:**

- **A SQL migration** for schema changes (tables, columns, indexes) and for data changes plain SQL does in one set-based statement.
- **A data step** when the rewrite needs Rust logic: parsing, a function the queries already use (so the stored rows and new writes agree by construction), or anything a recursive CTE would have to imitate. SQL that walks strings character by character is quadratic in SQLite, and it can't be fixed after it ships, because sqlx checksums the file.

**Rules for data steps:**

- **Append only.** Add a step to the end of `STEPS` with a new name. Never rename, reorder or remove one that has shipped: a file records names, not code.
- **Its code can change** after it ships (a data step has no checksum), but files that already ran it won't run it again. If they need the fix too, add a new step.
- **Address rows by `rowid`**, since ids can be NULL on hand-edited files. Write only the rows that change, and leave alone text that doesn't decode as UTF-8.
- **Keep it linear** in rows and string length. `tests/repos.rs` has a timing test for the first step.
- **Expand-only, like migrations.** Older releases open the file afterwards, so a step may rewrite values within their existing meaning and must not change what a column holds.

## Steps

- **`strip_connection_string_passwords`** (phase 3 Task 4, Decision 13.1 of the phase 3 plan). Applies `strip_connection_string_password` (`src/connection_string.rs`), the function `connections::save` applies to every save from now on, to each stored `connections.connection_string`. It removes `Password` and `Pwd` pairs (any case) from key=value strings (`Server=…;Password=…`), which the TypeScript stored with their password because it only knew how to strip one from a URL. It also removes URL passwords and `password`/`pwd` query parameters. It leaves SQLite strings alone, along with strings that hold no password.
- **`drop_legacy_built_connection_strings`** (phase 5d Task 3, Decision 12 of the 5d plan). Rows written before phase 5a hold the string the old `buildConnectionString` rebuilt from the row's own fields on every save. Core connects with a string when there is one and ignores the fields, so such a string goes stale as soon as a field is edited. The TypeScript dropped them on every load; this step does the same once per file, so the MCP server, which never runs that load, stops connecting with them. It is a port of `isLegacyBuiltString` (`src/lib/utils/connection-string-rules.ts`), as `is_legacy_built_string` in `src/connection_string.rs`, and follows that load row by row:
  - fields are read as `connections::load_all` reads them, and an empty `username` is first taken from the string's URL user, as the load did;
  - a non-empty string that is the old builder's for those fields (compared after trimming, with `postgresql://` read as `postgres://`, and through the WHATWG URL parser without its password) becomes NULL;
  - when the user came from the string, it is written to `username`, as the load's save wrote it back;
  - every other string, and every row with a value that isn't UTF-8, is left as it is.

  One deliberate difference: for a MySQL or MariaDB row whose SSL mode names an `Object.prototype` member (`toString`, …), the TypeScript built the member's source text into the string, which differs between JavaScript engines, so the step never calls that row's string legacy and keeps it.
- **`backfill_name_keys`** (phase 5d-1 probe fix, with `0001_name_keys.sql`). Sets `name_key` to `seaquel_types::names::name_key(name)` on every `connections`, `projects` and `saved_queries` row whose key is NULL and whose name is UTF-8 text, by rowid, in one pass. It is a data step rather than SQL because the key is Unicode NFC plus full case folding, and it must be the very function the writes use. A row it leaves NULL (no name, or bytes that aren't UTF-8) is still found by the duplicate check. Because an older release can leave new NULL keys after the step ran (a downgrade, then the upgrade again), Core also runs `refill_name_keys` on every writable open: a single `EXISTS` read, and the same fill when it finds one. That isn't recorded as a step. `refill_list_meta` (migration `0003`) runs right after it on the same opens, and after a downgrade it holds the write lock while it parses the saved workflows an older release rewrote without `meta` (about 1.5 s for 480 MiB of them) and counts the widgets of its versions; like this refill it runs at open, behind the storage gate on desktop. If `name_key` ever changes (a new Unicode version in `unicase` or `unicode-normalization` counts), add a step that recomputes every key.
- **`backfill_dashboard_name_keys`** (phase 5d-2, with `0002_window_state.sql`). `backfill_name_keys` for `dashboards`: the same function, the same rules (NULL key and UTF-8 text name only, by rowid, one pass), so Core's dashboard `NAME_TAKEN` check (Decision 21) is an index search. A beta-era dashboard with a NULL `project_id` gets a key too. `refill_name_keys` covers dashboards from here on.
