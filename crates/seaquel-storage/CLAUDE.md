# seaquel-storage

Moved from the root `CLAUDE.md`, which has the overview and the crate map. "Above" and "below" may point at sections that now live in another `CLAUDE.md`.

- `seaquel-storage` — the metadata SQLite database: open, schema and one typed function per query (`queries/`); the only place SQL for it lives. `data_dir(identifier)` reads `SEAQUEL_DATA_DIR` (an empty value is ignored), else the platform data dir plus the Tauri identifier. `data_local_dir(identifier)` is the folder for files that belong to the machine, the CLI the app installs and the DuckDB helper (`dirs::data_local_dir()` plus the identifier: the data dir on macOS and Linux, under `%LOCALAPPDATA%` on Windows); `SEAQUEL_DATA_DIR` wins there too and is then that folder itself, so the terminal binaries, the app's install and the tests agree on one helper and never reach the real folder under test. The file is `<data_dir>/seaquel.db` on desktop and `DATA_DIR/users/<id>/meta.db` on web. `Storage::open` runs the frozen baseline (`schema.rs`, which upgrades every released file), then numbered expand-only SQL migrations (`migrations/`, rules in its README), then Rust data steps (`data_steps.rs`, recorded in `_seaquel_data_steps`). Schema changes are new migration files, never baseline edits. The first is `0001_name_keys.sql` (5d-1): nullable `name_key` columns on connections, projects and saved queries with their indexes, and triggers that set a row's key to NULL when an older release renames it without one. Storage writes the key with the name, the `backfill_name_keys` data step fills the rows already there, and `refill_name_keys` (on every writable open, after Core's secrets upgrade) fills any NULL an older release left. `0002_window_state.sql` (5d-2) adds `windows`, `window_state` and `dashboards.name_key` (its trigger and index as `0001`'s). `0003_window_order_and_list_meta.sql` adds `write_seq` to both window tables and the list metadata `saved_canvases.meta` and `dashboard_versions.widget_count`, so `workflowsList` and `dashboardVersionsList` read no bodies; a body that can't be read is marked (`'null'`, `-1`) so NULL only means "not filled yet", and `refill_list_meta` (right after `refill_name_keys`, on the same opens) fills the NULLs an older release's writes leave. `0004_shared_links.sql` (5e) adds the shared projection's link columns (`projects.shared_dir`; `shared_path`, `shared_base`, `shared_file_id` on saved queries and dashboards; `shared_base`, `shared_file_id` on connections) and `0005_shared_connection_origin.sql` `connections.shared_origin`; only `set_link`, `set_shared_dir` and `set_origin` write them, so no library write or older release's save moves a link, and NULL means "not known" (no data step). `0006_history_params.sql` adds `query_history.params`, the bound values of an applied change as a JSON array in the cell wire format (NULL for runs, for rows older releases wrote, and for an apply with no values). `0007_ai_message_parts.sql` (phase 6) adds `ai_messages.parts`, a reply's tool calls as a JSON list (NULL means none; an older release ignores it and shows the text, and its `chatMessagesPut` keeps the stored value through `COALESCE`); `append_turn_in` writes a turn's rows, and the chat budget (`CONTENT_BYTES`, `max_chat_bytes`, `storedBytes`) counts `parts` with the content. The data steps are the phase 3 password strip, `drop_legacy_built_connection_strings` (5d-1: drops a pre-5a string equal to what the old TypeScript builder made of the row's fields, which the GUI's load used to do), `backfill_name_keys` and `backfill_dashboard_name_keys` (5d-2). Each new migration or data step makes `seaquel-cli` (`mcp` and the read commands) and `seaquel-tui` refuse the file (`STORAGE_NEEDS_UPGRADE`) until the app has opened it once. **Writes** go through `Storage::write`, which returns a `WriteTx` (`write.rs`): writers in one process queue on an async mutex that owns the storage's one **writer connection** (phase 7a; outside the pool, which gets `max_connections - 1`, at least 1; with `idle_timeout` set, as on web, a reaper closes it once it has gone unused that long), then begin with `BEGIN IMMEDIATE` on it; a writer still waiting after `WRITE_WAIT` (30 s) fails with `STORAGE_ERROR`, and read-only storage fails at once with `STORAGE_READ_ONLY`. Every write, `VACUUM` and checkpoint runs on that connection, and a `ROLLBACK` that fails closes it, so the next write opens a fresh one; `WriteTx` turns a `secure_delete` it set off again before handing the connection back. That includes the 25 single statements that used to go straight to the pool (`app_state::set`, `query_history::set_favorite`, `user_credentials`, `vault_state`, the license, `tutorial`, `import_state`, `themes::save_preferences`, the frozen-fixture saves), each now in its own `WriteTx`, so on read-only storage they fail with `STORAGE_READ_ONLY`. A write on any other connection would look external to the poll. `Storage::external_version()` (native) answers a counter over `PRAGMA data_version` on the writer connection, which only another connection's commit moves: it moves when the pragma differs from the last poll's, and once when the writer connection was replaced (two connections' values don't compare). It is `None` while a write holds the turn (`try_lock`); another connection's `wal_checkpoint(TRUNCATE)` also moves it once, with no commit; read-only storage polls on a connection of its own; `Storage::close` closes the writer after any write in flight. **Inside a write, read only through `&mut tx`**: a read through `&storage` takes a pool connection and doesn't see the transaction's writes (on wasm32, whose pool is the one connection, it waits for the transaction). The targeted functions (`connections`, `projects`, `project_labels`, `saved_queries`, `query_versions::append_keyframe`, and since 5d-2 `dashboards`, `dashboard_versions`, `saved_canvases`, `ai_chats`, `app_state`, `themes`, `windows`, `window_state`, `project_state::write_legacy_mirror`, and since 5e `shared_repos::{insert, update_json, delete}` and the link writes, …) take `&mut WriteTx`; the replace-all ones (`projects::save_all`, `saved_queries::save_all`, `project_state::save`, `ai_chats::replace_all_messages`, `themes::save_user_themes`, `shared_repos::save_all`, …) stay only for the frozen repo fixtures. `shared_repos::update_json` splices the named fields into the stored JSON and keeps every other byte. The `connection_overrides` table and its functions stay too, though nothing reads or writes overrides since they were retired in 5d-2. Query history is written only by `query_history::append` (the row plus the 500-row cap, favourites kept), `append_many` (Core's applies: many rows in one transaction, one prune; no RPC) and `set_favorite` (sets, never toggles), as `queryHistoryAppend`/`queryHistorySetFavorite`; `replace_all` stays only for its frozen repo fixture and has no RPC. A pending migration runs under a `BEGIN IMMEDIATE` lock held on the migrator's own connection (each migration is a savepoint inside it), so two pools or processes opening one file apply it once. While the baseline or a migration has work to do, the other opener retries the lock for up to 12 busy timeouts (`MIGRATION_WAIT_ATTEMPTS`, about a minute; `0003`'s fill takes about 3 s per GB of workflows and versions); with nothing pending it fails after one, so a lock another process holds doesn't stall startup. `StorageOptions { read_only: true }` (for `seaquel-cli`) opens with `SQLITE_OPEN_READONLY`, never sets the journal mode or creates the file, and runs nothing: if the baseline (`schema::is_current`), a migration or a data step has work to do it fails with `STORAGE_NEEDS_UPGRADE`, a missing file with `STORAGE_NOT_FOUND`. `schema: SchemaPolicy::RequireCurrent` (phase 7a, a second process such as the TUI; `WorkspaceSpec::second_process`) makes the same checks and refusals but opens writable: it never creates the file, leaves the journal mode as the app set it (WAL) and runs nothing; `max_bytes` applies. Fixtures in `crates/seaquel-storage/tests/fixtures` (each release's schema, the repo cases) are frozen. Codes that block the app: `LEGACY_STORAGE` (only pre-2026.4.5 JSON files, no `seaquel.db`), `STORAGE_CORRUPT`, `NO_DATA_DIR`; anything else is `STORAGE_ERROR`.
  - **One set of queries, two executors** (phase 8). Every query goes through the crate's `db` module (`src/db/`), picked by `target_arch`, not a feature. Natively `db/native.rs` re-exports sqlx under the names the queries use, so desktop and web storage is sqlx as before; nothing outside it names sqlx. On wasm32 `db/mem/` is the same API over `sqlite-wasm-rs`'s C API (`ffi.rs`, the crate's only `unsafe`, single-threaded SQLite), copying sqlx 0.8.6's binding, `rows_affected`, `fetch_optional` and type-compatibility rules and its error `Display` and codes, so `STORAGE_FULL`, the corrupt and busy checks read the same. The wrapper also compiles natively over `libsqlite3-sys` 0.30.1 for its tests. Its pool is one connection behind an async mutex (`lock.rs`: `futures::lock` on wasm32, tokio's natively), stricter than the native pools: a read through `&storage` while the same task holds a `WriteTx` waits, then fails after 30 s. `StorageOptions::in_memory(image)` (wasm32) deserializes an image (a desktop file's WAL header is rewritten first) or makes a new file, then runs the baseline, the migrations and the data steps as `Storage::open` does; `migrations.rs` (generated by `build.rs`) records them in `_sqlx_migrations` with sqlx's checksums (`migrations_match_sqlx` pins it), so a browser file opens natively with nothing pending (`tests/wasm_made.rs`, `tests/fixtures/wasm-made/`) and the other way round. `snapshot()` is `sqlite3_serialize`, refused while anyone holds the connection or a transaction is open; `commits()` counts commits through SQLite's commit hook and can run ahead of real changes (an empty `BEGIN IMMEDIATE … COMMIT` counts), never behind. The write turn races the executor's `sleep` (`Storage::with_executor`); a dropped `WriteTx` rolls back synchronously on wasm32. tokio, sqlx, `dirs` and `data_dir` are native only. The wasm tests run with `CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUNNER=wasm-bindgen-test-runner cargo test --target wasm32-unknown-unknown -p seaquel-storage --all-targets` (and the clang above).
