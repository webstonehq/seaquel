# seaquel-cli

Moved from the root `CLAUDE.md`, which has the overview and the crate map. "Above" and "below" may point at sections that now live in another `CLAUDE.md`.

- `seaquel-cli` — the `seaquel-cli` binary (clap), a per-target release asset the app downloads on request (`src-tauri` below), with six subcommands: `mcp [--connection …] [--project …] [--log-level …]`, `duckdb status|install [--from FILE --sha256 HEX]`, and the read commands (phase 7b, part 1; `docs/plans/2026-10-04-cli-read-commands.md`) `conn list|test`, `schema`, `saved list|show` and `query`, below. It opens `seaquel.db` read-only with `KeychainStore` (service `app.seaquel.desktop` in every build) and `~/.ssh/known_hosts`; the data dir is `data_dir("app.seaquel.desktop")`, `.dev` in a debug build, or `SEAQUEL_DATA_DIR`. Since it runs no migration or data step, a release that adds one (5d-1 and 5d-2 each add both, 5e adds `0004` and `0005`, the cleanup pass `0006`, phase 6 `0007`) makes it refuse the file with `STORAGE_NEEDS_UPGRADE` until the app has opened it once (which also runs the secrets upgrade the CLI never runs). Its Core has `LocalFiles` and `imports` (no `git`, so no shared projection), and no command uses them yet (`seaquel-core/tests/shared_cli.rs` builds a workspace as the CLI does: candidates and scans answer, writes are `STORAGE_READ_ONLY`). `--version` prints the desktop app's version (`seaquel-terminal`'s `build.rs` reads `src-tauri/Cargo.toml`) and the terms line; it checks no license. The binary can't be named `seaquel`: the app owns that name on every platform. Debug builds only (`cfg!(debug_assertions)`, `seaquel_terminal::TestHooks` under `SEAQUEL_CLI_TEST`) read the test hooks `SEAQUEL_CLI_TEST_SECRETS` (a JSON file loaded into a `MemoryStore`), `SEAQUEL_CLI_TEST_KNOWN_HOSTS`, `SEAQUEL_CLI_TEST_CALL_TIMEOUT_MS`, `_DUCKDB_HELPER` and `_DUCKDB_RELEASES` (`seaquel-terminal` below); a release build ignores them. In `mcp`, SIGTERM and SIGINT close connections and tunnels like stdin closing does. `tests/stdio.rs` runs the built binary and checks that stdout carries only JSON-RPC, the DuckDB startup line going to stderr. Its data dir, Core builder, test hooks, log filter, signals and version text come from `seaquel-terminal` (phase 7a). **DuckDB** runs in the helper (`seaquel-duckdb` above), so the CLI links no DuckDB but has reqwest (through `seaquel-http`, for `duckdb install`). `duckdb status` (`src/duckdb.rs`) prints one word on stdout, `installed <path>`, `missing`, `outdated` or `unsafe`, and exits 0 only when installed (so `status || install` works in a script); `duckdb install` prints the installed path on stdout and nothing else, its progress (the size, then a line per 10%), "already installed", the pruned count and failures on stderr, worded as the TUI words them (what failed, what to do, `CODE: message`); `--from FILE --sha256 HEX` (clap requires both) installs a copy of the release asset offline. SIGINT or SIGTERM drops the install, the runtime gets 3 s (`shutdown_timeout`) for the `.part` to go, and it exits 130. `outdated` and `install --help` say that one helper is kept per version, the two newest at a time. No logger is set up for `duckdb`. In `mcp`, an `ENGINE_NOT_INSTALLED` from a DuckDB connection is reworded by the helper's status (`seaquel-mcp`'s `duckdb_helper.rs`): missing, outdated or unsafe gives `DuckDB support isn't installed for seaquel-cli <version>. Run "seaquel-cli duckdb install", or use Install Command Line Tool in the Seaquel app.`; installed but refused (it won't start, or answers another version) says so and points at `seaquel-cli duckdb status`, never at `install`, which would find it intact and do nothing. When an exposed connection is DuckDB and an install would fix it, `McpServer::duckdb_helper_notice()` gives one stderr line (`seaquel-cli mcp: …`, whatever `--log-level`) and the server starts anyway; neither text names a connection or a path. `restricted` reaches the helper's `open` unchanged. `McpServer::close` disconnects its connections concurrently, since a helper's close can take its 2 s. **The read commands** (`conn.rs`, `schema.rs`, `saved.rs`, `query.rs`) each open a `Session` (`session.rs`): the same read-only workspace as `mcp`, so they write nothing, record no history and refuse a file the app hasn't upgraded or made (`STORAGE_NEEDS_UPGRADE`, `STORAGE_NOT_FOUND`, printed with "Open the Seaquel app once, then run this again."); the keychain behind a `SecretWait`, with one stderr line ("Waiting for the system keychain…") once a call has been pending 250 ms. Their connects carry no origin, so the connections belong to no window, like MCP's; `Session::close` closes them within 5 s (`CLOSE_WAIT`), then storage, and the runtime gets 3 s more for the cancels Core spawned. A connection, project or saved query is named by id, else by exact, case-sensitive name (`resolve.rs`, over `seaquel_mcp::exposed`'s now-public `find_connection`, `find_project` and `lookup`; the first two take a `Subject`, `Flag("--connection")` in `mcp`, whose messages are unchanged, and `Noun("Connection")`/`Noun("Project")` in the read commands, which name no flag: `Connection "x": no saved connection has this name or id`); a name several rows share is `AMBIGUOUS_CONNECTION`/`AMBIGUOUS_PROJECT`/`AMBIGUOUS_SAVED_QUERY` naming every id and ending "Pass the id instead." (`resolve::saved_connection` reads the projects and connections and resolves one, for `conn test`, `schema` and `query`). `conn list` and `saved list|show` connect to nothing; `conn list` never prints a connection string, and `saved show` prints the text as stored plus a newline when it has none. `schema CONNECTION [TABLE]` lists `schema_tables` (`kind` in Core's spelling: `table`, `view`, `materialized-view`; `rowCount` the engine's estimate or `null`) or describes one table through `table_metadata`, matching `TABLE` against a listed name or `schema.name` without splitting on `.`, so DuckDB's `catalog.schema` works (`TABLE_NOT_FOUND`, `AMBIGUOUS_TABLE`). **Connecting** (`connect.rs`; the TUI's `to_ask`/`failed` ported as the pure `ask_before`/`next`): at most 4 attempts, each secret asked for once, and a wrong one isn't asked for again (the command fails). Interactive means stdin and stderr are both terminals and `--no-input` isn't set (`prompt::for_command`), so piped SQL turns prompts off. Then a password the row doesn't save (or, after `SECRET_STORE_UNAVAILABLE`, one the keychain would have held) is asked for before connecting; a `CREDENTIALS_REQUIRED` is asked for only when Core's message, with the connection's quoted name taken out, names a password (not a missing host, user or key file); and `UNKNOWN_HOST_KEY` shows the SSH host and fingerprint (`seaquel_terminal::host_key_fingerprint`) and asks "Trust this host?", whose yes retries with `HostKeyPolicy::Trust`, so Core writes `~/.ssh/known_hosts`; `HOST_KEY_MISMATCH` is never offered. Not interactive, both fail with a sentence saying to run it in a terminal. A DuckDB `ENGINE_NOT_INSTALLED` is worded as in `mcp` (`seaquel_mcp::duckdb_helper::reword_connect_error`, taking the row's engine). `Prompter` is async: the terminal is read on a thread nothing waits for (passwords masked through `rpassword`; a y/N reads one line, only `y`/`yes` count), so a signal stops a waiting prompt; on Unix a stopped prompt puts the terminal's settings back with `tcsetattr` (echo on) and ends the line, on Windows that is a follow-up. Typed secrets are `Zeroizing` until they become `SuppliedSecrets`. **`query -c CONNECTION`** takes its SQL from exactly one of the positional argument, `-f FILE` (`-` is stdin), `--saved QUERY [--project P]` or stdin when it isn't a terminal (clap's `ArgGroup`; none is a usage error). A positional SQL that is a lone flag-shaped word (`--yse`, `-x=1`) is a usage error rather than SQL, so a mistyped flag can't replace a script piped to stdin; `-- note\nSELECT 1` and `-1` run. `--param NAME=VALUE` (split at the first `=`) binds `{{NAME}}` as text, and a parameter with no `--param` is `MISSING_PARAMETERS` before anything opens, so Core never binds NULL for it; blank text prints `nothing to run` and exits 0. It runs through `Workspace::run` (`RunTarget::All`, `history: None`, `defer_writes: false`) as typed, **not read-only**: Core's `CONFIRM_REQUIRED` is listed on stderr (up to 20, `  3. drops a table: DROP TABLE x`, words from `seaquel_terminal::destructive_reason`, then `…and N more`) and the CLI asks "Run them?" when interactive and reruns with `confirmed`, else fails saying to pass `--yes`, which sends `confirmed: true` from the start. `--limit N` is the run's `page_size` (default 1000, at most 99,999, Core's page cap `max_query_rows() - 1` at its default: clap refuses more as a usage error before anything connects, and a cap lowered with `SEAQUEL_MAX_QUERY_ROWS` is left to Core's `INVALID_ARGUMENT`; a SELECT shows its first N rows and Core's count), and `--limit 0` streams every row with no cap. Nothing limits what the SQL does: `query` has the user's full access to every saved connection, none of `mcp`'s limits (exposed connections only, read-only, the AI sharing flags), which matters when an agent with shell access can run it; a `--read-only` flag is a follow-up. A failing statement makes the exit code 1 and the statements after it still run and print. **Output.** `--format table|json`, table when stdout is a terminal, else JSON: lists as one pretty-printed array; `query` as JSON Lines, one object per statement written when it finishes (`statement`, Core's 0-based index of the statement in the text, `sql`, `columns`, `rows`, `totalRows`, `countEstimated` (then `totalRows` is only a lower bound), `truncated`, `rowsAffected`, `elapsedMs`, or `error {code, message}`; a statement without columns has no `columns`/`rows`/`totalRows`). Cells (`output::json_cell`): null, booleans, integers within ±2^53, finite floats and text stay JSON, anything else is `cell_text`'s string (the GUI's text), never cut. The table aligns by display width, cuts a cell at 60 columns with `…` and shows newlines and tabs as `↵`/`→`, with a blank line on stdout between two statements' tables; both formats hold a statement's rows until it finishes. stdout carries only results (rows, lists, a saved query's SQL, `ok`); prompts, notices, `nothing to run`, `query`'s table footers (`3 rows (12 ms)`, `1,000 of 52,331 rows (12 ms); --limit 0 for all`, `first 1,000 rows (12 ms); more weren't counted; --limit 0 for all` when Core couldn't count, `3 rows affected (1 ms)`, `done (1 ms)`) and errors go to stderr, errors as `seaquel-cli <command>: CODE: message` (a statement's, in table format, as `statement N: CODE: message`, N counting from 1, as the destructive listing does). Every stderr line goes through `session::say`/`say_text`, which drop a write to a closed stderr rather than panic as `eprintln!` would. Exit codes: 0, 1 for any failure, a statement's included, 2 for a usage error (clap's), 130 when stopped. SIGINT or SIGTERM (Ctrl+C on Windows) drops the command's work, so Core cancels a statement in flight, and closes the session; a second one during that close skips it (`session::until_stopped`, which prints `seaquel-cli <command>: stopped` and answers 130). A connect that gives up says `Gave up after 4 attempts.`; not interactive, a `SECRET_STORE_UNAVAILABLE` for a row a terminal run would ask about gets the same "run this in a terminal" sentence as a missing password. `tests/commands.rs` runs the binary on a sandbox data dir (`SEAQUEL_DATA_DIR`, `SEAQUEL_CLI_TEST_SECRETS`, `_KNOWN_HOSTS`, stdin null). **Dev builds:** a debug CLI looks under `app.seaquel.desktop.dev`, which is where `npm run tauri:dev` installs the CLI and the helper (its config identifier); a plain `npm run tauri dev` runs as `app.seaquel.desktop` and installs there instead, where only a release CLI looks. `SEAQUEL_DATA_DIR` lines up any pair.
