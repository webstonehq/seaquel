# The GUI's view models over Core

Moved from the root `CLAUDE.md`, which has the overview and the crate map. "Above" and "below" may point at sections that now live in another `CLAUDE.md`. Connections, `CoreClient` and DuckDB support are in `src/lib/core/CLAUDE.md`.

## Running queries in the GUI

- **The editor runs through a `QueryRunner`** (`src/lib/hooks/database/query-runner/`): `getQueryRunner` gives `CoreQueryRunner` (`db.run`/`db.page`) on every interface, the demo included.
- **`QueryExecutionManager`** (`query-execution.svelte.ts`) is a view model over run events. It decides nothing about what runs: no `$lib/sql` planning call, and no `provider.select`/`execute`. One operation per tab: a new run cancels the tab's previous run (all of it, not only its stream), Stop and closing the tab cancel in Core, and a page request while a run is going is ignored. Events go to the tab they started on, looked up through the `$state` proxy each time (mutate results through `getProxiedResult`). A result keeps `pageSource` (the SQL after substitution and its binds) for `goToPage`/`setPageSize`, which send `db.page`; `statementSql` stays the typed text. `columnSourcesFromRefs`/`sourceTableFromRef` resolve Core's `table`/`columnRefs` against the schema cache. `statementDeferred` is queued as a `{type: "sql"}` change with its binds (`pendingChanges.addSql`).
- **Destructive statements.** The editor's own synchronous wasm check prompts first and sends `confirmed` after the user agrees. Any other caller (the file-drop run, the reruns after a grid row delete or Set default) gets Core's `CONFIRM_REQUIRED` as `pendingConfirm`, which the editor shows for the active tab ("…and N more" past 100); it is cleared when another tab becomes active or its tab goes, and Confirm refuses if the active connection changed. The reruns send no parameter values yet.
- **History is append-only in the GUI.** `QueryHistoryManager` is a cache: a Core run's `done.history` goes in with `insertRecorded` (trimmed by the same rule as the file) and triggers `licenseNudgeStore.recordQuery()`; an apply's rows come back in Core's outcome and go in with `insertRecorded` too (no nudge); nothing in the GUI calls the storage client's `append` any more; the favourite toggle calls `setFavorite(id, value)`. A row with `params` (an applied grid edit) shows its values under the SQL, and opening it queues it again as a `{type: "sql", sql, params}` pending change (origin `history`) on the row's connection, focusing that connection's queue and opening the sheet, whatever the pending-changes setting; a row without them opens in an editor tab. Nothing replaces a connection's list, so a failed history load blocks nothing.

## Edits, pending changes and the data tab in the GUI

- **Edits go through an `EditService`** (`src/lib/hooks/database/edit-service/`, `plan`, `apply`, `tablePage`, `duckdbExtension`): `getEditService` gives `CoreEditService` (the edits service above) on every interface, the demo included. `QueryCrudManager`, `PendingChangesManager` and `DataTabManager` are view models over it; none builds, pages or classifies SQL. `$lib/sql`'s `changeSummary` feeds `describePendingChange`.
- **Edits go to the connection their data came from.** A `StatementResult` carries `connectionId` (the saved connection it ran on) and a data tab its own; edits, inserts, deletes, Set default, paging and the pending overlays use it, never the active connection, and look its Core id up after their last await, so a reconnect is followed and a disconnected or removed connection is refused. The sheet and header badge follow `state.pendingConnectionId` (the focused data tab's or result's connection, else the active one).
- **Queued or immediate** is the pending-changes setting (on by default). On, `db.planEdits` fills a queue entry's display fields and the entry keeps the `change` that apply sends back; a repeated edit of one cell replaces the queued one in data and query tabs alike, and a per-cell sequence drops a plan that lands after a later edit of that cell. Off, the edit is `db.applyChanges` with one change.
- **Apply** (`PendingChangesManager.apply`): a full success clears the queue; an atomic failure keeps it whole and marks the failed change; an in-order failure removes the applied prefix. An apply that ends without an answer (`NETWORK_ERROR`, `PROTOCOL_ERROR`, `UNKNOWN`, `CANCELLED`, `WS_CLOSED`, `CONNECTION_CLOSED`, `HTTP_5xx`, or an atomic `WORKSPACE_CLOSED`) is `interrupted` whatever its mode, since an atomic batch may have committed before its reply was lost; so is an outcome whose `failed` change carries `CONNECTION_CLOSED` (an engine out of process lost mid-apply), in any mode, after dropping what Core says ran: the queue is kept and marked (`state.pendingChangesInterrupted`, the sheet's "may be partly applied" banner), and the schema and the connection's data tabs reload. The sheet's confirm dialog lists the destructive statements `$lib/sql` finds and sends `confirmed` only when it listed some, so Core's `confirmRequired` reopens it with Core's list. `NO_ROWS_AFFECTED` is shown with the change's table and key (`stale-edit.ts`, i18n), `TRANSACTION_OPEN` as `edit_transaction_open`. The sheet shows each change's SQL with its values beside it.
- The sidebar's DROP and TRUNCATE send `dropObject`/`truncateTable` intents with `confirmed` (their own dialogs asked); the table editor applies its generated statements as typed changes with `confirmed: true`.
- **The data tab** (`DataTabManager.refresh`) sends a `TableQuery` through `tablePage`; the filter bar's operators are the generated `FilterOp`. One operation per tab: a new refresh, closing the tab or a project switch aborts the previous one.
- **Workflow query nodes are read-only**: `executeReadOnly` on the node's saved connection, at most `WORKFLOW_MAX_ROWS` (10,000; a cut result says so on the node), one `AbortController` per node (re-running or deleting it cancels). A write is refused with `READ_ONLY`.
- **The DuckDB extensions tab** runs on its tab's connection through `db.duckdbExtension`, on desktop and in the demo.

## The library in the GUI

- **Library writes go through a `LibraryService`** (`src/lib/hooks/database/library/`, `getLibrary()`): `CoreLibrary` (the `library` group) on every interface, the demo included, sharing `RustStorageClient`'s write queue so writes land in the order issued. `ConnectionManager`, `LabelManager`, `ProjectManager`, `SavedQueryManager` and `DashboardManager` call it at once, with no debounce. They build no ids, times, versions or prune plans and never compare names; an edit sends a patch of the fields that changed. `add` connects and loads the schema first and then calls `connectionCreate`, since the row's id is Core's; a failed create disconnects and leaves nothing. On web the vault is unlocked before `connectionCreate` (a cancelled unlock saves nothing) and the ciphertext written after it answers; if that write fails (a toast says so), the row keeps `savePassword` with nothing behind it and the next connect asks for the password. Refusals are worded by `library/messages.ts`; `NAME_TAKEN` names the row `takenBy` points at.
- **Other windows' and tabs' changes** (`ChangeFeed`, `LibrarySync`). The feed subscribes once per page, before the first `*List` call. It skips events carrying `pageOrigin()` (the write's answer already updated the page), groups the rest per kind and scope for 100 ms, and `LibrarySync` refetches what each group names and hands it to the manager that shows it. `RowSeqs` keeps the `seq` last applied per row (and per project's version list): a value is applied only when its `n` is higher, a deleted row leaves a tombstone, and a refetch of a row with this page's write in flight waits for that write's answer. A label write's answer holds only the label, so the page reads the project (and the connections it stripped) again rather than recording that `seq` for them. It follows the 5d-2 kinds too. A `projectState` event would apply only when it names this window without carrying its origin, which Core's origin check makes impossible, so other windows' view state never reloads here. A new epoch, and every `onResubscribed`, reload every list and setting (one during the first load reloads once after it). So does an `external` event (another process, such as the TUI, wrote the file; phase 7a): any number within 100 ms make one `{reason: "external"}` reload, which no kind subscriber sees and a new epoch or `stop` drops. It reads the repo list without any `git status` (`refreshRepos(ids, {status: false})`), and the managers keep the object a row already shows when it reads back unchanged (`keepSame(current, fromWire(row, current))`, `library/same-data.ts`: a deep comparison where `Date`s compare by time and a key holding `undefined` counts as absent), so a reload a second after every TUI query doesn't re-render the lists. `onEventsUnavailable` shows the header's "Not receiving updates" badge until the channel is back. The demo runs the same feed, but each tab has its own Core, so another tab's writes never arrive (the last tab to write wins).
- **Deleted elsewhere:** a connection is disconnected and every tab it owns closes, in every project (`connection-tabs-cleanup.ts`), with a toast; the active project switches to another, with a toast; a tab linked to a deleted saved query keeps its text and loses the link; a removed label disappears from connections. Kinds without a live view (a project that isn't active, history that isn't shown) are read when next shown.
- **Forms** (the connection tab in edit and reconnect mode, the project settings) keep their own copy and show "Changed in another window" with a Reload button when their row changes elsewhere; saving still sends only the fields the user changed. A refused reconnect save restores the changed fields and reads the connection again.
- **The secrets notice** (`stores/connection-secrets-notice.svelte.ts`, `components/connection-secrets-notice.svelte`): after the connections load, the page reads `connectionStringSecretsNotice`, names those connections once and clears the key when it's dismissed.
- The version limit settings clamp to at least 10 on save (`utils/version-limit.ts`).
- **Settings, view state, dashboards, workflows and chats** (5d-2). `getSettings()` gives a `SettingsService` (`CoreSettings` over the `settings` group), `getUi()` a `UiService` (`CoreUi`; the demo's window is `demo`), and the dashboard, workflow and chat calls are on `LibraryService`, the demo included. Everything but the view state is written at once. `PersistenceManager` is gone.
- **`WindowStateManager`** (`window-state.svelte.ts`) saves the window's view state of a project 500 ms after a change, only once that project's load has been restored (`markLoaded`), with `rev` counting on from the load's answer (and past a stale answer's). `flush` saves only projects with a pending save, active first; on web and in the demo `pagehide` saves the active project's pending view state (`saveOnPageHide`, the layout's `savesOnPageHide`): web as a `keepalive` fetch, the demo synchronously into the view-state journal (below), since Chromium runs no task between `beforeunload` and `pagehide`. A standalone window (the theme editor, the log viewer) runs it disabled and makes no `ui` call. A limit refusal is said once per project and limit. The connection order is stored at once (`projectSidebarSet`), and each window keeps its own active connection.
- **Settings stores** (editor, pending changes, update, license nudge, version limits, AI settings, themes, onboarding, tutorial, imports, the secrets notice) go through `settings` and apply another window's change at once (`stores/settings-sync.ts`: `WriteOrder`, `StoredSetting`). A refused set shows the stored value again. Themes apply live in every window. On web an AI key goes to the vault after Core stores the provider (`ProviderKeyNotSavedError` if that fails).
- **Dashboards** send patches, with `captureVersion` on the edits that version, and a refused edit shows the stored row again; a dashboard deleted elsewhere closes its tabs in every project. The history lists metadata and reads a snapshot only to compare or restore it (`loadVersion`).
- **Workflows** list summaries and read the body when one is opened (`loadWorkflow`); `saveWorkflow` is async and waits for Core's id. One past `max_workflow_bytes` is said once and stays open.
- **Chats** get Core's id before the first message. Core stores each turn's rows (below); the page writes no message itself (`LibraryService.putChatMessages` has no caller left). A chat Core answers `full`, or a turn refused with `CHAT_FULL`, shows "This chat is full" with a New chat button and sending off, keeping the refused turn on screen but not stored.

## The assistant in the GUI

- **`getAi()`** (`src/lib/hooks/database/ai/`) gives an `AiService` (`CoreAi` on desktop, web and the demo: `chat`, an async iterator of `AiEvent`s, `respond`, `generate`, `models`, `test`); `ai/testing.ts`'s `FakeAi` plays event sequences for the page's tests. The page has no provider client, tool definition, tool loop, prompt or mention resolver left (`services/ai/` keeps only `context.ts`'s `readOnlyError` for `executeReadOnly`; `ai-mentions.ts` keeps the popover's `buildMentionItems`/`mentionItemsFor`, gated on schema sharing), and no provider URL or header (`ai/no-model-calls.test.ts`).
- **Keys.** `CoreAi` takes the key from `aiKeyVault()` (`services/keyring.ts`) and sends it with its `providerId`, or neither: on desktop that is `null` and Core reads the keychain; on web the vault (`VaultKeyringService.getAIApiKeyForProvider`, which looks for the provider's row first and decrypts only when there is one, so a keyless provider never asks for an unlock; a turn asks quietly, so no "Vault unlocked" toast covers Stop; a cancelled unlock ends the turn with `VAULT_LOCKED`); in the demo the session keys (`services/session-keys.ts`, a `Map` in page memory, forgotten on reload). The settings form asks `aiSettingsStore.hasKey` (`settings.aiProviderHasKey` on desktop, the vault or session keys elsewhere); models and the provider test go through `ai.models`/`ai.test`.
- **A turn** (`UIStateManager`'s AI half in `ui-state.svelte.ts`, `AIChatManager`) follows Core's events. `sendAIMessage` sends what was typed (Core resolves mentions) with the chat's open Core connection, `clientTools: true` and `approval: "allowAll"` when the session's per-connection flag says so. The page stops a send itself only when the chat's connection is gone, isn't open ("Connect {name} to ask about it.") or has no model (a pending message, sent once a model is chosen). A new send stops any turn still running. `done.messages`/`error.messages` go through `applyTurnRows` by `seq` on per-row keys (`rowKey("aiMessage", id)`); a message the page shows that Core hasn't stored survives a refetch, and another window's `chatMessages` event during a turn waits for it. Stop cancels, answers nothing, and re-reads the chat once Core has stored the reply (`awaitOwnStore` lets that own-origin event through the feed). An `error` without rows from a transport ending (`WS_CLOSED`, …) re-reads the chat after the turn. Every code is worded by `ai/messages.ts` (i18n); an unknown one reads "Something went wrong ({code}). Try again." and never Core's message.
- **The reply.** Text streams; each tool call shows as one line (tool, SQL, row count or error) from `toolCall`/`toolDone` live and from `parts` after `done` or a reload (`ai/events.ts`). A reply ending in Core's `REPLY_CUT_NOTE` is shown without it and marked cut (`ai/reply.ts`, `splitCutNote`; `messageDraft` puts it back); a reply over 64 KiB is shown as plain text without `marked`, and a segment `marked` throws on falls back to plain text. The error under a reply is plain text.
- **Approvals.** The card answers `respond` (`allow`, `deny`, or `allowAll` when its own box is ticked; every card starts unticked; card ids are `<streamId>:<callId>`). "Allow all" is kept per connection for the session, with what the connection pointed at (engine, host, port, database): removed, or pointing elsewhere, it's forgotten (`forgetStaleAllowAll`, run by `ConnectionManager.onConnectionsChanged` and before each turn; `isAllowAll` is a pure read). A `clientTool` runs `handleDashboardToolCall` (`dashboard-tools.ts`) and answers. `respond` always goes after a microtask, so nothing calls the demo's module from inside its callback.
- **The inline prompt** (`ai-inline-prompt.svelte.ts`) calls `ai.generate` and inserts the SQL at the cursor without running it: "Inserted. Run it with ⌘↵."

## Shared projects and imports in the GUI

Desktop only (5e). The page never builds a file path, reads or writes a repo file, pairs a file with a row or parses another tool's file; nothing in `src/lib/hooks` imports `@tauri-apps/plugin-fs` (`shared-gui.svelte.test.ts` checks).

- **Seams** (`src/lib/hooks/database/shared/`): `getShared()` gives a `SharedService` (`CoreShared` over the `shared` group) and `getImports()` an `ImportsService` (`CoreImports`), both through `RustStorageClient`'s write queue (`SHARED_METHOD_KIND`, `IMPORTS_METHOD_KIND`); `NoShared`/`NoImports` answer `NOT_SUPPORTED` on web and in the demo, which hide the entry points as before. `notices.ts` words a `SyncReport` (one toast per notice, at most 5, then "…and N more"; `nameTaken` names the kind of row from `takenBy`'s id prefix; a connection `conflict` lists the replaced values), failures and the `shared` codes. `projection.ts`'s `reportProjection` says a library answer's `projection` (`failed` with `errorToast`; `FILE_CHANGED` on an edit says the repo's version is shown and the user's is in the history, on a removal or unshare that a teammate changed the file and it will reappear).
- **`SharedRepoManager`** is a view model: the repo list from `reposList` (no stored `syncStatus`, no replace-all save), git calls and each repo's status in memory, `syncProject`/`syncRepo` and the conflict dialog's state (`state.sharedConflict`). A pull, a commit and a resolution (once no conflicted file is left) call `syncRepo`; the five-minute background refresh syncs a repo whose status changed since its last pass; activating a linked project, startup (the active one), `linkProject` and `importProjects` sync too. A status that can't be read shows the repo as `error`. Core's events for a sync this page started carry its origin, which the feed skips, so after a sync that changed something, or a publish answered `FILE_CHANGED`, the page reads that project's rows itself (`UseDatabase.refreshProjectRows`). Another window's `sharedRepo` event refreshes that repo's list entry and status (`LibrarySync`). `state.sharedSyncSkipped` drives project settings' "Skipped" badge for a project skipped whole.
- **Managers.** `ProjectManager` has `linkProject`, `unlinkProject`, `unlinkWithConfirmation`, `importedConnectionsOf` (Core's `unlinkPreview`) and `importProjects`; `update` doesn't take `gitRepoPath`. `ConnectionManager`, `SavedQueryManager` and `DashboardManager` make no file calls: sharing and unsharing are patches, and every write answer goes through `reportProjection`. The sidebar's share switch sends `isLocalOnly: !!sharedConnectionId`, so one click shares an unshared connection.
- **Dialogs**, mounted once in `(app)/+layout.svelte`: the link dialog (`stores/link-project-dialog.svelte.ts`: the project's unlinked connections, all ticked but the local-only ones; only ticked ones are written to the repo), the unlink dialog (`stores/unlink-project-dialog.svelte.ts`: Cancel, Keep them, Remove them, listing what Core would remove), the shared-project import dialog (`services/shared-project-import.ts` over `scan`; directories a project here already links are marked and can't be ticked) and the conflict dialog (`sync-conflict-dialog.svelte`, opened by a conflicted sync or pull; `conflict-choice.ts` sends `null` to keep a side that deleted the file). Project settings asks the link dialog, and for a changed or cleared path the unlink dialog, before changing anything. The sync button's "Sync all" with uncommitted changes opens the commit dialog first, then pulls and pushes, and stops at a conflict; `pullRepo` answers `updated`, `conflicted` or `unchanged`, and a refused pull is worded by `pull-error.ts`.
- **Imports.** One `ConnectionImportStore` (`stores/connection-import.svelte.ts`, `tablePlusImportStore`/`dbeaverImportStore`) and one `connection-import-dialog.svelte`: "nothing found" and "couldn't read" are said, a candidate with a `problem` is listed with its reason and can't be ticked, `duplicateOf` is shown, and `ConnectionManager.importConnections` sends the ticked keys once (`imports.create`), reads the new connections and the order back, and names each failure.
- **Deep links** (`services/deep-link.ts`): the link's directory is matched to a local project through `scan`'s `linkedProjectIds`; a query or dashboard opens by its stored `sharedPath`, a connection by its template path (`sidebar/manage/share-link.ts`). A file that isn't stored says so; a connection in a directory no project links opens the import dialog with that directory ticked and opens the connection after the import; cancelling does nothing.
