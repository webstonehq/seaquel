# src-tauri (desktop)

Moved from the root `CLAUDE.md`, which has the overview and the crate map. "Above" and "below" may point at sections that now live in another `CLAUDE.md`.

- `src-tauri/` (desktop). Its commands are `core_call`; `cli_info` and `install_cli` (`cli_info.rs`, for the MCP settings panel); `duckdb_helper_offer`, `duckdb_helper_install`, `duckdb_helper_cancel` and `duckdb_helper_install_file` (`duckdb_helper.rs`, below); `core_stream` and `core_events` (below); and interface code (`copy_image_to_clipboard`, `open_path`, `get_data_dir`, `read_log_file`, `clear_log_file`, `get_username`, `install_update`, `check_for_update_command`). There are no `db_*`, `git_*`, `ssh_*`, license, import-reader or AI commands: `core_call` serves storage, `library`, `settings`, `ui`, `shared`, `imports`, `db`, `ai` (but `chat`), secrets, SSH, git and licensing, and passes the calling webview's label (`main`, `theme-editor`, `log-viewer`) as the write origin, which is also the window id a `ui` call must name; the page never sends one. `desktop_core(identifier, ImportPaths::from_env())` builds the app's one Core with `LocalFiles::Allowed`, `NativeHttp` and `AiEgress::Any` (a local Ollama over `http:` works), the four engines from `with_plugins(|id| id != "duckdb")` and DuckDB through `.duckdb_helper(DuckdbHelper { dir: cli_download::duckdb_helper_dir(identifier), version })` (`data_local_dir(identifier)` + `bin/duckdb`, so it follows `SEAQUEL_DATA_DIR` and is the terminal binaries' folder), plus `duckdb_helper_pinned` when the build has the pin. `run()` makes `tauri::generate_context!()` first and reads the identifier from it, so `npm run tauri:dev` gets the `.dev` folders. With no data-local dir DuckDB isn't registered (a connect is `ENGINE_NOT_AVAILABLE`) and `setup` logs `NO_HELPER_FOLDER` once the logger is attached. `src-tauri`'s tree has no `libduckdb-sys` (CI's "Native binaries' dependencies"). The main window's capability (`capabilities/default.json`) keeps only the `fs` permissions the exports, the theme import and the ERD viewer use (`read-text-file`, `write-text-file`, `write-file`, `temp-write`, `remove`, still `"path": "**"`); `read-dir`, `exists`, `mkdir` and `rename` went with the TypeScript projection in 5e. A saved connection's keychain entries and an AI provider's API key are written by Core inside the `library` or `settings` call (`SecretChanges`, `apiKey`), not from TypeScript; `services/keyring.ts` keeps the `secret` group for the keychain calls it still makes itself (database and SSH reads, the license key); it has no AI key read on the desktop (Core reads the key for each model call), and the `secret` group refuses `ai-api-key:*` anyway. It takes the request as the raw bytes of a `Uint8Array` (`invoke("core_call", bytes)`); an object is refused. Storage opens lazily on the first storage call (`DesktopWorkspace`): `LEGACY_STORAGE`/`STORAGE_CORRUPT`/`NO_DATA_DIR` are kept and returned to every storage call, other failures retry on the next call, and secret, SSH, git and license calls work either way. The real workspace polls for other processes' writes every second (`EXTERNAL_CHANGES_POLL`, `with_external_changes`); the stand-in below doesn't, since nothing else writes its file. `db` calls use one workspace for the whole run; if storage can't open for good, that's a stand-in workspace on an empty scratch storage, where form connects work and saved ones get the storage error.
  - **Streams and events.** `core_stream({request, channel})` takes a `db.queryStream`, `db.run`, `db.page`, `db.tablePage` or `ai.chat` request as JSON text (an invoke carrying a `Channel` can't have a raw body) and pushes `CoreEvent`s to the channel. It resolves with the number of events it sent, since the reply can overtake channel messages: the GUI waits for that many before it treats a stream with no `done`/`error` as cancelled. `core_events({channel})` is called once per page load; each webview label has its own sink and every sink gets every event, `storageChanged` included. The event pump starts when the storage workspace opens (not on the first `db` call), so a library write before any connect still reaches every window. A second call from the same label (a reload) replaces its sink, cancels that webview's streams, runs and turns (tracked by `Request::stream_id`) and closes its connections (`close_window` → `Workspace::close_owned_by(core, label)`, `WINDOW_CLOSED`, which every sink gets and the GUI keeps quiet; the closes run side by side, bounded by `CLOSE_WINDOW_WAIT`, 30 s, past which they are dropped with a WARN), and so does a destroyed webview (`forget_webview`, from `WindowEvent::Destroyed` in a spawned task). A first `core_events` from a label closes nothing. So `core_events` is async: it resolves once the old page's connections are closed, which frees a DuckDB file for the reloaded page's reconnect. A turn is cancelled through Core and polled to its end so its reply is stored; so is a turn whose channel refuses an event (`stop_turn`, bounded by `TURN_STOP_WAIT`).
  - **DuckDB support** (`duckdb_helper.rs`, desktop only; web and the demo don't have the commands). `duckdb_helper_offer` answers `{status, version, size, sizeError, fromFile, assetName}`: Core's status (`installed`, `missing`, `outdated`, `unsafe`), the compressed size (from the pin with no request, else one metadata request; not asked when installed), `sizeError` with the code when the size couldn't be had, so the dialog still knows the status, and `fromFile` when a pin is built in (only then can a picked file be checked). `duckdb_helper_install({channel})` streams `{bytes, total}` over a Tauri `Channel` (always one: `Channel` isn't `Deserialize`, so the prefetch passes one and doesn't listen) and resolves `{downloaded, pruned}`. **One download** (`HelperInstalls`, managed state): the first install runs Core's inside `Abortable` and publishes its progress and answer on `watch` channels, and an install while it runs (the prefetch, the dialog, the CLI flow) joins it, so the asset is fetched once and every joiner gets the same answer. `duckdb_helper_cancel` aborts it, which drops Core's future and its `.part`, and every joiner answers `CANCELLED`; it returns whether an install was registered. `duckdb_helper_install_file({path})` passes no hash, so the pin decides (`WRONG_FILE`). A debug build installs a `seaquel-duckdb` built beside the app instead of downloading only under the dev rule (`local_helper`, `may_use_debug_helper`: an identifier ending in `.dev` or a non-empty `SEAQUEL_DATA_DIR`; never in a release build), in the commands and the CLI flow alike. Errors are `RpcError {code, message}`. Logs: `activity=duckdb.helper` `event=offer|install|cancel` with status, code, `downloaded`, `pruned`, `from_file`, `running`; never a path, URL or picked file. Quitting drops nothing (tao's loop ends in `process::exit`), so each helper reads EOF, finishes its close checkpoint (up to 60 s) and exits 0; Core's `a_client_that_exits_leaves_its_helper_to_checkpoint` pins it.
  - **The command line tool.** The app doesn't bundle `seaquel-cli`. The app menu's "Install Command Line Tool…" (`cli_install.rs`; macOS, Linux and Windows) and Settings → MCP's button download the release asset that matches the app's version (`cli_download.rs`: the size and SHA-256 from GitHub's release metadata, at most 200 MiB) into `<data_local_dir>/<identifier>/bin/`, then link it: macOS symlinks `/usr/local/bin/seaquel-cli` to it, asking for admin rights through `osascript` only when needed and building that command from fixed paths only; Linux links `~/.local/bin/seaquel-cli` (deb, rpm and AppImage alike) and says when that folder isn't on `PATH`; Windows changes no `PATH`. After an app update the user installs again to get the matching CLI. **The DuckDB helper** is installed in the same flow, after every outcome but a cancel (an already-installed CLI included): the flow runs on a blocking thread and blocks on `duckdb_helper::install_for` with the app's own Core and `HelperInstalls`, so it shares Core's install lock and joins a download the dialog or the prefetch started. The app and the CLI of one version use the same helper. A helper failure doesn't fail the CLI's install: the dialog adds why, that only DuckDB connections need it, and `seaquel-cli duckdb install`; the dialogs are native and English only, and show no progress for the helper. Settings → MCP (`src/lib/components/settings/mcp/`, desktop only) shows the binary and whether it's on `PATH` (`cli_info`, which also reports `duckdbHelper` from the app's Core: `installed`, `missing`, `outdated`, `unsafe` or `unknown`; once the CLI exists a helper that isn't installed shows a warning naming "DuckDB support", for the app and the CLI alike (`helperWarning`, keys `settings_mcp_duckdb_helper_missing`/`_unsafe`; the old `settings_mcp_duckdb_missing`/`_unsafe` are unused, to be removed from all six locales once the translators are done)), the install (`installTarget`: `cli` runs `install_cli`, which adds the helper after the CLI; `helper`, for a current CLI, shows "Install DuckDB Support" and installs through the dialog's store, `installDuckdbHelperJoined`, so a dialog joins it and its bar shows "x MB of y MB"; a failure toasts `CODE: message`, `CANCELLED` is quiet), connection and project checkboxes, and the Claude Desktop JSON and `claude mcp add` line (`mcp-snippets.ts`, POSIX or PowerShell quoting, connections named by id).

- Desktop plugins still used: `tauri-plugin-updater`, `tauri-plugin-log` and others in `src-tauri/Cargo.toml`. Storage and the keychain go through `core_call`, not plugins.

## Configuration files

- `src-tauri/tauri.conf.json` - Tauri app configuration. Its CSP has `'wasm-unsafe-eval'` in `script-src` because WebKit and Chromium won't compile `seaquel-wasm` without it. The token allows compiling WebAssembly and nothing else (`eval()` and `new Function` stay blocked); don't swap it for `'unsafe-eval'`. Since phase 6 no model call leaves the page, so `connect-src` is `'self' ipc: http://ipc.localhost ws://localhost:1420 https://duckdb.org`: the dev server's HMR socket (older WebKit didn't match `ws:` to `'self'`) and the DuckDB community extension list; every other `fetch` in the page is relative, and the updater and licensing are Rust (`ai/no-model-calls.test.ts` pins the directive). The web build sends no CSP.
- `src-tauri/macos/duckdb-helper.entitlements.plist` - the helper's only entitlement, `disable-library-validation` (DuckDB's signed extensions). `tauri.conf.json` has no `bundle.macOS.entitlements`: the app is signed with the hardened runtime (Tauri's default) and no entitlements, as the CLI and TUI are, and `scripts/macos-entitlements.test.mjs` keeps `release.yml` that way.
